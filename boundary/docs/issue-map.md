# Boundary: Карта Issue-Инвариантов

> Обновление 2026-06-14: документ ниже является исторической картой issue.
> Текущая рабочая граница изменилась: `Boundary` — персистентный слой для
> `Dark`; `Matrix` и `Bulk` — рантайм-слои и не читают `Boundary`/SQLite
> напрямую. Старые формулировки про общую БД для `Dark`/`Boundary`/`Bulk`
> нужно читать как отменённый этап.

Этот документ нужен как краткая карта архитектурных issue, которые уже задают
смысл `Boundary`.

Его задача не заменить сами issue, а удерживать для `Boundary` такой порядок:

1. сначала мир как читаемая плоскость,
2. потом агент, чат и инструменты внутри мира,
3. потом протоколы, поток патчей и межмировая координация,
4. и только после этого узкие реализационные решения рефакторинга.

## Главный Вектор

### `#68` Самоавторская мультивселенная

Это главный смысловой issue для всего направления.

Из него следует:

- MetaFor не должен превращаться в проект, к которому отдельно прикручен 3D-редактор;
- сама мультивселенная должна быть authoring-средой;
- код, БД и пространство должны читаться как разные формы одной и той же логики;
- нужна отдельная авторская/редакторская БД поверх канонической логики БД;
- `Boundary` нужен как персистентная карта этой среды, а не как технический снимок без авторского смысла.

Для `Boundary` это означает:

- визуализировать нужно не "данные рядом с чатом", а форму мира, собранную для рантайма;
- агент, человек, другие ИИ, устройства, приложения и `git` должны быть адресуемыми участниками одной среды;
- будущий Bulk-аватар агента является проявленной формой того, что приходит из рантайм-проекции, построенной на данных Boundary.

## Пространственный Слой

### `#53` Bulk на базе `web-gpu-engine`

Этот issue фиксирует, что `web-gpu-engine` нужно читать как основу `Bulk`.

Из него следует:

- `Bulk` не должен зависеть от `Boundary` как от скрытого загрузчика;
- `Bulk` должен получать данные мира как данные проекции/рантайма, а не читать общий слой БД/мира;
- первый полезный срез это не "красивый интерфейс", а наблюдаемый Bulk-inspector;
- движок должен оставаться общим пространственным фундаментом, а не превращаться рано в монолит, специфичный только для MetaFor.

Для `Boundary` это означает:

- выдавать стабильный контракт снимка мира;
- не смешивать каноническую читаемую форму с проявленным представлением;
- не привязывать структуру мира к ad-hoc UI-состоянию.

## БД И Структурная Синхронизация

### `#51` Общая БД и patch как сигнал

Этот issue фиксирует базовую модель междоменной синхронизации.

Из него следует:

- персистентный Boundary является фиксированным слоем мира для `Dark`;
- частица, обращённая к рантайму, должна переносить данные, если получатель — `Matrix` или `Bulk`;
- лёгкий сигнал без данных допустим только там, где получатель имеет право читать Boundary;
- рантайм должен развиваться в `Matrix`/`Bulk`, а не в БД Boundary.

Для `Boundary` это означает:

- база есть boundary-отпечаток мира;
- рантайм не равен БД Boundary;
- между персистентным Boundary и рантайм-материализацией нужны Force/рантайм-данные.

### `#60` Рантайм-Адресация

Этот issue исторически уточнял внутреннюю механику старого `Boundary`.
В текущей архитектуре эту область нужно читать как рантайм-адресацию `Matrix`.

Из него следует:

- `id` это персистентный адрес строки, выдаваемый SQLite autoincrement;
- рантайм-индекс — это временная координата конкретной рантайм-сборки;
- рантайм-слой хранит состав мира и адресные карты;
- персистентный `Boundary` не становится владельцем этого рантайм-хранилища.

Для визуализации это критично:

- ни `Bulk`, ни чат, ни оверлеи инструментов не должны придумывать собственные идентичности поверх `id`;
- пересборка может менять локальные индексы, но не должна ломать персистентную адресацию мира.

## Протокол И Процессы

### `#65` Минимальная событийная модель

Этот issue задаёт протокольный инвариант.

Из него следует:

- протокол должен быть событийным, а не RPC-подобным;
- не нужно дублировать транспортную информацию внутри данных сообщения;
- подписчик сам решает, реагирует ли он на событие;
- нужно избегать ложной адресности поверх широковещательного канала событий.

Для `Boundary` это означает:

- world-events должны читаться как факты изменения;
- интеграция чата и инструментов не должна дрейфовать в псевдо-шину сообщений с искусственными целевыми конвертами;
- визуализация должна показывать событие мира, а не только транспортный конверт.

### `#64` Поток Weak-Процесса Через `W/Z`

Этот issue фиксирует минимальную модель исполнения процессов.

Из него следует:

- жизненный цикл блокировки принадлежит `Boundary`;
- `Photon` сообщает наблюдаемое состояние;
- `Z` координирует выбор исполнителя в `Bulk`;
- `W+ / W-` возвращают единый конверт результата обратно в `Boundary`;
- `Boundary` применяет пакет и только потом снимает блокировку.

Для world visualization это означает:

- процесс должен быть видим как состояние мира, а не как скрытая async-функция;
- координация и возврат результата должны быть отдельными наблюдаемыми событиями мира;
- исполнение инструмента можно проявлять как weak-опосредованный переход внутри общей физики.

## Открытые Онтологические Вопросы

### `#56` Гранулярность Пути Записи В БД

Пока не решено окончательно:

- достаточно ли пути записи групп строк;
- когда нужна запись на стадии сущности;
- как адресно писать живые рантайм-изменения.

### `#57` Сброс С Нуля Или Сравнение/Обновление

Пока не решено окончательно:

- остаётся ли мир в режиме полного пересоздания БД;
- или нужна модель сравнения/обновления для уже живой среды.

### `#58` Идентичность Для Переименования И Перестройки

Пока не решено окончательно:

- что переживает переименование;
- что переживает структурную перепись;
- где семантический ключ, а где первичная идентичность;
- как устроить происхождение и историю для действительно живой системы.

Для `Boundary` это означает простой инженерный вывод:

- нельзя преждевременно цементировать слишком узкий рантайм-API как окончательный;
- любой текущий рефакторинг нужно проверять на совместимость с живой моделью идентичности и пространственным авторингом.

## Что Это Значит Для Агентов И Инструментов

Если смотреть на issue вместе, получается уже довольно чёткая картина:

- агент должен иметь форму мира, а не быть только текстовым источником ответа;
- чат должен быть наблюдаемой поверхностью взаимодействия внутри мира;
- `git` уже является первым материальным миром и должен визуализироваться как мир объектов, истории и действий;
- скриншоты должны читаться как артефакты наблюдения мира, а не как внешний вспомогательный файл;
- вызовы инструментов должны быть событиями мира, которые можно видеть в `Boundary` и потом пространственно проявлять в `Bulk`.

То есть направление для MetaFor такое:

- не копировать внешний CLI-проект поверх мира;
- а делать сам мир средой, в которой агент видит, действует, читает `git`, принимает скриншоты и меняет состояние через одну общую геометрию.

## Практический Порядок Для Boundary Docs

Из всех этих issue вытекает строгий порядок документации и реализации:

1. Сначала объяснять, как выглядит одна локальная вселенная и её матрица состояния.
2. Потом объяснять, как в этой геометрии размещаются агент, чат, скриншоты, `git` и инструменты.
3. Потом объяснять поток патчей, событий и протокола.
4. Потом объяснять межмировые связи и более сложную координацию.

Если документация нарушает этот порядок, она почти неизбежно начинает выглядеть как
набор разрозненных технологий, а не как карта одной самоавторской мультивселенной.
