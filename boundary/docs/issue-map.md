# Boundary: Карта Issue-Инвариантов

Этот документ нужен как краткая карта архитектурных issue, которые уже задают
смысл `Boundary`.

Его задача не заменить сами issue, а удерживать для `Boundary` такой порядок:

1. сначала мир как читаемая плоскость,
2. потом агент, чат и инструменты внутри мира,
3. потом протоколы, patch-flow и межмировая координация,
4. и только после этого узкие реализационные refactor decisions.

## Главный Вектор

### `#68` Self-authoring мультивселенная

Это главный смысловой issue для всего направления.

Из него следует:

- MetaFor не должен превращаться в проект, к которому отдельно прикручен 3D-редактор;
- сама мультивселенная должна быть authoring-средой;
- код, БД и пространство должны читаться как разные формы одной и той же логики;
- нужна отдельная authoring/editing DB поверх канонической DB логики;
- `Boundary` нужен как первая читаемая карта этой среды, а не как технический snapshot без авторского смысла.

Для `Boundary` это означает:

- визуализировать нужно не "данные рядом с чатом", а world-form;
- агент, человек, другие ИИ, устройства, приложения и `git` должны быть адресуемыми участниками одной среды;
- будущий Bulk-аватар агента является manifested form того, что сначала должно быть читаемо в `Boundary`.

## Пространственный Слой

### `#53` Bulk на базе `web-gpu-engine`

Этот issue фиксирует, что `web-gpu-engine` нужно читать как основу `Bulk`.

Из него следует:

- `Bulk` не должен зависеть от `Boundary` как от скрытого загрузчика;
- `Bulk` должен читать world-data напрямую из общей DB/world-layer;
- первый полезный срез это не "красивый интерфейс", а наблюдаемый Bulk-inspector;
- движок должен оставаться общим пространственным фундаментом, а не превращаться рано в MetaFor-specific monolith.

Для `Boundary` это означает:

- выдавать стабильный world snapshot contract;
- не смешивать каноническую читаемую форму с manifested presentation;
- не привязывать структуру мира к ad-hoc UI-состоянию.

## DB И Structural Sync

### `#51` Общая БД и patch как сигнал

Этот issue фиксирует базовую модель междоменной синхронизации.

Из него следует:

- одна общая БД является фиксированным слоем мира для `Dark`, `Boundary` и `Bulk`;
- patch не переносит сами данные;
- patch только сигналит о том, что изменение уже произошло и нужный фрагмент нужно перечитать из БД;
- `Boundary` должен постепенно достраивать runtime, а не жить только полным rebuild.

Для `Boundary` это означает:

- база есть boundary-imprint мира;
- runtime `Boundary` не равен всей БД;
- нужен structural sync-layer между patch и runtime materialization.

### `#60` gravity$ как долгоживущая адресация

Этот issue уточняет внутреннюю механику `Boundary`.

Из него следует:

- `uuid` это стабильный внешний адрес;
- `braneIndex` это временная координата конкретной runtime-сборки;
- `gravity$` хранит состав мира и адресные мапы;
- `boundary$` остаётся производным materialized runtime-store.

Для визуализации это критично:

- ни `Bulk`, ни чат, ни tool overlays не должны придумывать собственные identity поверх UUID;
- rebuild может менять локальные индексы, но не должен ломать внешнюю world-адресацию.

## Протокол И Процессы

### `#65` Минимальная событийная модель

Этот issue задаёт протокольный инвариант.

Из него следует:

- протокол должен быть событийным, а не RPC-подобным;
- не нужно дублировать transport information внутри payload;
- подписчик сам решает, реагирует ли он на событие;
- нужно избегать ложной адресности поверх broadcast/event channel.

Для `Boundary` это означает:

- world-events должны читаться как факты изменения;
- chat/tooling integration не должна дрейфовать в псевдо-message bus с искусственными target-конвертами;
- визуализация должна показывать событие мира, а не только транспортный envelope.

### `#64` Weak process flow через `W/Z`

Этот issue фиксирует минимальную модель исполнения процессов.

Из него следует:

- lock lifecycle принадлежит `Boundary`;
- `Photon` сообщает observable state;
- `Z` координирует выбор исполнителя в `Bulk`;
- `W+ / W-` возвращают единый result envelope обратно в `Boundary`;
- `Boundary` применяет пакет и только потом снимает lock.

Для world visualization это означает:

- процесс должен быть видим как состояние мира, а не как скрытая async-функция;
- coordination и result return должны быть отдельными наблюдаемыми world-events;
- tool execution можно проявлять как weak-mediated transition внутри общей physics.

## Открытые Онтологические Вопросы

### `#56` Гранулярность DB write path

Пока не решено окончательно:

- достаточно ли row-group write path;
- когда нужен entity-stage write;
- как адресно писать живые runtime-изменения.

### `#57` Reset-from-zero vs compare/update

Пока не решено окончательно:

- остаётся ли мир в режиме полного пересоздания БД;
- или нужна compare/update модель для уже живой среды.

### `#58` Identity для rename и restructure

Пока не решено окончательно:

- что переживает rename;
- что переживает structural rewrite;
- где semantic key, а где primary identity;
- как устроить provenance/history для действительно живой системы.

Для `Boundary` это означает простой инженерный вывод:

- нельзя преждевременно цементировать слишком узкий runtime API как окончательный;
- любой текущий refactor нужно проверять на совместимость с живой identity-моделью и со spatial authoring.

## Что Это Значит Для Агентов И Инструментов

Если смотреть на issue вместе, получается уже довольно чёткая картина:

- агент должен иметь world-form, а не быть только текстовым источником ответа;
- чат должен быть observable interaction surface внутри мира;
- `git` уже является первым материальным миром и должен визуализироваться как мир объектов, истории и действий;
- screenshots должны читаться как world-observation artifacts, а не как внешний вспомогательный файл;
- tool invocations должны быть world-events, которые можно видеть в `Boundary` и потом spatially manifest в `Bulk`.

То есть направление для MetaFor такое:

- не копировать внешний CLI-проект поверх мира;
- а делать сам мир средой, в которой агент видит, действует, читает `git`, принимает screenshots и меняет состояние через одну общую геометрию.

## Практический Порядок Для Boundary Docs

Из всех этих issue вытекает строгий порядок документации и реализации:

1. Сначала объяснять, как выглядит одна локальная вселенная и её state matrix.
2. Потом объяснять, как в этой геометрии размещаются агент, чат, screenshots, `git` и инструменты.
3. Потом объяснять patch/event/protocol flow.
4. Потом объяснять межмировые связи и более сложную координацию.

Если документация нарушает этот порядок, она почти неизбежно начинает выглядеть как
набор разрозненных технологий, а не как карта одной self-authoring мультивселенной.
