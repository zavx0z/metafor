# actor — реляционное хранилище render-сцены

Документ описывает, как раскладывается **визуальная сцена** одного запущенного мира в реляционную форму. Это **презентационный слой** в смысле `store/README.md` §6 — координаты, цвета, размеры, иерархия отображения. Не путать с инстансным слоем (`view`), где живут текущие значения полей и состояния FSM.

**2 таблицы**. Минимально достаточный набор для того, чтобы внешний рендер (Bulk×WebGPU, debug-снимки, тесты) мог построить геометрию полностью из стора, без обращения к runtime-памяти.

---

## Что такое actor-сцена

Один запущенный корневой компонент порождает **дерево частиц**: сам компонент, его дочерние компоненты, узлы ветвления и группировки между ними. Это то самое дерево, которое формирует обход matter из meta-декларации.

Для рендера каждой частице нужны:
- её **shell** — оболочка, на которой располагается сама частица в пространстве (тор, сфера, плоскость — в зависимости от kind)
- её **fields-orbit** — точки, где визуализируются её поля относительно её shell-а

Actor хранит и то и другое — **в координатах относительно родителя**. Глобальные координаты вычисляются rendering-слоем при необходимости, не хранятся.

---

## Связь с другими слоями

- **meta** даёт схему: какие kind-ы частиц вообще бывают, какие поля у каждой меты
- **view** даёт состояние: текущие значения полей, текущее состояние FSM
- **actor** даёт сцену: где именно эти частицы и поля визуально расположены в данном запуске

`actor` ссылается на `view` через `meta_src` (адрес меты конкретной частицы) и `field_key` (имя поля), но не имеет FK на view-таблицы. Это сделано сознательно: actor-сцена может пересоздаваться независимо (relayout, переформатирование), не задевая инстансное состояние.

`actor` не ссылается на `meta` напрямую — meta живёт по `src`, который актор знает как обычный текст. Декларативная схема не нужна для рендера; нужны только конкретные числовые координаты и цвета.

---

## Группировка под `root_src`

В одной БД может одновременно жить **несколько разных миров** (разные корневые компоненты, например для multi-root сценариев или сравнительных рендеров). Каждый мир изолирован своим `root_src` — каноническим адресом корневой меты этого мира.

Все запросы к actor-таблицам **обязательно** включают `root_src` в фильтре. Это означает:
- `clearWorld(rootSrc)` чистит сцену одного мира, не задевая другие
- `selectAllParticleShells(rootSrc)` возвращает только частицы своего мира
- индексы построены с `root_src` первой колонкой

`root_src` — это **не FK на meta(src)**. Actor умышленно не валидирует существование меты, потому что render может работать со снимками миров, чьи декларации уже изменились или вовсе удалены. Сцена самостоятельна.

## Таблица 1. `actor_particle_shell`

Одна строка = одна частица в render-дереве.

| колонка | смысл |
|---|---|
| `particle_id` (PK) | глобальный id частицы |
| `root_src` | мир, к которому она относится |
| `parent_particle_id` | id родителя (NULL у корня мира; FK на самого себя) |
| `particle_kind` | `wimp` / `fuzzy` / `axion` / `macho` |
| `src` | адрес меты (для `wimp`-частиц; NULL для topology-узлов) |
| `meta_src` | адрес меты, к которой эта частица **визуально** относится (нужно при `wimp`-вложенных meta) |
| `label` | человекочитаемая подпись (имя меты или роль) |
| `depth` | глубина в дереве относительно корня мира (0 у корня, 1 у его детей и т.д.) |
| `shell_order` | позиция среди братьев (порядок в `parent_particle_id`-группе) |

Геометрия в координатах относительно родителя:

| колонка | смысл |
|---|---|
| `local_x`, `local_y`, `local_z` | положение центра shell-а |
| `shell_scale` | масштабный коэффициент |
| `shell_radius` | главный радиус оболочки (большой радиус тора / радиус сферы) |
| `shell_tube` | вторичный радиус (трубка тора; для сфер задаёт визуальную толщину) |

Цвет:

| колонка | смысл |
|---|---|
| `color_r`, `color_g`, `color_b` | компоненты цвета в линейном RGB (0..1) |

Все числовые величины проверяются CHECK-constraint-ом: `shell_scale > 0`, `shell_radius > 0`, `shell_tube > 0`, `depth >= 0`, `shell_order >= 0`.

**Индексы**:
- `(root_src, parent_particle_id, shell_order)` — обход детей родителя по порядку
- `(root_src, depth, shell_order)` — обход слой-за-слоем (для layered render)

**Каскад**: при удалении родительской частицы все её потомки удаляются автоматически (`ON DELETE CASCADE` на `parent_particle_id`).

## Таблица 2. `actor_field_orbit`

Одна строка = одна точка-визуализация поля частицы.

| колонка | смысл |
|---|---|
| `id` (PK) | глобальный id точки |
| `root_src` | мир |
| `particle_id` | FK на `actor_particle_shell(particle_id)` — какой частице принадлежит |
| `field_key` | имя поля в meta-схеме (`title`, `mode`) |
| `field_label` | подпись для отображения |
| `field_order` | позиция в orbit-кольце (порядок среди полей одной частицы) |

Тип значения для подсветки в render:

| колонка | смысл |
|---|---|
| `value_kind` | `number` / `text` / `bool` / `other` |
| `value_text` | сериализованное значение для дисплея (NULL если значение невыразимо текстом) |

Геометрия точки относительно центра shell-а родителя:

| колонка | смысл |
|---|---|
| `local_x`, `local_y`, `local_z` | положение точки |
| `sphere_radius` | радиус визуальной сферы для этой точки |

Цвет:

| колонка | смысл |
|---|---|
| `color_r`, `color_g`, `color_b` | RGB-цвет |

**Индекс**: `(root_src, particle_id, field_order)` — все поля одной частицы по порядку.

**Каскад**: удаление частицы удаляет её orbit-точки (`ON DELETE CASCADE` на `particle_id`).

## Алгоритм заполнения

Actor наполняется в **streaming-режиме**, по одной строке за раз, в процессе layout-прохода:

1. Layout-builder получает дерево descriptor-ов от dark-слоя (kind, parent, geometry-hints) и текущие значения полей от view-слоя.
2. Он вычисляет геометрию: координаты, радиусы, цвета — на каждом узле.
3. Для каждого узла дерева, в порядке обхода (parent → children):
   1. INSERT в `actor_particle_shell` со всеми вычисленными числами
   2. Для каждого поля частицы — INSERT в `actor_field_orbit`
4. После завершения прохода в БД лежит полная сцена.

**Перед** новым layout-проходом для того же мира вызывается `clearWorld(rootSrc)` — `DELETE` из обеих таблиц по `root_src`. Каскад убирает всё дерево разом.

**Транзакционность**: один полный layout-проход — одна транзакция (либо вся сцена записалась, либо никакая). Это нужно потому что render видит атомарный снимок мира — недопустима ситуация, когда часть частиц уже новая, а часть старая.

**Идемпотентность**: повторный layout того же мира поверх существующей сцены = `clearWorld(rootSrc)` + полный re-INSERT. Никакого инкрементального `UPDATE` существующих строк — это упрощает инвалидацию render-кешей (новые UUID-ы у частиц = render знает, что нужно перерисовать).

---

## Чтение

Чтение всегда адресное под `root_src`:

- **Все частицы мира**: select по `(root_src, parent_particle_id, shell_order)` — даёт упорядоченный поток. Render может строить дерево in-memory, либо обходить flat и собирать через `parent_particle_id`.
- **Только дети одного родителя**: запрос с фильтром `parent_particle_id = ?`.
- **Только корни мира**: фильтр `parent_particle_id IS NULL` (один или несколько корней — оба варианта возможны).
- **Слой по глубине**: фильтр `depth = N` — для layered render-режимов.
- **Поля одной частицы**: select из `actor_field_orbit` по `particle_id`, упорядочено по `field_order`.

Никогда не делается полный дамп всей БД. Если нужно "всё для мира X" — это всё равно `WHERE root_src = ?`, не глобальный SELECT.

---

## Что здесь **не** хранится

- **Текущие значения полей** — это `view` (`view_field_values`). В `actor_field_orbit.value_text` лежит **снимок для дисплея на момент layout-а**, не источник истины.
- **Состояния FSM** — это `view` (`view_wimp_states`).
- **Ссылки между полями** (entanglements, sources) — это `view`.
- **Декларация полей и meta-схема** — это `meta` (`field`, `superposition`, `matter_*`). Actor использует `field_key` и `meta_src` как opaque строки, не валидирует.
- **Глобальные координаты** — вычисляются render-слоем как композиция local-координат вверх по `parent_particle_id`-цепочке.
- **Геометрические инварианты типов оболочек** (тор vs сфера) — это **знание render-слоя** на основе `particle_kind`, не хранится в actor-схеме.

## Минимализм данных

Каждая колонка обоих таблиц либо **обязательна для геометрии конкретного узла** (координата, радиус, цвет), либо **служит ключом для адресации** (id, parent, root_src, order). Промежуточных производных полей нет:
- depth выводим из обхода parent-цепочки, но хранится — это компромисс ради быстрого "слой N мира X" запроса (один индекс vs рекурсивный CTE)
- `field_label` отдельно от `field_key` — потому что label **может отличаться** от key (например, локализация)

Если render-слою понадобится агрегация (например, "общий охват дерева" или "количество полей"), она вычисляется запросом, а не хранится отдельной колонкой.

---

## Эволюция

Если в будущем понадобятся другие render-атрибуты (прозрачность, текстуры, шейдер-параметры), они добавляются как **отдельная таблица** с FK на `particle_id` или `id`-orbit, а не как новые колонки в существующих таблицах. Это сохраняет принцип глубокой реляционности (`store/README.md` §2): любой опциональный render-аспект — отдельная сущность.

Если нужно поддерживать несколько render-конфигураций одной сцены (low-detail для миникарт, high-detail для основного view), таблицы группируются дополнительно по `render_profile` колонке — но это расширение схемы, а не runtime-режим.
