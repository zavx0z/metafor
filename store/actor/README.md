# actor — реляционное хранилище инстансов

Документ описывает, как раскладывается **состояние запущенных акторов** в реляционную форму. Это **инстансный слой** в смысле `store/README.md` §6.

В этом слое живёт только то, что необходимо для функционирования рантайма: какие акторы существуют, какие у них значения полей, в каком они сейчас состоянии, как связаны друг с другом и с родителями. Никаких визуальных данных — render полностью вычислим из связки `actor + meta + layoutConfig` и здесь не хранится.

---

## Что такое актор

Актор — это **запущенный экземпляр меты**. Одна мета (по `src`) может породить произвольное число акторов, каждый со своим состоянием. Актор — это «то, что живёт сейчас», в отличие от меты — «то, что объявлено в принципе».

У актора есть:
- собственный **id** (стабильный, генерируется при создании)
- ссылка на мету (`meta_src`) — декларация, по которой он работает
- набор **полей-инстансов** — копия meta-схемы полей, со значениями и со связями
- текущее **состояние FSM** (один из вариантов суперпозиции из меты)
- место в **иерархии акторов** — кто его породил, кому он передаёт значения

---

## Связь с meta

Актор ссылается на мету через `meta_src` (канонический адрес). Это **слабая ссылка** через текстовый ключ, а не FK на физическую запись. Причина: актор может ссылаться на мету, которая живёт в другой БД (например, шарёд-meta-каталог для группы подсистем) или которая ещё не загружена.

Внутри актора:
- `actor_field.meta_field_uuid` — какому полю меты соответствует поле инстанса
- `actor_state.meta_state_uuid` — в каком состоянии (по uuid из meta-`superposition`) сейчас актор

Если в текущей БД лежит и meta, и actor одного и того же мира — на этих ссылках можно поверх включать FK. Но это деталь реализации backend-а, не контракта.

---

## Группировка под `world`

В одной БД может одновременно жить несколько разных миров (разные корневые акторы, например для multi-root сценариев или для сравнительных запусков). Каждый мир имеет канонический адрес — `world` (`src` корневой меты этого мира).

Все запросы к actor-таблицам **обычно** включают `world` в фильтре. Это означает:
- сброс мира затрагивает только его строки
- enumerate-актор-ов даёт акторов одного мира
- индексы построены с `world` первой колонкой там, где это даёт ускорение

## Таблицы

### `actor`
Один запущенный актор.

| колонка | смысл |
|---|---|
| `uuid` (PK) | стабильный id актора |
| `world` | корневой `src` мира |
| `meta_src` | по какой мете работает |
| `position` | порядок появления в мире (стабильно отслеживает «возраст» актора) |

### `actor_edge`
Иерархия родитель → потомок. Один актор имеет одного родителя (или ни одного, если он корень мира). Это означает: edge-запись существует ровно одна на потомка.

| колонка | смысл |
|---|---|
| `child` (PK) | uuid дочернего актора |
| `parent` | uuid родительского актора (NULL у корня) |
| `position` | позиция среди братьев в порядке появления |

### `actor_field`
Поле-инстанс актора — соответствует одному полю из meta-схемы.

| колонка | смысл |
|---|---|
| `uuid` (PK) | id поля-инстанса |
| `actor` | FK на `actor` |
| `meta_field` | uuid соответствующего поля в meta-декларации |
| `position` | порядок (зеркалирует позицию в meta-схеме) |

### `actor_value`
Текущее значение поля. Одна строка на одно поле — поле всегда имеет ровно одно значение.

| колонка | смысл |
|---|---|
| `field` (PK) | FK на `actor_field` |
| `value_kind` | `null` / `boolean` / `number` / `string` / `enum` / `list` |
| `value_boolean` / `value_number` / `value_text` / `value_variant` | скалярная часть, заполняется одна из в зависимости от `value_kind` |

Для enum — `value_variant` указывает на конкретный `field_enum_variant.uuid` из meta-декларации.

Для списочных значений (`value_kind = 'list'`) — отдельная дочерняя таблица `actor_value_item` с порядком и тем же набором скалярных колонок (рекурсивная связь, как в `meta_mass_value`).

### `actor_value_item`
Элемент массива-значения. Используется когда `actor_value.value_kind = 'list'`.

| колонка | смысл |
|---|---|
| `field` (PK) | FK |
| `position` (PK) | позиция в массиве |
| `value_kind` / `value_*` | элемент списка |

### `actor_source`
Источник значения поля — указывает, что значение этого поля поступает от другого поля (другого актора). Используется для прямых проводок «родитель → потомок» через matter-bindings.

| колонка | смысл |
|---|---|
| `child_field` (PK) | поле-получатель |
| `parent_field` | поле-источник |

Когда обновляется `parent_field`, изменение должно прокидываться в `child_field` — это инвариант рантайма, обеспечивается FSM-движком (стор только хранит факт связи).

### `actor_state`
Текущее состояние FSM актора. Одна строка на актор.

| колонка | смысл |
|---|---|
| `actor` (PK) | FK на `actor` |
| `meta_state` | uuid состояния из meta-`superposition` |

### `actor_entanglement`
Семья entangled-акторов: набор акторов, которые делят общее значение через цепочку source-проводок. Когда у двух разных акторов поля имеют общий root-источник, они **запутаны** — изменение в любом из них синхронно отражается на других.

| колонка | смысл |
|---|---|
| `uuid` (PK) | id семьи |
| `world` | мир, в котором живёт |
| `root_field` | поле-источник, от которого расходится цепочка |

### `actor_entanglement_member`
Член семьи — один из запутанных акторов.

| колонка | смысл |
|---|---|
| `entanglement` (PK) | FK |
| `actor` (PK) | FK |
| `position` | порядок входа в семью |

### `actor_entanglement_field`
Описание разделяемого поля внутри семьи (одно поле в meta может породить несколько entangled-fields через разные source-цепочки).

| колонка | смысл |
|---|---|
| `uuid` (PK) | id |
| `entanglement` | FK |
| `meta_field` | uuid поля в meta-декларации |
| `position` | порядок |

### `actor_entanglement_field_member`
Конкретное поле-инстанс одного актора в составе entangled-поля.

| колонка | смысл |
|---|---|
| `entanglement_field` (PK) | FK |
| `actor_field` (PK) | FK на `actor_field` |
| `position` | порядок |

## Алгоритм заполнения

Запись актора в стор идёт **инкрементально**, по мере того как рантайм обнаруживает новые сущности. Каждый шаг — отдельная транзакция, не накапливаем «всё разом».

### Создание актора

1. INSERT в `actor` (uuid, world, meta_src, position).
2. INSERT в `actor_edge` (child = новый, parent = породивший актор или NULL).
3. Для каждого поля meta-схемы:
   1. INSERT в `actor_field`.
   2. Если значение скаляр — INSERT в `actor_value`.
   3. Если значение список — INSERT в `actor_value` (kind=list) + серия INSERT в `actor_value_item`.
   4. Если поле приходит от parent-field через source-binding — INSERT в `actor_source`.
4. INSERT в `actor_state` с initial-состоянием меты.

### Обновление поля

1. UPDATE `actor_value` (или замена `actor_value_item` для списка) на новое значение.
2. Стор не делает каскадного обновления entangled-полей — это ответственность FSM-движка, который читает `actor_source` и применяет изменение по цепочкам.

### Переход состояния

Один UPDATE `actor_state.meta_state`. Стор не валидирует, что переход разрешён условиями из meta — это дело FSM-движка, который перед записью проверяет conditions из meta-`transition`.

### Обнаружение entanglement

Когда новый актор создаётся, и его поле через `actor_source` ведёт к источнику, у которого уже есть другие потребители — формируется/расширяется семья:

1. Найти root-поле цепочки (рекурсивный обход `actor_source` вверх).
2. Если `actor_entanglement` с этим root-полем существует — INSERT в `actor_entanglement_member` и в `actor_entanglement_field_member`.
3. Иначе — INSERT в `actor_entanglement`, затем member-ы.
4. Если в результате семья оказалась состоящей из одного актора — DELETE её (одиночка не считается семьёй).

### Удаление актора

DELETE `actor` по `uuid`. Каскад FK снимает: `actor_field` → `actor_value` → `actor_value_item`, `actor_state`, `actor_edge` (как child), `actor_entanglement_member`. Если в семье после удаления остался один член — она тоже удаляется (валидируется на стороне рантайма перед commit-ом).

## Чтение

Чтение всегда адресное:

- **Один актор целиком**: SELECT из `actor` по uuid + JOIN на `actor_field` + JOIN на `actor_value` + JOIN на `actor_state`. Возвращает row-group для одного инстанса.
- **Дети актора**: `actor_edge` с `parent = ?`, упорядочено по `position`.
- **Все акторы мира**: `actor` с `world = ?`.
- **Поля одного актора**: `actor_field` с `actor = ?`, упорядочено по `position`.
- **Текущее состояние**: `actor_state` по `actor`.
- **Значение конкретного поля**: `actor_value` по `field`.
- **Семья enttanglement**: `actor_entanglement` по uuid + связанные member-ы.

Никогда не делается «дамп всего стора». Если рантайму нужен срез всего мира — он итерирует акторов по `actor.world = ?` и для каждого читает row-group.

---

## Что здесь **не** хранится

- **Декларация** (что такое поле, какие переходы возможны, какие условия) — это `meta`.
- **Render** (координаты shell-ов, точки полей, цвета, размеры) — **полностью вычислим** из `actor + meta + layoutConfig`, живёт в render-слое (Bulk×WebGPU и debug-вьюверы), не в сторе.
- **Кэшированные индексы и агрегации** (например, «все entangled поля в этом мире») — вычисляются запросами или живут как кэш в пределах одного запроса в потребителе.
- **In-memory состояние FSM-движка** (heap текущих переходов, lock-биты, очереди процессов) — рабочая память движка, не часть стора. Если что-то из этого нужно персистить (например, для recovery после крэша) — это отдельная сущность с явными таблицами, а не «часть actor».

---

## Минимализм данных

Каждая колонка таблиц либо обязательна для воспроизведения состояния актора, либо служит ключом для адресации. Производных полей нет:
- нет «количество детей у актора» — это `COUNT(actor_edge WHERE parent = ?)`
- нет «есть ли entanglement у этого поля» — это `EXISTS(actor_entanglement_field_member WHERE actor_field = ?)`
- нет «снимок всего значения как JSON» — значения разложены по `actor_value`/`actor_value_item`

Если потребителю нужна агрегация — она реализуется как метод стора (внутри — SQL-запрос с индексами), снаружи виден тот же адресный API.
