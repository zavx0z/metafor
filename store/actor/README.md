# actor — Персистентные Инстансы Boundary

> Обновление 2026-06-14: прежний `store` переименован в `Boundary`.
> `actor` здесь — часть персистентного Boundary, а не рантайм-модель `Energy` или
> `Bulk`. Рантайм-домены получают самодостаточные данные и не читают
> Boundary/SQLite напрямую.

Документ описывает, как раскладывается **состояние запущенных акторов** в реляционную форму. Это **инстансный слой** в смысле `store/README.md` §6.

В этом слое живёт только то, что необходимо для функционирования рантайма: какие акторы существуют, какие у них значения полей, в каком они сейчас состоянии. Никаких визуальных данных — рендер полностью вычислим из связки `actor + meta + layoutConfig` и здесь не хранится.

---

## Что такое актор

Актор — это **запущенный экземпляр меты**. Одна мета может породить произвольное число акторов, каждый со своим состоянием.

Важно: `actor` — это имя инстансного слоя store, а не новая доменная онтология. В доменах тот же носитель читается через их собственные проекции:

- в `Dark` это `wimp`;
- в `Boundary` это `brane`;
- в `Bulk` это проявленный рантайм-носитель (`tor`, если эта проекция выделена).

Поэтому store-актор не должен дублироваться как отдельная сущность рядом с `wimp`/`brane`/`tor`. Он фиксирует общий реляционный контракт для одной устойчивой идентичности: `uuid`, `parent`, `meta`, значения полей и текущее состояние. Доменная семантика остаётся в потребителях и протоколах, а store удерживает адресуемое состояние инстанса.

У актора есть:
- собственный **id** (стабильный, генерируется при создании)
- **родитель** (другой актор; NULL у корневого)
- ссылка на **мету** (по `src`) — декларация, по которой он работает
- набор **значений** для своих полей (где набор полей определён в meta-декларации)
- текущее **состояние FSM** (один из вариантов суперпозиции из меты)

Поля актора **не дублируются** в этом слое — они уже описаны в meta. Актор имеет только **значения** для уже объявленных в мете полей.

Никакого понятия «мира» (`world`) нет — все акторы живут в одном плоском пространстве. Корневые акторы (`parent IS NULL`) могут существовать в любом количестве.

## Связь с meta — жёсткая через FK

Актор ссылается на мету через `meta`-колонку (= `meta.src`). Это **полноценный FK** с `ON DELETE CASCADE`. Удаление меты автоматически снимает все акторы по ней (это корректно — если декларации больше нет, инстансы по ней теряют смысл).

Аналогично:
- `actor_value.field` → `field.uuid` (на какое поле меты ссылается значение)
- `actor_state.metaState` → `superposition.uuid` (текущая фаза FSM из meta-superposition)
- `value_enum.variant` → `field_enum_variant.uuid` (для значений типа enum; данные разнесены по типизированным подтаблицам, корневая `value` хранит только `kind`)

Стор и meta живут в одной БД — FK работают.

## Таблицы

### `actor`
Один запущенный актор.

| колонка | смысл |
|---|---|
| `uuid` (PK) | стабильный id актора |
| `parent` | uuid родителя (NULL у корневого; FK self → `actor.uuid`) |
| `meta` | FK на `meta.src` |
| `position` | порядок появления среди братьев |

**FK**: `parent` → `actor(uuid)` `ON DELETE CASCADE` (удаление родителя сносит детей). `meta` → `meta(src)` `ON DELETE CASCADE`.

### `value`
Запись значения. **Отдельная сущность, не привязанная к конкретному актору**. Один и тот же `value.uuid` может быть разделён несколькими акторами — это и есть механизм entanglement.

| колонка | смысл |
|---|---|
| `uuid` (PK) | id значения |
| `kind` | `null` / `boolean` / `number` / `string` / `enum` / `list` |
| `boolean` / `number` / `text` / `variant` | скалярная часть, заполнена одна из в зависимости от `kind` |

`variant` для enum — FK на `field_enum_variant.uuid` из meta.

**Жизненный цикл**: запись создаётся под одного владельца. Если рантайм решает, что эта запись должна быть разделена с другим актором — другой `actor_value` просто ссылается на тот же `value.uuid`. Удаление записи — когда на неё больше никто не ссылается (через триггер или явный GC; см. ниже).

### `value_item`
Элемент списочного значения. Используется когда `value.kind = 'list'`. Одна строка = один элемент.

| колонка | смысл |
|---|---|
| `value` (PK) | FK на `value.uuid` |
| `position` (PK) | позиция в массиве |
| `kind` / скалярные колонки | как в `value`, но без `list` (вложенных списков нет на этом уровне) |

### `actor_value`
Связь «актор → его значение для конкретного поля меты». Один актор имеет ровно одну запись на каждое объявленное в его мете поле.

| колонка | смысл |
|---|---|
| `actor` (PK) | FK на `actor.uuid` |
| `field` (PK) | FK на `field.uuid` (поле меты, к которому относится значение) |
| `value` | FK на `value.uuid` |

**PRIMARY KEY**: `(actor, field)` — один actor имеет одно значение per поле меты.

**Entanglement** = два `actor_value` указывают на один и тот же `value.uuid`:
```
actor_value (actorA, fieldX, valueV)
actor_value (actorB, fieldY, valueV)  -- та же V
```
Изменение `value` (через `value.uuid = V`) автоматически отражается на обоих акторах. Никаких отдельных entanglement-таблиц не нужно.

### `actor_state`
Текущее состояние FSM актора. Одна строка на актор.

| колонка | смысл |
|---|---|
| `actor` (PK) | FK на `actor.uuid` |
| `metaState` | FK на `superposition.uuid` (на какое состояние меты сейчас указывает) |

## Алгоритм заполнения

### Создание актора

1. INSERT в `actor` (uuid, parent, meta, position).
2. INSERT в `actor_state` с initial-состоянием меты (берётся из `superposition` где `position = 0`).
3. Для каждого `field`-а из meta (через мету актора):
   - INSERT в `value` с дефолтным значением (или текущим из binding-source — см. ниже).
   - INSERT в `actor_value (actor, field, value)`.
4. Если поле приходит от родительского актора через source-binding (matter declaration parent передаёт child) — вместо нового `value` берётся UUID существующей записи родительского `actor_value` и оба указывают на неё. **Это и есть entanglement по построению.**

### Обновление значения

1. UPDATE `value` (или замена `value_item` для списка) по `value.uuid`.
2. Все акторы, делящие эту запись через `actor_value`, видят новое значение мгновенно. **Не нужно явно прокидывать изменение по цепочкам.**

### Переход состояния FSM

UPDATE `actor_state.metaState` по actor-uuid. Стор не валидирует переход — это задача FSM-движка (читает условия из meta-`transition` и проверяет до записи).

### Удаление актора

DELETE `actor` по uuid. Каскад FK снимает: `actor_value` (по `actor`), `actor_state`. Дочерние акторы тоже удаляются (`parent` CASCADE).

`value`-записи **не удаляются автоматически** — они могут быть всё ещё разделяемы другими акторами. После удаления актора рантайм проверяет orphan-записи (`value` без записей в `actor_value`) и сносит их (отдельным DELETE или через триггер `AFTER DELETE ON actor_value`).

### Расщепление и слияние entanglement

**Слияние**: два актора, чьи поля до этого были раздельны, начинают разделять один `value`. Стор: меняется `actor_value.value` одного из них на uuid другого; старая запись становится orphan и удаляется.

**Расщепление**: разделяемая запись становится локальной для одного актора. Стор: создаётся новая `value`-запись (копия), `actor_value.value` одного из акторов переключается на неё. Прежняя запись остаётся для остальных делящих её акторов.

## Чтение

- **Все корневые акторы**: `SELECT uuid FROM actor WHERE parent IS NULL ORDER BY position`.
- **Дети актора**: `SELECT uuid FROM actor WHERE parent = ? ORDER BY position`.
- **Все поля одного актора с значениями**: JOIN `actor_value` + `value` + `field` (meta) по `actor = ?`.
- **Кто разделяет это значение**: `SELECT actor FROM actor_value WHERE value = ?`. Если результат — одна строка, это локальное значение; если несколько — это entangled-семья.
- **Поля разделяемые между двумя акторами**: `SELECT a1.field, a2.field FROM actor_value a1 JOIN actor_value a2 ON a1.value = a2.value WHERE a1.actor = ? AND a2.actor = ? AND a1.actor != a2.actor`.
- **Текущее состояние**: `SELECT metaState FROM actor_state WHERE actor = ?`.

## Что здесь **не** хранится

- **Декларация** (что такое поле, какие переходы возможны, какие условия) — `meta`.
- **Render** — вычислим из `actor + meta + layoutConfig`, живёт в рендер-слое.
- **Производные множества** («все entangled партнёры этого актора», «все потомки», «все мёртвые orphan-`value`») — вычисляются запросами.
- **Рантайм-состояние FSM-движка** (heap, lock-биты, очереди) — рабочая область движка.

## Минимализм

5 таблиц вместо 11 в предыдущей версии. Уменьшение достигнуто за счёт:

- удалена `actor_field` — поля декларированы в meta, не нужно их повторно перечислять для каждого инстанса (`actor_value.field` напрямую ссылается на `field.uuid`)
- удалена `actor_edge` — `actor.parent` через self-FK даёт ту же иерархию
- удалена `actor_source` — entanglement выражается через общий `value.uuid`, source-проводки исчезают как отдельная сущность (это просто разделение записи)
- удалены 4 таблицы `actor_entanglement_*` — entanglement = общая строка, никаких метаданных «семьи» хранить не нужно (вычислимо: `SELECT actor FROM actor_value WHERE value = ?`)
- удалён `world` — нет понятия мира, все акторы в одном пространстве, корни различаются `parent IS NULL`

## Открытые вопросы по entanglement

Пользователь отметил, что нужно **более глубокое исследование**, что должно храниться в каких полях, потому что в meta запутанность задаётся через matter-binding и даёт более широкие возможности, чем простое разделение значения.

Текущая модель (общий `value.uuid`) предполагает: entanglement — **только** разделение записи. Это покрывает базовый кейс «parent передаёт значение child через matter-binding».

Что **не** покрывает текущая модель:
- **Направление**: source-bindings имеют направление (parent → child). Общая строка симметрична. Если рантайм гарантирует, что child не пишет сам — направление обеспечивается дисциплиной, не схемой. Если бы хотелось зафиксировать направление в схеме — нужна была бы доп. колонка `actor_value.source` (FK на пару `(actor, field)`-источник) или возврат отдельной таблицы `value_source`.
- **Дериативные значения**: matter-binding может содержать выражение `expr` («child = parent.length + 1»). Тогда child не равен parent, а вычисляется. Общая строка не работает — нужны отдельные `value`, и связь между ними — не «равенство», а «вычисление».
- **Семьи > 2**: если три актора делят одно значение через цепочку bindings — общая строка покрывает это естественно (все три указывают на одну запись). Семья — производное множество, не хранится.
- **Разделённый список**: если list-значение разделяется, изменение `value_item.position=N` затрагивает всех — это нормально. Но если кто-то хочет вставлять/удалять элементы только у себя — нужен локальный fork (см. «расщепление» выше).

Эти нюансы определяются семантикой meta-binding-ов (типы: `static`, `variable`, `dynamic` — см. `meta/sql/matter.sql:matter_binding`). До прояснения этой семантики со стороны рантайма схема стора **минимальная и без добавок**: общая строка + при необходимости явное расщепление.
