# Правила для работы с MetaFor фреймворком

<!-- markdownlint-disable MD041 MD003 MD022 MD026 MD031 MD032 MD040 MD024 MD047 -->

## Документация

**ВСЕГДА смотрите подробное описание в JSDoc комментариях файла `metafor.d.ts`** - там находится полная документация API с примерами использования.

## Архитектурные принципы

### Контекст (Context)

- Контекст должен содержать ТОЛЬКО простые типы: string, number, boolean, array, enum
- Массивы в контексте должны содержать только ID (числа или строки)
- Сложные объекты храните в core, а не в контексте
- Используйте осмысленные значения по умолчанию

### Регистрация и теги компонентов

- **Тег компонента всегда имеет вид `meta-<name>`**, где name - это имя компонента
- **Имя компонента** используется для создания уникального тега
- **Любое изменение в логике компонента требует нового имени**
- Используются только именованные теги
- Это обеспечивает уникальность версий компонентов
- Позволяет безопасно кэшировать разные версии
- **Использование компонента**:

  ```javascript
  // Импортируем компонент
  const counterComponent = MetaFor("counter", {
    /* конфигурация */
  })

  // Используем имя компонента в теге
  document.body.innerHTML = `<meta-counter></meta-counter>`
  ```

````

### Core
- Core - это простой объект с данными, используемыми во всех состояниях
- Сложные объекты и структуры данных храните в core
- Core доступен во всех процессах и реакциях
- Используйте простые свойства для хранения данных
- **Core может быть определен как объект или как функция с ref:**

  ```javascript
  // Простой объект (если не нужны ссылки на DOM элементы)
  .core(
    /**@type import("./websocket.t").WebSocketCore*/ ({
      socket: null,
      url: "ws://localhost:3000",
      maxReconnectAttempts: 5,
      reconnectDelay: 1000,
      reconnectTimer: null,
    })
  )

  // Функция с ref (если нужны ссылки на DOM элементы)
  .core(
    /**@type import("./websocket.t").WebSocketCore*/ ((ref) => ({
      socket: null,
      url: "ws://localhost:3000",
      maxReconnectAttempts: 5,
      reconnectDelay: 1000,
      reconnectTimer: null,
      button: ref()
    }))
  )
````

### Состояния (States)

- Перечисляйте ВСЕ состояния в массивах реакций, не используйте ["*"]
- Состояния должны быть простыми и понятными
- Используйте условия переходов на основе контекста
- Не создавайте вложенные или параллельные состояния

### Процессы (Processes)

- Процессы по природе асинхронны, но могут быть и синхронными
- **ВАЖНО: Все процессы должны иметь обработчики success и error**
- Используйте типизацию для данных процессов
- Группируйте связанную логику в одном процессе
- **success и error обработчики должны быть синхронными**
- Асинхронные операции выполняйте только в action функциях
- Для последовательных асинхронных операций создавайте отдельные процессы

#### Правильный формат процессов

```javascript
// Базовая структура процесса
.processes((process) => ({
  stateName: process()
    .action(({ context, core }) => {
      // Асинхронная или синхронная логика
      return Promise.resolve(data) // или просто return data
    })
    .success(({ update, data }) => {
      // Синхронное обновление контекста
      update({ field: data.value })
    })
    .error(({ update, error }) => {
      // Синхронная обработка ошибки
      update({ error: error.message, status: "error" })
    })
}))
```

#### Лучшие практики

- **Передавайте данные через action:** возвращайте данные из action, получайте их в success
- **Используйте reject для ошибок:** `Promise.reject(error)`, не `resolve({ success: false })`
- **Обработчики должны быть простыми:** только обновление контекста, без сложной логики

```javascript
// ✅ Хорошо - данные передаются через action
.action(({ core }) => Promise.resolve("connected"))
.success(({ update, data }) => update({ status: data }))

// ❌ Плохо - данные дублируются в success
.action(({ core }) => Promise.resolve())
.success(({ update }) => update({ status: "connected" }))
```

### Реакции (Reactions)

- **ВАЖНО: Реакции предназначены для реагирования на события других акторов, а не на собственные изменения состояния**
- Для управления собственными переходами состояний используйте процессы и их success/error обработчики
- Реакции связывают разные акторы в событийной архитектуре
- Используйте специфичные фильтры для точного отбора событий
- Группируйте связанные реакции по состояниям
- Используйте осмысленные заголовки для реакций

#### Правильный формат реакций

```javascript
.reactions((reaction) => [
  [
    ["idle", "active"], // состояния, в которых активна реакция
    reaction({ label: "Обработка сообщений от другого актора" })
      .filter({
        tag: "user-profile", // имя компонента-отправителя
        op: "replace",   // операция патча
        path: "/context", // путь в патче
        value: 1         // значение (опционально)
      })
      .equal(({ update, context, patch, meta }) => {
        // Синхронная обработка события
        update({
          lastMessage: patch.value,
          messageCount: context.messageCount + 1
        })
      })
  ]
])
```

#### Важные правила

- **Перечисляйте ВСЕ состояния явно:** `["idle", "active"]`, не используйте `["*"]`
- **Фильтры должны быть специфичными:** указывайте конкретные теги, операции, пути
- **Обработчики должны быть синхронными:** только обновление контекста
- **Не реагируйте на собственные события:** это приводит к циклам

### Изоляция акторов

- **ВАЖНО: Акторы MetaFor имеют полную изоляцию с независимой реализацией DOM**
- Все взаимодействия между акторами происходят через патчи в сообщениях
- Используйте систему сообщений и реакций для связи между компонентами

### Представление (View)

- Используйте декларативный template API с `@zavx0z/template`
- Разделяйте логику и представление
- Используйте условный рендеринг вместо скрытия элементов
- Применяйте семантическую разметку
- Используйте CSS-переменные для динамических стилей

#### Структура view конфигурации

```javascript
.view({
    // Используем ссылки из core (если они там определены)
    // ссылка создается в core через ref()
  render: ({ context, state, core, update, html, style }) => html`
    <div>
    <h2>${context.label}</h2>
    <input value=${context.value}
            oninput=${e => update({ value: e.target.value })} />

    ${context.items.length > 0
        ? html`
        <ul>
            ${context.items.map((item, i) => html`<li>${i}: ${item}</li>`)}
        </ul>
        `
        : html`<span>Список пуст</span>`
    }
    </div>`,
  style: ({ css }) => css`
    :host {
      display: block;
      padding: 1rem;
    }
    h2 {
      color: var(--primary-color, #333);
    }
  `,

  onMount() {
    // Инициализация после монтирования
    console.log('Component mounted')
  },

  onDestroy() {
    // Очистка при уничтожении
    console.log('Component destroyed')
  }
})
```

#### Доступные утилиты в render

- **`html`** - функция шаблонизации (аналог lit-html)
- **`style`** - динамические стили
- **`update`** - функция обновления контекста
- **JavaScript выражения** - тернарные операторы, логические операторы, map, filter
- **`context`** - текущий контекст
- **`state`** - текущее состояние
- **`core`** - объект core с данными

#### Важные правила

- **Используйте `ViewDefinitionParams` для типизации** функции рендеринга
- **Ссылки из core используются через `ref(coreRef)`** в шаблоне
- **События привязываются через `@event=${handler}`**
- **Стили инкапсулированы** благодаря Shadow DOM

## Стиль кода

### Именование

- Используйте camelCase для полей контекста
- Используйте kebab-case для имен компонентов
- **Тег компонента всегда `meta-<name>`** — используйте имя компонента
- Используйте PascalCase для типов и интерфейсов
- Используйте описательные имена для процессов и реакций

### Тесты

- Именуйте тесты через точку: `file.name.spec.ts`
- Пишите тесты таргетированно для конкретных функций
- Используйте русские сообщения в expect: `expect(result, 'сообщение').toBe(expected)`
- **В тестах используйте имя компонента для создания элемента**
- Не используйте статические теги вида `<meta-test>`, `<meta-example>`
- Тесты служат примерами кода для документации

#### Правильный формат тестов

```javascript
import { test, expect } from "bun:test"
import { MetaFor } from "../web/metafor.ts"

test("Описание теста на русском", async () => {
  // Создание компонента
  const testComponent = MetaFor("test-component")
    .context((types) => ({
      value: types.number.required(0),
    }))
    .states({ idle: {} })
    .core()
    .processes(() => ({}))
    .reactions(() => [])
    .view({
      render: ({ context, html }) => html`<div>${context.value}</div>`,
    })

  // Создание элемента с именем компонента
  document.body.innerHTML = `<meta-test-component></meta-test-component>`

  // Ожидание и проверки
  await Bun.sleep(10)
  expect(result, "описание ожидания").toBe(expected)
})
```

#### Важные правила

- **Всегда используйте имя компонента:** `<meta-<name>>`, не статические теги
- **Русские сообщения в expect** помогают понять ошибки
- **Тесты должны быть независимыми** и не влиять друг на друга
- **Используйте `Bun.sleep()` для ожидания** асинхронных операций

## Ограничения

### Не поддерживается

- Вложенные состояния
- Параллельные состояния
- Условные переходы на основе событий
- Прямой доступ к DOM в представлении

### Альтернативы

- Вместо вложенных состояний используйте флаги в контексте
- Вместо параллельных состояний используйте отдельные компоненты
- Вместо прямого доступа к DOM используйте refs
- Для связи между компонентами используйте передачу контекста через `context=${object}`
