# 📝 AI Markdown Standards

Этот документ описывает строгий стандарт написания Markdown-документации для AI-ассистентов.

**Контекст:**

* **Автоматическая генерация:** AI генерирует Markdown-контент.
* **Линтинг:** Все документы проходят проверку markdownlint.
* **Стиль:** Используется стиль "compact" для таблиц.

---

## 1. Таблицы

### 1.1. Форматирование разделителей

Разделитель таблицы **обязан** иметь пробелы с обеих сторон от дефисов.

**✅ Правильно:**

```markdown
| Колонка 1 | Колонка 2 |
| --------- | --------- |
| Значение  | Значение  |
```

**❌ Неправильно:**

```markdown
| Колонка 1 | Колонка 2 |
|----------|----------|
| Значение  | Значение  |
```

### 1.2. Выравнивание контента

Контент в ячейках таблицы **должен** быть отделен от границ (pipe) пробелами.

**✅ Правильно:**

```markdown
| Значение | Описание |
| -------- | -------- |
| 1        | Первый   |
```

**❌ Неправильно:**

```markdown
|Значение|Описание|
|-------|-------|
|1|Первый|
```

### 1.3. Многострочный контент в ячейках

**⛔ Запрещено:** Использовать inline HTML (`<br>`) для переносов строк внутри ячеек таблицы.

**✅ Альтернативы:**

1. **Текстовые разделители:** Использовать точку с пробелом или точку с запятой.
2. **Нумерация:** Использовать цифры с точкой внутри текста.
3. **Разделение на строки:** Вынести сложный контент за пределы таблицы.

**Пример:**

```markdown
❌ Неправильно:
| Действие | Описание |
|----------|----------|
| Шаг 1    | Первое действие.<br>Вторая строка. |
```

```markdown
✅ Правильно:
| Действие | Описание |
| -------- | -------- |
| Шаг 1    | Первое действие. Вторая строка. |
```

---

## 2. Списки

### 2.1. Нумерованные списки

**Правило:** Все элементы нумерованного списка **должны** начинаться с `1.` (стиль "1/1/1").

**✅ Правильно:**

```markdown
1. Первый пункт
1. Второй пункт
1. Третий пункт
```

**❌ Неправильно:**

```markdown
1. Первый пункт
2. Второй пункт
3. Третий пункт
```

### 2.2. Вложенные списки

Вложенные списки **должны** иметь отступ в 4 пробела.

**✅ Правильно:**

```markdown
1. Родительский пункт
    1. Дочерний пункт
    1. Еще один дочерний
```

### 2.3. Маркированные списки

Использовать звёздочку (`*`) для маркированных списков.

**✅ Правильно:**

```markdown
* Пункт 1
* Пункт 2
```

**❌ Неправильно:**

```markdown
- Пункт 1
- Пункт 2
```

---

## 3. Inline HTML

**⛔ Запрещено:** Использовать inline HTML-теги в Markdown-документах.

**Список запрещенных тегов:**

* `<br>` — использовать перенос строки (два пробела в конце строки или пустая строка)
* `<div>` — использовать блоки кода или цитаты
* `<span>` — использовать курсив или жирный шрифт
* `<a>` — использовать Markdown-ссылки `[текст](url)`

**Исключения:** HTML допустим только в случаях, когда Markdown не предоставляет альтернативы (например, специфические атрибуты для презентаций).

---

## 4. Заголовки

### 4.1. Иерархия

Заголовки **должны** следовать строгой иерархии без пропусков уровней.

**✅ Правильно:**

```markdown
# H1
## H2
### H3
```

**❌ Неправильно:**

```markdown
# H1
### H3 (пропущен H2)
```

### 4.2. Стиль

Использовать стиль `#` для заголовков, а не подчеркивание.

**✅ Правильно:**

```markdown
## Заголовок
```

**❌ Неправильно:**

```markdown
Заголовок
---------
```

### 4.3. Запрет выделения вместо заголовков (MD036)

**⛔ Запрещено:** Использовать выделение (`**текст**` или `*текст*`) вместо заголовков.

Если текст выглядит как заголовок (короткий, выделен, стоит отдельно) — используй заголовок.

**✅ Правильно:**

```markdown
### Минимальная ответственность

Каждый уровень отвечает только за свою область.
```

**❌ Неправильно:**

```markdown
**Минимальная ответственность**

Каждый уровень отвечает только за свою область.
```

**Исключения:**

* Выделение текста внутри параграфа — допустимо
* Выделение в списках для акцента — допустимо

---

## 5. Код

### 5.1. Блоки кода

Блоки кода **должны** иметь указание языка для подсветки синтаксиса.

Для простого текста использовать `text`.

**✅ Правильно:**

````markdown
```typescript
const x: number = 42;
```
````

**❌ Неправильно:**

````markdown
```
const x: number = 42;
```
````

### 5.2. Inline-код

Inline-код **должен** быть обрамлен обратными кавычками без пробелов внутри.

**✅ Правильно:**

```markdown
Функция `processData()` возвращает результат.
```

**❌ Неправильно:**

```markdown
Функция ` processData ` возвращает результат.
```

---

## 6. Пробелы и пустые строки

### 6.1. Пустые строки вокруг блоков

Блоки (заголовки, списки, таблицы, код) **должны** быть отделены пустыми строками.

**✅ Правильно:**

```markdown
## Заголовок

Текст параграфа.

* Пункт 1
* Пункт 2

Следующий параграф.
```

### 6.2. Конец файла

Файл **должен** заканчиваться одной пустой строкой.

### 6.3. Конец строки

Строки **не должны** содержать trailing spaces (пробелы в конце строки), за исключением случаев, когда два пробела используются для принудительного переноса строки.

---

## 7. Ссылки и изображения

### 7.1. Ссылки

Использовать inline-формат ссылок для коротких URL.

**✅ Правильно:**

```markdown
[Текст ссылки](https://example.com)
```

Для длинных URL использовать reference-формат:

```markdown
[Текст ссылки][ref]

[ref]: https://very-long-url.example.com/path/to/resource
```

### 7.2. Изображения

Изображения **должны** иметь alt-текст.

**✅ Правильно:**

```markdown
![Описание изображения](path/to/image.png)
```

**❌ Неправильно:**

```markdown
![](path/to/image.png)
```

---

## 8. Чек-лист перед генерацией

Перед генерацией Markdown-документа AI **обязан** проверить:

* [ ] Все таблицы имеют пробелы в разделителях
* [ ] Все таблицы имеют пробелы вокруг контента в ячейках
* [ ] Отсутствует inline HTML (`<br>`, `<div>`, `<span>`)
* [ ] Нумерованные списки начинаются с `1.`
* [ ] Маркированные списки используют `*` (звёздочку)
* [ ] Заголовки следуют иерархии без пропусков
* [ ] Заголовки используются вместо выделения (`**текст**`) для заголовков (MD036)
* [ ] Блоки кода имеют указание языка
* [ ] Блоки кода используют правильный язык (MD040)
* [ ] Блоки отделены пустыми строками
* [ ] Списки окружены пустыми строками (MD032)
* [ ] Файл заканчивается пустой строкой

# 📘 AI Documentation Standards (Docs-as-Code)

Этот документ описывает строгий стандарт ведения документации для AI-ассистентов.

**Контекст проекта:**

* **Динамичное развитие:** Код быстро эволюционирует.
* **Нет обратной совместимости:** Мы не поддерживаем старые версии.
* **Принцип:** Вся документация живет **внутри кода** в формате TSDoc.

---

## 1. Философия: High Signal-to-Noise Ratio

Документация должна объяснять **"Зачем"** и **"Как это работает внутри"**, а не пересказывать **"Что это"**.

* **⛔ Запрещено:** Переводить названия переменных на русский язык в описании.
* **⛔ Запрещено:** Создавать TSDoc-блоки ради галочки. Лучше отсутствие описания, чем бесполезный шум.
* **✅ Требуется:** Описывать неявные связи, ограничения и алгоритмы.

---

## 2. Структура документации

### 2.1. Точка входа (Module Level)

Главный файл модуля (`src/index.ts`) **обязан** содержать тег `@packageDocumentation`.
Текст должен описывать **текущую архитектуру** (паттерны, ответственность модуля).

### 2.2. Уровень Сущности (Class / Interface / Properties)

**🔴 The Value-Add Test (Тест на ценность):**
Прежде чем создать TSDoc-блок (`/** ... */`) для свойства, задай вопрос: *"Дает ли это описание информацию, которой нет в названии и типе?"*

* Если **НЕТ** → **Не создавай TSDoc-блок вообще.**
* Если **ДА** → Пиши.

**Что считается ценной информацией:**

1. **Связь с железом/системой:** "Данные отправляются в GPU", "Синхронизируется с БД".
2. **Ownership / Lifecycle:** "Нужно вызывать dispose()", "Ссылка (не клон)".
3. **Side Effects:** "Изменение сбрасывает кэш", "Триггерит перерисовку".
4. **Unit of Measure:** "Секунды", "Радианы", "Нормализованный вектор".

**Пример:**

* ❌ `name: string;` (Без TSDoc, так как "Имя" очевидно)
* ✅ `/** Уникальный идентификатор (UUID v4). */ uuid: string;`
* ✅ `/** Если true, пересчитывает матрицу каждый кадр. */ matrixAutoUpdate: boolean;`

### 2.3. Уровень Метода (Public)

**⛔ Правило "Нет Дублирования Типов":** Запрещено указывать типы в тегах (`@param {number}`).
**⛔ Правило "Smart Default":** Запрещен тег `@default`, если значение видно в сигнатуре.

**Обязательные теги (если есть что сказать):**

* **@param:**
  * **Никаких переводов!** (❌ `color - Цвет`).
  * Для **generic-названий** (`name`, `id`, `data`, `config`) **ОБЯЗАТЕЛЬНО** описывать ожидаемую структуру, формат или допустимый словарь.
  * Для **чисел**: Обязательно указывать допустимый диапазон (`[0..1]`) и поведение при выходе за него.
* **@returns:** Описывай **результат**, а не тип. Если возвращает `this` (chaining) — укажи это.
* **@throws:** Обязательно, если метод валидирует входные данные.

### 2.4. Уровень Метода (Private / Protected)

Добавлять TSDoc **ТОЛЬКО** если метод содержит сложный математический алгоритм или нетривиальную бизнес-логику. Хелперы оставлять без документации.

---

## 3. Правила форматирования

1. **Таблицы:** Для матриц состояний.
2. **Ссылки:** `{@link ClassName}`.
3. **Примеры (`@example`):** Обязательны для конструкторов и методов с неочевидными аргументами.

---

## 4. Процесс изменения кода (Workflow)

Соблюдайте правило **Атомарности** и **Чистоты Контекста**.

> **"Изменение кода, обновление локальной документации и обновление глобального контекста должно происходить в одной итерации."**

1. **Локально:** Изменил логику → Переписал TSDoc. Удалил старое.
2. **Глобально:** Архитектура сменилась → Переписал `@packageDocumentation`.

---

**Пример эталонной документации:**

```typescript
/**
 * Модуль управления боевыми единицами.
 * @packageDocumentation
 */

export class CombatUnit {
    /**
     * Текущее здоровье.
     * Влияет на скорость передвижения (при < 20% замедление).
     */
    public health: number = 100;

    public mesh: Mesh;

    /**
     * Вычисляет урон и применяет его к состоянию юнита.
     * 
     * @param amount - Величина урона.
     * **Ограничение:** Должно быть `> 0`. Отрицательные значения игнорируются.
     * 
     * @param type - Тип воздействия.
     * * `'physical'` — учитывает броню.
     * * `'pure'` — игнорирует броню.
     * 
     * @returns `true`, если юнит погиб от удара.
     * 
     * @example
     * ```ts
     * const isDead = unit.takeDamage(50, 'pure');
     * ```
     */
    public takeDamage(amount: number, type: 'physical' | 'pure' = 'physical'): boolean {
        // ... implementation
    }
}
```

# Функциональное программирование — правила для AI-агента

## 🎯 Основные принципы

### 1. Чистые функции (Pure Functions)

* Функция получает **только данные**, которые реально нужны для работы
* Функция **не принимает другие функции** как параметры
* Функция **не имеет сайд-эффектов** (не меняет внешнее состояние)
* Функция **возвращает новые данные**, не мутирует входные

✅ Правильно:

```typescript
function parseInput(input: InputType): OutputType[] {
  // вход → выход, без изменений снаружи
}
```

❌ Неправильно:

```typescript
class Parser {
  private state: Map = new Map()  // ❌ скрытое состояние
  parse(input: any, callback: (x) => void) {  // ❌ функция как параметр
    this.state.set(...)  // ❌ сайд-эффект
  }
}
```

### 2. Готовый формат данных

* Данные передаются **уже в нужном формате**, без трансформаций внутри функции
* Если нужно извлечь/преобразовать — делаем это **до вызова функции**

✅ Правильно:

```typescript
// В координаторе — подготовка
const processed = prepareData(rawData)
const mapped = transformItems(items)

// В чистой функции — только работа с готовым
function processItems(
  prepared: PreparedItem[],
  config: Config
): Result[] { ... }
```

❌ Неправильно:

```typescript
function processItems(
  rawItems: RawItem[]  // ❌ сырые данные, нужно преобразовывать внутри
): Result[] {
  // ❌ трансформации внутри чистой функции
  const prepared = rawItems.map(transform)
  // ...
}
```

### 3. Прозрачный конвейер данных

* Каждая функция — **этап конвейера**: принимает результат предыдущей, возвращает для следующей
* Все промежуточные структуры **явные**, не скрыты в `this`

```text
coordinator()
  ↓
extractData() → DataType[]
  ↓
transformItems() → TransformedItem[]
  ↓
processItems() → Result[]
  ↓
persist
```

### 4. Массивы и Map для однородных данных

* Работаем с **массивами** (`Item[]`) или **Map** (`Map<number, Item>`), не смешиваем
* Индексы — это позиции в массиве (`items[0]`), не дублируем в кортежах

✅ Правильно:

```typescript
// items — просто массив, индекс = позиция
items: Item[]

// Доступ: items[index] — O(1), прозрачно
const item = items[index]
```

❌ Неправильно:

```typescript
// Лишние индексы в кортежах, если индекс = позиция
items: [number, Item][]  // ❌ дублирование

// Лишнее преобразование
const items = data.items.map(([_, item]) => item)  // ❌ если можно сразу Item[]
```

### 5. Явное состояние модуля

* Состояние хранится **в модуле** (глобальные `let`), не в классе
* Функции работают с этим состоянием явно

✅ Правильно:

```typescript
// Глобальное состояние модуля
let cache: Map<string, any> | null = null
let config: Config | null = null

export async function init(cfg: Config) {
  config = cfg  // явное присваивание
  // ...
}
```

❌ Неправильно:

```typescript
class Manager {
  private cache: Map  // ❌ скрыто в this
  init() { this.cache = ... }  // ❌ неявное изменение
}
```

### 6. Минимум абстракций

* Не создаём классы-обёртки для одной функции
* Если логика простая — **функция в файле**, не класс

✅ Правильно:

```typescript
// validator.ts — одна функция
export function validate(input: Input): ValidationResult { ... }
```

❌ Неправильно:

```typescript
// Validator.ts — класс для одной функции
export class Validator {
  validate(input: Input): ValidationResult { ... }
}
```

## 📋 Чек-лист для кода

Перед созданием функции спроси:

* [ ] Принимает ли функция **только данные**, которые реально нужны?
* [ ] Возвращает ли функция **новые данные**, не мутируя вход?
* [ ] Есть ли **сайд-эффекты** (логирование, изменение внешних переменных)?
* [ ] Нужно ли **преобразовывать данные** внутри функции (значит, подготовка должна быть снаружи)?
* [ ] Можно ли заменить класс на **простую функцию**?
* [ ] Прозрачен ли **поток данных** (вход → выход, без скрытых шагов)?

## 🚫 Запрещено

* Передавать функции как параметры в чистые функции
* Хранить состояние в `this` вместо явных переменных
* Делать трансформации данных внутри чистых функций
* Создавать классы для одной-двух функций
* Использовать кортежи `[index, value]` если индекс = позиция в массиве

## ✅ Разрешено

* Глобальные `let` для состояния модуля
* Классы только для **неизбежного состояния** (внешние API, драйверы, работа с ресурсами)
* Массивы и Map для однородных данных
* Промежуточные структуры с явными именами
