# Workflow через GitHub Issues

Правила работы с задачами через GitHub Issues в проекте MetaFor.

## Создание задачи

1. **Заголовок** — краткое описание сути изменения (верхний регистр для глаголов: РЕАЛИЗОВАТЬ, ИСПРАВИТЬ, УДАЛИТЬ)
2. **Описание** — цель, контекст, необходимые действия, ограничения, ожидаемый результат
3. **Метки** — при необходимости (например, `bug`, `enhancement`, `refactor`)
4. **Project** — добавить в GitHub Project для трекинга

## Выполнение задачи

### 1. Обсуждение в issue

- Фиксируй ключевые решения и наблюдения в комментариях
- При обнаружении проблем/улучшений — добавляй комментарий с описанием
- Предложения по изменению контракта/архитектуры требуют обсуждения

### 2. Реализация

- Делай изменения в рабочей директории
- Пиши тесты для фиксации контракта (если применимо)
- Следуй соглашениям проекта:
  - `rules/types.md` — типизация
  - `rules/tsdoc.md` — документация
  - `rules/domains/` — архитектура доменов

### 3. Коммит

Формат сообщения коммита:

```
[тип/тип] область — описание

### Основные изменения:
- суть изменений строго из diff

### Улучшения кода:
- рефакторинг, конфиги, зависимости

### Исправления в тестах:
- только если изменены test/spec файлы
```

**Типы коммитов (приоритет):**

1. `feat` — новая функциональность
2. `fix` — исправление ошибки
3. `refactor` — рефакторинг без изменения поведения
4. `type` — изменения типов
5. `test` — добавление/изменение тестов
6. `docs` — документация

**Области (domain-aware):**

- `dark` — Dark domain (gravity, strong, weak, em)
- `boundary` — Boundary domain
- `bulk` — Bulk domain
- `metafor` — ядро (DSL, AST)
- `app` — приложения
- `tests` — интеграционные тесты
- `types` — общие типы
- `rules` — правила проекта

**Важно:**

- Используй `Refs #<number>` для привязки к issue (issue не закроется)
- Используй `Closes #<number>` только если задача завершена полностью
- Заголовок макс. 72 символа
- Порядок слов в описании должен совпадать с порядком типов в тегах

**Примеры:**

```
[refactor] dark — удалить избыточный tag из типа Wimp

### Основные изменения:
- Удалено поле tag из типа Wimp
- Обновлены JSDoc примеры (DarkMatter, Wimp, Fuzzy)

### Улучшения кода:
- Упрощён контракт частицы

### Исправления в тестах:
- Обновлены тесты wimp.test.ts (17 тестов)

Refs #26
```

```
[feat/test] tests — реализовать тесты частицы Macho

### Основные изменения:
- Добавлены тесты множественности Macho

### Исправления в тестах:
- Создан tests/macho.test.ts
- 12 тестов проходят

Refs #27
```

### 4. Верификация

- Запусти тесты: `bun test`
- Проверь сборку: `bun run build`
- Убедись, что изменения не ломают существующую функциональность

### 5. Пуш

```bash
git push origin <branch>
```

GitHub автоматически:

- Прикрепит коммит к issue (через `Refs` / `Closes`)
- Покажет коммит в timeline задачи

## Закрытие задачи

- Закрывай issue вручную после проверки всех изменений
- Если использовал `Closes #<number>` — issue закроется автоматически после пуша

## Специфика проекта MetaFor

### Доменная изоляция

- Production-код: прямые импорты между доменами запрещены
- Тесты: могут использовать относительные импорты для интеграции
- Протоколы: меж-доменное взаимодействие через force channels

### Контракты частиц

- Контракты исследуются и фиксируются через тесты
- Временная логика допускается только в тестах
- Не добавлять runtime-функциональность без необходимости

### Трёхдоменное чтение

Система читается как `Domain × Force × Entity`:

- **Dark** — скрытая связность, память, иерархия
- **Boundary** — уплощение, фиксация, канонализация
- **Bulk** — проявление, исполнение, процесс
