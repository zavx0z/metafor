# Живая память MetaFor для стартового доведения

Дата фиксации: 2026-06-11.

Этот файл хранит не стенограмму разговора, а устойчивое рабочее понимание, с которым нужно вести дальнейшую разработку MetaFor.
Он существует потому, что контекстное окно модели ограничено и может быть сжато.

## Главный вектор

MetaFor доводится не как очередной AI-инструмент, IDE-агент, workflow-движок или VR-приложение.
MetaFor доводится как цифровая среда, в которой человек, агент, голос, зрение, речь, приложения, процессы, память, патчи, снапшоты, 3D-пространство и логика находятся в одной живой системе.

Практическая цель текущего стартового прохода: привести MetaFor к состоянию, в котором дальнейшая разработка уже идет из этой среды, через ее контекст, процессы, интерпретатор, наблюдаемую историю и пространственную модель, а не как внешняя работа над набором разрозненных инструментов.

## Рабочая модель системы

Первичная модель не командная.
Система живет от значений полей:

```text
значения полей -> контекст -> состояние -> переход -> процесс -> новые значения полей
```

Команда является поверхностным случаем.
Более точная инженерная форма: создать условия в контексте, при которых нужный процесс может протекать.

Эта модель должна влиять на API, UI, runtime, тесты и документацию.
Если новая реализация начинает выглядеть как обычный командный бот, внешний orchestrator или набор ручных tool calls, нужно вернуться к полям, контексту, состояниям и процессам.

## Текущий порядок стартового доведения

Стартовое доведение разбито на два этапа.

Первый этап - довести `Dark` как самодостаточный слой скрытой связности: `Wimp`, `Fuzzy`, `Macho`, `Axion`, нити связности, bindings, историю/структурные изменения и протокольный выход.

Второй этап - `Boundary`: ловить частицы из `Dark` по протоколу и фиксировать их как граничный отпечаток. `Boundary` не должен придумывать частицы сам и не должен подменять `Dark`; он принимает и канонически фиксирует то, что приходит из скрытой связности.

## Store, commit и protocol patch

Store хранит полную каноническую форму мира. Легкий protocol patch с UUID не переносит мир; он сигналит доменам, что уже зафиксированная часть мира изменилась и ее нужно читать из Store.

В распределенной системе может быть несколько Store-реплик: серверные SQLite-базы, browser IndexedDB и другие runtime-узлы. Между ними нельзя разводить независимый `db-sync` и отдельный domain patch, потому что это создает гонку сигнала против данных.

Правильная модель: один causal commit envelope. Внутри него `writes` нужны тем Store-репликам, которым надо применить данные, а `signals` являются легкими доменными patches. На приемнике сначала атомарно применяются `writes` в локальный Store, и только после local commit сигналы доставляются `Dark` / `Boundary` / `Bulk`.

Следствие для агента и любого внешнего участника среды: изменение значения поля не должно требовать двух ручных действий - отдельно писать в БД и отдельно слать patch.
У участника должен быть один смысловой вход: изменить значение поля / изменить контекст.
Внутри этого входа среда сама должна сделать store transaction, сформировать commit envelope, применить `writes` и разослать `signals`.
Если API вынуждает агента синхронизировать БД и patch вручную, это не пользовательская обязанность, а признак незавершенного runtime-контракта.

Фиксация 2026-06-13: runtime protocol module перенесен из корня проекта в `store/protocol`.
Подписки и низкоуровневые каналы должны импортировать протокол из Store.
Отправка доменных сигналов после materialization встроена в ORM-методы Store: `actor.create`, `topology.create`, `wimp.states.add`, `wimp.processes.add`, `wimp.matter.*` и другие write-методы сами рождают protocol signal после SQL-записи.
Dark/Weak/Gravity не должны отдельно отправлять protocol patch или создавать локальный `BroadcastChannel` после ORM-записи.
Файл `store/server.ts` удален как неверная граница; SQLite-open/update адаптер живет в `store/sqlite.ts`.
Следующий шаг этого же направления - схлопнуть ORM-сигналы в полноценный transactional commit envelope.

## Интерпретатор

## Рабочее правило: редактирование через API интерпретатора

Когда работа идет внутри текущей среды интерпретатора, агент не должен чувствовать
себя обычным внешним coding-agent и править активный source напрямую через
локальный filesystem patch.

Для файлов, которые относятся к активному process/source/context интерпретатора,
рабочий путь правки: API интерпретатора, прежде всего
`POST /processes/:id/apply_patch` или `POST /processes/:id/source`.

Локальные filesystem-правки допустимы только для чтения/диагностики, для файлов
вне активного графа процесса, для durable memory/docs вне interpreter context или
когда пользователь явно разрешил прямую локальную правку.

Если есть сомнение, активен ли файл в интерпретаторе, сначала проверить это через
API интерпретатора (`/processes`, `/processes/:id/modules`, `/context`) и только
потом выбирать способ правки. Это правило зафиксировано после ошибки, когда
часть изменений была сделана как обычным агентом через локальный patch, хотя
нужно было идти через API среды. Никогда не возвращаться к этой ошибке.

Текущий интерпретатор - первый рабочий interpreter world.
Он нужен не только для удобной отладки.
Он показывает будущий способ жизни MetaFor: система не останавливается глобально, а локально открывает внимание к процессу, source, frame, scope, терминалу, патчу, breakpoint, snapshot и action.

В дальнейшем интерпретаторная способность должна жить внутри MetaFor-процессов.
Поэтому любые изменения интерпретатора нужно оценивать не как изменения IDE, а как изменения органа самонаблюдения и самодоработки среды.

## Агент внутри среды

Агент здесь не внешний исполнитель.
Агент является участником одной среды с человеком.

Функциональные соответствия:

- голосовой ввод - слух агента;
- речевой синтез - будущая речь агента;
- скриншоты, камеры, 3D-пространство и визуальные поверхности - зрение агента;
- `@meta/*` API, браузер, окно, ввод и процессы - органы действия;
- interpreter context, patches, snapshots, terminal, events - нервная система разработки;
- история, store и timeline - память;
- повторяемые процессы и навыки - функциональное подсознание.

Подсознание в этой системе означает не скрытую магию, а наблюдаемые, повторяемые действия, которые превращаются в устойчивые процессы и могут выполняться машинально через контекст.

## Самоулучшение

MetaFor должен позволять агенту улучшать свои процессы не через изменение весов модели, а через развитие функциональной среды:

- анализ прошлых патчей, снапшотов и событий;
- выделение повторяемых действий;
- превращение их в процессы, навыки и поля контекста;
- проверку будущих вариантов через replay/simulation;
- обновление правил и компонентов среды при появлении новых требований.

Это рекурсивный контур:

```text
мы строим MetaFor -> MetaFor дает агенту органы и процессы -> агент помогает строить MetaFor -> среда дает более сильные органы и процессы
```

## Что должно сохраняться после компрессии

После любой компрессии контекста будущий агент должен восстановить минимум:

1. MetaFor - цифровая среда для совместного развития человека и AGI, а не инструмент вокруг модели.
2. Основная логика - поля, контекст, состояния, переходы и процессы.
3. Интерпретатор - первый interpreter world и будущий орган самонаблюдения среды.
4. Человек и агент работают вместе в одном live-контексте.
5. Голос, зрение, речь, память и навыки должны становиться частями среды.
6. Новые фундаментальные понимания нужно фиксировать патчами в durable memory, а не оставлять только в чате.
7. В формулировках не снижать уже реализованное до "система пытается"; говорить "строится", "уже реализовано", "доводится", "связывается", "проходит стартовый/финальный проход", когда это соответствует состоянию репозитория.

## Правило доработки этой памяти

Если во время разработки становится понятнее, как на самом деле устроен MetaFor, агент обязан добавить маленькое точное обновление в этот файл или в более подходящий durable слой.

Хорошее обновление:

- меняет будущие инженерные решения;
- короткое;
- проверяемое по коду, документации, API или словам автора;
- не превращает файл в эмоциональную стенограмму;
- не дублирует уже существующую публичную документацию без необходимости.
