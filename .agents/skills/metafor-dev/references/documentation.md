# Правила документации MetaFor

Документация MetaFor образует одну связную систему, распределённую между
реальными владельцами. Она не является набором самостоятельных обзоров одного и
того же механизма.

## Иерархия владельцев

* `docs/README.md` является единственной картой действующих документов и общих
  правил их ведения.
* Корневой документ системы или домена кратко задаёт общий смысл, пользовательскую
  картину, общий жизненный цикл, границы и карту ответственности.
* Package README описывает только назначение, собственный закон, жизненный цикл,
  поддерживаемые случаи исполнения и наблюдаемый результат своего package.
* Общий для нескольких packages факт остаётся только у общего владельца. Package
  README ссылаются на него и не копируют таблицу, словарь или общий lifecycle.
* Непакетные законы находятся в принадлежащей системе директории `docs/`, если у
  них нет более точного доменного владельца.
* Руководство разработки владеет командами, локальным запуском, diagnostics и
  процедурами проверки, но не становится вторым архитектурным контрактом.
* Карточки, Git и artifacts хранят состояние реализации, историю решений и
  evidence. Постоянные документы не превращаются в журналы задач.

Корневой документ связывает package owners, а каждый package README контекстно
возвращает читателя к общему закону системы. Отдельный раздел-копия карты ссылок
не создаётся, если те же связи уже выражены картой ответственности.

## Содержание смысловых документов

Обычная документация отвечает понятным языком:

1. что существует и зачем;
1. какое событие начинает работу;
1. кто принимает решение;
1. что делает владелец;
1. какой результат наблюдаем;
1. где заканчивается его ответственность и начинается следующий владелец.

Принятый конечный закон описывается положительно, а не как опровержение старого
решения. Граница формулируется через владельца и допустимое действие. История
ошибок, прежние названия и прототипные отрицания остаются в task/Git evidence.

Owner docs не перечисляют внутренние файлы, module layout, generic-параметры,
DTO fields, cache names, URL query, transaction markers, build scripts, точные
сообщения, порты, версии toolchain, live timings, screenshots, test counts,
статусы разработки и команды проверки. Эти сведения переносятся к TSDoc,
development guide, tests или task evidence по их настоящей ответственности.

Принятый архитектурный закон может предшествовать реализации. Состояние
реализации при этом остаётся в project task и проверках. Внутрикодовая
документация не описывает ещё не существующие entrypoints, types или methods.

## Термины и имена packages

Один термин обозначает одну сущность и не подменяет package, платформенную
часть, environment, capability, роль, устройство или воплощение соседними
словами. Текст использует понятный русский язык; точные имена кода, платформ и
протоколов сохраняются там, где без них теряется смысл. Если терминов много,
один общий владелец даёт короткий словарь без повторов в package docs.

Первое полное scoped package name прямо в предложении объявляет короткий alias:
`@scope/name` (далее — `name`). Все следующие упоминания в том же документе
используют alias. Правило применяется ко всем scoped names. Namespace вроде
`@internal/*` описывается как множество packages; уже короткое unscoped name не
получает alias самому себе.

## Контекстные ссылки

Ссылка является частью предложения, которое сообщает проверяемый закон и
называет ответственность документа по ссылке. Предложение сохраняет смысл без
Markdown, а текст ссылки называет предмет закона: например, «устойчивый запуск
выпуска», а не «README», «документация» или «подробнее здесь».

Ссылку не выносят в отдельное навигационное предложение и не повторяют рядом,
если владелец уже контекстно объявлен. После перемещения документа сохраняют
нужные compatibility anchors либо согласованно обновляют все входящие links.

## Внутрикодовая TSDoc

Подробная техническая документация живёт только в TSDoc рядом с реально
существующим public code и читается из source/IDE. Отдельные HTML, site, output,
generator configs, scripts, dependencies и команды `docs:*` не создаются.

Значимый public entrypoint, interface, type, function или adapter документирует:

* владельца и границу ответственности;
* contract methods и type parameters, когда их смысл не очевиден;
* lifecycle, состояния и инварианты;
* side effects и внешние ресурсы;
* platform-specific behavior;
* ошибки, unsupported cases и fail-closed исходы;
* контекстную ссылку на пользовательский owner document;
* ссылки на tests, доказывающие важные сценарии.

Очевидная signature не пересказывается, internal helper не получает комментарий
ради количества, а TSDoc не выдаёт планируемый API за существующий.

## Общий механизм и platform adapters

Если browser, Bun или другая среда выполняют одну ответственность разными
технологиями, сначала определяется один public semantic interface. Общий
жизненный цикл описывается через него, а различия находятся в platform adapters.

Действительно разные ответственности не объединяются только потому, что
касаются соседних данных. Например, общий contract не должен насильно смешивать
политику browser Cache Storage, Bun filesystem publication, transport и cleanup,
если у них разные владельцы и законы.

## Проверка изменения

До редактирования сверить документы-владельцы, public types, code/tests,
package exports, связанные карточки и существенную Git-историю. После правки:

* убедиться, что один закон имеет одного владельца и не продублирован;
* проверить соответствие терминов и package aliases;
* проверить контекст всех изменённых links и anchors;
* убедиться, что технические сведения находятся у TSDoc/development/tests;
* перечитать итоговый текст как одну связную историю;
* выполнить `git diff --check` и релевантные проверки ссылок/contracts.

Документационный test или isolated audit подтверждает только проверенное
свойство и не заменяет owner review смысла.
