# MetaFor Dev

Вести разработку линейно: один минимальный причинный путь, автоматические тесты,
затем видимое проявление в Bulk. Не расширять область следующего шага, пока
текущий не доказан кодом, тестами и наблюдением.

## Начало работы

1. Сохранить чужие изменения: проверить `git status --short --branch` и не
   сбрасывать незнакомый diff.
2. Проверить целостность project skill и получить impact-план для затрагиваемых
   путей:

   ```bash
   bun .agents/skills/metafor-dev/scripts/metafor-dev.mjs validate
   bun .agents/skills/metafor-dev/scripts/metafor-dev.mjs impact --check --paths <paths...>
   ```

3. Проверить контур через единую CLI-точку, не читая внутренний helper:

   ```bash
   bun .agents/skills/metafor-dev/scripts/metafor-dev.mjs doctor
   ```

4. Если все сервисы остановлены и runtime нужен для задачи, запустить их:

   ```bash
   bun .agents/skills/metafor-dev/scripts/metafor-dev.mjs run world start
   ```

5. Если поднята только часть сервисов, не запускать второй контур. Сначала
   диагностировать владельцев портов и существующие процессы.
6. Для текущего этапа прочитать
   [`references/current-milestone.md`](references/current-milestone.md). Не
   загружать остальные references без соответствующей задачи.

## Выбор рабочего потока

### Запуск или диагностика

- Использовать `metafor-dev.mjs doctor` как первый machine-readable evidence.
- Использовать `metafor-dev.mjs run world logs` только для контура, запущенного
  этим skill.
- Использовать `metafor-dev.mjs run world stop` только для процесса, которым
  владеет state-файл skill. Никогда не останавливать найденный чужой контур.
- При неполном или ошибочном запуске прочитать
  [`references/runtime.md`](references/runtime.md).

### Визуальная приёмка

- Сначала доказать здоровье runtime через `metafor-dev.mjs doctor`.
- Затем прочитать
  [`references/visual-acceptance.md`](references/visual-acceptance.md) и открыть
  `http://localhost:4004/` в браузере Codex.
- Проверять не только загрузку страницы, но и причинно ожидаемое проявление.
- Логи использовать как вторичное evidence; пользователь должен видеть основной
  результат в Bulk.

### Изменение runtime

1. Прочитать только относящиеся к шагу project docs и canonical concept.
2. Сформулировать один проверяемый результат и запрещённые побочные пути.
3. Сначала добавить или уточнить автоматический тест.
4. Выполнить минимальное изменение без широкого рефакторинга доменов.
5. Запустить узкие тесты, затем typecheck и относящиеся к изменению suites.
6. Повторить `impact --check` по фактическому diff и выполнить указанные live
   scenarios.
7. Провести живую визуальную приёмку в Bulk.
8. Только после доказательства обновить текущий milestone skill.

### Делегирование субагенту

- Передавать один ограниченный результат, точные файлы или область поиска,
  критерий завершения и разрешённые проверки.
- Просить использовать `$metafor-dev`, чтобы субагент получил тот же запуск и
  приёмку без копирования длинных инструкций в prompt.
- Не поручать параллельным агентам менять один причинный контракт или одну
  каноническую формулировку.
- Принимать результат только после локальной проверки diff, тестов и Bulk.

## Границы

- Не копировать в skill онтологию: она принадлежит canonical concept и project
  documentation.
- Не превращать diagnostics logger в Particle protocol или историю Bulk.
- Не добавлять в Particle trace envelope, causal parent или renderer commands.
- Не считать пустую сцену ошибкой, если Meta ещё не загружена.
- Не запускать постоянный render loop ради приёмки.
- Не коммитить runtime state, логи или PID-файлы: они хранятся во временной
  директории пользователя.

## Развитие skill

После каждого устойчивого повторения сокращать ручной сценарий до команды
канонической CLI или узкой reference. Удалять устаревший путь вместо накопления
альтернатив. При изменении портов, health contract, команды запуска или входа
Bulk обновлять этот skill в отдельном reviewable diff и снова запускать
`metafor-dev.mjs validate`.
