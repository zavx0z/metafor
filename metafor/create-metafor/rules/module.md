# Правило: Структура файлов модуля

| Файл | Обязательность | Назначение |
| ---- | -------------- | ---------- |
| `{name}.ts` | **Обязательно** | Основная логика и публичный API модуля. |
| `{name}.spec.ts` | Опционально | Unit-тесты, покрывающие основные сценарии. |
| `{name}.t.ts` | Опционально | TypeScript типы, интерфейсы и перечисления (enum). |

---

## Правила именования типов

1. **Типы принадлежат модулю, который их использует.**
   - `load.ts` → типы в `load.t.ts`
   - `execute.ts` → типы в `execute.t.ts`

2. **Кросс-модульные зависимости типов.**
   - Если типы одного модуля зависят от типов другого — импортируй через `.t.ts` файл.

3. **Чистые функции.**
   - Модули с чистой логикой не должны импортировать типы из модулей с сайд-эффектами.
   - Импортируй только из `.t.ts` файлов.

4. **Разделение ответственности.**
   - `.ts` — только функции и логика.
   - `.t.ts` — только типы (никаких импортов функций, только другие типы).
   - `.spec.ts` — только тесты.

5. **Публичный API.**
   - `.t.ts` — все типы модуля (внутренние и публичные).
   - `index.ts` — ре-экспорт только публичных типов из `.t.ts`.

---

## Подход к вынесению типов в `.t.ts`

### 1. Вынесение параметров функций

**Правило:** Если сигнатура функции содержит анонимный объект с 3+ полями — вынеси в отдельный интерфейс.

**Преимущества:**

- **Повторное использование** — тип можно импортировать в других модулях
- **Документированность** — TSDoc на уровне типа, а не только в параметрах функции
- **Согласованность** — единый стандарт для всех модулей
- **Рефакторинг** — изменение в одном месте, а не во всех сигнатурах

### 2. Не дублируй типы из других модулей

**Правило:** Если тип уже определён в другом модуле — импортируй, не создавай дубликат.

**Преимущества:**

- **DRY** — нет дублирования структур
- **Автоматическая синхронизация** — изменения в исходном модуле не требуют изменений у тебя
- **Семантическая точность** — тип называется так, как задумано в исходном модуле

### 3. Минимальный публичный API в `index.ts`

**Правило:** Экспортируй только то, что нужно внешним потребителям.

**Что экспортировать:**

- Классы и устройства для публичного API
- Типы данных для других модулей (например, для `@boundary/fields`)
- Типы для внутреннего использования (сериализация, тесты)

**Что НЕ экспортировать:**

- Типы, которые можно импортировать напрямую из исходного модуля
- Внутренние функции с префиксом `_`

### 4. Чек-лист для вынесения типов

Перед созданием типа в `.t.ts` спроси:

- [ ] Тип используется в 2+ функциях модуля?
- [ ] Тип содержит 3+ поля?
- [ ] Тип может понадобиться другим модулям?
- [ ] Тип описывает параметры или результат функции?
- [ ] Тип не дублирует существующий тип из другого модуля?

Если **хотя бы один ответ "да"** — выноси в `.t.ts`.

## Примеры из кодовой базы

### `@boundary/matrix`

- `matrix.t.ts` — `MatrixInitParams`, `MatrixStateExport`
- `matrix.ts` — `_initMatrix(params: MatrixInitParams, ...)`
- `index.ts` — ре-экспорт типов для публичного API

### `@force/weak`

- `execute.t.ts` — `ExecuteParams`
- `execute.ts` — `executeProcess(params: ExecuteParams)`
- `load.t.ts` — `LoadActionParams`, `ActionFn`

### `@boundary/fields`

- `index.t.ts` — ре-экспорт типов из `@boundary/matrix`
- `prepare.ts` — `PreparedData`
- `superposition.t.ts` — `CompiledRules`
