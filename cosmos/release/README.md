# `@cosmos/release`

`@cosmos/release` (далее — release) подключает выпуск к HTTP, RPC и runtime Cosmos.
Подготовкой артефактов владеет [`@metafor/tech-build`](../../tech/build/README.md),
составом, публикацией и восстановлением — [`@metafor/tech-release`](../../tech/release/README.md). [Устойчивый запуск
выпуска](../startup/README.md#как-начинается-работа) делает подготовленного
кандидата действующим вместо предшественника.

Выпуск объединяет точные версии release, `@internal/*` (далее —
internal-пакеты) и `@metafor/*` (далее — metafor-пакеты). Internal-пакеты
объявляют свои части и общую версию по
[закону внутренних пакетов](../internal/README.md#внутренний-пакет-и-его-возможность).

## Что называется выпуском

Выпуск — согласованный набор точных версий packages со всеми платформенными
частями этих версий. Startup остаётся отдельной устойчивой частью установленной
среды, пока выпуск заменяется.

Состав выпуска однозначно задаёт:

1. входящие packages;
1. точную версию каждого package;
1. все платформенные части выбранных версий;
1. удовлетворённые зависимости между packages.

Каждый package сам объявляет поддерживаемые environments. Одна package version
охватывает все объявленные платформенные части. Release читает это объявление,
проверяет полный состав и готовит только допустимые parts; выбор места их
воплощения не меняет состав выпуска.

Совместимым является только полный состав, в котором присутствуют все
выбранные packages и их parts, а зависимости удовлетворяются выбранными
версиями.

<a id="публичный-граф-artifacts"></a>

## Публичный граф artifacts

Каждый package объявляет весь свой публичный граф через
`package.json#exports`. Корневые conditional exports задают platform parts, а
public subpaths — отдельно загружаемые code units, styles, WebAssembly и другие
принадлежащие package файлы. Общие chunks являются производным результатом
одной сборки этого графа, а не вторым описанием состава.

Некорневой export может ссылаться на точный публичный export прямой runtime
dependency. Сборка разрешает его до исходного файла и публикует результат под
объявленным ключом и версией собираемого package. Это общее правило для кода,
styles и остальных файлов; локальный файл-посредник не требуется. Зависимость
сохраняет авторство исходника и не становится отдельным участником release.

Обычные package dependencies связываются в готовые artifacts владельца.
Отдельным участником выпуска dependency остаётся только когда он сам объявлен
release package; прочие owners не получают Cosmos-specific metadata или
runtime adapters. Package-local compiler plugin может изменить только способ
получения outputs и не объявляет artifacts, environments или состав выпуска.

Одна package version охватывает весь опубликованный граф во всех объявленных
environments. Release считает новую версию подготовленной только после
проверки полного server-side графа immutable outputs и его dependency closure.
Root intent по-прежнему задаёт желаемый состав, а фактически полученные browser
artifacts — текущее состояние конкретной среды. Установка и удаление различий,
восстановление и owner caches сохраняют прежний единый release lifecycle; новый
граф не создаёт отдельный resource manifest, cache или state protocol.

## Ленивая загрузка и handover

Обновление серверного release заменяет его процесс целиком вместе с
принадлежащими ему доменными воплощениями. Фиксированный startup сохраняет
[устойчивую границу запуска](../README.md#текущий-контур-запуска).
Транспортная реализация, её допуск и native dependencies меняются в этом полном
переходе; обновление отдельных доменов внутри действующего процесса не выполняется.

Серверный release исполняет [причинный состав MetaFor](../../docs/ARCHITECTURE.md#рождение-вселенной)
из проверенного кода своего выпуска. Он предоставляет один сетевой вход Dark
и владеет зависимыми воплощениями Boundary, Energy и Matrix. Готовность
слушателя не заменяет готовность доменов; отказ обязательного участника
завершает весь принадлежащий release состав. Bulk в этот запуск не входит.

Состояние мира хранится отдельно от неизменяемого кода выпуска. При handover
release закрывает приём новых изменений, дожидается причинного подтверждения
принятой работы и освобождает доменные воплощения до передачи входа. Новый
release восстанавливает их из того же состояния. Отказ подтвердить этот срез
остаётся отказом перехода, а не разрешением прервать принятую работу.

Несколько public code units одного environment собираются вместе. Общий код
публикуется один раз, а branches, доступные только через динамический import,
загружаются из сети при первом использовании. Отсутствие ещё не запрошенного
lazy artifact в browser cache не является неполным выпуском; offline first use
такого artifact закономерно требует, чтобы он уже был получен ранее.

Перед переключением release проверяет eager closure нового runtime. Artifacts
действующего предшественника остаются доступны, пока он завершает уже принятую
работу и может обратиться к своим lazy branches. Только после handover release
удаляет больше не принадлежащие действующему графу entries и завершает ту же
восстанавливаемую транзакцию.

Изменение читаемой формы artifact identity сначала доставляется отдельным
полным выпуском reader-а при прежнем составе. Writer начинает публиковать новую
форму только после подтверждённой активации reader-а. Частичный candidate и
параллельный compatibility protocol не заменяют эту последовательность.

<a id="обновление-browser-release"></a>

## Как сменяется выпуск

Когда среде назначен новый состав:

1. release получает целевой состав;
1. получает и проверяет все его packages и платформенные части;
1. готовит полного кандидата рядом с действующим выпуском;
1. проверяет полноту и совместимость кандидата;
1. запрашивает handover у startup;
1. startup запускает кандидата, переводит на него новые события, дожидается
   операций предшественника и завершает прежнее исполнение;
1. новый release восстанавливает принадлежащие ему обязательные связи.

Прерванная подготовка продолжается из последнего пригодного состояния.
Частичный состав и смесь package versions не становятся действующим выпуском.

Наблюдаемый результат — environment управляет один полный совместимый release,
а предшественник завершает уже принятую работу до уничтожения.

Отказ подготовки рабочего входа завершает запуск с исходной ошибкой после
освобождения принадлежащих кандидату ресурсов. Ожидание штатной остановки
действующего мира сохраняет отдельный жизненный цикл.

## Один закон для всех environments

Для browser и Bun действует один закон выпуска. Различаются средства получения,
хранения и исполнения artifacts, а состав, package versions и проверяемая
identity остаются общими.

Участник может получить уже подготовленный выпуск от другого участника.
Получатель проверяет полный опубликованный состав и сохраняет его artifacts;
исходники и сборщик для этого перехода не требуются. Источник байтов не выбирает
за получателя допустимую версию: целевой выпуск назначается явно, а его identity
сохраняется при смене источника.

Серверная композиция `@cosmos/release/node` создаёт одного сетевого участника
и связывает его с явно переданным источником проверенного состава. Импорт
композиции ничего не запускает. Вызывающая Meta сохраняет решение о запуске,
допуске новых передач, ожидании принятых работ и закрытии участника.

Release владеет физической композицией RTC, signaling, повторного подключения,
допуска соседей и резервного WebSocket через локальный proxy. Реализация этих
транспортов меняется вместе с выпуском; устойчивый startup только проверяет и
запускает выбранные байты. Нейтральная библиотека `@metafor/tech-peer` (далее —
peer) предоставляет транспортные механизмы, а предметная Meta управляет
участником через States и Process.

Установленный кандидат и действующее исполнение различаются. Только startup
подтверждает смену действующего выпуска после готовности кандидата. Прерванное
получение возобновляется по тому же проверяемому составу; частичный результат
не используется для исполнения. Изменение source manifests при публикации
само по себе не переключает уже работающий server release.

В [общей системе Cosmos](../README.md#распределение-ответственности) release
владеет технической целостностью выпуска. Internal- и metafor-пакеты сохраняют
смысл предоставляемых возможностей и предметной работы.

## Знакомство участников

При выданном разрешении release подключает общий signaling к своему сетевому
входу. Библиотека peer владеет [допуском группы и обменом
предложениями связи](../../tech/peer/README.md); release предоставляет ему свой
listener и сохраняет управление HTTP и обновлением выпуска. Разрешение остаётся
у серверного исполнения и авторизованного участника, не входит в browser code
или адрес запроса.

Signaling знакомит участников и не получает права назначать выпуск. При
передаче серверного входа release закрывает принадлежащие этому исполнению
signaling-сессии. Получение установленного выпуска и его активация сохраняют
свои отдельные разрешения и причинный переход через startup.

В Quantum-исполнении Cosmos читает только явно выбранную приватную конфигурацию
и credential внутри Mass своего экземпляра, чтобы открыть пассивный broker.
Это не создаёт сетевого участника: его запуск, ожидание передач и остановка
принадлежат объявленной Meta. Конфигурация должна уже существовать; первое
заполнение её канонической directory Mass сохраняет отдельного владельца
подготовки и не выполняется скрыто при старте.
Credential-authenticated carrier доступен до Meta `started` и сохраняется до
завершения Meta `stopping`, включая принятые резервные передачи. Application
admission сохраняет отдельную границу и не открывается вместе с carrier.

## Наблюдение сетей участников

Сетевое наблюдение показывает собственные фактические связи доменов и отчёты
разрешённых соседних пиров. Оно является read-only telemetry, а не рабочим
транспортом Oracle/Force или каноническим графом мира. Identity соседа задаёт
авторизованная связь; один signaling join не доказывает наличие его внутренних
доменов. Источник и время получения сохраняются отдельно. Disconnect и истечение
срока наблюдения делают внутренние сведения неизвестными, а не восстанавливают
их по предположению.

Локальные сведения читаются через существующий loopback-вход release. Соседи
обмениваются только ограниченными собственными отчётами через общую peer-сеть;
отчёты не пересылают наблюдения третьих пиров. Локальный viewer использует
существующие service WebSocket и BroadcastChannel. Credential, приватная
конфигурация, filesystem paths и содержимое мира в эти сообщения не входят.

## Наблюдение browser release

Service release сообщает только собственный запуск, созданные им WebSocket и
результаты принадлежащих ему обращений к cache и HTTP. Наблюдатель получает
текущий снимок и ограниченную историю; пропущенные события не восстанавливаются
по предположению. Готовность runtime, открытие соединения, запрос его закрытия
и подтверждённое закрытие различаются. Размер текстового сообщения означает
число UTF-8 bytes, а ответ HTTP не доказывает чтение всего тела.

Каждое исполнение отвечает отдельно, поэтому перекрывающиеся исполнения
выпуска сохраняют собственные связи. Наблюдение не изменяет загрузку и управление
выпуском; его недоступность не останавливает прикладную работу. Этот срез не
охватывает устойчивый startup, раннюю navigation, серверные исполнения или RTC.

## Подключение технического выпуска

`server/services.ts` передаёт `tech` разрешение имён в каталоги, профиль сборки
и политику состава Cosmos. Собственных компилятора, очереди публикации,
вычисления версий или восстановления байтов в Cosmos нет. HTTP-запросы читают
готовые артефакты; отсутствие файла не запускает сборку.

Запуск сервера вызывает восстановление через API `tech`. Опубликованные
версии проверяются и при необходимости восстанавливаются из сохранённых
байтов без typecheck и компиляции текущих исходников. Новая подготовка допустима
для ещё не опубликованной версии. Доставка source maps остаётся отдельной
HTTP-операцией без помещения карты в browser cache.
