# `@cosmos/startup`

`@cosmos/startup` (далее — startup) — минимальная устойчивая часть Cosmos, с
которой начинается работа установленной среды. Она нужна, чтобы при первом
запуске, возвращении после остановки и обновлении получить пригодный выпуск и
передать ему управление.

В [общем жизненном цикле Cosmos](../README.md#текущий-контур-запуска) startup
сохраняет устойчивый вход, а `@cosmos/release` (далее — release) владеет
[подготовкой полного выпуска](../release/README.md#что-называется-выпуском).

## Зачем нужен startup

Основное поведение Cosmos и MetaFor может обновляться. Перед ним остаётся
небольшая часть, способная начать работу, когда выпуск ещё отсутствует, был
остановлен или должен быть заменён.

Startup получает назначенный для environment выпуск, проверяет кандидата и
переключает исполнение. Состав выпуска, получение его packages и подготовка
следующего кандидата принадлежат release.

Сам startup также имеет версию и заменяется платформой целиком. При обычной
смене выпуска он остаётся устойчивой опорой для действующего и нового
исполнения.

## Как начинается работа

Когда платформа запускает Cosmos или действующий release запрашивает handover:

1. startup получает проверенный выпуск и создаёт его новое исполнение;
1. запускает кандидата рядом с действующим исполнением;
1. после подтверждения готовности направляет кандидату новые события;
1. дожидается операций, уже принятых предшественником;
1. завершает прежнее исполнение.

Наблюдаемый результат — в environment действует одно готовое исполнение
выпуска. Кандидат получает работу только после успешного запуска, а
предшественник завершает уже принятую работу до уничтожения.

Если рабочий вход является исключительным ресурсом среды, кандидат сначала
подготавливается без этого входа. Затем предшественник закрывает приём новой
работы, завершает принятую и освобождает вход; кандидат занимает его, подтверждает
готовность и получает право принимать работу. На время передачи входа новая
работа может быть недоступна. До его освобождения неудачную подготовку можно
отменить, сохранив предшественника; после освобождения ошибка перехода остаётся
явной и не вызывает автоматического выбора прежней версии.

Для установленного серверного состава startup сохраняет единственную запись
действующего выпуска. Полученный и проверенный кандидат становится действующим
только через этот переход. При обычном запуске сохранённый выбор проверяется
повторно; source manifests не заменяют его. Startup не пересобирает отсутствующие
или повреждённые artifacts и не выполняет автоматический restart либо rollback.

При отмене серверного запуска startup завершает уже созданное исполнение и
подтверждает его остановку перед освобождением владения средой. Отказ действующего
исполнения завершает установленный запуск с ошибкой после освобождения
принадлежащих ему ресурсов.

## Browser и Bun

В browser startup начинает работу внутри уже созданного Window, запускает
Service Worker и передаёт управление browser-частям release. Первоначальные
глобальные обработчики Worker принадлежат startup: ошибки направляются в текущий
console, а ограниченным журналом и его чтением владеет release.

Ошибка первого запуска остаётся явным отказом этого исполнения startup.
Последующие fetch/message events получают тот же отказ и не повторяют
подготовку или запуск кандидата. Новый запуск требует явного нового исполнения
startup либо успешной явной активации подготовленного кандидата.

В Bun тонкая точка входа запускает startup, а startup создаёт отдельное
исполнение server-части release и наблюдает его жизненный цикл.

Обе реализации принадлежат одному startup contract: после минимального входа
всей дальнейшей работой владеет действующий release.
