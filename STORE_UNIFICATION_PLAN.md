# План Архитектуры Boundary И Рантайма

Дата фиксации: 2026-06-14.

Этот документ фиксирует текущий рабочий рубеж после переименования `Store` в
`Boundary` и выделения `Energy` как рантайм-домена.

## Главная Граница

Текущая архитектура читается так:

```text
DSL / MetaFor source
  -> материализация Dark
  -> персистентная форма Boundary
  -> Force/рантайм-данные
  -> рантайм состояния Energy
  -> рантайм проекции Bulk
  -> видовой клиент AppWeb
```

Ключевой инвариант:

- `Dark` имеет доступ к `Boundary`;
- `Boundary` владеет персистентной формой (`wimp`, `actor`, `topology`);
- `Energy` не читает `Boundary`/SQLite;
- `Bulk` не читает `Boundary`/SQLite;
- WebSocket/Force переносит рантайм-данные, а не синхронизирует базу.

## Почему Старый Подход Убран

Старый подход пытался сделать общий слой БД/мира для всех доменов.
Это создавало ложную простоту: любой рантайм-слой мог перечитать данные из
одной базы, но доменные границы размывались.

Текущий подход другой:

- персистентная истина фиксируется в `Boundary`;
- рантайм-истина живёт в `Energy` и `Bulk`;
- рантайм-получатель получает достаточно данных в сообщении;
- если `Energy` или `Bulk` получили только UUID и должны лезть в SQLite, это
  ошибка контракта.

## Boundary

`Boundary` — персистентная граница.

Он отвечает за:

- декларативные и материализованные строки WIMP;
- строки `actor`/`value`/`state`;
- строки `topology`;
- стабильную UUID-идентичность;
- путь записи через SQL/ORM;
- Force-сигнал после коммита.

`Boundary` не отвечает за:

- исполнение процессов;
- рендер-проекцию;
- браузерное зеркало;
- жизненный цикл рантайм-блокировок;
- скрытую загрузку данных для `Energy` или `Bulk`.

## Energy

`Energy` — рантайм времени, перехода и изменения состояния.

Он отвечает за:

- применение рантайм-значений и состояния;
- weak-step;
- рантайм-переход;
- координацию W/+Z/-Z на рантайм-уровне;
- публикацию рантайм-частиц Force после локального изменения.

`Energy` получает самодостаточные данные и не читает БД.

## Bulk

`Bulk` — рантайм проявления и рендер-проекции.

Он отвечает за:

- проявленную проекцию мира;
- shell-носители;
- орбиты полей;
- геометрию Z-up/mm;
- инкрементальные события рендера `upsert`/`remove`;
- исполнение action-модуля там, где это относится к проявленному процессу.

`Bulk` не импортирует персистентный actor API как источник рендера.

## AppWeb

`AppWeb` остаётся видовым клиентом.

Он должен получать:

- события рендера;
- строки мира;
- данные проекции, готовые для показа.

Он не должен:

- поднимать старые воркер-рантаймы;
- держать браузерный IndexedDB как рантайм-реплику;
- читать Boundary DB;
- восстанавливать старое зеркало синхронизации БД.

## Force

Force использует один транспортный канал и `part` внутри каждого `Particle`.

Лёгкий сигнал без данных допустим только там, где получатель имеет право
читать `Boundary`, то есть внутри пары `Dark`/`Boundary`.

Для `Energy` и `Bulk` данные должны быть самодостаточными:

```text
{ part, op, path, value: runtimeData }
```

Нельзя возвращаться к двойному действию:

```text
write DB
send Force manually
```

Смысловой вход должен быть один: изменить значение, состояние или контекст.
Внутри этого входа среда делает Boundary transaction и публикует нужный
рантайм-сообщение.

## Ближайший Рубеж

1. Проверить, что `Dark` стабильно пишет `zavx0z/git` в `Boundary`.
2. Сформировать рантайм-данные из строк Boundary без синхронизации БД.
3. Поднять `Energy` на этих рантайм-данных.
4. Поднять рантайм проекции `Bulk` без чтения Boundary.
5. Дать `AppWeb` готовые события рендера и строки мира.
6. Собрать сквозную проверку: `Dark -> Boundary -> Energy -> Bulk -> AppWeb`.

## Нельзя Делать

- Восстанавливать старый `store/db`.
- Делать `Energy` или `Bulk` SQLite-репликами.
- Возвращать браузерное зеркало IndexedDB как рантайм-срез.
- Делать строки рендера частью персистентного actor API.
- Заставлять рантайм-получателя читать Boundary по UUID.
- Держать старые audit-документы как рабочую архитектуру.
