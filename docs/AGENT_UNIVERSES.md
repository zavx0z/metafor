# Агентные Вселенные MetaFor

MetaFor является Мультивселенной. Она не сводится к агентной системе: разные
Вселенные могут описывать разные миры, развиваться независимо и использовать
общие законы ядра.

Этот документ фиксирует важный подход к тем Вселенным, в которых действуют
агенты. Он дополняет общую архитектуру MetaFor, а не заменяет её.

## Архитектурный смысл

Обычная агентная система передаёт модели промпты, skills и каталог
инструментов. Модель должна одновременно понять намерение, выбрать инструмент,
составить параметры и организовать техническую последовательность.

В агентной Вселенной MetaFor эта граница проходит иначе:

> Агент понимает, что должно измениться в предметном мире, но не обязан знать,
> каким инструментом и каким техническим способом это будет выполнено.

Agent описывается Meta-пакетом и материализуется как Atom. Его окружают другие
описанные через Meta Tool, Device и Service Atoms:

- Tool Atom предоставляет предметное действие;
- Device Atom представляет устройство и его наблюдаемые возможности;
- Service Atom представляет внешний или внутренний сервис;
- Agent Atom понимает цель и предлагает изменение доступных ему фактов.

Инструмент, устройство или сервис не остаётся неформальной функцией за
пределами мира. Он получает собственные Fields, Superposition, Process, Mass,
Energy и Matter-связи.

Agent Atom не стоит над Вселенной и не управляет её State напрямую. Все
участники находятся в общей причинной системе.

## Основной цикл

Агенту достаточно предметной проекции:

- назначения доступных Atom;
- текущего State;
- значимых Fields и их текущих значений;
- человекопонятных описаний States;
- релевантных переходов Superposition.

Дальнейший цикл имеет следующий смысл:

```text
цель
→ Agent предлагает допустимое изменение Fields
→ Matrix вычисляет State и Transition
→ State разрешает объявленный Process
→ Energy исполняет Process Tool, Device или Service Atom
→ Boundary проверяет proposal и фиксирует разрешённый результат
→ изменённый мир становится входом следующего причинного такта
```

Agent не выбирает Action, не вызывает Process напрямую и не устанавливает
State. State вычисляет Matrix. Process привязан к State и исполняется Energy.
Результат Process является предложением; канонический мир меняет Boundary
commit.

Детерминирована причинная оркестрация, но не внешний мир. Сеть, модель,
устройство или сервис могут завершить Process ошибкой. Поэтому Agent не должен
заранее объявлять фактический успех. Сначала выражается намерение, затем
Process получает результат, и только после этого он может стать каноническим
фактом.

## Fields и комбинаторность

Fields — минимальные значимые переменные предметного мира. Каждое независимое
Field увеличивает:

- объём текущего контекста;
- число возможных комбинаций;
- сложность Superposition;
- стоимость проверки;
- вероятность противоречий.

Новое Field оправдано, когда оно является самостоятельным каноническим фактом
или предметным намерением и действительно влияет на причинное поведение.

Field не следует добавлять только ради:

- удобства одного Process;
- технической фазы вызова;
- кэша или диагностики;
- значения, уже выраженного State;
- payload или истории, которым принадлежит Mass;
- живого handle, которому принадлежит Energy.

Небольшое число Fields создаёт множество формально проверяемых конфигураций:

\[
N = |F_1| \times |F_2| \times \ldots \times |F_k|
\]

Не каждую конфигурацию нужно описывать отдельной инструкцией. Достаточно
объявить смысл Fields, States, Conditions и допустимых переходов.

## Смысл States

State — смысловое положение Atom в причинном мире, а не произвольный статус и
не журнал строк алгоритма.

Полезный State позволяет понять:

1. Что сейчас происходит с сущностью?
2. Что уже произошло и гарантированно истинно?
3. Какие дальнейшие действия разрешены?

State оправдан, когда меняются доступные переходы, активный Process,
восстановление, Matter или наблюдаемое положение сущности. Не каждый `await`,
сетевой frame или внутренний этап алгоритма должен становиться State.

Поэтому формула проектирования звучит так:

> Минимум независимых Fields, достаточно смысловых States и максимум поведения
> из их комбинаций.

Формулировка «достаточно States» важнее идеи механически увеличить их
количество. Состояние должно раскрывать предметную причинность, а не
процедурную реализацию.

## Инструменты, устройства и сервисы вокруг Agent

Фраза «Agent не выбирает инструмент» не означает, что инструменты исчезают.
Они становятся частью Вселенной.

Agent взаимодействует с Tool, Device и Service Atoms через их предметные
Fields и связи, а не через произвольный imperative API. Техническая реализация
остаётся внутри Process соответствующего Atom.

Например, Agent может видеть:

```text
Tool Atom: общий чат
State: чат доступен
Field: сообщениеКОтправке
```

Ему не требуется знать:

```text
openWebSocket()
sendFrame()
waitAck()
reconnect()
```

Agent задаёт `сообщениеКОтправке`. Matrix вычисляет дальнейшее состояние, а
Process Chat Atom использует соединение из Energy.

Если выбор конкретного устройства или сервиса сам имеет предметный смысл, он
может быть выражен через объявленный topology Field и Matter. Это остаётся
изменением мира, а не прямым tool-вызовом.

## Mass, Energy и Matter

Mass содержит материал, который должен сохраняться: историю, payload, файлы,
логи, ответы и другие артефакты. Meta объявляет именованные JSON/binary key-files,
а Process работает с ними через `MassHandle`; путь, MIME и версия не являются
частью декларации. Mass не заменяет Fields и State и не образует отдельный
Artifact-домен.

Energy содержит живые runtime-сущности: WebSocket, stream, peer connection,
decoder, session и другие handles. Они не помещаются в Fields или Mass.

Matter связывает Agent с окружающими Tool, Device и Service Atoms. Прямые
bindings позволяют им разделять нужные Fields, Mass и Energy, сохраняя
владельцев и причинные границы.

Независимые Atoms могут исполнять Processes параллельно. Агенту не требуется
создавать искусственную техническую последовательность, если несколько
изменений уже разрешены одним каноническим тактом.

## Bulk и интерфейс

Интерфейс не должен становиться imperative controller, управляющим Вселенной
в обход её причинных законов.

Bulk проявляет Вселенную для конкретного наблюдателя. Он владеет своей
производной проекцией, локальным выбором, камерой и способом взаимодействия,
но не становится обязательным сетевым входом, маршрутизатором доменов или
владельцем канонических фактов. Человек может иметь отдельное воплощение Bulk
в каждой вкладке или окне. Внешний агент не объявляется клиентом Bulk
автоматически: его способ наблюдения и внесения намерения требует отдельного
семантического решения.

По мере развития Bulk интерфейс формируется как проявление текущего мира:

- Atom и их Matter-топологии;
- Fields и State;
- доступных действий и наблюдаемых результатов;
- положения Agent и окружающих его Tool, Device и Service Atoms.

Одна и та же Вселенная сможет получать разные формы наблюдения и
взаимодействия без переноса UI-логики в Agent или окружающие Atoms.

Это направление развития Bulk. Его нельзя выдавать за уже завершённый
универсальный интерфейс текущего runtime или за transport всей Вселенной.

## Преимущества перед tool-first подходом

| Свойство          | Tool- и skill-first система                  | Агентная Вселенная MetaFor                            |
| ----------------- | -------------------------------------------- | ----------------------------------------------------- |
| Рабочий контекст  | Инструкции, tools, параметры и исключения    | Fields, State и релевантная Superposition             |
| Решение Agent     | Выбор API и технической последовательности   | Выбор предметного изменения                           |
| Исполнение        | Модель оркестрирует вызовы                   | Matrix и Energy следуют декларации                    |
| Безопасность      | В основном инструкции и проверки tool-вызова | Conditions, State, write-set и Boundary commit        |
| Замена реализации | Меняет tool-схему и инструкции               | Process меняется за стабильным предметным контрактом  |
| Композиция        | Новые tools увеличивают контекст             | Новые Atoms входят в Matter и общую причинность       |
| Наблюдаемость     | Логи отдельных вызовов                       | Канонические Fields, State, Mass и execution identity |
| Интерфейс         | Отдельная управляющая оболочка               | Будущее проявление мира через Bulk                    |

Skills остаются полезным способом постепенно загружать процедурное знание для
разработки, исследования и ещё не описанных областей. После появления
Meta-пакета рабочему Agent не нужно повторно загружать процедуру исполнения:
она принадлежит соответствующему Process.

## Компактная карта возможного

Superposition даёт основу для компактной карты поведения Atom:

- какие States существуют;
- какие переходы между ними допустимы;
- какие Conditions открывают переход;
- какие Fields доступны для предметного изменения;
- какое положение Atom занимает сейчас.

В целевом агентном интерфейсе Agent держит в рабочем контексте цель, текущее
положение и релевантный фрагмент этой карты, а не полные инструкции всех
Process. Это позволяет вычислять предметный путь к цели без загрузки схем
инструментов на каждом шаге.

Сама декларация Superposition уже существует в MetaFor. Универсальная
проекция, которая автоматически выбирает релевантный фрагмент и передаёт его
любому Agent как planner-контекст, требует отдельной реализации и проверки.

## Конечная конфигурация и эволюция

Каждая конкретная Meta-конфигурация конечна:

- конечно число Fields;
- конечно число States;
- конечно число Transitions;
- конечно число Process и Matter-связей.

Мультивселенная при этом не ограничена первой конфигурацией. По результатам
эксплуатации могут появляться последовательные версии:

\[
M_1 \rightarrow M_2 \rightarrow M_3 \rightarrow \ldots
\]

Здесь различаются два контура:

- рабочий контур изменяет Fields и причинное положение Atoms;
- метаконтур изменяет саму декларацию Fields, States, Process и Matter.

Связи ограничивают эволюцию: изменение Meta-пакета не должно молча разрушать
Fields, события, bindings и гарантии, на которые опираются другие Atoms.
Совместимость определяется не только инициатором изменения, но и существующей
топологией зависимостей.

Автономное изменение структуры Agent-ом и формальная модель структурных прав
пока относятся к направлению развития. Их нельзя смешивать с уже действующим
контуром изменения Fields.

## Граница действующего и развиваемого

Текущая рабочая архитектура уже утверждает:

- Agent не устанавливает State; State вычисляет Matrix;
- Process привязан к State и исполняется Energy;
- результат Process проходит Boundary commit;
- Fields, Mass и Energy имеют разные роли;
- Tool, Device и Service могут быть описаны Meta-пакетами и материализованы как
  Atoms;
- Matter связывает Atoms и передаёт объявленные bindings;
- Bulk проявляет канонический мир.

Следующие положения являются направлением развития, пока для них не создан
отдельный полный runtime-контракт:

- универсальная компактная загрузка Superposition в контекст любого Agent;
- автоматическое планирование пути к цели по всей Вселенной;
- автономное изменение Agent-ом структуры Meta-пакетов;
- структурные права и автоматическая проверка совместимости такой эволюции;
- законченный универсальный интерфейс, формируемый Bulk.

Рабочий контур изменения Fields и метаконтур изменения самой декларации нельзя
смешивать.

## Проверка Meta-пакета для Agent

При проектировании Agent и окружающих его Atom нужно спросить:

1. Какое минимальное предметное изменение должен уметь предложить Agent?
2. Какие Tool, Device и Service Atoms образуют его окружение?
3. Какие Fields являются независимыми каноническими фактами?
4. Какие States действительно меняют смысл и доступные действия?
5. Скрыты ли API и transport за Process соответствующего Atom?
6. Не объявляется ли результат внешнего мира до фактического успеха?
7. Разделены ли сохраняемый материал Mass и живые handles Energy?
8. Описаны ли связи и параллельность через Matter?
9. Может ли реализация Process измениться без изменения предметного интерфейса?
10. Остаётся ли наблюдаемая форма мира ответственностью Bulk?

Главный критерий:

> Agent способен действовать через компактную модель мира, не получая
> техническую инструкцию для каждого инструмента, устройства и сервиса.
