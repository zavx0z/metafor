# Работа с Meta-пакетами

Meta описывает структурную единицу: Component, Container, Domain, Repo или
другого владельца поведения. Её canonical `src` совпадает с `package.json#name`
владеющего пакета и сохраняет scope. Ссылки композиции используют это имя.
Физический каталог и Git repository не назначают identity Meta.

Один repository может содержать несколько Meta-пакетов в объявленных workspaces.
Каждый такой пакет владеет своей декларацией и поведением; совпадающие имена
доступных пакетов отклоняются как неоднозначная identity.

## Исходники и установленный код

Явно выбранная корневая декларация принадлежит ближайшему package manifest.
Discovery подготовки и авторинга находит доступные пакеты, их объявленные
workspaces и зависимости без исполнения деклараций. Наличие кода само по себе
не включает Meta в живой мир и не разрешает исполнение её процессов.

Runtime получает явно выбранный набор кода из storage. Подготовка, доставка,
проверка и сохранение артефактов принадлежат [выпуску](../tech/release/README.md).
Предоставленный runtime resolver связывает тот же canonical `src` с entry и
каталогом action-модулей установленного артефакта. Он читает только выбранный
storage root или явный mapping и не ищет замену в соседних checkout при
отсутствии кода. Авторинг исходников требует отдельного source preparation root.

Установленная структурная Meta выбирается по публичному `./meta` независимо от
namespace пакета. Продуктовый `.` сам по себе не является декларацией Meta;
Meta-only `.` допустим только при явном выборе такого владельца. Относительные
action-модули разрешаются от каталога установленной версии пакета, а не от
каталога публичного alias декларации. Так перенос публичного входа сохраняет
identity владельца и базу его подготовленного кода.

## Исполнение и авторинг

Запуск установленного мира обходится без исходного checkout. Boundary хранит
канонические декларации, экземпляры и их состояние; Mass сохраняет принадлежащие
им материалы. Подготовленный выпуск предоставляет исполняемый код Processes и
установленные Meta-декларации, необходимые его загрузчикам и проекциям. Первое
наполнение мира использует выбранную декларацию, а восстановление сохраняет
канонический мир Boundary. Перенос данных Boundary сохраняет его описание и
состояние без исходного `meta.ts`; для исполнения сохраняется соответствующая поставка
артефактов. Согласованное восстановление Boundary, Mass и причинной истории
подчиняется [закону checkpoints](CHECKPOINTS.md).

### Принятый порядок рабочего авторинга

Рабочий авторинг деклараций разделяет
[изменение мира и явную публикацию](../create-metafor/rules/rpc.md#рабочая-версия-и-явная-публикация).
Полное введение этого порядка, включая composition и новые исполнители,
описывает [переход на Oracle Environment](ORACLE_ENVIRONMENT_PLAN.md).

Рабочая версия Meta изменяется в Boundary через разрешённые намерения Oracle и
обычный Force path. Поддерживаемые изменения на существующих исполнителях
становятся доступны работающему миру без перезапуска. Пошаговое изменение и
проверка мира предшествуют публикации исходников.

Явный commit выбирает проверенный срез рабочей версии и публикует его в
файловую систему владельца пакета. Публикация связывает точное имя пакета,
происхождение изменения, выбранную каноническую версию и область операции.
Выбранный срез заменяет файловую проекцию без дополнительной проверки свежести
файлов или согласования с владельцем. Права доступа задаются общим Oracle
Environment; публикация сохраняет назначенный scope и проверки операции.
Исходники остаются на машине владельца: удалённый агент обращается к ней через
разрешённый протокол, а не получает обязательный checkout.
Git фиксирует полученную файловую проекцию отдельной разрешённой операцией.

### Данные и исполняемый код

Исходники служат подготовке новой реализации и сохранению принятых версий.
Изменение исполняемого кода требует подготовки новых артефактов и их подключения
по [жизненному циклу выпуска](../cosmos/release/README.md). Установленный runtime
сохраняет явно выбранные артефакты исполнения; расположение исходников не
становится его fallback.

Явная активация подготовленных деклараций использует только проверенные
артефакты выбранного выпуска и ожидаемую причинную границу существующего мира.
Первый совместимый профиль сохраняет identity и порядок прежних Fields,
States, Processes, Mass и Matter; новые сущности добавляются после прежних.
До первого изменения проверяется весь набор. Обычный Force path сохраняет
экземпляры и их материалы, а завершение подтверждается применённой границей.
Частично принятый или неизвестный исход требует решения владельца и не
повторяется автоматически. Обычное восстановление такой активации не выполняет.

Обычная работа с данными не требует исходников. Изменение значения Field
существующего Atom выражает предметное намерение, а сообщения, история чата и
другие материалы записываются объявленными Processes в Mass. Такие действия
подчиняются собственным правам и причинным законам и не становятся авторингом
только из-за записи данных.
Материализация новых Atom по уже установленной декларации и её Matter также
относится к исполнению. Авторинг нужен для изменения самой формы или состава
декларации, а не для каждого рождения её экземпляра.

## Корневые рабочие окружения

Отдельные корневые Meta `workspace-capsule` и `intel-macos-chrome-studio`
выбираются как точные пакеты по [закону развёртывания окружений](ENVIRONMENTS.md#развёртывание).
Имя пакета задаёт форму нового корня и не переименовывает существующий Atom.

Выбор другого корня не заменяет сохранённый Boundary. Сохранённые профили и
материалы подключаются по явному источнику и согласованному протоколу импорта
Mass. Объявленная ссылка не подтверждает перенос, авторизацию или право
принять живого владельца. Закрытые снимки подчиняются
[согласованному восстановлению](CHECKPOINTS.md).

## Базовые агенты пакета

Создаваемый Meta-пакет содержит каталог `agents` с базовыми JSX-компонентами.
Завершающий callback `agents` связывает их с Atom своего уровня, инструментами
и представлениями. Каждый Agent получает отдельный сохраняемый Chat;
представлением по умолчанию является чат с инспектором.

Базовая файловая декларация задаёт начальное устройство. Расширение состава
и конфигурации следует [принятому порядку рабочего авторинга](#принятый-порядок-рабочего-авторинга).
Компоненты занимают именованные слоты, сохраняя владельцев
операций и identity агента. Представления агента и человека используют один
назначенный контекст Atom; чтение Mass, Graph и наблюдение Force сохраняют свои
права. Передача принятой версии другому пиру подчиняется разрешённым связям
и не требует копирования исходного checkout.

## Граница работы агента

Если задача относится к Meta-пакету, область работы по умолчанию ограничена:

- его `meta.ts` и непосредственно принадлежащими ему декларациями;
- action-модулями и типами, которые эти декларации непосредственно используют;
- точечными тестами и документацией этого Meta-пакета.

Это не даёт права менять продуктовый server, UI, Docker/lifecycle, соседний
submodule или ядро MetaFor. Такая работа начинается только по прямому запросу.
Внешний Concept не является зависимостью Meta-пакета и не используется как
скрытый источник требований.

Пример: задача про Browser Atom в пакете Capsule разрешает
менять его `meta.ts`, actions/types и Meta-тест. Она сама по себе не разрешает
менять Capsule UI, Chrome Studio или контейнерный API.

## Проверка

MetaFor и внешние репозитории сохраняют отдельные workspace и проверки:

1. изменения ядра проверяются из корня MetaFor;
2. Meta-пакет проверяется командами его владельца;
3. полный продуктовый contour запускается только когда задача действительно
   пересекает его границу.

Не следует считать тесты MetaFor доказательством работы внешнего Meta-пакета и
наоборот.
