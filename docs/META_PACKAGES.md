# Работа с Meta-пакетами

Meta описывает структурную единицу: Component, Container, Domain, Repo или
другого владельца поведения. Её canonical `src` совпадает с `package.json#name`
владеющего пакета и сохраняет scope. Ссылки композиции используют это имя.
Физический каталог и Git repository не назначают identity Meta.

Один repository может содержать несколько Meta-пакетов в объявленных workspaces.
Каждый такой пакет владеет своей декларацией и поведением; совпадающие имена
доступных пакетов отклоняются как неоднозначная identity.

## Исходники и установленный код

Явно выбранная корневая декларация принадлежит ближайшему package manifest.
Discovery подготовки и авторинга находит доступные пакеты, их объявленные
workspaces и зависимости без исполнения деклараций. Наличие кода само по себе
не включает Meta в живой мир и не разрешает исполнение её процессов.

Runtime получает явно выбранный набор кода из storage. Подготовка, доставка,
проверка и сохранение артефактов принадлежат [выпуску](../tech/release/README.md).
Предоставленный runtime resolver связывает тот же canonical `src` с entry и
каталогом action-модулей установленного артефакта. Он читает только выбранный
storage root или явный mapping и не ищет замену в соседних checkout при
отсутствии кода. Авторинг исходников требует отдельного source preparation root.

Установленная структурная Meta выбирается по публичному `./meta` независимо от
namespace пакета. Продуктовый `.` сам по себе не является декларацией Meta;
Meta-only `.` допустим только при явном выборе такого владельца. Относительные
action-модули разрешаются от каталога установленной версии пакета, а не от
каталога публичного alias декларации. Так перенос публичного входа сохраняет
identity владельца и базу его подготовленного кода.

## Граница работы агента

Если задача относится к Meta-пакету, область работы по умолчанию ограничена:

- его `meta.ts` и непосредственно принадлежащими ему декларациями;
- action-модулями и типами, которые эти декларации непосредственно используют;
- точечными тестами и документацией этого Meta-пакета.

Это не даёт права менять продуктовый server, UI, Docker/lifecycle, соседний
submodule или ядро MetaFor. Такая работа начинается только по прямому запросу.
Внешний Concept не является зависимостью Meta-пакета и не используется как
скрытый источник требований.

Пример: задача про Browser Atom в пакете Capsule разрешает
менять его `meta.ts`, actions/types и Meta-тест. Она сама по себе не разрешает
менять Capsule UI, Chrome Studio или контейнерный API.

## Проверка

MetaFor и внешние репозитории сохраняют отдельные workspace и проверки:

1. изменения ядра проверяются из корня MetaFor;
2. Meta-пакет проверяется командами его владельца;
3. полный продуктовый contour запускается только когда задача действительно
   пересекает его границу.

Не следует считать тесты MetaFor доказательством работы внешнего Meta-пакета и
наоборот.
