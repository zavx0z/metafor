# Interpreter World

Эта заметка - живая фиксация понимания, к которому мы приходим перед изменением
кода. Ее задача не описать уже готовый API, а удержать правильную модель
системы, чтобы дальнейшие изменения не свелись к привычным, но неверным
категориям вроде "IDE + debugger" или "AI управляет UI".

Когда формулировки станут точными, из этой заметки должны появиться
архитектурные изменения серверного состояния, API и UI-host слоя.

## Как Мы Работаем С Заметкой

Эта заметка редактируется по ходу обсуждения.

Порядок работы:

1. Формулируем один смысловой вопрос.
2. Уточняем ответ.
3. Сразу фиксируем уточнение в этой заметке.
4. Только после стабилизации модели переходим к изменениям кода.

Заметка не является финальной спецификацией. Это рабочая поверхность, на
которой мы постепенно отделяем истинные инварианты интерпретаторной среды от
случайных текущих реализаций.

## Текущая Формулировка

`@metafor/interpreter` - это не IDE и не debugger-wrapper.

Это интерпретаторная среда разработки, где мысли и намерения пользователя вместе
с AI-агентом интерпретируются в работающий код, который существует в реальном
времени. Разработка ведется через само исполнение: execution point, frames,
scopes, values, expressions, terminal output, breakpoints и изменение source на
ходу.

Главная сущность здесь - не UI, не агент, не workspace и не debugger.

Главная сущность - среда-интерпретатор: единая живая интерпретаторная среда,
внутри которой разработка идет через исполнение.

```text
Interpreter World
  live process
  source linked to execution
  frames / scopes / values
  breakpoints
  terminals / output
  participants
  spatial representation
  action history
```

В текущий момент сам интерпретатор и есть начальная форма такого `Interpreter
World`. Он еще недоделан относительно будущей модели, но его нужно читать не
как внешний инструмент, а как первую работающую среду мира, в которой ведется
разработка.

В дальнейшем главной средой станет сам MetaFor с `Bulk` как проявленной
пространственной средой. Интерпретатор при этом не исчезает и не становится
посторонним инструментом. Он остается одной из сред/миров внутри MetaFor,
потому что MetaFor мыслится как multiverse: разные world-среды могут
сосуществовать, взаимодействовать и быть вложены друг в друга.

Иерархия по текущему пониманию:

```text
MetaFor multiverse
  Bulk spatial environment
  actor worlds
  interpreter worlds
  modules / processes / actions
  participants
```

Поэтому `Interpreter World` - это не финальный верхний уровень всей системы, а
стартовая и необходимая среда для разработки MetaFor, которая в будущем будет
жить внутри большей MetaFor/Bulk среды.

Текущая реализация еще не завершает эту модель. Главный недоделанный участок:
из самой среды-интерпретатора пока нельзя полноценно выбирать, запускать и
менять запускаемые модули.

Сейчас интерпретатор уже может запускать модуль, останавливать процесс,
показывать source/runtime context, ставить breakpoints, делать step/eval и
читать состояние исполнения. Но изменение source запускаемого модуля пока не
является полноценным действием самой интерпретаторной среды.

Это будущая центральная возможность: запускать разные модули и менять модуль из
интерпретатора, в том же контексте исполнения, где видны execution point,
frames, scopes, values, terminal output и история действий участников.

## Непрерывность Системы

Система не должна мыслиться как то, что полностью останавливают ради
разработки.

Правильная модель: среда продолжает жить, а пользователь и агент в реальном
времени направляют ее изменение. Интерпретатор не просто показывает уже
написанный код, а становится механизмом перевода намерения в работающую
структуру исполнения.

Это означает:

- мы разрабатываем систему в процессе ее собственной работы;
- развитие кода происходит во время работы системы;
- остановка одного execution point или одного потока не равна остановке всей
  среды;
- несколько потоков/акторов могут продолжать исполняться, пока один поток
  изучается или изменяется;
- изменение source должно стремиться к применению внутри живого контекста:
  hot path, controlled restart конкретного модуля/потока или другой механизм
  без глобальной остановки среды;
- история действий пользователя, агента и голоса является частью этого
  непрерывного процесса.

`breakpoint` и `execution point` здесь не должны пониматься как глобальная
остановка мира. Это локальная точка внимания и вмешательства в живой системе.

## Время, История И Симуляция

Среда должна поддерживать не только live execution, но и работу со временем.

В MetaFor должна быть возможность:

- остановиться в определенной точке времени;
- рассмотреть состояние системы в этой точке;
- смоделировать дальнейшие процессы из выбранного состояния;
- пройти по возможному будущему;
- вернуться по истории назад;
- сравнить фактический путь с ожидаемым или смоделированным.

Это шире, чем обычный replay одного события. Событие, process, actor state,
field values, переходы состояний, output patches и действия участников должны
быть частью исторического контекста.

Основание для этого уже заложено: MetaFor построен на JSON Patch, и патчи
хранятся. Значит история системы может быть представлена как последовательность
сохраненных изменений.

Эти patch-истории должны позволять:

- восстановить состояние на выбранный момент;
- увидеть, какие изменения привели к текущему состоянию;
- откатиться по истории назад;
- повторно проиграть изменения;
- смоделировать альтернативное продолжение из выбранной точки;
- связать действие пользователя/агента с конкретными patch последствиями.

Timeline должна быть общей для среды, а не отдельной независимой историей
каждого actor/process. MetaFor - единое пространство в multiverse, поэтому
взаимодействия акторов, процессов, модулей, участников и пространственных
сущностей должны читаться в одной истории.

При этом данные должны оставаться минимальными:

- хранить нужно сами адресные изменения, а не дублирующие snapshots без
  необходимости;
- actor/process/module/field должны быть фильтрами и адресами внутри общей
  timeline;
- производные представления истории должны вычисляться из минимального
  сохраненного набора;
- отдельная локальная история допустима только как projection/view, а не как
  отдельный источник истины.

Доступ к истории и данным должен работать по уровням вложенности.

Это нужно читать не как простое дерево прав доступа, а как многоуровневое
вложенное векторное пространство. MetaFor - единое пространство, но внутри него
есть вложенные уровни/подпространства: multiverse, world, actor, process,
field/value и другие будущие вложенные сущности.

Агент, пользователь или другой участник может находиться на конкретном уровне
вложенности, то есть в конкретном подпространстве, и получать доступ к данным
этого уровня.

Например, если агент находится на уровне одного actor:

- он видит историю, значения, процессы и события этого actor;
- он может работать с вложенными сущностями этого actor;
- он видит соседние actors на том же уровне, если они входят в доступный
  контекст взаимодействия;
- он не видит parent actors выше своего уровня вложенности;
- он не обязан видеть всю глобальную timeline как плоский поток;
- глобальная история при этом остается единой, но представляется агенту через
  scope выбранного actor.

Также может быть агент системного уровня. Такой агент видит всю систему в
целом: global timeline, все worlds/actors/processes, связи между ними и
межуровневые последствия изменений.

Следовательно, видимость агента определяется не тем, что данные физически
разделены, а уровнем присутствия и ролью агента:

- actor-level agent видит свой actor, соседей и вложенные сущности, но не
  parent actors;
- system-level agent видит всю систему целиком;
- будущие уровни могут задавать другие scope-ы видимости и действия.

Соседи не означают "все actors того же уровня". Соседство должно вычисляться
по реальным связям.

Для этого в MetaFor и нужна реляционная база: она дает возможность адресно
искать связи, зависимости, shared values, topology relations, process/event
связи и другие отношения. Actor-level scope агента должен строиться запросом к
этим отношениям, а не грубым раскрытием всех сущностей на уровне.

То есть уровни вложенности не создают отдельные источники истины. Они задают
адресуемые scope/view-ы внутри общей минимальной истории, как вложенные
подпространства в одном общем пространстве.

Интерпретатор в такой модели является не только live-debug средой, но и средой
навигации по истории исполнения:

```text
past state -> current live state -> simulated future
```

Откат назад не должен пониматься как простое undo в редакторе. Это перемещение
по истории работающей actor-системы, где можно восстановить контекст, увидеть
причины текущего состояния и проверить другие варианты дальнейшего развития.

## Пути Изменения Живой Системы

На ближайший этап MetaFor разрабатывается как обычный код, но внутри среды
интерпретаторов. Основной рабочий scope - процессы и actions, которые можно
запускать, проверять и развивать независимо от всей системы MetaFor.

То есть сейчас основной рабочий путь - source-level изменение отдельных
модулей/process/action entrypoints, только не во внешней IDE, а в живом
интерпретаторном контексте.

Дальше, когда будут запущены MetaFor actors, добавится второй путь -
runtime/model-level изменение самой работающей actor-системы.

Этот будущий режим нельзя заранее сводить к привычным IDE или debugger
моделям. Когда MetaFor actors начнут работать как живая система, разработка
станет другой: пользователь и агент будут менять не только текст модулей, но и
активную структуру акторов, их состояния, связи, процессы и взаимодействия.
Такой режим не похож на существующие инструменты разработки и должен
проектироваться из природы MetaFor, а не копироваться из привычных сред.

## Граница С MetaFor

Интерпретатор не является самой MetaFor и не должен подменять ее смысл.

Рабочая цель MetaFor находится в доменах `Dark`, `Boundary`, `Bulk`, store,
actor/process runtime и протоколах самой MetaFor. Там должны реально
исполняться код и процессы выполнения.

Интерпретатор - это среда разработки и наблюдения, через которую пользователь и
агент могут работать над MetaFor. Он может запускать модули, показывать
execution point, source, frames/scopes, terminal output, breakpoints и давать
единый action layer для человека, агента и голоса. Но это не делает
интерпретатор владельцем MetaFor runtime.

Важно не смешивать два вопроса:

- MetaFor работает, когда ее код, процессы выполнения и протоколы реально
  проходят через `Dark` / `Boundary` / `Bulk` / store runtime.
- Интерпретатор работает как среда разработки, когда через него можно видеть,
  менять и повторно исполнять этот код.

На ближайшем этапе мы не тестируем готовый интерпретатор как отдельный продукт.
Интерпретатор сам будет развиваться в процессе работы над MetaFor.

Первый путь - source-level:

- меняется обычный TS/JS/source модуль;
- изменение проходит через source buffer, save/apply, controlled restart или
  будущий hot-apply механизм;
- runtime/source identity, source maps и breakpoints должны оставаться связаны
  с измененным кодом.

Второй путь - runtime/model-level:

- меняется не просто текст файла, а модель работающей MetaFor-системы;
- actor graph, значения, состояния, связи и процессы могут меняться как часть
  живого исполнения;
- source может быть следствием или фиксацией этого изменения, а не всегда
  первичной точкой входа.

Оба пути должны быть действиями среды-интерпретатора. Они не должны расходиться
на "пользователь редактирует файл" и "агент меняет runtime" как разные
workflow. Пользователь, агент и голос работают с одной живой системой, просто
через разные способы присутствия.

## Processes, Actions И Bulk

На ближайшем этапе в MetaFor нужно разрабатывать прежде всего процессы и
actions. Они должны прогоняться независимо от всей системы MetaFor, как обычный
код, но разработка должна начинаться не с отдельного файла, а с визуальной
сущности в `Bulk`.

Рабочий порядок:

1. В `Bulk` visual editor создается сущность, которая подразумевает process.
2. Эта сущность создается на лету в работающей системе, без остановки среды.
3. События, которые при переходе в состояние попадают в этот process, сразу
   начинают приходить в эту сущность.
4. Уже внутри этой сущности ведется разработка action/process через
   интерпретаторный мир.
5. Когда action готов, он остается подключенным к этой Bulk/process сущности,
   а не переносится туда задним числом.

Текущее понимание:

- Bulk visual editor задает сущность process/action до написания кода;
- эта сущность создается в работающей системе без глобальной остановки;
- события перехода в состояние сразу попадают в создаваемый process;
- если реализация process/action еще не готова, система не останавливается и не
  ставит мир на паузу; она начинает работать медленнее из-за незавершенного
  process, пока пользователь и агент не завершат его разработку;
- интерпретатор помогает разработать и проверить action/process внутри этой
  сущности;
- готовый action становится реализацией уже существующей Bulk/process сущности;
- дальше Boundary/Bulk runtime сможет исполнять этот action как часть
  многоакторного процесса.

Главное преимущество такого режима: пользователь и агент видят в реальном
времени данные, которые поступают в еще разрабатываемый process. Эти данные не
нужно придумывать искусственно и не нужно выносить в отдельный тестовый стенд.

Интерпретатор используется как среда прохождения всего process:

1. В process начинают приходить реальные события и значения.
2. Пользователь и агент видят входной поток, текущие значения, состояния и
   ошибки.
3. Через интерпретатор они шаг за шагом разрабатывают action.
4. Expression/eval/scopes/source changes используются на реальных данных.
5. Process доводится до готовности внутри той же живой системы.

То есть разработка process происходит не отдельно от runtime, а на реальном
потоке данных, который уже проходит через систему.

Этот же механизм нужен как live-отладка работающей системы.

Если система ведет себя некорректно, например process выдает не те данные,
пользователь и агент должны иметь возможность войти в этот process через
интерпретатор и увидеть:

- какие события вошли в process;
- какие значения были на входе;
- какой execution path прошел action;
- какие intermediate values появились внутри;
- какие output/patches/process result были выданы;
- где именно возникло расхождение с ожидаемым поведением.

То есть интерпретатор работает и как среда разработки process, и как среда
диагностики уже работающего process. Разница только в причине входа:

- process еще не реализован и разрабатывается на живых данных;
- process уже реализован, но работает неправильно и требует отладки/правки.

Текущий `Bulk` уже является проявлением/визуализацией: он строит WebGPU view
по actor/world rows, показывает shells/fields и связан с process execution через
Bulk x Weak.

Но визуализация сейчас недоработана. Целевая форма Bulk для разработки - не
просто viewport, а 3D node system:

- processes/actions должны быть представлены как подключаемые узлы;
- связи, зависимости, входы/выходы и состояния должны быть видимы в 3D;
- готовый action должен подключаться к системе визуально, а не только через
  текстовый config;
- взаимодействия акторов и потоков должны быть наблюдаемы как часть node graph;
- визуальная система должна оставаться проявлением работающей actor-системы,
  а не отдельным редактором, оторванным от runtime.

## Actor-First Создание

В будущей визуальной среде разработка должна уметь идти через создание actor.

Пользователь не обязан начинать с текстового файла или с готовой meta-схемы.
Рабочая модель:

1. Создать actor как живую сущность в среде.
2. Построить actor из существующей meta, если подходящая meta уже есть.
3. Или создать новую meta, если существующей meta недостаточно.
4. Затем на основе этой meta строить новые actors.

То есть визуальная среда должна поддерживать оба направления:

- `existing meta -> new actor`;
- `new actor intent -> new meta -> actors built from that meta`;
- `actor prototype -> meta/template -> new actor instances`.

Это важно, потому что actor - проявленная рабочая сущность, с которой
пользователь и агент могут взаимодействовать в живой среде. Meta при этом
остается структурной основой, но создание новой структуры может начинаться от
намерения создать actor в пространстве.

Созданный actor может стать прототипом. Когда его структура, fields,
processes/actions и связи стабилизируются, среда должна уметь зафиксировать его
как meta/template. После этого из этой meta можно создавать другие actor
instances.

## Участники

Пользователь, AI-агент, голосовой ввод и внешние инструменты должны быть разными
способами присутствия в одной среде.

Они не должны иметь разные смысловые API:

```text
user       \
agent       -> interpreter action layer -> interpreter state -> events -> clients
voice      /
tools     /
```

Если пользователь нажимает Step, агент делает Step или голосовая команда делает
Step, это одно и то же действие интерпретатора с разным `actor`.

Если пользователь открывает source, агент указывает source или голос просит
показать execution point, это тоже действие над той же средой, а не управление
чужим UI.

## Что Это Не Такое

Это не WebStorm-совместимый debugger frontend.

Это не Chrome DevTools wrapper.

Это не "AI кликает по интерфейсу".

Это не терминальный voice-control.

Это не desktop-only IDE.

Это не набор отдельных REST endpoints для workspace/debug/view/terminal как
самостоятельных подсистем.

Все эти вещи могут быть транспортом, клиентом, проекцией или внутренней деталью,
но не продуктовой моделью.

## Процесс Как Место Разработки

Код не просто редактируется в стороне и потом запускается.

Код исполняется в процессе, и разработка происходит вокруг живого процесса:

1. Запущен модульный процесс.
2. Среда знает source, runtime scripts и source maps.
3. Конкретный поток/контекст попадает в execution point.
4. Пользователь и агент видят frames, scopes и values.
5. Expression выполняется в выбранном frame.
6. Source меняется в контексте того, что видно в runtime.
7. Изменение применяется к среде: save, controlled restart, reload, hot path
   или другой будущий механизм без глобальной остановки среды.
8. История действий остается общей.

Поэтому `source.edit` здесь не обычная функция IDE. Это действие в живом
интерпретаторе, связанное с текущим runtime/source контекстом.

## Серверная Граница

Сервер должен владеть смысловым состоянием интерпретаторной среды.

Это не значит, что UI вторичен или не участвует в среде. UI - полноценный
способ присутствия пользователя в интерпретаторе. Но UI не должен быть
единственным владельцем того состояния, которое имеет смысл для совместной
разработки.

Серверное:

- процессы и lifecycle модулей;
- runtime state;
- source identity и связь source с runtime;
- breakpoints;
- frames/scopes/value inspection;
- terminal sessions и output;
- открытые source buffers, dirty/revision/save state;
- действия участников;
- история действий;
- shared navigation: active source, selected frame, revealed execution point;
- spatial meaning: какие interpreter devices существуют и к чему они привязаны.

Клиентское:

- физический render;
- конкретный viewport;
- DPR, canvas size, локальные координаты pointer events;
- pose устройства или камеры, если это только способ просмотра;
- временные детали ввода конкретного клиента.

Граница не должна проходить по слову "UI". В 3D/AR смысловое расположение,
выделение объекта, раскрытый frame или показанный source - часть совместной
разработки, а не декоративное состояние.

Более точная формулировка:

- UI владеет физическим способом просмотра и ввода;
- сервер владеет общим смыслом действия и состояния;
- если состояние важно агенту, другому клиенту, голосу, истории действий или
  будущему XR-host, оно должно быть частью интерпретаторной среды, а не
  скрытым локальным состоянием одного browser UI.

Например:

- локальный размер canvas - клиентское состояние;
- локальное движение мыши во время drag - клиентское состояние;
- выбранный frame, source range или runtime value - состояние среды;
- действие "пользователь смотрит/указывает сюда" - состояние среды;
- конкретная матрица камеры устройства может быть локальной, если она не
  является общим жестом/указанием в пространстве.

## Самодостаточный API Интерпретатора

Для работы с интерпретатором агент не должен использовать `@meta/macos`,
desktop automation, Chrome screenshots или другой внешний host API напрямую как
смысловой канал в обход интерпретатора.

Внешние API допустимы как capabilities/tools, но вызываться они должны через
API интерпретатора или как действие, зарегистрированное в интерпретаторной
среде. Тогда действие попадает в общий state, history, permissions/scope и
становится видимым пользователю, агенту, голосу и будущим hosts.

Прямая работа с внешним API допустима только как низкоуровневая диагностика
host-окна или инфраструктуры, когда сам интерпретаторный API еще не может дать
нужный физический сигнал. Это не финальный рабочий маршрут среды.

Рабочий канал агента, пользователя, голоса и будущих hosts - API самого
интерпретатора:

```text
GET  /health
GET  /modules
GET  /context
GET  /modules/:id/context
GET  /interpreters
POST /interpreters/action
GET  /events
GET  /console
```

Публичный REST слой не имеет отдельного agent namespace: весь API
интерпретатора предназначен для всех участников и host-клиентов. Endpoints
называются по смысловым ресурсам среды: `/displays`, `/interpreters`,
`/hud/terminal`, `/context`, `/modules/:id/context`.

Если нужно понять, где мы находимся, какой модуль активен, где execution point,
какой frame выбран, какие scopes/values доступны, какие терминальные данные
есть и какие действия допустимы, это должно читаться из server-owned
interpreter state.

Текущий контекст среды должен включать не только runtime pause point, но и
человеческую навигацию по source:

- какой display активен;
- какой module принадлежит display;
- какой source открыт;
- где находится cursor/caret;
- какой source range выделен;
- какой текст выделен;
- какой frame выбран;
- какой terminal input набран.

Этот контекст читается через API интерпретатора (`/context`,
`/modules/:id/context`, `/interpreters`), а UI-host только обновляет его
событиями среды.

Внешний browser/desktop host может показывать это состояние, но не должен быть
единственным местом, где оно существует.

Текущий важный gap: часть interpreter workspace API уже дает нужный рабочий
интерфейс, но некоторые значения `ui`/`display` еще зависят от подключенного
browser-host и его controller state. Это нужно считать временной
реализационной стадией, а не финальным контрактом.

Финальный инвариант:

- API интерпретатора самодостаточен для навигации, действий и диагностики;
- UI является клиентом API, а не владельцем interpreter state;
- агент работает через API интерпретатора, а не через прямые клики/скриншоты;
- `@meta` и другие desktop tools могут быть подключенными инструментами, но не
  используются напрямую в обход интерпретатора для управления средой.

## Пространственная Среда

Текущий browser UI - только один host.

Внутри уже используется WebGPU `Space`, `ViewPoint`, `HUD` и `UIDisplay`.
Каждый модульный `UIDisplay` должен читаться как отдельное физическое
интерпретаторное устройство, помещенное в общее пространство.

Будущие hosts:

- desktop canvas;
- Electron overlay;
- mobile;
- XR;
- AR;
- 3D spatial environment.

Все они должны проецировать одну и ту же интерпретаторную среду, а не владеть
собственной версией workflow.

## Модульность

Модуль остается основной единицей запуска и исполнения, но выбор и запуск
модулей должен происходить внутри самой среды-интерпретатора.

В конечном результате среда-интерпретатор должна позволять:

- видеть доступные модули/entrypoints;
- выбирать модуль для запуска;
- запускать новый модуль;
- останавливать и перезапускать модуль;
- менять запущенный модуль;
- держать несколько модульных interpreter devices в одном пространстве.

Внутри среды-интерпретатора модульный interpreter device является устойчивой
единицей разработки. Process/run внутри него временный: процесс можно
перезапустить, завершить или поднять снова, но устройство интерпретатора и его
контекст разработки продолжают существовать.

Несколько модулей - это несколько независимых interpreter devices в одном
пространстве. Не должно быть:

- global current module;
- default display;
- main display;
- общих breakpoints между дисплеями;
- общих source/frame/scope/terminal состояний между модулями;
- фокуса одного дисплея, который меняет состояние другого.

Общее пространство может видеть несколько устройств, но runtime/source контекст
каждого модуля остается module-scoped.

## Actor Model И Потоки Исполнения

MetaFor строится как актерная модель. Поэтому среда-интерпретатор не должна
мыслиться как отладка одного линейного процесса или одного единственного
call stack.

В конечном результате среда должна уметь запускать в интерпретации и отладке
несколько разных потоков исполнения одновременно. Это нужно не для независимых
запусков рядом, а для разработки многопоточной/многоакторной системы, которая
в процессе исполнения взаимодействует сама с собой.

Пока рабочее слово `поток` означает смысловой поток исполнения/акторную линию
внутри MetaFor, а не обязательно OS thread. Такой поток может быть связан с
модулем, процессом, actor/process entity, worker-ом или будущей доменной
проекцией. Точное определение нужно уточнить.

Инвариант:

- несколько потоков могут быть активны одновременно;
- каждый поток должен иметь собственный execution context;
- остановка одного потока не должна уничтожать контекст остальных;
- пользователь и агент должны видеть, какой поток остановлен, какой выполняется,
  какой ожидает события, а какой завершился;
- breakpoints, source, frames, scopes и terminal/output должны быть привязаны к
  правильному модулю и потоку;
- взаимодействия между потоками должны быть наблюдаемыми: сообщения, события,
  зависимости, ожидания, передачи значений, ошибки и переходы состояния не
  должны теряться в отдельных логах;
- интерпретатор должен позволять разрабатывать взаимодействие потоков как часть
  живого процесса, а не только рассматривать каждый поток как отдельный target;
- пространственная среда должна позволять разложить несколько потоков рядом и
  работать с ними как с наблюдаемыми частями одной интерпретаторной среды.

## Action Layer

Нужен не отдельный API участника и не отдельный UI API, а единый слой действий интерпретатора.

Рабочая форма:

```text
interpreter.action({
  actor,
  target,
  kind,
  params,
  baseRevision?
})
```

Примеры смысловых действий:

```text
process.start
process.stop
process.restart

source.open
source.edit
source.apply
source.save
source.reveal
source.openSelection

execution.pause
execution.resume
execution.step
execution.eval

breakpoint.set
breakpoint.remove

value.inspect
scope.expand
frame.select

terminal.write
terminal.clear

space.focus
space.arrange
participant.pointAt
```

Имена предварительные. Смысл важнее конкретного spelling.

## Текущая Реальность Кода

Сервер уже владеет существенной частью живого процесса:

- `InterpreterModuleManager` создает module-scoped interpreters;
- `TargetSupervisor` запускает Bun-процесс и собирает stdout/stderr;
- `ProtocolClient` подключается к runtime;
- `SnapshotStore` держит paused state, frames и scopes;
- `BreakpointStore` хранит и применяет breakpoints по модулю;
- HTTP/WS сервер рассылает module state, target events, console и protocol events.

Но часть общего live-контекста сейчас слишком сильно живет в browser-host:

- workspace routes (`/displays`, `/interpreters`, `/hud/terminal`) пока
  проксируют часть действий в подключенный UI-host;
- active source/frame/terminal context берется из UI controller;
- source pane в interpreter UI сейчас read-only;
- workspace files есть как list/read source path, но нет полноценной server-side
  document/buffer/edit/apply/save модели;
- action history участников пока не является первым классом среды.

Это не означает, что текущая реализация неправильная как этап. Это означает,
что следующий архитектурный шаг должен переносить смысловое состояние среды на
сервер, а browser-host оставлять проекцией.

## Ближайший Рубеж MetaFor Runtime

На текущем этапе глобальная задача не в том, чтобы сделать интерпретатор
готовым продуктом. Интерпретатор будет развиваться в процессе. Ближайшая
цель - довести саму MetaFor до рабочего runtime-контура, где реально
исполняется код, проходят процессы, работают протоколы и изменения фиксируются
в общей реляционной форме.

Минимальный первый контур:

```text
Dark materializes store
  -> Boundary observes store
  -> Boundary emits process/state event
  -> Bulk executes action/process
  -> Boundary applies result
  -> store records value/state change
  -> Bulk/App sees the changed world
```

Этот контур важнее полной готовности UI. UI, голос и агент должны работать с
тем же смысловым action/state layer, но сначала нужна серверная возможность
прогнать один живой процесс через домены MetaFor.

Текущий фактический разрыв:

- `Dark` уже пишет в новый `store.wimp / store.actor / store.topology`;
- `Boundary` все еще читает старый отсутствующий `store/db`-контракт;
- `Bulk process` умеет выполнять action-модуль, но target resolver тоже завязан
  на старый `DbBackend`;
- `Bulk render` использует старые render-row exports из `@store/actor`, хотя
  новый `@store/actor` должен оставаться canonical instance-state, а не render
  projection;
- `app/web` поднимает оболочку, но worker entrypoints еще не переведены на
  новый store path.

Следовательно, ближайшая разработка должна идти не от интерфейса и не от
agent-specific API, а от первого вертикального server/runtime smoke-сценария.

Рабочая формулировка для следующего кода:

```text
matter("zavx0z/git")
  -> creates canonical actors/values/states in store
  -> Boundary adapter builds runtime branes/fields/states from store
  -> Weak runtime performs one transition
  -> process/action target is resolved from store
  -> action result writes value/state back into shared store
```

Для этого нужно отдельно решить один архитектурный вопрос: является ли shared
`value.uuid` достаточной канонической основой для Boundary entanglement и
process input/output, или в ближайшем рубеже уже нужен минимальный provenance
слой для source-binding direction.

## Нельзя Делать Дальше

Нельзя строить новый слой как "AI automation API for UI".

Нельзя добавлять отдельную agent-specific ветку workflow.

Нельзя использовать `@meta` или desktop/browser automation напрямую в обход API
интерпретатора как основной способ понимать и двигать состояние среды.

Нельзя делать UI владельцем runtime/source state.

Нельзя считать пространственные действия второстепенной декорацией, если они
помогают совместно двигаться по коду.

Нельзя проектировать API только под desktop/browser.

## Вопросы Для Прояснения

- Что является минимальной атомарной единицей `Interpreter World`: модуль,
  процесс, target run или более широкая среда?
- Как связать source buffer revision с runtime script/source map identity?
- Какие source changes могут применяться без restart, а какие требуют restart?
- Что должно быть общим пространственным состоянием, а что локальной позой
  устройства?
- Как фиксировать действия пользователя, агента и голоса в одном журнале?
- Как показывать агентское намерение до изменения кода: proposal, preview,
  claim, apply?
- Какая часть `store` должна стать долговременной памятью интерпретаторной
  среды, а какая останется runtime state?
- Для ближайшего MetaFor runtime smoke считать `actor_value.value` единственным
  source of truth shared-state, или сразу фиксировать direction/provenance
  source-binding отдельной связью?

## Рабочее Правило

Пока эта заметка не станет достаточно точной, кодовую архитектуру не менять.

Сначала уточняем смысловую модель. Затем меняем серверный контракт. Затем
подключаем UI, агента, голос и hosts как клиентов этой среды.
