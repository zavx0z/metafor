# Архитектура строк для WebGPU: практический план (Фазы 2.1–2.2)

## Фаза 2.1 — сначала вычислительная простота

На старте системы приоритетом должна быть **простота вычислений в шейдере**, а не плотная упаковка памяти.

Рекомендуемая структура:

- `stringRegistry: array<vec3<u32>>` или плоский `array<u32>` в формате `[pointer, length, hash]`
- `stringHeap: array<u32>` с UTF-32 кодовыми точками

Плюсы такого формата:

- Прямой доступ к символу: `stringHeap[pointer + i]`
- Минимум ветвлений и циклов в шейдере
- Низкий риск thread divergence
- Предсказуемая производительность и простая отладка

На этом этапе перерасход VRAM из-за UTF-32 оправдан: упрощение кода и стабильность производительности важнее микро-экономии памяти.

## Фаза 2.2 — корректность сравнения через 2 шага

32-битный хэш ускоряет сравнение, но **не может гарантировать уникальность**. Коллизии неизбежны, поэтому сравнение строк должно быть двухступенчатым:

1. Быстрый путь: сравнение `hash`
2. Проверочный путь: при равенстве `hash` — посимвольное сравнение

Такой подход дает баланс:

- в большинстве случаев — почти максимальная скорость;
- во всех случаях — корректный результат без ложных совпадений.

## Unicode: минимальный набор обязательных тестов

Чтобы система реально была универсальной, тесты должны покрывать не только кириллицу:

1. **Эмодзи и supplementary planes** (`👍`, `😂`) — проверка кодовых точек `> U+FFFF`
2. **Канонически эквивалентные формы** (`café` vs `cafe\u0301`) — проверка NFC-нормализации
3. **Символы нулевой ширины** (`\u200B`) — невидимые символы должны влиять на сравнение
4. **CJK** (`你好`) — базовая проверка мультиязычности

## Практические правила для команды

- Делать простые и выровненные структуры данных для GPU.
- Не полагаться только на 32-битный хэш.
- Нормализовать строки на CPU до интернирования (NFC).
- Добавить Unicode-тесты как обязательный regression-набор.
- Оптимизации памяти переносить на более поздние фазы после замеров.
