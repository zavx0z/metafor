# 🌌 MetaFor: Архитектура FSM в TAKT-ритме

MetaFor построен на разделении **смысла** и **механики**:

- **MONAD** — семантика, намерения, координация
- **BOUNDARY** — детерминированные вычисления переходов
- **BULK** — проявление, исполнение процессов, эффекты среды

---

## 🔷 Базовый принцип

FSM в MetaFor работает пакетно, в ритме **TAKT**.

Ключевая модель цикла:

1. сначала синхронизируется топология и состояние,
2. затем выполняется runtime-шаг переходов,
3. результат интерпретируется через намерения,
4. действия исполняются и цикл повторяется.

---

## 🌀 TAKT-цикл (актуальная модель)

## TAKT 0 — `updateBoundary()` (пакетное добавление/удаление монад)

`updateBoundary()` синхронизирует топологию монад в Boundary:

- **пакетное добавление** новых монад в Boundary,
- **пакетное удаление** монад из Boundary,
- обновляет внутренние соответствия (`monadId <-> braneIndex`),
- фиксирует начальные состояния новых монад,
- **не вычисляет runtime-переходы**,
- **эмитит birth-сигналы** для новых монад.

Birth-сигнал:

- `oldState: undefined`
- `newState: <первое состояние суперпозиции>`

Это нужно, чтобы корректно оповещать систему о создании новой монады и запускать процесс первого состояния (если у него есть intention).

---

## TAKT 1 — `updateMonads()` (runtime transition step)

Runtime-переходы выполняются только здесь:

1. применяются обновления полей,
2. BOUNDARY выполняет шаг переходов,
3. при фактическом изменении состояния формируется runtime-event,
4. BOUNDARY выставляет `lock = 1`.

---

## TAKT 2 — Интерпретация в MONAD

MONAD разбирает изменения:

- для birth (`oldState === undefined`) — инициализационная оркестрация,
- для runtime (`oldState !== undefined`) — доменная логика перехода.

Проверяется `intention` нового состояния:

- если намерения нет — lock снимается автоматически,
- если намерение есть — lock удерживается до завершения процесса.

---

## TAKT 3 — Исполнение в BULK / Weak Force

Для состояний с intention:

- исполняется процесс (`action`),
- применяются эффекты,
- после завершения вызывается `releaseLock()`.

---

## 🔒 Lock: кто ставит и кто снимает

| Слой | Ставит lock | Снимает lock |
|---|---|---|
| **BOUNDARY** | Автоматически при реальном runtime-переходе | Никогда |
| **MONAD** | Никогда | Автоматически, если нет intention |
| **BULK / Weak** | Никогда | Явно через `releaseLock()` |

---

## 📣 Семантика `onStateChange`

`onStateChange` получает пакет событий, который может включать:

1. **Birth-event**  
   `oldState === undefined`
2. **Runtime-transition**  
   `oldState !== undefined`

Рекомендуемая практика — разделять их явно:

- birth — для инициализационных сценариев,
- runtime — для рабочей бизнес-логики переходов.

---

## 🧠 Ответственность слоёв

## MONAD

- хранит именованную семантику состояний и намерений,
- публикует birth/runtime события,
- координирует lock-ритм.

## BOUNDARY

- выполняет детерминированные переходы,
- работает с числовым представлением и GPU-механикой,
- управляет `dirty/lock` на уровне вычисления.

## BULK

- исполняет процессы,
- применяет эффекты и завершает цикл снятием lock.

---

## ✅ Практические правила

1. После `createMonad()` / `deleteMonad()` вызывайте `updateBoundary()`.
2. Используйте birth-события из `updateBoundary()` для сигнализации создания монады.
3. Не трактуйте birth как runtime-переход.
4. Runtime-логику обрабатывайте через `updateMonads()` + `onStateChange`.
5. Для состояний с intention завершайте цикл через `releaseLock()`.

---

## 🕯️ Итог

В MetaFor роли строго разделены:

- `updateBoundary()` — **commit структуры + birth signaling** (без runtime-вычисления),
- `updateMonads()` — **runtime-эволюция FSM**,
- `MONAD` — интерпретация и оркестрация,
- `BULK` — исполнение и завершение такта.

Это сохраняет предсказуемость TAKT-ритма и убирает неоднозначность между созданием монады и её runtime-поведение.
