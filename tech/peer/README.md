# Связи участников

`@metafor/tech-peer` (далее — peer) связывает участников надёжными прямыми
WebRTC DataChannels и при явном разрешении переносит сообщения через
авторизованный WebSocket relay. Владелец назначает каждому участнику непрозрачный адрес и
явно разрешает начальный вход в доверенную группу. Адрес участника сохраняется
при пересоздании связи; каждое соединение получает отдельное поколение.

Одновременные запросы получить ещё не открытую связь выбирают одно предложение.
Все ожидающие вызовы получают одну установленную связь; проигравшее предложение
не требует повторять прикладной запрос. Смена такого предложения не означает
разрыв уже открытого потока и не создаёт вторую рабочую RTC-связь пары.

Для первой связи участники обмениваются предложением и ответом через
авторизованный rendezvous. После появления связей существующий участник может
передать предложение и ответ двум своим соседям. Они создают собственную прямую
связь, которая продолжает передавать данные после отключения rendezvous и
посредника. Перед первым прикладным сообщением участник пробует прямое соединение
в ограниченный срок. Успешное соединение сразу переносит это сообщение по WebRTC;
истечение срока или отказ разрешает резервный путь. Позднее открытие WebRTC
переводит дальнейшую передачу на прямое соединение. Если владелец разрешил relay на
сервере и у обоих участников, signaling знакомит участников, а каждый
транспортный канал получает отдельную авторизованную WebSocket-связь к выбранному
участнику при недоступности прямого пути. Каждая пара
использует одну RTC-связь для всех своих прикладных каналов. Владелец может
назначить внутри неё несколько независимых ordered DataChannels. Каждый имеет
свои очередь, сборку сообщений и порядок доставки, поэтому ожидание отправки
в одном канале не задерживает очередь другого. Пропускная способность сети
остаётся общей. Без такого назначения используется один DataChannel.
При резервной передаче получатель подтверждает скопированные фрагменты, а
отправитель ограничивает их число в пути. Это подтверждение освобождает место
для следующих фрагментов; завершённая доставка сообщения подтверждается
отдельно. Несовместимый transport-протокол отклоняется при знакомстве.
Переключение пути сохраняет поколение логической связи, порядок сообщений внутри
каждого канала и единственную доставку каждого сообщения в пределах поколения. Подтверждение transport
означает приём сообщения peer, а исполнение приложения подтверждает его
собственный протокол.

Потеря WebSocket сохраняет открытые прямые связи. Relay-enabled участник
повторяет подключение к серверу; потеря обоих путей закрывает логическую связь
и не повторяет прикладные сообщения в новом поколении. Участники явно
устанавливают новую связь после восстановления доступности. Relay получает
адрес отправителя из авторизованной сессии; данные приложения доступны
владельцу relay, тогда как прямой путь защищён WebRTC transport.

Room token разрешает вход в доверенную группу. Участники доверяют посреднику,
которого явно выбирают для знакомства; этот допуск не удостоверяет устройство
криптографически и не выдаёт полномочий назначать выпуск, исполнять команды или
изменять чужое состояние. Прикладные протоколы и проверка их полномочий принадлежат
вызывающему владельцу. Peer передаёт строки и bytes и освобождает собственные
соединения при закрытии.

Общий lifecycle одинаков для browser и Bun; adapter предоставляет RTC, а
владелец назначает ICE servers согласно своей сети. Доступность прямого пути
зависит от сети и её NAT. STUN обнаруживает доступный адрес, а TURN при явном
назначении владельцем может переносить зашифрованный WebRTC transport.

В составе MetaFor peer остаётся независимой технологической библиотекой;
[внешний уровень исполнения](../../cosmos/README.md) владеет её прикладной
композицией с runtime, выпуском и инфраструктурой.
