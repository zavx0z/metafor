# Git Meta: Эволюция дизайна

Этот документ описывает различные подходы к реализации `git/meta.ts`, которые были рассмотрены в процессе разработки. Каждый вариант имеет свои преимущества и недостатки с точки зрения производительности GPU, читаемости и поддерживаемости.

---

## Вариант 1: startsWithIn в GPU (отклонён)

**Идея:** Использовать оператор `startsWithIn` для проверки префиксов команд прямо в GPU.

```typescript
.states({
  ожидание: {
    "инициализация репозитория": { cmd: { startsWithIn: ["clone", "init"] } },
    "работа с файлами": { cmd: { startsWithIn: ["add", "mv", "restore"] } },
  }
})
```

**Анализ:**

| Критерий | Оценка |
| :--- | :--- |
| **GPU производительность** | ❌ O(n×m) — проверка каждого префикса |
| **Читаемость** | ✅ Понятная декларация |
| **Поддерживаемость** | ✅ Легко добавлять команды |
| **Код вне MetaFor** | ✅ Нет |

**Почему отклонён:**

- Сложная реализация в WGSL-шейдере
- Потенциальное влияние на производительность при длинных списках
- Избыточная сложность для простой задачи

---

## Вариант 2: Парсинг в process, enum групп (отклонён)

**Идея:** Парсить команду в process и устанавливать enum группы.

```typescript
.context((t) => ({
  group: t.enum("start", "work", "examine", ...).optional()
}))

.states({
  ожидание: {
    "инициализация": { group: { eq: "start" } },
    "работа": { group: { eq: "work" } },
  }
})
```

**Анализ:**

| Критерий | Оценка |
| :--- | :--- |
| **GPU производительность** | ✅ O(1) — простая проверка eq |
| **Читаемость** | ⚠️ Дублирование имён состояний и групп |
| **Поддерживаемость** | ⚠️ Нужно обновлять states при добавлении группы |
| **Код вне MetaFor** | ✅ Нет |

**Почему отклонён:**

- 10+ состояний для групп — избыточно
- Дублирование: состояния и группы называются одинаково

---

## Вариант 3: Описательные состояния (отклонён)

**Идея:** Использовать описательные имена состояний на русском.

```typescript
.states({
  ожидание: {
    "инициализация репозитория": { group: { eq: "start" } },
    "работа с файлами": { group: { eq: "work" } },
    "просмотр изменений": { group: { eq: "examine" } },
    "управление историей": { group: { eq: "history" } },
    ...
  }
})
```

**Анализ:**

| Критерий | Оценка |
| :--- | :--- |
| **GPU производительность** | ✅ O(1) — простая проверка eq |
| **Читаемость** | ✅ Описательные имена на русском |
| **Поддерживаемость** | ⚠️ Много состояний (10+) |
| **Код вне MetaFor** | ✅ Нет |

**Почему отклонён:**

- Состояния используются только для transitions, а не для данных
- В будущем context будет сопоставляться с render для доступа к дочерним данным
- Состояния не должны дублировать значения context — они отвечают за переходы, а не за данные

---

## Вариант 4: Минимальные состояния + enum в context (✅ ТЕКУЩИЙ)

**Идея:** Только 2 состояния (`idle`/`active`), проверка enum в view.

```typescript
.context((t) => ({
  group: t.enum("start", "work", ...).optional()
}))

.states({
  idle: { active: {} },
  active: { idle: { group: null } },
})

.view({
  render: ({ context, html }) => html`
    ${context.group === "start" && html`<meta-for src="zavx0z/start"></meta-for>`}
    ${context.group === "work" && html`<meta-for src="zavx0z/work"></meta-for>`}
  `
})
```

**Анализ:**

| Критерий | Оценка |
| :--- | :--- |
| **GPU производительность** | ✅ O(1) — простая проверка в view |
| **Читаемость** | ✅ Минимум состояний, декларативный view |
| **Поддерживаемость** | ✅ Легко добавлять группы |
| **Код вне MetaFor** | ✅ Нет |

**Почему выбран:**

- Минимальный граф состояний (2 состояния)
- Декларативный view реагирует на изменения context
- Простая логика переходов
- Все данные внутри MetaFor (patterns в core)

## Ключевые решения

### 1. Всё внутри MetaFor

**Правило:** Никаких внешних функций или констант.

```typescript
// ❌ Нельзя
const PATTERNS = { start: /^(clone|init)$/ }
function getGroup(cmd) { ... }

// ✅ Можно
.core({
  patterns: {
    start: /^(clone|init)$/,
    work: /^(add|mv|restore)$/,
  }
})
.processes((process) => ({
  idle: process()
    .action(({ core }) => {
      // Используем core.patterns
    })
}))
```

### 2. Типизация через context

**Правило:** Использовать `NonNullable<typeof context.field>` вместо хардкода.

```typescript
// ❌ Нельзя
return { group: group as "start" | "work" | "examine" }

// ✅ Можно
return { group: group as NonNullable<typeof context.group> }
```

**Преимущества:**

- Типы автоматически синхронизируются с context schema
- Нет дублирования строковых литералов
- Рефакторинг context автоматически обновляет process

### 3. Regex паттерны в core

**Идея:** Хранить паттерны групп в core для эффективной проверки.

```typescript
.core({
  patterns: {
    start: /^(clone|init)$/,
    work: /^(add|mv|restore|rm|clean|sparse-checkout)$/,
    examine: /^(show|status|diff|log|range-diff|shortlog|describe)$/,
    ...
  }
})

.processes((process) => ({
  idle: process()
    .action(({ core }) => {
      for (const [key, regex] of Object.entries(core.patterns)) {
        if (regex.test(core.command)) return { group: key }
      }
    })
}))
```

**Преимущества:**

- O(n) проверка где n = количество групп (10)
- Паттерны объявлены декларативно
- Легко добавлять новые группы

### 4. Валидация данных на каждом этапе

**Правило:** Проверять каждое значение перед использованием.

```typescript
.action(({ core, context }) => {
  // 1. Проверка входных данных
  if (!context.command) {
    throw new Error("Команда не указана")
  }
  
  // 2. Парсинг команды
  const parts = context.command.split(" ")
  const command = parts[0]
  
  // 3. Проверка что команда извлечена
  if (!command) {
    throw new Error("Не удалось извлечь команду")
  }
  
  // 4. Извлечение аргументов
  const args = parts.length > 1 ? parts.slice(1).join(" ") : null
  
  // 5. Поиск группы по паттернам
  let group: string | null = null
  for (const [key, regex] of Object.entries(core.patterns)) {
    if (regex.test(command)) {
      group = key
      break
    }
  }
  
  // 6. Проверка что группа найдена
  if (!group) {
    throw new Error(`Неизвестная команда: ${context.command}`)
  }
  
  return { group, command, args }
})
```

**Почему это важно:**

- ❌ **Неправильно:** `const command = parts[0] || ""` — скрывает ошибки, `regex.test("")` может вернуть неожиданное значение
- ✅ **Правильно:** Явная проверка `if (!command) throw new Error(...)` — сразу видно проблему

**Преимущества:**

- Раннее обнаружение ошибок
- Понятные сообщения об ошибках
- Типобезопасность на каждом этапе
- Легче отлажить

### 5. Label для полей context

**Правило:** Label должен объяснять **критерий** или **формат**, а не дублировать имя поля.

```typescript
.context((t) => ({
  // ❌ Избыточно: "Группа команды" — "Группа" уже ясно из enum
  group: t.enum("start", "work", ...).optional({ label: "Группа команды" }),

  // ✅ Правильно: "Тип операции" — объясняет критерий группировки
  group: t.enum("start", "work", ...).optional({ label: "Тип операции" }),

  // ❌ Избыточно: "Текст ошибки" — тип string уже ясен
  error: t.string.optional({ label: "Текст ошибки" }),

  // ✅ Правильно: просто "Ошибка"
  error: t.string.optional({ label: "Ошибка" }),

  // ❌ Избыточно: "Имя команды без аргументов" — слишком подробно
  command: t.string.optional({ label: "Имя команды без аргументов" }),

  // ✅ Правильно: просто "Команда"
  command: t.string.optional({ label: "Команда" }),

  // ❌ Избыточно: "Аргументы команды через пробел" — слишком подробно
  args: t.string.optional({ label: "Аргументы команды через пробел" }),

  // ✅ Правильно: просто "Аргументы"
  args: t.string.optional({ label: "Аргументы" }),
}))
```

**Принципы:**

1. **Краткость** — 1-3 слова
2. **Критерий для enum** — объясняет, по какому принципу группируются значения
3. **Без дублирования** — не повторяй очевидное из типа или имени поля
4. **Формат для сложных типов** — если важно (например, "CSV" или "JSON")

**Примеры для enum:**

| Поле | ❌ Плохо | ✅ Хорошо |
| :--- | :--- | :--- |
| `group` | "Группа" | "Тип операции" |
| `status` | "Статус" | "Стадия жизненного цикла" |
| `role` | "Роль" | "Уровень доступа" |
| `priority` | "Приоритет" | "Критичность задачи" |

## Итоговая архитектура

```text
┌─────────────────────────────────────────────────────────┐
│  Context                                                │
│  group: enum("start", "work", "examine", ...)          │
└─────────────────────────────────────────────────────────┘
                          ↓
┌─────────────────────────────────────────────────────────┐
│  States (2 состояния)                                   │
│  idle ↔ active                                          │
└─────────────────────────────────────────────────────────┘
                          ↓
┌─────────────────────────────────────────────────────────┐
│  Core                                                   │
│  command: string                                        │
│  args: string[]                                         │
│  patterns: { start: /^.../, work: /^.../, ... }        │
└─────────────────────────────────────────────────────────┘
                          ↓
┌─────────────────────────────────────────────────────────┐
│  Process (idle → active)                                │
│  1. core.command + core.patterns → group               │
│  2. update({ group })                                   │
└─────────────────────────────────────────────────────────┘
                          ↓
┌─────────────────────────────────────────────────────────┐
│  View (декларативный)                                   │
│  context.group === "start" → <meta-for src="...">      │
│  context.group === "work" → <meta-for src="...">       │
│  ...                                                    │
└─────────────────────────────────────────────────────────┘
```

## Рекомендации для ИИ

При создании новых `meta.ts` файлов следуйте этим принципам:

1. **Минимум состояний** — только если они действительно нужны для логики
2. **Проверка в view** — если можно проверить значение в render, не создавайте состояние
3. **Всё внутри MetaFor** — никаких внешних функций/констант
4. **Типизация через context** — `NonNullable<typeof context.field>`
5. **Паттерны в core** — для сложной логики проверки
