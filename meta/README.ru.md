# @metafor/meta

[← Корень](../README.ru.md) | **Русский** | [English](README.md)

## Назначение

- Декларативная фабрика `MetaFor()` описывает актор: контекст → состояния → core → процессы → реакции → представление.
- Результат — чистая схема (`Meta`), которую могут интерпретировать `@metafor/atom`, no-code инструменты и агенты.
- README фиксирует принципы, а точные сигнатуры находятся в Typedoc (`meta/docs/typedoc/index.html`).

## Цепочка `MetaFor()`

```ts
const component = MetaFor("user-profile", { desc: "Карточка пользователя" })
  .context(/* 1 */)
  .states(/* 2 */)
  .core(/* 3 */)
  .processes(/* 4 */)
  .reactions(/* 5 */)
  .view(/* 6 */)
```

Каждый шаг возвращает объект со следующей стадией цепочки. Методы не мутируют предыдущие структуры — это гарантирует стабильный shape схемы.

### Фотон на уровне схемы

Схема, описанная через `MetaFor()`, определяет, как фотон будет выглядеть в рантайме:

- `context` задаёт, какие значения можно «записать» в импульс (`value`).
- `states` описывают, какие суперпозиции будут «детектировать» импульс.
- `processes` генерируют интенсивность (количество патчей) и фазу (порядок обновлений).
- `reactions` формируют поляризационные фильтры (`filter` → `path/op/value`).

Без схемы фотон не имел бы смысла, а с ней — любое изменение кодируется в тех же измеримых параметрах, что и в физической аналогии.

### 1. `context(types => schema)`

- допускаются только `string | number | boolean | enum | array`;
- `required`/`optional` определяют наличие значения (optional → `null`);
- метаданные добавляются вызовом `({ label: "..." })`;
- генератор типов (`types`) импортируется из `@zavx0z/context`.

### 2. `states(superposition)`

- описывает переходы конечного автомата;
- условия используют те же операторы, что и декларативные фильтры (`eq`, `gt`, `between`, `pattern`, `includes`, `isEmpty` и т. д.);
- `validateNoUnconditionalCycles` проверяет, что нет бесконечных безусловных циклов.

### 3. `core(initializer?)`

- хранит сложные структуры, сервисы, DOM/Canvas ссылки (`ref()` только для DOM);
- инициализатор может быть функцией или plain-object, возвращающее значение сериализуется в схему.

### 4. `processes(builder)`

- имя процесса = имя состояния (исключение — `process.destroy()` для финализации);
- `action` может быть async, `success`/`error` всегда синхронные;
- `process.destroy({ label }).before(fn)` описывает очистку перед `destroy`.

### 5. `reactions(builder)`

- декларативные фильтры `reaction().filter(({ self, context }) => conditions)` используют `SelfInfo` без `destroy`;
- `equal` получает полный `Self`, `update`, `context`, `core`, `patch`, `timestamp`;
- в массиве каждый элемент — `[states[], reaction]`, где `states` перечислены явно (без `["*"]`).

### 6. `view({ render, style })`

- `render` работает через `html` из `@zavx0z/template` и получает `{ context, state, core, update, html }`;
- `style` принимает `{ css }` и возвращает scoped-стили;
- дочерним атомам можно пробрасывать `context`/`core` атрибутами.

## Зачем нужны поддерживающие типы

`MetaForConfig`, `Meta<C, S, I>`, `ViewDefinitionParams`, `Superposition`, `ProcessesDeclaration`, `ReactionsDeclaration` — это не просто вспомогательные структуры. Они формируют язык описания поля:

- **MetaForConfig** даёт контекст схеме (описание, режим разработки), позволяя документировать актор так же тщательно, как физик описывает эксперименты.
- **Meta** фиксирует «геном» актора — поле читает именно его, а не исходный код.
- **ViewDefinitionParams** формализует поток данных между контекстом, состоянием и представлением, чтобы рендер был продолжением автомата.
- **Superposition** и декларации процессов/реакций описывают реальные силы: переходы, импульсы, фильтры. Без них фотон не знает, как вести себя.

Подробные сигнатуры ищите в Typedoc — там отображается вся эта «система координат» с актуальными полями.

## Как живёт пакет

Meta — это инструмент инженера поля, поэтому и скрипты выстроены вокруг его жизненного цикла:

- `bun run build` / `build:watch` — «синтез» схемы в разные режимы (минимизированный и с sourcemap), чтобы её можно было передавать агентам и инструментам.
- `bun run typegen` — публикация типовой карты (`dist/index.d.ts`), обеспечивающей типобезопасность при интеграции.
- `bun run docs` — генерация Typedoc как «учёта экспериментов»; без него невозможно прочитать схему глазами другого инженера.
- `bun run clear` — сброс лаборатории перед новым циклом.

## Документация и проверки

- **Typedoc** (`bun run docs`) — консолидированная база знаний о каждом узле цепочки `MetaFor()`.
- **Тесты** (`bun test --filter meta`) подтверждают, что схемы ведут себя корректно в Happy DOM: один `expect()` с понятным человеку сообщением, обязательная очистка временных артефактов.
- **Публикация** — это заранее повторяемый ритуал: `bun run build && bun run typegen && bun publish --access public`. Только так схема попадает в общее поле без потерь.

Поведенческие сценарии расположены в `meta/*.spec.ts` и `meta/*.t.ts`, а философия поля — в `../.cursor/rules/metafor.mdc`: вместе они объясняют не «как собрать код», а **как мыслить системами, где импульс несёт смысл**.
