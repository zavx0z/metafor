# MF-420 — Устранить стартовую задержку edge traffic Hamiltonian

## Зачем

После загрузки ноды и рёбра уже видимы, но стартовые сообщения успевают
потратить короткое presentation-время до materialization маршрутов. Следующий
видимый traffic появляется только с двухсекундным heartbeat и выглядит как
поздняя пачка.

## Решение владельца

Сообщения должны отрисовываться на edge максимально быстро после загрузки.
Первое доступное routed presentation должно показывать уже наблюдённый
стартовый traffic, не ожидая следующего heartbeat.

## Подтверждённая причина

* Traffic subscription и bounded backlog создаются до WebGPU runtime.
* Текущая очередь передаёт события в `NodeSystemSurface` до первой routed
  topology, поэтому их 1200 ms lifetime идёт при пустой route map.
* Window heartbeat каждые 2000 ms создаёт свежую пару
  `window-heartbeat`/`worker-state`; host heartbeat периодически добавляет
  `ping`, `pong`, `topology` и `orchestration-envelope`.
* Живое наблюдение чистой вкладки подтвердило прирост active traffic на два
  сообщения каждые примерно 2005 ms и синхронные heartbeat-пачки.

## Требуемый закон

* До первой routed topology Hamiltonian сохраняет bounded стартовые traffic
  observations вне `NodeSystemSurface`.
* Сразу после установки первого routed layout очередь передаётся surface, и
  presentation lifetime каждого стартового сообщения начинается в этот момент.
* После открытия gate новые observations передаются немедленно без очереди.
* Дубликаты, payload-free envelope, hidden-page suppression и
  render-on-demand сохраняются.

## Критерии готовности

* Стартовый traffic не истекает до появления первого edge route.
* Первый routed render показывает накопленные сообщения без ожидания
  двухсекундного Window heartbeat.
* После старта каждое новое сообщение по-прежнему принимается немедленно.
* Очередь остаётся bounded и не переносит payload.
* Unit tests, typecheck, browser build и чистая live-проверка проходят.

## Доказательство результата

* Новый `HamiltonianTrafficPresentationGate` удерживает до 256 observations,
  открывает только сообщения с materialized edge ID и передаёт последующие
  сообщения немедленно.
* На измеренном старте очередь выросла до 19 observations во время layout. На
  первой готовой сцене через 719,2 ms одновременно присутствовали 6 рёбер и 16
  активных частиц; ожидания следующего двухсекундного heartbeat не было.
* После следующей topology materialization три ожидавших edge ID были приняты,
  а pending queue стала пустой.
* Финальный чистый reload без diagnostic injection: `scene=ready`, 7 нод,
  9 рёбер, `accepted=9`, `active=9`, `pending=0`, console/network errors нет.
* `bun test hamiltonian/browser/orchestration/traffic-presentation.spec.ts
  hamiltonian/core/traffic.spec.ts pkg/ui/node/edge-particle.test.ts
  pkg/ui/node/viewport.test.ts`: 21 pass, 0 fail.
* `bun run typecheck`, строгий Hamiltonian TypeScript, browser bootstrap build,
  orchestration browser build и `git diff --check` прошли.
