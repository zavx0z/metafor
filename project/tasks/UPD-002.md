# UPD-002 — Обновлять всю клиентскую сборку через Service Worker

## Коротко

Service Worker будет отвечать за обновление всей браузерной части Hamiltonian,
а не только собственного файла и маленького испытательного модуля. Он заранее
скачает и проверит полный новый выпуск, затем переключит страницы на него одним
reload без промежуточной смеси старых и новых файлов.

## Зачем

После `UPD-001` весь код обновлений собран под одной физической границей, но
действующее поведение всё ещё разделено на три параллельных пути:

* сам Service Worker обновляется через browser-managed `registration.update()`;
* Service Worker отдельно проверяет и кеширует один маленький versioned module,
  выбранный вручную через `HAMILTONIAN_VERSION`;
* вся настоящая клиентская сборка определяется host source fingerprint, после
  чего страница сама решает выполнить reload.

Такое устройство сохранило прежний экспериментальный механизм, но не даёт
Service Worker полной ответственности за браузерный выпуск.

## Связь с дорожной картой

Это вторая задача линии
[`Обновления Hamiltonian`](../ROADMAP.md#обновления-hamiltonian). Закрытая
`UPD-001` создала внутреннюю структуру `hamiltonian/update/{shared,host,browser}`
без изменения поведения; `UPD-002` использует эту границу для нового единого
закона клиентского обновления.

## Связанные задачи и история

* Закрытая `MF-412` ввела `HAMILTONIAN_VERSION` и отдельный versioned module как
  испытание одинаковых bytes и SHA-256 в Window, Dedicated Worker и Bun process.
  Это был standalone proof, а не окончательная модель клиентской сборки.
* Закрытая `MF-428` отдельно доказала SemVer и browser-managed обновление самого
  Service Worker с сохранением logical identity и новой execution incarnation.
* Закрытая `UPD-001` намеренно только перенесла существующие решения. Её
  инвентаризация зафиксировала два самостоятельных browser-перехода: обновление
  Service Worker и reload всей отданной host клиентской сборки по source
  fingerprint.
* В обсуждении после `UPD-001` владелец выбрал Service Worker единственным
  владельцем обновления всей клиентской сборки. Серверные процессы остаются
  отдельной будущей работой.

## Подтверждённые факты

* Текущий Service Worker перехватывает и обслуживает из Cache Storage только
  URL под `/versions/`, а не полный набор файлов клиентской сборки.
* Текущий top-level manifest описывает один синтетический module через ручные
  `version`, `moduleUrl` и `sha256`; выпуск самого Service Worker находится в
  отдельном поле `serviceWorker`.
* Настоящие HTML, JavaScript, CSS, orchestration, layout Worker и Web Push
  client сейчас входят в host source fingerprint и отдаются напрямую host.
* Page принимает `source-update`, самостоятельно сравнивает fingerprint и
  вызывает reload независимо от release cache Service Worker.
* Уже исполняющийся Window main нельзя заменить внутри прежнего JavaScript
  realm; для перехода на новый полный выпуск всё равно требуется reload.
* `HAMILTONIAN_VERSION` также используется испытательными Bun embodiments.
  Service Worker не может обновлять серверные процессы.

## Решения владельца

* Service Worker отвечает за обновление всей клиентской сборки Hamiltonian.
* Идентичность клиентского выпуска выводится из точных файлов и хешей сборки, а
  не задаётся вручную значением `v1`, `v2` или временем запуска host.
* Host собирает и атомарно публикует выпуск и manifest, но не принимает за page
  самостоятельное решение о reload.
* Page выполняет один reload только после сообщения Service Worker о полностью
  готовом выпуске.
* Обновление серверных процессов не входит в эту задачу и позже получает
  отдельный server-release механизм.

## Целевое поведение

1. Host успешно собирает полный набор файлов, необходимый для рождения нового
   browser realm, и публикует один manifest с identity выпуска и SHA-256 каждого
   файла.
1. Service Worker обнаруживает новый manifest, скачивает все файлы выпуска и
   проверяет каждый файл до публикации готовности.
1. Неполная загрузка, неверный hash или failed build не меняют активный выпуск;
   страницы продолжают получать прежний полностью готовый набор.
1. Если изменился файл самого Service Worker, его замена проходит штатным
   browser-managed lifecycle. Новый execution продолжает тот же exact release
   transition с прежней logical identity.
1. После готовности полного выпуска Service Worker атомарно назначает его
   активным и сообщает каждой управляемой странице exact release identity.
1. Каждая страница принимает одну новую identity один раз, выполняет reload и
   после него получает все статические файлы одного выпуска через Service
   Worker.
1. Закрытая или поздно подключившаяся страница при следующем открытии сразу
   получает текущий активный выпуск без ручной версии host.

## Поведение процесса

Первый срез должен зафиксировать exact состав клиентского выпуска и frozen
manifest contract до изменения runtime. Затем отдельно регистрируются
последовательные срезы для атомарной публикации host, полной подготовки cache,
обслуживания navigation/static requests, переключения active release, одного
page reload и удаления прежних параллельных browser-path. Каждый новый механизм
получает собственную подзадачу и checkpoint до перехода к следующему.

## Границы

* Не обновлять Bun process, production-домены или другие устройства.
* Не удалять server-side использование `HAMILTONIAN_VERSION`, пока для него не
  создан отдельный договор замены.
* Не передавать код через Web Push; он остаётся только способом пробуждения и
  начала проверки.
* Не считать отправку manifest, окончание download либо `registration.update()`
  успешным переходом до готовности полного выпуска и подтверждённого нового
  browser realm.
* Не смешивать файлы двух выпусков и не удалять прежний готовый cache до
  подтверждения нового.
* Не вводить remote registry, подпись выпусков, trust root, anti-rollback,
  межмашинную доставку или общий rollback.
* Не менять logical identity Service Worker, profile ownership, topology,
  peer, Oracle/Force transport или обязанности Dark, Boundary, Matrix, Energy,
  Bulk и Force.
* `skipWaiting()` и `clients.claim()` не считаются старым механизмом сами по
  себе; их точное место меняется только при доказанной необходимости нового
  атомарного перехода.

## Критерии готовности

* Один manifest однозначно описывает весь клиентский выпуск и точный hash
  каждого его файла; identity выпуска детерминирована его содержимым.
* Service Worker загружает и проверяет полный выпуск до переключения и затем
  обслуживает navigation, scripts, styles и Worker resources только из одного
  active release.
* Page больше не принимает host `source-update` как отдельное решение об
  обновлении и не загружает синтетический versioned module по ручной browser
  version.
* Browser-путь больше не зависит от `HAMILTONIAN_VERSION`; отдельный маленький
  module и его `/versions/...` cache path удалены из client update.
* Изменение обычного клиентского файла без изменения Service Worker также
  приводит к подготовке нового полного выпуска и одному reload всех текущих
  страниц.
* Изменение Service Worker и остальных клиентских файлов одним build приводит
  к одному согласованному переходу, а не к двум конкурирующим обновлениям.
* Failed build, network interruption, неверный hash и закрытие страницы во
  время подготовки сохраняют прежний active release и допускают повтор.
* Два одновременно запущенных Chrome-профиля независимо переходят на один exact
  release, сохраняют разные profile/Worker identity и не смешивают caches,
  lifecycle или transport.
* Cold restart host с теми же browser bytes не создаёт reload, а поздно
  подключившийся профиль получает уже текущий выпуск.
* Испытательные server embodiments продолжают работать по прежнему договору до
  отдельной задачи обновления серверных процессов.

## Проверка результата

* Frozen manifest и release-identity tests по точному набору файлов.
* Tests атомарной подготовки, hash mismatch, partial fetch, cache retention и
  retry.
* Service Worker fetch tests для navigation, JavaScript, CSS, Worker и
  неизменяемых assets одного active release.
* Page tests для одного `release-ready → reload`, duplicate message и cold host
  с неизменным release.
* Integration tests совместной смены Service Worker и клиентских assets без
  mixed release.
* Строгие host и WebWorker TypeScript checks, реальные browser/Worker builds и
  полный `bun test hamiltonian`.
* Живой сценарий двух Chrome-профилей: исходный выпуск, новый выпуск с обычным
  client asset, новый выпуск вместе с Service Worker, failed preparation и
  восстановленный exact final release без cross-profile edges.
* `git diff --check`, полный import/URL audit и отсутствие старого browser-path
  `HAMILTONIAN_VERSION`, `/versions/...` и самостоятельного page
  `source-update`.
