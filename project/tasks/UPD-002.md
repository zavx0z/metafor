# UPD-002 — Обновлять всю клиентскую сборку через Service Worker

## Коротко

Service Worker будет отвечать за атомарную смену всей загружаемой браузерной
части Hamiltonian после неизменяемого startup. Он заранее скачает и проверит
новый набор `release`/`internal`/`metafor`, затем переключит страницы на него
одним reload без промежуточной смеси старых и новых файлов. Доказанное
состояние задаётся версиями workspace-пакетов и их зависимостями, а не отдельным
release manifest.

## Зачем

После `UPD-001` весь код обновлений собран под одной физической границей, но
действующее поведение всё ещё разделено на три параллельных пути:

* сам Service Worker обновляется через browser-managed `registration.update()`;
* Service Worker отдельно проверяет и кеширует один маленький versioned module,
  выбранный вручную через `HAMILTONIAN_VERSION`;
* вся настоящая клиентская сборка определяется host source fingerprint, после
  чего страница сама решает выполнить reload.

Такое устройство сохранило прежний экспериментальный механизм, но не даёт
Service Worker полной ответственности за загружаемый браузерный выпуск. Новый
clean-room loader из `LOAD-001` уже отделил неизменяемый startup от сменяемого
release и internal packages; эта задача должна продолжать именно его, а не прежний
prototype release path.

## Связь с дорожной картой

Это вторая задача линии
[`Обновления Hamiltonian`](../ROADMAP.md#обновления-hamiltonian). Закрытая
`UPD-001` создала в прототипе структуру
`hamiltonian/update/{shared,host,browser}` без изменения поведения. Новый
update-механизм не переносит оттуда source автоматически и строится поверх
фактического loader contract `LOAD-001`.

Задача начинается после
[`LOAD-001 — Загружать браузерный функционал через минимальный Service
Worker`](LOAD-001.md). `LOAD-001` определяет неизменяемый startup, сменяемый
release, `fetch` loading, пространства `internal`/`metafor` и независимые
caches; `UPD-002` затем определяет полный состав и атомарную смену
многосоставного functional release после startup.

## Зависимость

Состояние `IN_PROGRESS`. Владелец признал доказанный текущий loader checkpoint
достаточным для локальных development update-срезов; `LOAD-001` остаётся
открытой для собственной незавершённой работы и больше не блокирует эту задачу.

## Связанные задачи и история

* Закрытая `MF-412` ввела `HAMILTONIAN_VERSION` и отдельный versioned module как
  испытание одинаковых bytes и SHA-256 в Window, Dedicated Worker и Bun process.
  Это был standalone proof, а не окончательная модель клиентской сборки.
* Закрытая `MF-428` отдельно доказала SemVer и browser-managed обновление самого
  Service Worker с сохранением logical identity и новой execution incarnation.
* Закрытая `UPD-001` намеренно только перенесла существующие решения. Её
  инвентаризация зафиксировала два самостоятельных browser-перехода: обновление
  Service Worker и reload всей отданной host клиентской сборки по source
  fingerprint.
* `LOAD-001` доказала цепочку, позднее нормализованную как
  `startup → release → internal`, загрузку code bytes через `fetch`, запуск
  internal RPC внутри Service Worker и восстановление
  caches. WSS принадлежит RPC/control, а не delivery code bytes.
* Владелец выбрал Service Worker единственным владельцем атомарной смены всей
  загружаемой клиентской части после startup. Серверные процессы остаются
  отдельной будущей работой.

## Подтверждённые факты

Следующие пункты описывают прежний prototype update path, а не clean-room
loader `LOAD-001`:

* Текущий Service Worker перехватывает и обслуживает из Cache Storage только
  URL под `/versions/`, а не полный набор файлов клиентской сборки.
* Текущий top-level manifest описывает один синтетический module через ручные
  `version`, `moduleUrl` и `sha256`; выпуск самого Service Worker находится в
  отдельном поле `serviceWorker`.
* Настоящие HTML, JavaScript, CSS, orchestration, layout Worker и Web Push
  client сейчас входят в host source fingerprint и отдаются напрямую host.
* Page принимает `source-update`, самостоятельно сравнивает fingerprint и
  вызывает reload независимо от release cache Service Worker.
* Уже исполняющийся Window main нельзя заменить внутри прежнего JavaScript
  realm; для перехода на новый полный выпуск всё равно требуется reload.
* `HAMILTONIAN_VERSION` также используется испытательными Bun embodiments.
  Service Worker не может обновлять серверные процессы.

## Актуальная граница действующего Hamiltonian-контракта

Следующий contract-этап заменил package names и технический способ commit, но
не отменил доказанный результат `UPD-002`: Service Worker меняет весь browser
release после неизменяемого startup, code bytes получает через `fetch`, а
изменение требует нового SemVer и immutable artifact.

Текущая реализация использует packages `@hamiltonian/startup`,
`@hamiltonian/release` и `@internal/*`, cache-derived current state, один
фиксированный cache `transaction` и не хранит active/pending state либо UUID
caches. Действующим законом владеет `hamiltonian/README.md`; описания
`@startup/*`, `@release/*`, owner transaction caches и active switch ниже
остаются исторической формой первоначального checkpoint, а не current contract.
Родитель `UPD-002` остаётся `IN_PROGRESS` до отдельного reconciliation после
закрывающей проверки следующей package/release линии.

## Решения владельца для checkpoint UPD-002

* Service Worker отвечает за обновление всей загружаемой клиентской части
  Hamiltonian после startup.
* Статические HTML, `@startup/main` и `@startup/service` не входят в сменяемый
  functional release этой задачи.
* Release состоит из согласованного набора `@release/*`, `@internal/*` и
  `@metafor/*` packages и принадлежащих им ресурсов; cache ownership из `LOAD-001`
  сохраняется.
* Code bytes и текущее package state загружаются через `fetch`. Internal RPC
  WSS сообщает о новом доказанном состоянии, но не переносит artifact bytes.
* Последняя доказанная версия каждого сменяемого package записывается в
  корневых workspace dependencies как нижняя граница `workspace:^<version>`.
  Собственная точная версия package и сохранённый response сообщают, какие
  bytes фактически используются.
* Host принимает не готовые номера версий, а выбранный для каждого package вид
  SemVer-изменения `patch | minor | major`, вычисляет следующую версию и
  собирает всю группу до изменения доказанного состояния.
* Host атомарно публикует версии и artifacts только после успеха всей группы,
  но не принимает за page самостоятельное решение о reload.
* Постоянный Cache Storage имеет только имя владельца namespace: `release`,
  `internal` или `metafor`; неизменяемый startup отдельно использует `startup`.
  Transaction cache с техническим идентификатором существует только во время
  подготовки, никогда не записывается как постоянное место active package и
  удаляется после commit, rollback либо восстановления прерванной транзакции.
* Active package state указывает точную версию и versioned endpoint внутри
  канонического Cache Storage владельца. После active switch прежний endpoint
  того же package удаляется; другие packages владельца не затрагиваются.
* Любое изменение source, состава или bytes package требует новой собственной
  SemVer и нового immutable versioned artifact. Нельзя обслуживать изменённую
  сборку под уже опубликованной версией или оставлять прежний artifact
  приоритетным для стабильного package URL.
* Page выполняет один reload только после сообщения Service Worker о полностью
  готовом выпуске.
* Обновление исполняющихся серверных процессов не входит в эту задачу.
  `@release/server` обслуживает browser release и не перезапускает Bun process.

### Требования к собираемому пакету

* Каждый собираемый browser artifact, включая фиксированные `@startup/*` и
  сменяемые `@release/*`/`@internal/*` packages, оформляется отдельным
  workspace-пакетом. Поле `name` его `package.json` является единственным
  каноническим именем package в build-запросе, результате сборки и уведомлении об
  обновлении.
* Корневой export пакета обязан вести на собираемый клиентский entrypoint. Если
  `exports` является объектом с дополнительными server или route subpath, в нём
  обязательно присутствует `"."`; внутренний subpath не используется как имя
  package при сборке.
* Пакет обязан объявлять строгий `scripts.typecheck` и lifecycle
  `scripts.prebuild`, запускающий `bun run typecheck`. Ошибка `prebuild` не
  допускает запуск основной сборки.
* `scripts.build` является одной непосредственно исполняемой production-командой
  `bun build`. Она указывает относительный к package root source entrypoint, все
  необходимые `target`/`format`/`external` параметры, production profile и
  единый outfile `dist/index.js`. Отдельные `build:development` и
  `build:production` не создаются.
* Host читает и разбирает package-owned `scripts.build`. В production он
  исполняет команду без изменения. Только при `NODE_ENV=development` host
  сохраняет package-owned параметры, удаляет `--production` и
  `--drop console.debug`, добавляет `--sourcemap=inline` и исполняет полученную
  development-команду. Другие build-команды и shell-ветвление не принимаются.
  Реестр package names в build module запрещён: любой Hamiltonian workspace
  package с этим contract находится по своему `name` и корневому export.
* Development-сборка минифицируется, сохраняет `console.debug` и включает
  inline source map. Production-сборка выполняется с `--production`,
  минифицируется, полностью удаляет `console.debug` через `--drop` и не создаёт
  source map. Обязательная рабочая логика не помещается в аргументы
  `console.debug`, потому что production drop удаляет и их вычисление.
* Корневой `scripts.dev` явно запускает Hamiltonian с
  `NODE_ENV=development`, чтобы ленивые и явные package builds преобразовывались
  в development-профиль. Корневой `scripts.build` параллельно запускает
  package-owned production-команды; обычный `scripts.start` не включает
  development-преобразование. Одноразовые клиентские diagnostics, не нужные
  production, записываются через `console.debug`; ошибки остаются в production.
* Запущенный из package root `bun run build` обязан самостоятельно выполнить
  строгую проверку и создать непустой `dist/index.js`. Это одинаковый договор
  первоначальной и повторной сборки.
* Host находит package root по каноническому имени, отдельно выполняет строгий
  `prebuild`, затем разбирает и запускает `scripts.build` с выбранным профилем.
  Параметры конкретного artifact не дублируются в route, macro или runtime
  build helper.
* Если artifact требует особые HTTP headers, package объявляет их строковыми
  значениями в `artifact.headers`. Host применяет это поле одинаково для любого
  package; проверки конкретного package name в build module запрещены.

### Требования к development build endpoint

* Единственный endpoint browser code — `/code`; query parameter `module`
  содержит каноническое package name. `GET` читает package-owned
  `dist/index.js`: если файл существует и непуст, host отдаёт его без сборки;
  если файл отсутствует или пуст, host лениво запускает `scripts.build` и
  отдаёт artifact только после успешного завершения. Одновременные первые
  запросы одного package используют один pending build; после ошибки следующий
  `GET` может повторить попытку.
* Явная повторная сборка выполняется через `POST /code` с единственным JSON-body
  `{packages: {name, change}[]}`, где `change` принимает только `patch`, `minor`
  или `major`. Готовый номер версии снаружи не передаётся. Query parameters для
  POST не поддерживаются. Host принимает только непустой набор сменяемых
  `@release/*` и `@internal/*` packages и параллельно запускает их
  `scripts.build`.
* Ответ `POST /code` имеет один формат `{success, results, packages}`; каждый
  result содержит каноническое имя, вид изменения, прежнюю и новую версии, exit
  code, полные `stdout`/`stderr` package process и metadata artifact. Failed
  group возвращает `422`, сохраняет прежние готовые artifacts, возвращает
  пустой `packages` и не публикует уведомление.
* После успеха всей выбранной группы host публикует одно RPC WebSocket message
  с каноническими package names, точными новыми версиями, source endpoints и
  cache owners. Service Worker получает bytes каждого artifact отдельным
  последующим `GET`; WebSocket code bytes не переносит.
* Service Worker сохраняет полученное намерение обновления в Cache Storage,
  загружает всю группу во временные owner caches и одним изменением active
  state открывает её loader. Ошибка или остановка Worker до active switch не
  меняет действующие entries. После пробуждения Worker сверяется с текущим
  доказанным состоянием host и продолжает незавершённое обновление.
* Общая сборка всех Hamiltonian packages является только локальной командой и
  не образует update contract. После успешной замены выбранной группы Worker
  закрывает прежний RPC transport, снимает active registration и один раз
  навигирует каждый управляемый Window на его текущий URL. Startup заново
  регистрирует Worker, а новая инкарнация запускает service-side modules из
  сохранённых caches.

## Целевое поведение

1. Host принимает группу package changes, вычисляет новые SemVer и собирает все
   artifacts во временное место, не изменяя опубликованные версии.
1. После успеха всей группы host одним commit текущего корневого package
   публикует новые доказанные версии и сообщает их Service Worker.
1. Service Worker скачивает точные версии во временные owner caches и проверяет
   package name/version каждого response до публикации готовности.
1. Неполная загрузка, неверная версия или failed build не меняют активный набор;
   страницы продолжают получать прежний полностью готовый набор.
1. Неизменяемые startup scripts, включая executable Service Worker startup, не
   заменяются этим release transition. Новая инкарнация Worker восстанавливает
   активные release/internal packages из origin-bound caches.
1. После готовности всей группы Service Worker атомарно заменяет active package
   state и сообщает каждой управляемой странице о завершённом обновлении.
1. Каждая страница принимает одно завершённое обновление, выполняет reload и
   после него получает все сменяемые artifacts одного выпуска через Service
   Worker, сохраняя тот же startup.
1. Закрытая или поздно подключившаяся страница при следующем открытии сразу
   получает текущий активный выпуск без ручной версии host.

## Поведение процесса

Локальные development update-срезы выполняются поверх уже доказанного loader
checkpoint. Версионирование package, атомарная публикация build-группы и
транзакционное переключение browser caches получают отдельный последовательный
срез. Каждый новый механизм получает собственную подзадачу и checkpoint;
остановленная `.1` не возобновляется.

## Подзадачи

### UPD-002.1 — Зафиксировать полный состав клиентского выпуска

Статус и исполнитель: `STOPPED BEFORE IMPLEMENTATION`; product-исполнитель не
запускался, runtime result отсутствует.

Классификация: исторический contract-срез прежнего prototype release. Он был
остановлен до implementation и не является текущей формой будущего manifest.

Прежнее требование: один browser-safe manifest contract перечислял каждый
канонический файл нового Window realm вместе с SHA-256. После `LOAD-001` эта
граница заменена: будущий manifest должен описывать только сменяемые artifacts
`import`/`internal`/`metafor` после startup и сохранять их cache ownership.

Основание и связанная история: закрытая `MF-412` доказала exact bytes только
синтетического versioned module; `MF-428.3`–`MF-428.8`, result `1579d11cd` и
closing `63be214c6` доказали отдельный lifecycle executable Service Worker;
`UPD-001.1` inventory `f8f18e75f`, result `97442bb8b` и closing `6d07a5046`
собрали update-код в `hamiltonian/update`, но намеренно сохранили оба browser
transition. Новый срез не восстанавливает закрытые задачи, а заменяет их
раздельные release shapes одним договором текущего родителя.

Наблюдаемое расхождение: действующий `HamiltonianBrowserManifest` описывает
только ручной `version/moduleUrl/sha256` и отдельный `serviceWorker`, тогда как
настоящий browser source fingerprint отдельно охватывает bundles и напрямую
served text, исключает бинарный font и не является manifest, проверяемым
Service Worker.

Причина: standalone proof `MF-412`, Worker lifecycle `MF-428` и общий page
source reload развивались как три разных механизма; structural `UPD-001` по
решению владельца не меняла их поведение и договоры.

Разрешённое изменение одного механизма: отсутствует, пока `LOAD-001` не
завершена. После зависимости руководитель регистрирует новый последовательный
contract-срез, не продолжая этот остановленный artifact inventory.

Regression или опровергающее доказательство: будущая frozen проверка должна
отделять неизменяемые HTML/`@startup/main`/`@startup/service` от сменяемых
importers, modules и ресурсов, фиксировать cache owner каждого artifact и
отвергать возврат WSS code delivery. Точный inventory выбирается новым срезом.

Среда и критерий приёмки: canonical `main` из подготовительного commit этого
среза; focused shared/host tests, существующие browser release tests, строгий
host/WebWorker TypeScript check и `git diff --check` проходят, а runtime diff
отсутствует.

Фактические действия:

Результат и вывод:

Подготовительный commit: этот commit.

Result checkpoint:

Решение о продолжении: срез остановлен после owner-решения сначала определить
минимальный browser loader в `LOAD-001`. Его прежний contract сохранён только
как история отвергнутого порядка. После завершения зависимости руководитель
зарегистрирует новый последовательный срез многосоставного выпуска на основе
`startup → import → internal/metafor`.

### UPD-002.2 — Обновлять выбранные модули и один раз перезапускать браузер

Состояние результата: принят владельцем в development checkpoint родительской
задачи; выполнялся текущей задачей без субагента.

Классификация: локальный development update выбранного набора modules, а не
полный versioned release и не общая сборка всех Hamiltonian packages.

Требование: `POST /code` принимает один внешний формат для одного и нескольких
modules — один или несколько повторяемых query parameters `module`. Host
отвергает пустой запрос и любое неизвестное или неизменяемое package name до
сборки, удаляет повторы и параллельно запускает package-owned `scripts.build`
всего выбранного набора.

Наблюдаемое расхождение: действующий endpoint собирает и сообщает только один
module, Service Worker обновляет одну cache entry, но уже исполняющиеся Window
и Service Worker modules продолжают работать до новой execution incarnation.

Причина: build notification пока содержит единственное поле `module`, а после
успешного `cache.put` отсутствует transition текущих browser clients и active
Service Worker registration.

Разрешённое изменение одного механизма: если хотя бы одна сборка неуспешна,
host возвращает общий unsuccessful response и не публикует уведомление. После
успеха всего набора host публикует одно сообщение
`{type: "build", modules: [...]}`. Service Worker принимает только этот массив,
заранее получает и проверяет каждый artifact, затем заменяет выбранные cache
entries. После успешной замены всего набора Worker один раз снимает текущую
registration и навигирует каждый управляемый Window client на его текущий URL.
Startup заново регистрирует Service Worker; новая инкарнация загружает

### UPD-002.6 — Публиковать и применять группу пакетов транзакционно

Статус и исполнитель: `IN_PROGRESS`; текущая задача без субагента. По решению
владельца текущий checkpoint фиксируется перед отдельным пересмотром
границы неизменяемого startup loader.

Классификация: замена принятого development build notification на
версионированную транзакцию host и Service Worker без отдельного release
manifest и без изменения неизменяемого startup.

Требование: `POST /code` принимает только `{packages: {name, change}[]}`. Поле
`change` является видом SemVer-изменения `patch | minor | major`; номера версий
в запросе запрещены. Host вычисляет новые версии от последнего доказанного
состояния, собирает всю группу во временное место и не меняет package manifests,
действующие artifacts или RPC state при любой ошибке. Успех всей группы
публикует точные версии и artifacts, затем отправляет одно уведомление.

Package contract: каждый сменяемый artifact имеет собственную точную `version`
и `artifact.cache`. Корневой Hamiltonian package перечисляет доказанные версии
сменяемых packages диапазонами `workspace:^<version>`. Эти package manifests
являются источником release state; отдельный manifest-файл не создаётся.

Browser contract: Worker сохраняет pending package versions в Cache Storage,
загружает группу во временные owner caches, проверяет response name/version и
одним active-state write переключает все entries. До этого write loader видит
только прежние bytes. После RPC reconnect Worker читает текущее состояние через
`GET /code`, сравнивает его с cache и повторяет пропущенное или прерванное
обновление. Полностью применённая версия повторного reload не вызывает.

Regression или опровергающее доказательство: failed group не меняет версии,
root dependencies, доступные artifacts, browser cache и navigation. Успешная
группа повышает каждую версию ровно по выбранному change, обновляет оба cache
owner одним active switch и навигирует каждую Window ровно один раз. Worker,
пропустивший RPC, получает то же состояние после reconnect.

Среда и критерий приёмки: canonical `main` от baseline `34b998211`; strict
TypeScript, package builds, focused server transaction tests, изолированный
Puppeteer regression, live `$metafor-dev` update и `git diff --check` проходят.
Постоянные iTerm, Hamiltonian и CDP Chrome остаются работающими для проверки
владельца. Коммит создаётся только после отдельного утверждения владельца.

Фактические действия:

* Сменяемые packages получили точные SemVer и `artifact.cache`, а корневой
  Hamiltonian package — caret dependencies доказанного набора. Новый
  `release.ts` сериализует публикации, собирает группу в staging-директорию,
  публикует versioned artifacts и записывает корневой package последней точкой
  готовности.
* `POST /code` принимает JSON `packages[{name, change}]`, вычисляет SemVer
  сам и после успеха всей группы отправляет одно RPC `release` message.

### UPD-002.13 — Загружать пакеты по каноническим package URL

Статус и исполнитель: `IN_PROGRESS`; текущая задача без субагента по прямому
решению владельца продолжать реализацию в этом чате.

Классификация: новое требование к HTTP identity browser artifacts и runtime
resolution bare package imports. Оно продолжает тот же результат `UPD-002`, но
меняет отдельный delivery/build mechanism после завершённого correction-среза
`.12`, поэтому получает следующий номер.

Требование: стабильный browser artifact одного workspace package доступен по
каноническому URL `/<package-name>`, например `/@release/main` и
`/@internal/visual`; exact version использует тот же URL с `version`. `/code`
остаётся control endpoint: `GET /code` возвращает доказанное package state, а
`POST /code` публикует группу. Query `module` больше не является identity
artifact и не встречается в source, build output, Cache Storage или network
requests.

Window resolution: исходники и готовые ESM artifacts сохраняют bare imports
`@startup/*`, `@release/*`, `@internal/*` и `@metafor/*`. Один import map с
prefix entries направляет namespaces в одноимённые URL; package build оставляет
только самостоятельно доставляемые зависимости external. Conditional browser
adapter отдельного package запрещён. Service Worker и Dedicated Worker code,
который не исполняется как document ESM graph, продолжает получать bytes через
loader либо входит в собственный bundle.

Основание и связанная история: `.10` физически отделила Visual от
`@release/main`, но для сохранения package import ввела conditional browser
export `@internal/visual/endpoint.ts`, который при сборке заменяет
`import("@internal/visual")` на `import("/code?module=@internal/visual")`.
`.11` затем привязала owner-cache routing к query `module`, а `.12` исправила
финализацию этих entries в канонических owner caches. Владелец отклонил
transport URL внутри package composition и выбрал namespace endpoints для всех
browser packages. Ранее доказанные cache ownership и transaction laws
сохраняются.

Наблюдаемое расхождение: source `@release/main` выглядит как package
composition, но production artifact содержит transport-specific `/code`
import. HTML, startup main/service, release state, loader и caches повторяют
`/code?module=...`; `/code` одновременно является state/command API и delivery
surface каждого artifact.

Причина: browser не разрешает bare package specifier без import map. `.10`
решила это package-owned conditional export, поэтому Bun выбирает browser
adapter и встраивает его transport URL вместо сохранения external import.

Разрешённое изменение одного механизма: добавить один статический import map
namespace-to-path, оставить independently delivered Window dependencies
external, удалить Visual browser adapter и обслуживать `@startup`, `@release`,
`@internal`, `@metafor` через одинаковые parameter routes одного resolver.
Перевести startup/release cache lookup и active package matching с query на
pathname. Не менять состав release, SemVer policy, owner caches, атомарную
публикацию, RPC, restart protocol или `/sw`.

Migration boundary: изменение фиксированных HTML и startup packages не может
быть доставлено действующим release transition. Проверка нового договора
начинается с одной origin-scoped `clear-site-data` exact managed target; старый
`GET /code?module=...` compatibility route не сохраняется. Package source,
composition или bytes получают новые SemVer и immutable artifacts по
действующему закону.

Regression или опровергающее доказательство: source и production artifacts
содержат bare package imports и не содержат `/code?module=`; Visual
implementation остаётся только в самостоятельном internal artifact. HTTP
boundary принимает stable и exact versioned namespace URL, `GET/POST /code`
сохраняют state/publication contract, а legacy query artifact request не
обслуживается. Browser regression после clean startup, group update, failed
preparation, reconnect и cold offline restore видит только канонические owner
caches и package pathname entries без mixed release.

Среда и критерий приёмки: canonical `main` от baseline `0c30318cd`; strict
TypeScript, development/production builds, server/package/boundary tests,
полный релевантный Hamiltonian suite, `git diff --check` и живой
`$metafor-dev` clean/update contour. Existing Hamiltonian не дублируется;
startup migration выполняется только bundled `clear-site-data`, после чего
managed target остаётся владельцу.

Фактические действия:

* Добавлен единый pathname resolver browser package: stable URL имеет вид
  `/<package-name>`, exact immutable URL добавляет только `?version=<semver>`.
  Корневой server явно объявляет одинаковые parameter routes для namespaces
  `@startup`, `@release`, `@internal` и `@metafor`; `/code` принимает только
  state GET без query и publication POST. Legacy `GET /code?module=...`
  возвращает `404`.
* HTML получил один import map namespace prefixes. `@startup/main` и
  `@release/main` сохраняют bare imports `@release/main` и
  `@internal/visual`; их production build оставляет independently delivered
  packages external. Conditional transport adapters `endpoint.ts` и
  `endpoint.d.ts` удалены, а side-effect type exports не подменяют runtime
  package composition.
* Startup и release loaders, owner-cache routing, active-state validation и
  cleanup переведены с query `module` на package pathname. Package-owned
  `Service-Worker-Allowed: /` сохраняет корневой scope для startup Worker,
  который теперь загружается по `/@startup/service`; специальной ветки Visual
  или реестра package names в handler не добавлено.
* Новые immutable artifacts опубликованы как `@startup/main@0.1.1`,
  `@startup/service@0.1.1`, `@release/main@0.1.4`,
  `@release/service@0.1.4` и `@internal/visual@0.1.2`; root caret dependencies,
  package manifests и `bun.lock` согласованы. Production current и immutable
  artifacts четырёх startup/release packages побайтно совпадают;
  `@release/main@0.1.4` имеет размер `285` bytes, содержит bare
  `@internal/visual` и не содержит transport URL.

Результат и вывод:

* Stable и exact package delivery отделены от `/code`; source, production
  artifacts, network requests и Cache Storage больше не используют
  `/code?module=`. `@release/main` и `@internal/visual` остаются двумя
  физическими artifacts в caches их владельцев, без дублирования Visual bytes.
* Strict TypeScript всех шести затронутых startup/release/visual/server
  packages и тестового contour прошёл; production build прошёл. Focused

  `3450 expect()`. Корневой aggregate typecheck после успешных package checks

  `hamiltonian/update`, не затронутого этим срезом.

  hash comparison и полный legacy URL audit прошли. Единственные оставленные
  упоминания `/code?module=` являются отрицательными regression assertions.
* После одной предусмотренной migration-команды `clear-site-data` live target
  обновил Visual `0.1.1 → 0.1.2`, применил release и переподключил Worker.
  Cache Storage содержит только `startup`, `release`, `internal`, не содержит
  `*:release:<uuid>`; Visual существует только как
  `/@internal/visual?version=0.1.2` в `internal`. Controller и registration
  используют `/@startup/service`, release state сообщает канонические exact
  endpoints, legacy artifact GET возвращает `404`. Это live proof, а не owner

Среда и критерий приёмки: canonical `main` от baseline `944e1be45`; сохранить
пользовательские изменения `internal/visual/index.ts` и

до отдельного `.15`.

### UPD-002.16 — Не реэкспортировать типы из другого package

Статус и исполнитель: `READY`; после подготовительного project-коммита
назначается внутреннему субагенту текущей задачи.

Классификация: новое owner-требование к package type ownership, обнаруженное
после закрытия следующей package/release линии. Оно продолжает type-boundary
результат `.14`, но меняет отдельный механизм public barrel.

Требование: type re-export допустим только между файлами одного workspace
package. Package не реэкспортирует тип, объявленный другим package; consumer
импортирует type напрямую у владельца. В `startup`, `release` и `internal` не
остаются `export type ... from`, `export {type ...}`, `export *` либо
`import type → export`, пересекающие разные ближайшие `package.json`.

Основание и связанная история: `.14` закрепила source-linked public types без
generated declarations. Поздняя closing correction следующей линии разделила
service/server env exports, но не проверяла package ownership target каждого
оставшегося type re-export. Прямое уточнение владельца разрешило реэкспорт
внутри package и запретило его из другого package.

Наблюдаемое расхождение: AST-аудит 35 source/declaration файлов подтвердил
ноль нарушений в `startup` и `internal`, но два в `@hamiltonian/release`:
`release/server/index.ts` и `release/server/shared/contracts.ts`
реэкспортируют `BrowserPackageEnvironment` и `PackageEnvironment`, объявленные
в package `@metafor/hamiltonian` под `hamiltonian/shared/package/environment.ts`.
Остальные восемь найденных type re-export declarations не пересекают границу
`@hamiltonian/release` и допустимы.

Причина: server barrel повторил удобные environment aliases рядом с release
contracts, не проверяя ближайший package owner исходной декларации. Эти aliases
затем начали использовать package build, publication и boundary test вместо
прямого type import у владельца.

Разрешённое изменение одного механизма: удалить только два cross-package
type re-export; направить production type-consumers package build/publication
и boundary test прямо к owner declaration. Добавить общий TypeScript AST
regression package ownership для `startup`, `release` и `internal`. Не менять
runtime, package conditions, build behavior, release protocol или допустимые
внутрипакетные re-exports.

Regression или опровергающее доказательство: test обходит source, включая
`.d.ts`, разрешает direct type declarations и re-export с одинаковым ближайшим
`package.json`, но падает на cross-package type target независимо от формы
export. Текущий witness до fix находит ровно два нарушения; после fix список
пуст. Existing env type consumers и canonical typecheck проходят.

Среда и критерий приёмки: focused package-boundary regression, canonical
`bun run typecheck`, полный Hamiltonian suite и `git diff --check`. Managed
runtime и browser не используются.

Фактические действия: не начаты.

## Границы

* Не обновлять Bun process, production-домены или другие устройства.
* Не включать HTML, `@startup/main` или `@startup/service` в сменяемый release.
* Не переносить code bytes через WSS; package state может прийти через RPC
  release, а artifacts загружаются через `fetch`.
* Не удалять server-side использование `HAMILTONIAN_VERSION`, пока для него не
  создан отдельный договор замены.
* Не передавать код через Web Push; он остаётся только способом пробуждения и
  начала проверки.
* Не использовать `registration.update()` как механизм смены загружаемого
  functional release; executable startup Service Worker этой задачей не
  заменяется.
* Не смешивать файлы двух выпусков и не удалять прежний готовый cache до
  подтверждения нового.
* Не вводить remote registry, подпись выпусков, trust root, anti-rollback,
  межмашинную доставку или общий rollback.
* Не менять logical identity Service Worker, profile ownership, topology,
  peer, Oracle/Force transport или обязанности Dark, Boundary, Matrix, Energy,
  Bulk и Force.
* `skipWaiting()` и `clients.claim()` принадлежат неизменяемому startup и не
  меняются этой задачей.

## Критерии готовности

* Package versions и корневые caret dependencies однозначно задают последнее
  доказанное состояние сменяемых artifacts без отдельного manifest-файла.
* Service Worker загружает и проверяет всю запрошенную группу до active switch
  и затем обслуживает release/internal packages только из атомарно выбранного
  package state, не заменяя startup.
* Page больше не принимает host `source-update` как отдельное решение об
  обновлении и не загружает синтетический versioned module по ручной browser
  version.
* Browser-путь больше не зависит от `HAMILTONIAN_VERSION`; отдельный маленький
  module и его `/versions/...` cache path удалены из client update.
* Изменение обычного клиентского файла без изменения Service Worker также
  приводит к подготовке нового полного выпуска и одному reload всех текущих
  страниц.
* Изменение Service Worker functionality выполняется заменой загружаемого
  service-side module, а не browser-managed заменой startup script.
* Failed build, network interruption, неверная версия и закрытие страницы во
  время подготовки сохраняют прежний active release и допускают повтор.
* Два одновременно запущенных Chrome-профиля независимо переходят на один exact
  release, сохраняют разные profile/Worker identity и не смешивают caches,
  lifecycle или transport.
* Cold restart host с теми же browser bytes не создаёт reload, а поздно
  подключившийся профиль получает уже текущий выпуск.
* Испытательные server embodiments продолжают работать по прежнему договору до
  отдельной задачи обновления серверных процессов.
