# HAM-002 — Собрать визуальный слой Hamiltonian в одном контуре

## Коротко

После универсализации `nodes` собрать product-specific визуальный код
Hamiltonian в одной внутренней директории `hamiltonian/visualization/` с
понятными слоями projection, layout composition, presentation, HUD и live
acceptance. Не переносить туда универсальные законы node-system.

## Зачем

Сейчас визуальная реализация исторически распределена между
`hamiltonian/browser/orchestration.ts`, `browser/orchestration/*`, browser
entrypoints, lifecycle projection, HUD-панелями и тестами. Это затрудняет ответ
на два разных вопроса: что является причинным законом Hamiltonian, а что только
его визуальной проекцией и composition универсальных `@nodes/*` пакетов.

## Историческая линия и отличие

* `MF-415` создала живую orchestration scene.
* `MF-419`/`MF-420` и закрытые NODES-задачи вынесли и стабилизировали layout.
* `MF-424` принимает отдельные наблюдаемые дефекты живого вида вместе с
  владельцем; это не задача организации исходников.
* `HAM-001` владеет retained declarations и lifecycle согласованностью; это не
  presentation layer.
* `NODES-009.1`–`NODES-009.5` удалили Hamiltonian-specific catalog и HUD
  coupling из общей библиотеки, доказали package/browser boundaries и обновили
  живой Service Worker. Эти закрытые срезы удовлетворили подготовительную
  зависимость; открытый родитель `NODES-009` не блокирует этот refactor.

Поэтому работа получает новый стабильный номер, а не `MF-424.4` и не подзадачу
`HAM-001`.

## Предварительный инвентарь

До реализации повторно проверить актуальный tree, но начать с:

* `hamiltonian/browser/orchestration.ts` — bootstrap и composition сцены;
* `hamiltonian/browser/orchestration/lifecycle-projection.ts` — projection
  Hamiltonian declarations/lifecycle в `NodeSystemDocument`;
* `canvas-view.ts`, `workspace.ts`, `selection-retention.ts` — HUD и workspace;
* `responsive-layout.ts`, `layout-transition.ts` — consumer layout policy и
  presentation transition;
* `traffic-presentation.ts` — live message presentation;
* `spatial-runtime.ts` — наблюдаемая spatial state;
* `hamiltonian/browser/layout-worker.ts` — browser Worker entrypoint;
* связанные `*.spec.ts`, `browser-build.spec.ts`, `host.ts` bundle ownership и
  разделы `hamiltonian/README.md`.

Каталог transport family, палитра и легенда являются Hamiltonian-specific и
должны войти в этот контур. Generic `NodeSystemDocument`, validation,
`@nodes/layout`, HUD-free renderer primitives и optional `@nodes/hud` остаются
в универсальных пакетах.

## Целевая граница

`hamiltonian/visualization/` владеет только visual projection и composition.
Предлагаемая внутренняя структура уточняется отдельным подготовительным срезом,
но должна различать как минимум:

* `projection/` — declarations/lifecycle -> generic node document;
* `layout/` — выбор universal adapter, responsive policy и transitions;
* `presentation/` — WebGPU surface, traffic, palette и selection;
* `hud/` — Inspector/canvas controls composition;
* browser entrypoint/bootstrap, который соединяет слои, но не содержит их
  реализацию целиком.

Названия являются направлением, а не разрешением механически переместить файлы
без проверки dependency graph.

## Границы

* Подготовительный gate закрыт срезами `NODES-009.1`–`NODES-009.5`; открытый
  родитель `NODES-009` не нужно закрывать перед началом.
* Не менять lifecycle, transport, declaration или Force semantics.
* Не менять принятую геометрию и визуальный результат попутно с перемещением.
* Не копировать код или типы из `nodes` в Hamiltonian.
* Не превращать `visualization/` во второй универсальный UI package.
* Каждый новый визуальный дефект по-прежнему регистрируется и принимается через
  `MF-424`, а не скрыто исправляется этим structural refactor.

## Первый срез после запуска

Получивший эту родительскую задачу агент сначала переводит `HAM-002` в
`IN_PROGRESS`, указывает себя исполнителем и регистрирует подзадачу
`HAM-002.1 — Зафиксировать ownership и import graph визуального слоя` отдельным
подготовительным project-коммитом. Этот диагностический срез:

1. снимает актуальный import graph и ownership inventory без перемещения кода;
2. фиксирует точную целевую структуру `hamiltonian/visualization/` и полный
   список move-only файлов;
3. отделяет bootstrap entrypoints, причинный lifecycle contract и bundle
   ownership от projection, layout composition, presentation и HUD;
4. задаёт независимые последующие move-срезы и проверки каждого слоя;
5. останавливается, если обнаруживает необходимость менять поведение, другой
   owning contract или новый визуальный дефект: это не расширяется скрыто в
   structural refactor.

Только после checkpoint `HAM-002.1` начинается перенос по одному слою. После
структурной эквивалентности выполняется live Hamiltonian regression без
заявления новой эстетической приёмки.

## Критерии готовности

1. Product-specific visual code находится под одним явным owning contour.
2. Browser entrypoints содержат bootstrap, а не смешанную реализацию всех слоёв.
3. Projection, layout composition, presentation и HUD имеют односторонние
   зависимости и отдельные тесты.
4. Ни один universal package не импортирует Hamiltonian.
5. Browser bundles, package/root typecheck и Hamiltonian tests проходят.
6. Живой пользовательский сценарий визуально и причинно эквивалентен baseline;
   новая эстетическая приёмка не приписывается structural refactor.
