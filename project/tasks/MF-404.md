# MF-404 — Добавить создание и обновление Process

## Зачем

Process должен создаваться и изменяться через общий структурный договор, а не
через отдельный неуправляемый генератор.

## Действующая основа

Field уже доказывает форму одной declaration entity, один accepted patch и
общий live-first/source projection path.

## Границы

* Добавить entity `process` в тот же `meta.declaration.apply` и использовать тот
  же live-first/source projection path, что и для Field.
* Включить Process descriptor и ограниченный набор принадлежащих ему action и
  handler source artifacts в один заранее проверенный target patch.
* Не создавать отдельный Process generator.
* Не добавлять произвольный filesystem/source writer.
* Hot reload, restart, access policy и capability scope не входят в задачу.

## Критерии готовности

Один доверенный агент создаёт и обновляет Process через RPC, а source,
Boundary, Matrix и наблюдаемый результат согласованы без отдельного генератора.

## Доказательство результата

* Public contract принимает `process add/replace`, закрытый descriptor,
  inline success/error handlers и один owned `actions/<file>.ts`.
* Source projector атомарно публикует и восстанавливает `meta.ts` вместе с
  существующим либо новым action artifact; accepted cause остаётся в той же
  Force Particle history без второго журнала.
* Обычный service test создаёт State и Process через RPC, повторяет принятую
  operation, обновляет Process с сохранением `localId` и проверяет action bytes
  и каноническую Boundary row.
* Полный `bun run check`: 2190 tests, 0 failures, 85 985 assertions в 259 files;
  TypeScript и 42 ожидаемых отрицательных type-доказательства прошли.

Текущий slice намеренно ограничен `add/replace`: Process key и тип сохраняются
при replace, action path ограничен одним файлом внутри `actions/`. Remove, move,
hot reload, restart и новая access policy в эту задачу не входят.
