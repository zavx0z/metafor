# HAM-004 — Собрать целостные требования к Hamiltonian

## Коротко

Все требования к загрузке, размещению, запуску, обновлению и сетевой работе
Hamiltonian сначала собираются и согласуются в одной карточке. После этого
открытые задачи будут пересмотрены, а владелец определит, что исправить, в каком
порядке выполнять работу и какие отдельные задачи ещё нужны.

## Зачем

Исходная архитектура обсуждалась в нескольких сессиях и затем частями попала в
`MF-411`, `MF-425`, `UPD-002`, историю `HAM-003`, `MF-414`, `MF-426` и другие
карточки.
Из-за этого широкое требование к Hamiltonian было сужено до отдельных механизмов,
например только обновления браузерной сборки, тогда как владелец требует также
первичную загрузку исполняемого кода и дальнейшую работу в распределённой сети.

Эта карточка нужна как единственное место предметного обсуждения до изменения
графа исполнения. Она не заменяет постоянные документы-владельцы и не является
разрешением начинать реализацию.

## Связь с дорожной картой

Карточка уточняет направление
[`Hamiltonian и воплощения`](../ROADMAP.md#hamiltonian-и-воплощения) и линию
[`Загрузка Hamiltonian`](../ROADMAP.md#загрузка-hamiltonian), после которой
следует [`Обновления Hamiltonian`](../ROADMAP.md#обновления-hamiltonian). Она должна
согласовать три последовательных этапа дорожной карты: одну Вселенную на одном
устройстве, ту же Вселенную на нескольких устройствах и только затем несколько
Вселенных.

Крупное направление пока не изменяется. После сбора требований владелец отдельно
решит, какие формулировки должны перейти в постоянный документ Hamiltonian,
`ROADMAP.md`, действующие карточки и граф исполнения.

может независимо завершиться согласованной картой изменений проектных задач.

## Подтверждённые факты

* Первый запрос нового браузера не может обслужить ещё не установленный Service
  Worker, поэтому Bun-часть обязана вернуть минимальный HTML/startup.
* Текущие `GET /` и `GET /index.html` возвращают HTML из
  `hamiltonian/public/index.html` через `handleNavigation()`.
* Настоящие `app.js`, orchestration, CSS и browser Worker сейчас загружаются
  напрямую с host; Service Worker обслуживает из release cache только
  `/versions/...`.
* Действующий versioned module является испытательным `createEmbodiment()`, а не
  полным выпуском функционала Hamiltonian.
* `MF-412` доказала один Service Worker control socket, SHA-256 проверку,
  Cache Storage, Window/Dedicated Worker/Bun execution и физический Android
  контур без переноса production-кода MetaFor.
* `MF-428` доказала browser-managed обновление самого Service Worker с
  сохранением logical identity и новой execution incarnation.
* `UPD-002` уже зафиксировала разрыв: полный browser release ещё не принадлежит
  единому Service Worker release path, а server release оставлен будущей работой.
* Межустройственная доставка выпуска и догоняющее обновление после offline пока
  являются целевым направлением, а не доказанным runtime.
* `LOAD-001` уже реализовала clean-room browser loader: неизменяемый `startup`
  запускает обновляемые importers, `@import/service` выбирает первый
  `internal/rpc` module, code bytes загружаются через `fetch`, а WSS открывает
  уже загруженный RPC module.
* Cache Storage разделён на `startup`, `import`, `internal` и будущий `metafor`;
  автоматизированный изолированный Chrome regression доказал cold restoration
  первых трёх без доступной HTTP-доставки artifacts.

следующему вопросу. Формулировка получает новое состояние только по явному
решению владельца.

## Решения владельца

* Создать отдельную `HAM-004 — Собрать целостные требования к Hamiltonian`.
* На текущем этапе только обсуждать и фиксировать требования; не начинать
  реализацию.
* Каждое уточнение из последующих обсуждений сразу отражать в этой карточке,
  чтобы оно не оставалось только в истории чата.
* Перед каждым следующим механизмом пересматривать открытые и исторические
  связанные задачи. После owner-approved размещения обсуждение и реализация
  могут продолжиться в задаче-владельце, не ожидая завершения всех остальных
  вопросов HAM-004.
* Новую задачу или подзадачу создавать только после evidence-backed gate и
  отдельного решения владельца; HAM-004 сама product-код не изменяет.
* Цель временного HTTPS seed — один раз доставить устанавливаемый browser loader;
  после установки функциональные выпуски должны быть доступны через другие
  действующие части распределённого Hamiltonian.
* Первоначальный Service Worker loader не обновляется. Выдавший PWA HTTPS server
  и его origin могут быть уничтожены; следующие server instances работают на
  других HTTPS-адресах.
* Запрос направляется не другому Service Worker, а доступному Hamiltonian server.
  Текущий адрес выбирается из сохранённого и обновляемого списка участников.
* Неизменяемость Service Worker loader не означает неизменяемость его поведения:
  постоянная оболочка регистрирует события, загружает, проверяет и исполняет
  сменяемый функциональный выпуск внутри того же Service Worker execution.
* Для исполнения сменяемого JavaScript выбран `Function()`/`eval()`, а не
  динамический `import()`, поздний `importScripts()` или отдельный Blob Worker.
* Целевой loading path имеет вид: startup восстанавливает importers из cache или
  получает их через `fetch` → importers выбирают `internal`/`metafor` modules →
  loader получает, проверяет, сохраняет и запускает code. Internal RPC module
  отдельно открывает WSS для signaling, control и получения source addresses.
* WebRTC DataChannel не переносит исполняемый выпуск. Он принадлежит рабочему
  Oracle/Force transport, который устанавливается с помощью signaling
  ограниченного числа HTTPS Hamiltonian servers.
* HTTPS Hamiltonian servers совмещают installation seed, HTTP(S) code
  delivery/update и WSS signaling/control. Остальные server participants могут
  не иметь HTTPS ingress.
* Постоянство WSS означает непрерывную логическую связь через последовательность
  новых физических соединений, а не вечную жизнь одного socket.
* На следующем сетевом этапе internal RPC WSS переносит snapshot/delta списка
  HTTPS source/signaling peers. Каждый participant сохраняет проверенный список
  и регистрируется у новых peers.
* Web Push используется после долгого отсутствия WSS: он пробуждает Service
  Worker, после чего Worker обновляет список адресов и восстанавливает
  регистрацию в signaling-сети.
* В качестве базового кандидата рассматривается одна общесетевая VAPID key pair:
  private key реплицируется только между допущенными HTTPS signaling peers, а
  peers координируют отправку Push. Это технически допустимо; до принятия решения
  нужно определить admission, отзыв, rotation и аудит общей authority.
* Push не рассылается всем participants. HTTPS signaling peers выборочно будят
  только тех, кто давно не проявлялся в signaling-сети; security общей VAPID
  authority рассматривается как разрешимый отдельный контракт.
* Текущий этап ограничен устройством самой сети и распределением ответственности.
  Детальные протоколы взаимодействия и координации peers, включая выбор
  получателя Push и безопасность общей authority, будут подняты на следующем
  этапе и сейчас не должны задерживать определение сетевого механизма.
* Текущий исполняемый контур содержит один Hamiltonian HTTPS peer и множество
  браузеров. Множественные server peers остаются целевой архитектурой, но их
  координация и распределение VAPID authority в первую реализацию не входят.
* VAPID key pair является общей identity отправляющего Hamiltonian server, а не
  identity браузера. Разные Chrome profiles создают независимые subscriptions,
  и в текущем контуре этих subscription достаточно как идентификаторов и
  адресов browser participants; отдельная installation key pair не вводится.
* Для выборочной доставки server хранит соответствие `browser participant →
  PushSubscription`. Общий VAPID key только подтверждает отправителя; конкретный
  получатель определяется единственным endpoint, на который server отправил
  request.
* Минимальный browser loader уже разделён на HTML, `@startup/main`,
  `@startup/service`, `@import/main` и `@import/service`. Startup неизменяем и
  не знает modules; importers обновляемы и владеют их составом.
* В текущем контуре Service Worker startup получает importers через `fetch` или
  cache. `@import/service` выбирает первый `internal/rpc` module, а
  `@import/main` остаётся пустым до выбора первого реального Window module.
* Сменяемый browser release не является одним bundle: это целостно публикуемый
  набор частей для разных browser execution environments.
* Для каждого следующего шага сначала определяется задача-владелец. Найденный
  существующий номер используется только при совпадении договора и среды
  приёмки; место обнаружения и близость файлов сами по себе недостаточны.

## Минимальный browser loader текущего контура

Действующая граница материализована в `LOAD-001`:

1. Первый HTTPS response доставляет статические HTML, `@startup/main` и
   `@startup/service`.
1. `@startup/main` устанавливает Service Worker, дожидается управления страницей,
   отправляет `connect` и запускает `/import/main`.
1. `@startup/service` восстанавливает `/import/service` из cache `import` либо
   получает его через `fetch`, проверяет и запускает с универсальными loader
   primitives.
1. `@import/service` выбирает `/internal/rpc`; import-layer loader получает его
   через `fetch`, сохраняет в cache `internal` и запускает внутри Service Worker.
1. Загруженный RPC module открывает `/sw` к единственному известному peer и
   подтверждает двусторонний transport через повторяющийся `ping`/`pong`.
1. HTML/startup, importers и internal module восстанавливаются из независимых
   caches. Cache `metafor` появится лениво с первым module этой среды.

Каталог нескольких signaling peers, полный release manifest, hashes и атомарная
смена всего многосоставного выпуска в этот минимальный контур не входят.

## Gate размещения минимального browser loader

Проверены `ROADMAP.md`, `BACKLOG.md`, `TODO.md`, все открытые Hamiltonian/update
карточки, закрытые `MF-412`, `MF-428` и `UPD-001`, product-коммиты их механизмов,
текущие update/cache/Service Worker sources и Git-история `UPD-002`.

Найденная линия:

* `MF-412` доказала синтетический versioned module, Cache Storage и одинаковые
  bytes в нескольких runtime, но не production loader полного функционала;
* `MF-428` доказала browser-managed замену executable Service Worker и
  profile-scoped lifecycle, но не WSS-загрузку сменяемого Worker functionality;
* `UPD-001` только собрала прежние update-механизмы в `hamiltonian/update` и
  прямо потребовала отдельную следующую работу для нового механизма;
* `UPD-002` зарегистрирована коммитом `22a0be9c5`, а её первый срез — коммитом
  `0d6d4de20`; runtime result после них отсутствует. Её действующий договор
  предполагает сначала определить полный host-published release, затем cache,
  active switch и page reload.

Новое требование отличалось причинно: сначала был нужен самостоятельно
принимаемый loader `startup → import → internal/metafor`. В реализованном
one-signaling-peer контуре code bytes получает import-layer loader через
`fetch`, а загруженный internal RPC module открывает WSS. Это initial loading и
отдельный acceptance result, а не первый manifest slice уже определённого
полного выпуска.

Владелец принял отдельное размещение и точный номер `LOAD-001`. Задача
регистрируется перед `UPD-002`; прежняя `UPD-002.1` останавливается до
implementation без переписывания её истории, а `UPD-002` ждёт доказанного
minimal loader result.

## Проверенные ограничения Web-платформы

Ограничения сверены 14 августа 2026 года с действующими спецификациями:

* [Service Workers](https://w3c.github.io/ServiceWorker/v1/) задаёт origin-bound,
  событийный и прерываемый браузером Worker; при загрузке script обновления
  request получает `service-workers mode: none`;
* [WebRTC](https://w3c.github.io/webrtc-pc/) экспонирует
  `RTCPeerConnection` только в `Window`, оставляет signaling внешнему каналу и
  требует новый signaling exchange для renegotiation и ICE restart. ICE
  candidates могут быть host, server-reflexive, peer-reflexive или relay;
  browser ограничивает раскрытие адресов ради privacy, поэтому candidate address
  является transport metadata, а не device identity;
* [RFC 8445 — ICE](https://www.rfc-editor.org/rfc/rfc8445.html) определяет
  candidates как transport addresses для NAT traversal, а
  [RFC 8828](https://www.rfc-editor.org/rfc/rfc8828.html) — browser policies,
  ограничивающие раскрытие IP addresses из-за privacy и fingerprinting;
* [Web Application Manifest](https://w3c.github.io/manifest/) ограничивает
  navigation scope одним origin и связывает browser identity приложения с
  same-origin `start_url`.
* [Fetch](https://fetch.spec.whatwg.org/#http-cors-protocol) разрешает server
  явно открыть cross-origin response через CORS;
* [Content Security Policy](https://w3c.github.io/webappsec-csp/#directive-connect-src)
  применяет `connect-src` к `fetch()` и WebSocket connections.
* [HTML](https://html.spec.whatwg.org/multipage/webappapis.html#hostloadimportedmodule)
  запрещает динамический `import()` в `ServiceWorkerGlobalScope`, а
  [Workers](https://html.spec.whatwg.org/multipage/workers.html#worker) не
  экспонирует конструктор `Worker` в этом global scope;
* [WebSocket](https://websockets.spec.whatwg.org/) экспонируется в Worker и
  разрешает произвольный `ws:`/`wss:` URL; CORS к handshake не применяется,
  но browser отправляет `Origin`, который remote server обязан проверять;
* [CSP](https://w3c.github.io/webappsec-csp/#can-compile-strings) применяет
  `script-src 'unsafe-eval'` к `eval()` и `Function()`.
* [Push API](https://w3c.github.io/push-api/) запускает неработающий Service
  Worker для доставки Push; options существующей subscription неизменяемы, а
  `applicationServerKey` требует соответствующий private key отправителя. Push
  endpoint уникально определяет одну subscription; сама subscription имеет
  собственные `p256dh` key pair и `auth` secret и может быть обновлена browser с
  заменой endpoint и ключей.
* [RFC 8292 — VAPID](https://www.rfc-editor.org/rfc/rfc8292.html) задаёт
  application-server identity: ограниченная публичным VAPID-ключом subscription
  принимает request с JWT, подписанным соответствующим private key.
* [Chrome Help — multiple profiles](https://support.google.com/chrome/answer/2364824)
  подтверждает, что Chrome profiles хранят browser data раздельно; следовательно,
  их origin-bound Service Worker registrations и PushSubscription не являются
  одной общей установкой Hamiltonian.

В терминах Push API `application server` — это сервер, отправляющий Web Push.
Поэтому `applicationServerKey` в нашей схеме является публичной половиной VAPID
key pair Hamiltonian, а не ещё одним ключом сверх VAPID. Browser-generated
ключи шифрования конкретной PushSubscription (`p256dh` и `auth`) относятся к
шифрованию payload; скрытый browser private key не выдаётся Hamiltonian и не
реплицируется. TLS certificate/key HTTPS server образуют третью, независимую
группу ключей.

Один и тот же VAPID private key технически может храниться у нескольких
доверенных отправителей. Push service не знает, какой именно HTTPS peer сделал
подпись: для него все такие peers представляют одну application-server
authority. Поэтому при ограниченном доверенном наборе HTTPS Hamiltonian peers
репликация общего VAPID private key является допустимой базовой схемой, а не
ограничением Web Push. Её цена — общий радиус компрометации и невозможность
отозвать один скопированный ключ без rotation общей пары и новой PushSubscription.

Из этого следует разделение двух identity:

* browser identity установленной PWA остаётся привязана к исходному HTTPS
  origin, даже когда исходный server больше не работает;
* logical identity участника Hamiltonian не должна выводиться из временного URL
  и может сохраняться при получении новых transport-адресов.

Service Worker может хранить и выдавать уже подготовленный functional release.
Для code delivery ему не требуется Window или WebRTC bridge: importer вызывает
`fetch` к выбранному HTTPS Hamiltonian source, проверяет response и сохраняет
его в origin-bound storage. Если source находится на другом origin, remote
server должен вернуть подходящий `Access-Control-Allow-Origin`; opaque
`no-cors` response для проверяемого исполняемого выпуска не подходит. При
передаче authorization headers server также должен обслужить CORS preflight.

WSS не переносит code bytes. Его открывает уже загруженный internal RPC module
для signaling, control и получения следующих source addresses.

## Сменяемый функционал внутри Service Worker

Web-платформа не запрещает исполнять полученный source text в Service Worker
вообще. При разрешающей CSP оболочка может скомпилировать уже проверенный текст
через `Function()` или `eval()` и сохранить предоставленные им функции в своей
таблице обработчиков. Это отдельный механизм от browser-managed обновления
Service Worker script и поэтому не противоречит `HAM-004-R17`.

Постоянная оболочка обязана зарегистрировать `install`, `activate`, `fetch`,
`message` и все другие нужные типы событий при самой первой оценке своего
script. Сменяемый выпуск предоставляет только функции, которым эти стабильные
обработчики передают события. Добавлять новый тип события поздним загруженным
кодом нельзя считать надёжным: браузер фиксирует обслуживаемые типы событий при
первой оценке Worker.

Blob URL не даёт отдельного исполняемого Worker внутри Service Worker. Рабочий
вариант — получить bytes, проверить release, преобразовать его в source text и
скомпилировать в текущем `ServiceWorkerGlobalScope`. После остановки браузером
память пропадает, поэтому при следующем событии оболочка должна прочитать
активный release из Cache Storage или IndexedDB, снова проверить его identity и
восстановить таблицу функций до обработки события.

Целевой сетевой путь разделяет обязанности. Cross-origin internal RPC WSS служит
для discovery/control и сообщает source addresses; `fetch` получает code bytes.
После проверки подписи/hash Worker атомарно сохраняет полный release и только
затем меняет активную таблицу функций. Точные source-address protocol, ABI
выпуска и правило переключения между старой и новой таблицами ещё не выбраны.

WebRTC DataChannel используется отдельно для рабочего Oracle/Force transport.
HTTPS Hamiltonian server даёт signaling, необходимый для установления такой
связи с server participants без собственного HTTPS ingress, но не переносит
обычный Oracle/Force payload после установления прямого DataChannel.

Cross-origin WSS сам по себе не является небезопасным. `wss:` даёт TLS-защиту и
проверку remote server certificate; `Origin` позволяет server отвергнуть чужое
browser-приложение. Этого недостаточно для identity Hamiltonian: browser
`WebSocket` API не позволяет произвольно добавить `Authorization` header,
поэтому после соединения нужен протокольный challenge-response со стабильным
ключом участника и защитой от replay. Долгоживущий secret нельзя считать
безопасным только потому, что он помещён в URL, cookie или subprotocol.

## Доказанное пробуждение для восстановления RPC WSS

Прототип Hamiltonian подтверждает нужный lifecycle: Web Push пробуждает тот же
зарегистрированный Service Worker без открытой Hamiltonian Page, Worker
восстанавливает control startup из Cache Storage и открывает новый WSS.
Причинность reconnect защищена одноразовыми `wakeId` и скрытым `wakeProof`.

В принятом clean-опыте Chrome 151 при `0` Hamiltonian Page/Window clients и
сохранённом пустом окне Chrome reconnect занял `803 ms`; WSS прожил `40.046 s`
и подтвердил четыре heartbeat ACK. Поэтому остановка прежнего Worker/WSS не
является препятствием для восстановления internal RPC/signaling после Push.

Граница доказательства также уже измерена: heartbeat не удержал один Worker
execution навсегда, и за следующие `250.840 s` новый socket без Push не появился.
При полном закрытии всех окон Chrome тот же browser process дважды не доставил
Push до TTL. Следовательно, `40.046 s` — наблюдавшаяся жизнь одного физического
WSS, а не гарантированный браузером бюджет. Постоянный механизм имеет два слоя:
обычный WSS reconnect поддерживает логическое присутствие, пока execution жив;
`Push → wake → новый WSS → address sync` возвращает participant после сна.

Evidence закреплено постоянным контрактом
[`hamiltonian/README.md`](../../hamiltonian/README.md), результатом
`b53e057346` и closing-коммитом `0e1e17b490`.

* предложение исправлений карточек, зависимостей, приоритетов и новых задач.

Не входит до отдельного решения владельца:

* изменение runtime, HTML, Service Worker, Bun processes или transport;
* запуск реализации одной из затронутых задач;
* автоматический выбор release authority, storage или network carrier;
* объявление локального испытания доказательством межустройственной работы;
* создание новых задач до завершения ревизии и решения владельца.

## Критерии готовности

* Все требования текущего обсуждения имеют устойчивый ID, точную формулировку и
  различимое состояние.
* Для каждого требования указаны evidence, постоянный владелец и текущее
  фактическое покрытие либо разрыв.
* Все открытые связанные задачи перечитаны и сведены в матрицу покрытия без
  изменения их смысла молча.
* Все противоречия и неоднозначные владельцы предъявлены владельцу и получили
  явное решение.
* Владелец утвердил, какие карточки изменить, какие задачи создать и в каком
  порядке расположить работу.
* Принятые изменения документов, карточек и графа зафиксированы отдельными
  project-коммитами; product-код не изменён.
* Карточка содержит достаточный handoff, чтобы продолжить обсуждение без
  скрытой истории чата.

## Проверка результата

* Перечитать карточку после каждого обсуждения и убедиться, что новое требование
  отражено до перехода к следующему вопросу.
* Проверить ссылки, уникальность номера и отсутствие `HAM-004` одновременно в
  `BACKLOG.md` и `TODO.md`.
* Выполнить `git diff --check` для каждого project-коммита.
* Перед итоговой ревизией повторно сверить `docs/README.md`, `ROADMAP.md`,
  `BACKLOG.md`, `TODO.md`, связанные карточки, code/public contracts/tests и
  существенную Git-историю.
* Финальную матрицу и очередь считать принятыми только после owner review.

## Текущее состояние и следующий шаг

`HAM-004` остаётся в `DRAFT` для будущей распределённой сети, authority и
server-side loading. Browser-граница уже материализована в `LOAD-001` как
`startup → import → internal/metafor`: code bytes загружаются через `fetch`, а
WSS принадлежит internal RPC. Автоматизированный browser regression доказал
первую установку, точные caches и cold restoration в изолированном профиле;
canonical live owner acceptance и решение о первом Window/Metafor module
остаются в `LOAD-001`.

`UPD-002` ждёт завершения этой зависимости и затем определяет атомарную смену
многосоставного набора `import`/`internal`/`metafor`, не включая неизменяемый
startup и не возвращая WSS code delivery. Product-код в `HAM-004` не изменяется.
