# HAM-004 — Собрать целостные требования к Hamiltonian

## Коротко

Все требования к загрузке, размещению, запуску, обновлению и сетевой работе
Hamiltonian сначала собираются и согласуются в одной карточке. После этого
открытые задачи будут пересмотрены, а владелец определит, что исправить, в каком
порядке выполнять работу и какие отдельные задачи ещё нужны.

## Зачем

Исходная архитектура обсуждалась в нескольких сессиях и затем частями попала в
`MF-411`, `MF-425`, `UPD-002`, `HAM-003`, `MF-414`, `MF-426` и другие карточки.
Из-за этого широкое требование к Hamiltonian было сужено до отдельных механизмов,
например только обновления браузерной сборки, тогда как владелец требует также
первичную загрузку исполняемого кода и дальнейшую работу в распределённой сети.

Эта карточка нужна как единственное место предметного обсуждения до изменения
графа исполнения. Она не заменяет постоянные документы-владельцы и не является
разрешением начинать реализацию.

## Связь с дорожной картой

Карточка уточняет направление
[`Hamiltonian и воплощения`](../ROADMAP.md#hamiltonian-и-воплощения) и линию
[`Обновления Hamiltonian`](../ROADMAP.md#обновления-hamiltonian). Она должна
согласовать три последовательных этапа дорожной карты: одну Вселенную на одном
устройстве, ту же Вселенную на нескольких устройствах и только затем несколько
Вселенных.

Крупное направление пока не изменяется. После сбора требований владелец отдельно
решит, какие формулировки должны перейти в постоянный документ Hamiltonian,
`ROADMAP.md`, действующие карточки и граф исполнения.

согласовать несколько самостоятельных владельцев, механизмов и сред приёмки.
Он не является подзадачей одной из перечисленных карточек и после обсуждения
может независимо завершиться согласованной картой изменений проектных задач.

## Подтверждённые факты

* Первый запрос нового браузера не может обслужить ещё не установленный Service
  Worker, поэтому Bun-часть обязана вернуть минимальный HTML/bootstrap.
* Текущие `GET /` и `GET /index.html` возвращают HTML из
  `hamiltonian/public/index.html` через `handleNavigation()`.
* Настоящие `app.js`, orchestration, CSS и browser Worker сейчас загружаются
  напрямую с host; Service Worker обслуживает из release cache только
  `/versions/...`.
* Действующий versioned module является испытательным `createEmbodiment()`, а не
  полным выпуском функционала Hamiltonian.
* `MF-412` доказала один Service Worker control socket, SHA-256 проверку,
  Cache Storage, Window/Dedicated Worker/Bun execution и физический Android
  контур без переноса production-кода MetaFor.
* `MF-428` доказала browser-managed обновление самого Service Worker с
  сохранением logical identity и новой execution incarnation.
* `UPD-002` уже зафиксировала разрыв: полный browser release ещё не принадлежит
  единому Service Worker release path, а server release оставлен будущей работой.
* Межустройственная доставка выпуска и догоняющее обновление после offline пока
  являются целевым направлением, а не доказанным runtime.

уточнение владельца должно быть внесено сюда или в раздел решений до перехода к
следующему вопросу. Формулировка получает новое состояние только по явному
решению владельца.

| ID | Состояние | Требование |
| --- | --- | --- |

| HAM-004-R2 | ПОДТВЕРЖДЕНО ИСТОРИЕЙ | Bun host, Service Worker и Window bootstrap являются частями одного распределённого Hamiltonian; позднее такие части работают и на других устройствах. |
| HAM-004-R3 | ПОДТВЕРЖДЕНО ИСТОРИЕЙ | Платформенные операции различаются, но смысловая ответственность Hamiltonian за подготовку и запуск точного кода сохраняется во всех средах. |
| HAM-004-R4 | ПРИНЯТО | Первая HTML-страница является только минимальным входом: она устанавливает или подключает Service Worker и передаёт ему дальнейшую загрузку браузерного выпуска. |
| HAM-004-R5 | ПРИНЯТО | Первичная загрузка и последующее обновление не образуют независимые системы: оба случая используют один release lifecycle, но с разной исходной локальной версией. |
| HAM-004-R6 | ПОДТВЕРЖДЕНО ИСТОРИЕЙ | Исполняемые части, включая Dark, не выбирают версию кода; Hamiltonian готовит точный выпуск и требует повторный запрос или новое воплощение. |
| HAM-004-R7 | ПОДТВЕРЖДЕНО ИСТОРИЕЙ | Стабильные части Hamiltonian остаются тонкими; заменяемый функционал поставляется версионным выпуском, а не встраивается в них целиком. |
| HAM-004-R8 | ПОДТВЕРЖДЕНО ИСТОРИЕЙ | Серверная часть выполняет тот же смысловой loading/update lifecycle через подходящие Bun/OS-process механизмы, а не через буквальный browser Service Worker API. |
| HAM-004-R9 | ЦЕЛЬ ВЛАДЕЛЬЦА | В распределённой сети точный функциональный выпуск должен распространяться между участвующими устройствами; конкретные authority, carrier и recovery ещё не выбраны. |
| HAM-004-R10 | ПОДТВЕРЖДЕНО ИСТОРИЕЙ | Hamiltonian выполняет bootstrap, code delivery, размещение, signaling и перевоплощение, но не остаётся посредником обычного Oracle/Force realtime после знакомства частей. |
| HAM-004-R11 | ПРИНЯТО | До начала прикладной работы участник должен установить свою identity кода и при необходимости перейти на требуемый выпуск. |
| HAM-004-R12 | ЦЕЛЬ ВЛАДЕЛЬЦА | Первичная установка PWA получает минимальный loader с временного HTTPS seed; после успешной установки доступность функционального кода и его обновлений не должна зависеть от продолжения работы этого seed. |
| HAM-004-R13 | ЦЕЛЬ ВЛАДЕЛЬЦА | Участники Hamiltonian обмениваются актуальными адресами доступных HTTPS seed и добавляют новые адреса по мере их появления. |
| HAM-004-R14 | ОГРАНИЧЕНИЕ WEB-ПЛАТФОРМЫ | Service Worker registration, scope, storage и установленная PWA привязаны к исходному origin; другой HTTPS origin не переносит и не продолжает эту browser identity автоматически. |
| HAM-004-R15 | ТЕХНИЧЕСКИ ДОПУСТИМО | Уже установленная PWA может получить функциональный выпуск от другого HTTPS endpoint или peer, проверить его и сохранить под своим исходным origin; новый endpoint является transport/source, а не новым origin приложения. |
| HAM-004-R16 | ОГРАНИЧЕНИЕ WEB-ПЛАТФОРМЫ | `RTCPeerConnection` доступен Window, а Service Worker является событийным и может быть остановлен браузером; постоянное peer-соединение нельзя возлагать только на Service Worker execution. |
| HAM-004-R17 | ОГРАНИЧЕНИЕ WEB-ПЛАТФОРМЫ | Peer-delivered функциональный выпуск не заменяет код самого Service Worker: browser-managed update Worker повторно получает script с его same-origin URL, минуя действующий Worker. |
| HAM-004-R18 | СЛЕДСТВИЕ | Новый пользователь может установить PWA с любого действующего HTTPS seed и присоединиться к той же логической сети Hamiltonian, но браузер считает установку с другого origin отдельной PWA и отдельным Service Worker scope. |

## Решения владельца

* Создать отдельную `HAM-004 — Собрать целостные требования к Hamiltonian`.
* На текущем этапе только обсуждать и фиксировать требования; не начинать
  реализацию.
* Каждое уточнение из последующих обсуждений сразу отражать в этой карточке,
  чтобы оно не оставалось только в истории чата.
* После сбора требований пересмотреть все открытые связанные задачи, определить
  необходимые исправления, зависимости и очередь запуска.
* Новые задачи создавать только после этой ревизии и отдельного решения
  владельца.
* Цель временного HTTPS seed — один раз доставить устанавливаемый browser loader;
  после установки функциональные выпуски должны быть доступны через другие
  действующие части распределённого Hamiltonian.

## Проверенные ограничения Web-платформы

Ограничения сверены 14 августа 2026 года с действующими спецификациями:

* [Service Workers](https://w3c.github.io/ServiceWorker/v1/) задаёт origin-bound,
  событийный и прерываемый браузером Worker; при загрузке script обновления
  request получает `service-workers mode: none`;
* [WebRTC](https://w3c.github.io/webrtc-pc/) экспонирует
  `RTCPeerConnection` только в `Window`;
* [Web Application Manifest](https://w3c.github.io/manifest/) ограничивает
  navigation scope одним origin и связывает browser identity приложения с
  same-origin `start_url`.

Из этого следует разделение двух identity:

* browser identity установленной PWA остаётся привязана к исходному HTTPS
  origin, даже когда исходный server больше не работает;
* logical identity участника Hamiltonian не должна выводиться из временного URL
  и может сохраняться при получении новых transport-адресов.

Service Worker может хранить и выдавать уже подготовленный functional release,
но сам WebRTC DataChannel должен жить в активном Window либо во внешней
Bun-части. Полученные там bytes можно передать локальному release/cache
механизму. Точный владелец этого bridge ещё должен быть выбран.

## Предварительная карта покрытия

Карта не изменяет границы перечисленных задач. Она показывает, где при будущей
ревизии искать существующее покрытие и разрывы.

| Область требования | Текущий владелец или кандидат | Известный разрыв |
| --- | --- | --- |
| Общий смысл, identity и authority Hamiltonian | `MF-411` | закон ещё не закрыт и должен включить loading lifecycle без сведения Hamiltonian к серверу обновлений |
| Одна Вселенная на одном устройстве | `MF-425` | необходимо согласовать Bun, Service Worker и Window как одно целое |
| Полный браузерный выпуск | `UPD-002` | карточка описывает обновление, но должна быть проверена на полный первичный loading path |
| Физические границы кода | `HAM-003` | структурный refactor не должен заранее решать предметный loading/update contract |
| Места исполнения и active copy | `MF-414` | зависит от общего закона `MF-411` |
| Несколько устройств | `MF-426` | artifact delivery, offline catch-up и release authority не доказаны |
| Прямой рабочий transport | `MF-410` | должен оставаться отделён от control/code delivery Hamiltonian |
| Source history, promotion и rollback | `MF-402` | не заменяет runtime release lifecycle; точная связь ещё не выбрана |

## Порядок обсуждения

1. По одному сформулировать простые проверяемые требования к первому HTML и
   browser bootstrap.
1. Зафиксировать общий контракт выпуска: состав, identity, проверка, хранение,
   активация и повторный запуск.
1. Отдельно определить поведение Window main, Dedicated Worker и Service Worker.
1. Отдельно определить серверную загрузку, запуск и замену Bun OS processes.
1. Определить discovery, delivery, authority и recovery для нескольких устройств.
1. Установить границу Hamiltonian с Oracle/Force realtime и source/Git lifecycle.
1. Сверить каждое принятое требование с owner docs, public contracts, кодом,
   проверками и всеми открытыми задачами.
1. Предъявить владельцу матрицу `требование → существующее покрытие → конфликт →
   изменение карточки или новая задача`.
1. Только после решения владельца изменить зависимости, приоритеты и очередь в
   `TODO.md`, а также зарегистрировать недостающие задачи.

## Поведение процесса

* Текущий этап — сбор и согласование требований в состоянии `DRAFT`.
* Обсуждается один вопрос за раз; после ответа владельца карточка обновляется до
  следующего вопроса.
* Новая формулировка не стирает подтверждённое решение молча: противоречие
  отмечается, после решения актуальный закон заменяет прежний, а историческая
  версия сохраняется только когда объясняет отказ.
* Факт текущего кода, историческое решение, целевая архитектура и предложение
  исполнителя отмечаются разными состояниями.
* Пока реестр требований не согласован, `ROADMAP.md`, `TODO.md` и связанные
  карточки не перераспределяются.
* Каждое принятое изменение карточки или проектного графа фиксируется отдельным
  project-коммитом до следующего этапа или реализации.
* Реализация, запуск runtime и изменение product-кода в границы HAM-004 не входят.

* Каков точный минимальный HTML и когда первая страница обязана перейти под
  управление Service Worker?
* Какие файлы и entrypoints образуют один полный browser release?

  declarations и прямые transports после обновления?
* Какой постоянный реестр действительно нужен и в каком месте; SQLite, JSON или
  иной формат пока не выбран.
* Какие существующие задачи нужно уточнить, какие зависимости изменить и какие
  самостоятельные задачи создать после согласования требований?

## Границы

Входит:

* фиксация требований и решений владельца;
* evidence-backed сверка с историей, документацией, кодом и проверками;
* последующая ревизия всех открытых задач, связанных с Hamiltonian;
* предложение исправлений карточек, зависимостей, приоритетов и новых задач.

Не входит до отдельного решения владельца:

* изменение runtime, HTML, Service Worker, Bun processes или transport;
* запуск реализации одной из затронутых задач;
* автоматический выбор release authority, storage или network carrier;
* объявление локального испытания доказательством межустройственной работы;
* создание новых задач до завершения ревизии и решения владельца.

## Критерии готовности

* Все требования текущего обсуждения имеют устойчивый ID, точную формулировку и
  различимое состояние.
* Для каждого требования указаны evidence, постоянный владелец и текущее
  фактическое покрытие либо разрыв.
* Все открытые связанные задачи перечитаны и сведены в матрицу покрытия без
  изменения их смысла молча.
* Все противоречия и неоднозначные владельцы предъявлены владельцу и получили
  явное решение.
* Владелец утвердил, какие карточки изменить, какие задачи создать и в каком
  порядке расположить работу.
* Принятые изменения документов, карточек и графа зафиксированы отдельными
  project-коммитами; product-код не изменён.
* Карточка содержит достаточный handoff, чтобы продолжить обсуждение без
  скрытой истории чата.
