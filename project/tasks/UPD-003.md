# UPD-003 — Синхронизировать пакетные сборки по среде и состоянию кэша

## Коротко

Один package можно будет импортировать по одному имени, но собирать отдельно
для Window, browser Worker, Service Worker, Bun server и server Worker. При
обновлении Service Worker покажет host фактическое содержимое своих постоянных
кэшей, получит только необходимые изменения и применит их через одну
восстанавливаемую транзакцию без отдельного active manifest.

## Зачем

Доказанный checkpoint `UPD-002` уже доставляет browser packages по
каноническим package URL и раскладывает их по owner caches, но дальнейшая
проверка владельца открыла четыре связанных ограничения другого договора:

* один package пока имеет только одну browser-сборку и не может явно выбрать
  разные entrypoints для разных сред выполнения;
* env отсутствует в identity cache entry, поэтому разные сборки одного package
  нельзя хранить и проверять независимо;
* host передаёт Worker готовый package state с `endpoint` и `cache`, хотя URL и
  cache owner однозначно выводятся из package name, env и namespace;
* постоянный cache `release` одновременно хранит code и
  `/code?state=active`, а прерванная попытка использует несколько
  `*:release:<uuid>` caches. Из-за этого техническое состояние дублирует
  фактическое содержимое постоянных caches и оставляет лишние storages.

Параллельно действующая host publication пишет child manifests раньше root
manifest. Владелец выбрал обратную модель: root `hamiltonian/package.json`
сначала фиксирует намерение, а после остановки server по нему восстанавливает
несошедшиеся child versions и artifacts.

## Связь с дорожной картой

Это следующий отдельный этап линии
[`Обновления Hamiltonian`](../ROADMAP.md#обновления-hamiltonian) после
[`UPD-002 — Обновлять всю клиентскую сборку через Service
Worker`](UPD-002.md). `UPD-002` остаётся владельцем уже доказанного
checkpoint `startup → release → internal`, package SemVer, canonical package
URL, namespace owner caches, development artifacts и diagnostics.

`UPD-003` меняет не отдельную ошибку этого checkpoint, а следующий package и
transaction contract: env-aware builds, cache-derived current state,
delta-only server response, один transaction cache и root-first recovery.
Поэтому работа вынесена в самостоятельную задачу по прямому решению владельца,
а не добавлена correction-подзадачей `UPD-002`.

## Подтверждённые факты

На baseline `88631dbf63b1faa862d93881c56290e749a436c7`:

* `@startup/main` выполняет `import("@release/main")`, но не объявляет
  `@release/main` в своих `dependencies`.
* `@startup/service` загружает `@release/service`, но не объявляет его в
  `dependencies`.
* `@release/service` импортирует Loader-типы относительным путём через границу
  package из `../../startup/service/loader`.
* `@internal/visual`, `@release/main`, `@release/service` и startup packages
  имеют по одному build entrypoint и одному `dist/index.js`.
* `artifact.cache` дублирует cache owner, уже выводимый из namespace
  `@startup`, `@release`, `@internal` или `@metafor`.
* Server кеширует найденный `PackageOwner` вместе со значениями `build`,
  `cache` и `headers`, прочитанными из `package.json`; последующее изменение
  manifest не видно этому объекту без перезапуска процесса.
* Browser release state содержит передаваемые host поля `endpoint` и `cache`.
* Постоянный `release` cache хранит `/code?state=active` и
  `/code?state=pending` рядом с code responses.
* Одна попытка обновления создаёт отдельные
  `<owner>:release:<crypto.randomUUID()>` caches.
* Host сейчас сначала записывает новые exact versions в child manifests, затем
  последним записывает root caret dependencies.

## Решения владельца

### 1. Одно имя package, разные среды выполнения

Source во всех средах использует только bare package specifier, например:

```ts
await import("@internal/visual")
```

Env не добавляется в import specifier и не становится package subpath.
Одинаковый specifier должен разрешаться в нужный source entrypoint выбранной
средой сборки.

Package объявляет entrypoints стандартным полем `exports` корневого subpath
`"."`. Имена сред являются project conditions внутри стандартного conditional
exports mechanism; отдельное custom-поле manifest для artifact type не
создаётся:

```json
{
  "exports": {
    ".": {
      "metafor:main": {
        "types": "./main.ts",
        "browser": "./main.ts"
      },
      "metafor:worker": {
        "types": "./worker.ts",
        "browser": "./worker.ts"
      },
      "metafor:service-worker": {
        "types": "./service-worker.ts",
        "browser": "./service-worker.ts"
      },
      "metafor:server": {
        "types": "./server.ts",
        "bun": "./server.ts"
      },
      "metafor:server-worker": {
        "types": "./server-worker.ts",
        "bun": "./server-worker.ts"
      }
    }
  }
}
```

Package объявляет только реально поддерживаемые им branches. Обязательного
`default` fallback нет: сборка в неподдерживаемой или неуказанной среде должна
завершиться ошибкой разрешения, а не молча выбрать чужой entrypoint.

Текущие канонические env:

| Env | Место исполнения | Build target |
| --- | ---------------- | ------------ |
| `main` | Window main realm | `browser` |
| `worker` | browser Dedicated Worker | `browser` |
| `service-worker` | browser Service Worker | `browser` |
| `server` | основной Bun server process | `bun` |
| `server-worker` | Worker, созданный Bun server | `bun` |

`server` и `server-worker` различаются обязательно: одинаковый Bun target не
означает одинаковый lifecycle, globals или entrypoint. Будущие точные среды
вроде `shared-worker`, `audio-worklet` и `paint-worklet` можно добавить новыми
conditions; эта задача их не вводит.

Builder выбирает ровно одну project condition
`--conditions=metafor:<env>` и соответствующий target. TypeScript package check
использует ту же condition через `customConditions`. Если package имеет
несколько env entrypoints, каждый env является отдельной build и typecheck
единицей; одна резолюция не пытается одновременно выбрать несколько branches.

### 2. Версия и identity env artifact

SemVer принадлежит package целиком, а не отдельному env. Если изменился хотя бы
один опубликованный env package, package получает новую версию. Для этой версии
должны существовать все объявленные и входящие в выпуск env artifacts; env с
неизменившимися bytes можно безопасно переиспользовать при публикации новой
версии, но нельзя оставить выпуск частично собранным.

Package, который не изменялся, не получает новую версию, не пересобирается и не
перекладывается в browser cache. Полная composition нужна для сравнения и
удаления, а не для механической замены неизменившихся entries.

Точная identity одного artifact:

```text
package name + env + package version + SHA-256 + byte size
```

Для browser-delivered artifact pathname остаётся одним каноническим package
path. Env передаётся query parameter, а не сегментом пути:

```text
стабильный: /@internal/visual?env=main
точный:     /@internal/visual?env=main&version=0.1.3
```

Один общий helper обязан одинаково строить и разбирать URL на server, в
Service Worker и в tests. Порядок и набор query parameters каноничны; разные
строки не должны обозначать одну identity.

Browser Cache Storage применяется только к browser env
`main | worker | service-worker`. `server` и `server-worker` входят в package
resolution/build law, но их живые Bun processes и artifacts не становятся
browser cache entries и не обновляются Service Worker в этой задаче.

### 3. Никаких передаваемых endpoint, cache owner и дополнительных ID

`endpoint` не хранится и не передаётся в package state, RPC request, RPC
response, transaction intent или server plan: он всегда выводится общим URL
helper из package name, env и version.

`artifact.cache` удаляется из package manifests и public contracts. Owner
постоянного cache выводится из namespace:

* `@startup/*` → `startup`;
* `@release/*` → `release`;
* `@internal/*` → `internal`;
* `@metafor/*` → `metafor` после отдельного включения этой namespace.

Дополнительный `artifact.type` не вводится. `artifact.headers` может остаться
только для HTTP delivery properties, которые нельзя вывести из env или
namespace; headers не являются маркером среды.

Отдельные `releaseId`, `generation`, transaction UUID и Worker incarnation для
этого release protocol не вводятся. Package versions, env, digest, фактическое
содержимое canonical caches и наличие фиксированного transaction cache дают
все необходимые признаки.

### 4. Полный desired state принадлежит server, фактический current state — Worker

После успешной host publication server отправляет по существующему release RPC
только сигнал `release-changed` без package list, versions, endpoints и старого
state. Несколько сигналов разрешено объединить: сигнал означает только
«проверь текущее состояние сейчас» и поэтому не может нести устаревший release.

При сигнале, новом RPC connection и восстановлении прерванной транзакции
Service Worker динамически собирает полный current state из постоянных
canonical code caches и отправляет server по одной записи на фактически
найденный browser artifact:

```text
package name, env, version, SHA-256, byte size
```

Server читает актуальный root intent, child manifests, dependency graph и
published artifacts, сравнивает их с current state Worker и отвечает только
операциями:

```text
update: package name, env, version, SHA-256, byte size
remove: package name, env, version
```

Полный `desired` list не возвращается. Unchanged entries в ответ не входят.
URL, cache owner, release ID и transaction ID не входят ни в одну операцию.
Server не хранит и не replay-ит прежние package-state notifications; после
reconnect всегда выполняется новая сверка с текущими root и caches.

Server определяет removal сравнением полного желаемого состава и dependency
closure с полным current state Worker. Удаление package не требует отдельного
вида release и не заставляет заново заменять остальные packages.

### 5. Одна фиксированная browser-транзакция

На origin существует не более одного технического Cache Storage с точным
именем `transaction`. Owner-specific `release:<uuid>` caches не создаются.

Первой операцией обновления Worker открывает `transaction` и сразу записывает
полученный server delta под ключом `/code?state=active`. Внутри transaction
cache эта запись означает выполняемое намерение, а не отдельное постоянное
описание уже активного release. Только после неё разрешено начинать network
fetch и записи code responses.

Успешный порядок:

1. Worker получает server delta.
2. Worker первой записью сохраняет delta в
   `transaction[/code?state=active]`.
3. Worker fetch-ит только `update` artifacts и проверяет package name, env,
   version, SHA-256 и byte size.
4. Worker сохраняет подготовленные responses в `transaction`; неизменившиеся
   canonical entries не копируются.
5. После полной проверки Worker переносит только изменившиеся entries в
   namespace owner caches и удаляет только указанные `remove` либо прежние
   версии обновлённых `(package, env)` slots.
6. Во всех canonical owner caches остаётся не более одной exact entry на
   `(package, env)` действующего состава.
7. Последней commit-операцией Worker удаляет Cache Storage `transaction`.
8. После commit Worker выполняет один предусмотренный reload управляемых
   Window.

Постоянного `/code?state=active` и `/code?state=pending` больше нет ни в
`release`, ни в другом code cache. Действующий current state собирается из
canonical entries динамически. Пока `transaction` существует, loader не
собирает и не запускает новый release из частично изменённых owner caches;
существующие JavaScript realms продолжают работать, а новый startup ждёт
завершения либо восстановления транзакции.

Если Worker остановлен после любой промежуточной записи, новый Worker видит
фиксированный `transaction`, заново собирает current state canonical caches,
сверяется с текущим server desired state и продолжает или пересобирает delta.
Частично подготовленные bytes можно переиспользовать только после повторной
проверки exact identity. Успех определяется отсутствием `transaction`, поэтому
UUID и incarnation для восстановления не нужны.

Разные Chrome profiles не делят Cache Storage origin между собой: каждый
profile независимо имеет собственные canonical caches и не более одной своей
транзакции.

### 6. Root manifest сначала фиксирует host-намерение

`hamiltonian/package.json` является единственным host intent и recovery source.
Отдельные release manifest, journal, `generation` и `releaseId` не создаются.

Обычная публикация выполняется в таком порядке:

1. Host перечитывает manifests, валидирует входной request, полный membership и
   dependency graph, затем вычисляет target package versions.
2. Host сохраняет прежние root dependency values в памяти текущей операции и
   атомарно записывает target caret versions в root
   `hamiltonian/package.json` до typecheck, build и artifact publication.
3. Host выполняет необходимые checks/builds только для изменяемых packages;
   для новой версии package материализует все его опубликованные env artifacts.
4. После полного успеха artifacts host атомарно обновляет exact versions только
   изменившихся child package manifests.
5. Host перечитывает root, children и artifacts и доказывает их схождение,
   включая digest и size каждого env.
6. Только после схождения server открывает новый state для delivery и отправляет
   один `release-changed` signal.

Если обычная операция завершилась ошибкой в том же процессе, host атомарно
возвращает прежние root dependency values, сохраняет прежние child versions и
published state, возвращает caller текущий failure response с результатами и
не отправляет сигнал.

После аварийной остановки server до открытия package routes сравнивает root
intent с child exact versions и immutable env artifacts. Любое расхождение
считается незавершённой host-транзакцией: необходимые checks, builds,
publication и child writes выполняются заново до схождения. Пока состояние не
сошлось, server не выдаёт его Worker и не отправляет `release-changed`.
Неустранимая recovery error оставляет видимое root intent и явную диагностику;
server не выдумывает прежнее намерение и не создаёт второй journal.

Root write не делает несколько файлов физически атомарными. Атомарность
результата обеспечивается ранним durable intent, повторяемыми действиями,
запретом delivery несошедшегося state и финальной проверкой.

### 7. Dependency graph и границы типов проверяются до публикации

Перед root intent write host проверяет полный runtime composition текущих
`@release/*` и `@internal/*` packages:

* каждый runtime dependency release package присутствует в root membership;
* выбранная root version удовлетворяет dependency range потребителя;
* новый package можно добавить только вместе с валидной dependency closure;
* package нельзя удалить, пока он нужен оставшемуся package;
* исключённый package и все лишние env entries попадут в browser `remove`;
* package manifest перечитывается перед каждой сборкой и публикацией; кешировать
  разрешено только найденный package root и путь к `package.json`, но не его
  изменяемое содержимое.

`@startup/main` обязан объявить dependency на `@release/main`, а
`@startup/service` — на `@release/service`, потому что они фактически загружают
эти packages.

Public Loader contract переносится из startup package в `@release/service`.
Release определяет требуемый ему интерфейс, startup импортирует этот type через
объявленную package dependency и предоставляет реализацию. Относительные
type-imports через границу `web/release → web/startup` удаляются.

Source-linked public types сохраняют закон `UPD-002.14`: изменение export
package видно зависимому typecheck без предварительного artifact build.

### 8. Immutable env artifacts проверяются по bytes

Для каждого опубликованного `(package, env, version)` server вычисляет SHA-256
и byte size. Worker вычисляет их по полученному body и принимает response
только при полном совпадении server delta, canonical URL и identity headers.

Если exact artifact отсутствует, server возвращает ошибку и не запускает
ленивый build под уже объявленной exact version. Уже существующий exact target
можно переиспользовать только при совпадающих bytes; другой digest под той же
package version запрещён. После схождения root, child manifest и artifacts
package version обозначает фиксированный набор env bytes.

## Поведение процесса

* Сначала новый договор переносится в постоянный документ-владелец Hamiltonian
  и public types; только затем меняются host и Worker mechanisms.
* Каждый следующий срез изменяет один механизм и получает отдельную подзадачу,
  preparatory project commit, focused regressions и result checkpoint.
* В `UPD-003.1` оставленный development contour `UPD-002` не изменяется;
  последующие срезы заменяют его механизмы только после отдельного
  preparatory project commit.
* При обнаружении требования к обновлению живого Bun process, новому transport,
  `@metafor/*` или package resources работа останавливается и предъявляется как
  отдельное расширение, а не включается молча.

## Подзадачи

### UPD-003.1 — Зафиксировать единый env-контракт package

Статус и исполнитель: `REVIEW`; выполнено в текущей задаче без
субагента.

Классификация: первый contract-срез нового самостоятельного package update
договора; не исправляет code checkpoint `UPD-002.15` и не меняет runtime.

Требование: постоянный владелец Hamiltonian и development guide должны
однозначно закрепить список env, conditional `exports`, bare imports,
source-linked types, один package SemVer, отдельные build/typecheck единицы и
отсутствие `default` fallback.

Основание и связанная история: `UPD-002.13` доказала один канонический package
URL и bare import, `.14` — source-linked public types. Новый owner-approved
контракт сохраняет эти результаты, но различает несколько entrypoints одного
package по среде сборки.

Наблюдаемое расхождение: Hamiltonian README и development guide сейчас
описывают один browser entrypoint, один `dist/index.js`, `artifact.cache` и URL
без env. Они не различают `main`, `worker`, `service-worker`, `server` и
`server-worker` и противоречат принятому следующему направлению.

Причина: прежний договор был намеренно ограничен одним browser artifact на
package и не имел project conditions в standard `exports`.

Разрешённое изменение одного механизма: изменить только постоянный
Hamiltonian package law и его development guide. Package manifests, public
types, builder, server, Worker, artifacts, versions и live contour не менять.

Regression или опровергающее доказательство: документация одновременно
сохраняет bare package specifier и требует явный `metafor:<env>` без default;
`server` и `server-worker` перечислены отдельно; browser URL содержит env в
query, а не в pathname. `git diff --check` проходит, product files отсутствуют
в diff.

Среда и критерий приёмки: canonical `main`, baseline `3f71e76bf`; перечитать
документы и diff, не запускать build/runtime. После result checkpoint `.2`

## Открытые вопросы

Поведенческих решений, блокирующих задачу, не осталось. Для `.2` выбран
package-owned outfile из `build:<env>`: server проверяет уникальность paths
нескольких env, но не навязывает `dist/<env>` layout. Public package URL и
identity от filesystem layout не зависят.

## Границы

* Не обновлять и не перезапускать живые Bun server/server-worker processes.
  Здесь фиксируются их package env и build entrypoints, а не deployment.
* Не включать неизменяемые HTML и executable `@startup/*` bytes в сменяемый
  browser release.
* Не переносить code bytes через WebSocket; RPC передаёт signal, current
  metadata и delta, artifacts загружаются через `fetch`.
* Не вводить отдельные manifest/journal/releaseId/generation, transaction UUID,
  Worker incarnation или endpoint fields.
* Не вводить `artifact.type`; удалить `artifact.cache`, сохранив только
  действительно необходимые delivery headers.
* Пока не реализовывать `@metafor/*`; namespace rule сохранить как дальнейшее
  расширение.
* Packages и принадлежащие им CSS/WASM/assets держать в следующей задаче; эта
  задача проверяет JavaScript artifacts и не скрывает resource gap.
* Не менять `bun.lock` только ради package version writes: текущий runtime от
  этого не ломается. Реальный lockfile defect требует отдельного evidence.
* Не вводить remote registry, signatures, trust root, anti-rollback,
  межмашинную доставку или общий rollback выпусков.
* Не заменять Service Worker executable через `registration.update()` и не
  менять startup ownership, logical identity, topology или RPC transport.

## Критерии готовности

* Один bare import package разрешается в разные source entrypoints только по
  явно выбранному `metafor:<env>`; unsupported env не получает fallback.
* `main`, `worker`, `service-worker`, `server` и `server-worker` различены в
  package contract, build и types; package публикует один SemVer с полным
  набором объявленных env artifacts.
* Browser cache URL содержит env query и version, а pathname остаётся единым
  package name. В metadata и RPC нет endpoint или cache owner.
* `artifact.cache` отсутствует; owner cache однозначно выводится из namespace.
* Host перечитывает manifests и отклоняет invalid membership, dependency range,
  addition или removal до root intent write.
* `@startup/main`/`@startup/service` объявляют фактические release dependencies;
  Loader types принадлежат `@release/service`, а relative cross-package import
  отсутствует.
* Root manifest записывает target intent до действий; normal failure возвращает
  прежние root versions, crash recovery сходится вперёд, а incomplete state не
  выдаётся browser.
* Successful publication отправляет только один payload-free signal. Worker
  отправляет фактический полный current state, а server возвращает только
  `update/remove` для различий.
* Canonical caches содержат только code и не содержат `/code?state=active` либо
  `/code?state=pending`; технические `*:release:<uuid>` storages отсутствуют.
* Прерванную browser transaction однозначно обозначает один непустой cache
  `transaction`, где первой записью является `/code?state=active`; успешный
  commit удаляет cache целиком.
* Loader не запускает mixed canonical state при существующей transaction.
  После recovery остаётся один exact artifact на `(package, env)` желаемого
  состава и выполняется один reload.
* Изменение одного package/env не пересобирает и не заменяет неизменившиеся
  packages; removal удаляет только entries вне desired dependency closure.
* Server и Worker проверяют package, env, version, SHA-256 и size; другие bytes
  под уже опубликованной exact identity отвергаются.
* Два Chrome profiles независимо сходятся к одному desired state без общих
  caches, transactions, Workers или лишних reload.

## Проверка результата

* Package-resolution tests каждого поддерживаемого и неподдерживаемого env,
  включая различие `server`/`server-worker` и bare `@internal/visual`.
* TypeScript checks каждого env с `customConditions`; named export виден из
  source без build.
* Build tests нескольких env одного package, package-wide SemVer, reuse
  неизменившихся env bytes и отсутствие частичного выпуска.
* URL/parser tests canonical query, namespace cache ownership и отсутствие
  endpoint/artifact.cache в public contracts.
* Dependency graph tests: valid closure, missing member, incompatible range,
  addition и forbidden removal.
* Host tests: root-first intent, failed-build rollback, process interruption на
  каждой write boundary, restart recovery, immutable digest conflict и запрет
  delivery incomplete state.
* RPC tests: payload-free signal, current cache request, delta-only response,
  unchanged state, removal, reconnect и отсутствие stale replay.
* Service Worker tests: first intent write, partial fetch, digest/size mismatch,
  partial canonical apply, restart resume, transaction deletion, loader guard,
  removal и один reload.
* Strict affected-package typechecks, production/development env builds, полный
  `bun test hamiltonian`, `git diff --check` и audit старых fields/cache names.
* Живой managed contour через `metafor-dev`: два Chrome profiles, изменение
  одного env, group update, removal, failed host build, interrupted Worker,
  восстановление exact caches и owner review оставленного результата.
