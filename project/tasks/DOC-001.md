# DOC-001 — Вернуть единые правила документации MetaFor

## Коротко

Документация снова становится одной связной системой без дублирования и
технического шума: общие документы дают короткий закон и карту владельцев,
package README объясняют собственный смысл и жизненный цикл, а техническая
механика живёт во внутрикодовом TSDoc рядом с реальным public code.

## Зачем

После закрытых документационных срезов `MF-411` правила остались распределены
по истории, текущим docs и карточке. Последняя Cosmos-правка вынесла часть из
них в отдельный `cosmos-development` skill и снова добавила в обычные README
cache names, build targets, source paths, DTO/type names и transaction details.
Это повторяет уже исправленную причину прежнего раздутого Hamiltonian README.

## Связанные задачи и история

* Thread `01a018eb-c0c4-7ad3-8572-4a7d5a99ac66` содержит owner corrections и
  документационные срезы `MF-411`.
* Commit `5b02f0f9c` разделил 1097-строчный Hamiltonian README между root,
  package owners, prototype и development documentation.
* Commit `7f664d156` переписал package README понятным языком и убрал статусы,
  caches, transactions, RPC/HTTP и implementation reports.

  contracts: owner, lifecycle, side effects, errors и links to tests. Очевидные
  signatures и internal helpers не пересказываются.

## Решения владельца

* Правила ведения документации принадлежат `$metafor-dev`; отдельный
  Cosmos-specific documentation skill не нужен.
* Документация образует одну связную систему, распределённую по реальным
  владельцам, а не набор повторяющих друг друга обзоров.
* Корневой README содержит короткий общий закон, пользовательскую картину и
  карту ответственности; package README описывает только собственный смысл,
  lifecycle, случаи исполнения и наблюдаемый результат.
* Общий факт находится у одного владельца и не копируется в package docs.
* Обычная документация использует понятный язык, положительные законы и один
  термин для одной сущности. Технические формы, status/evidence и история задач
  в неё не входят.
* Первое scoped package name объявляет короткий alias; дальше используется он.
  Namespace описывается как множество packages.
* Каждая ссылка встроена в проверяемое предложение, называет предмет закона и
  его владельца; предложение сохраняет смысл без Markdown.
* Внутрикодовый TSDoc описывает только существующий public code: owner,
  contract, lifecycle, invariants, side effects, errors и связанные tests. Он
  не генерируется в HTML/site/output и не пересказывает очевидные signatures.
* Когда browser и Bun имеют одинаковую ответственность, общий механизм
  описывается через public interface, а различия — через platform adapters.

## Границы

* Не менять runtime, public API, package manifests или tests поведения.
* Не восстанавливать TypeDoc generation/toolchain.
* Не переписывать документы из вкуса: каждое удаление или перенос имеет
  подтверждённого владельца.
* Не включать prototype evidence, task history и live status в постоянные docs.

## Критерии готовности

* `$metafor-dev` является единственным skill-владельцем правил документации.
* Текущая documentation hierarchy соответствует принятой линии `MF-411`.
* Owner docs кратки, package-specific и связаны контекстными ссылками.
* Техническая документация остаётся внутрикодовой TSDoc без generation.
* Независимый review не находит потерянных законов или дублирующих owners.

## Проверка результата

* Audit current source/package exports against changed docs.
* Проверка локальных links/anchors и terminology/noise gates.
