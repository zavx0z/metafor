# MF-428 — Service Worker доступен без открытых вкладок

## Коротко

Один зарегистрированный Service Worker Hamiltonian остаётся доступен, когда
все Page и Window clients закрыты. Chrome может останавливать и повторно
запускать его внутреннее исполнение: это не создаёт новую предметную сущность.
Когда Bun нужно связаться с Service Worker, Web Push пробуждает его, после чего
тот восстанавливает управляющий WebSocket.

Та же сущность находится на живой сцене. Отдельной «технической части», новой
ноды при каждом запуске и отдельной «визуализации» у задачи нет.

## Зачем

Hamiltonian нужен Service Worker, с которым Bun может причинно восстановить
связь без открытой страницы. Один WebSocket этого не обеспечивает: когда Chrome
останавливает исполнение, socket закрывается и не может доставить событие.
Стандартный Push API оставляет постоянный внешний канал браузеру, запускает
зарегистрированный Service Worker по серверному событию и позволяет ему открыть
новый control WebSocket.

Текущая нода одновременно показывает `Service Worker`, лишнюю подпись
`ServiceWorkerGlobalScope`, сокращённое «Воплощение» и одностороннее
`WS — выход`. Такая нода не является точным состоянием требуемого доступного
Service Worker.

## Связь с дорожной картой

Задача уточняет текущий этап
[`MF-425 — Управлять одной Вселенной на одном устройстве`](MF-425.md).
Доступный без Page Service Worker является браузерной частью Hamiltonian в той
же Вселенной и наблюдается на живой сцене как работающая сущность, а не как
декоративная схема.

Задача не является подзадачей визуальной приёмки `MF-424`, потому что здесь
принимается один runtime-закон самого Hamiltonian. Она не относится к будущим
этапам нескольких устройств или нескольких Вселенных (`MF-426` и `MF-427`).

Полный переиспользуемый Web Push выделяется в самостоятельную задачу
[`WEBPUSH-001`](WEBPUSH-001.md). MF-428 зависит от неё и сохраняет у себя только
Hamiltonian-адаптер: устойчивую identity Service Worker, причинный wake proof,
control WSS и живую визуальную проекцию тех же lifecycle-событий.

## Подтверждённые факты

* Отдельного HTTP ping между Bun host и Service Worker сейчас нет.
* Bun host передаёт прикладные `ping`, а Service Worker отвечает `pong` по уже
  открытому control WebSocket.
* Page передаёт собственный heartbeat и при отсутствии ответа пытается снова
  связаться с Service Worker. Это механизм удержания при открытой странице, но
  он исчезает после закрытия последнего Window client.
* В текущем обычном Chrome Service Worker завершался несмотря на обмен по
  WebSocket; новое подключение получало новые identity Worker и WebSocket.
  Воспроизводимый чистый замер нужно сохранить как evidence этой задачи.
* Стандарт обычного Web Service Worker разрешает user agent завершать Worker,
  когда ему нечего обрабатывать. Chromium документирует idle-завершение через
  30 секунд и предельное время одного незавершённого события около 5 минут.
* Документация Chrome о продлении жизни сообщениями WebSocket начиная с Chrome
  116 описывает Service Worker расширения Chrome. Область этой официальной
  страницы нельзя использовать как отрицательное доказательство для обычного
  Web Service Worker.
* Владелец ранее наблюдал более долгую работу Service Worker в другом проекте,
  но MF-428 не восстанавливает его старую реализацию: механизм проектируется и
  принимается заново по текущему Chrome и текущему Hamiltonian.
* Исходные фрагменты показывают, что текущая нода не выражает требование
  постоянной жизни и содержит отвергнутую владельцем подпись.
* В Chrome `151.0.7922.76` тот же отрицательный результат получен в двух чистых
  контурах: отдельный CDP-профиль по HTTP и обычный профиль без remote debugging
  по доверенному HTTPS. В обоих случаях подтверждённый WebSocket heartbeat не
  предотвращает замену worker/socket примерно через 30 секунд.
* Дополнительный HTTP `fetch` перед `pong` и незавершённый Web Lock также не
  удержали то же исполнение Worker; экспериментальный код после проверки удалён.
* Причинный `ping → pong` подтверждает доступность текущего WebSocket. Он не
  определяет identity Service Worker и не должен создавать новую ноду после
  повторного запуска исполнения.
* `ExtendableEvent.waitUntil` не превращает WebSocket frame в браузерное
  событие: он продлевает только доверенный текущий event, синтетический event
  отвергается, а Chrome ограничивает один незавершённый event примерно пятью
  минутами. Значит, это не бесконечный keepalive и не Bun → SW transport.
* Рабочий патч fail-closed связывает `identity` и каждый `pong` с точным
  `workerEntityId`, указанным при открытии control WebSocket; один socket больше
  не может приписать подтверждённый heartbeat другой identity.
* Рабочая lifecycle-проекция сохраняет одну ноду по стабильной identity.
  Закрытие точного WebSocket при готовом Push переводит её в `standby`; ошибка
  отправки Push или reconnect переводит ту же ноду в `error`. Новое внутреннее
  исполнение обновляет только диагностический факт `Исполнение`. Это проверено
  кодом и тестами, но ещё не принято владельцем на живой сцене.
* Во время живой приёмки обнаружено, что нода временами выходила из parent
  Chrome: поздние status-наблюдения host и page ошибочно назначали Service
  Worker владельцем самого себя. Исправление закрепляет browser runtime как
  единственного owner во всех entity-наблюдениях Service Worker; Push,
  heartbeat, standby и новое внутреннее исполнение больше не меняют parent.
* В примере доклада Антона Петрова `eolme/sw-chat` открытая Page каждую секунду
  передаёт Service Worker сообщение `ping`, а Worker отвечает `pong`; этот
  механизм делит один WebSocket между вкладками, но не работает без последней
  Page.
* Стандартный Web Push доставляется через push service браузера. Если
  зарегистрированный Service Worker не исполняется, user agent запускает его и
  передаёт доверенное событие `push`; открытая Page для этого не требуется.
* PushSubscription теперь регистрирует у Bun сам идентифицированный Service
  Worker по control WSS. Сервер выводит worker/device identity из socket;
  прежний HTTP endpoint с заявленными клиентом identity удалён.
* Ожидаемый `wakeId` вооружается до асинхронной отправки. Зашифрованный Push
  несёт также непубликуемый одноразовый `wakeProof` и свежие capability/host
  identity после Bun restart. Worker объявляет успех только после обратного
  `wake-confirmed` от сервера.
* Исполняемые tests подтверждают быструю доставку до завершения server send,
  fail-closed proof, сохранение VAPID/PushSubscription и восстановление с новым
  token/host epoch после полного Bun restart.
* Live HTTPS-опыт обычного Chrome подтвердил при `0` Hamiltonian Page/Window
  clients цепочку `push-sent → новый runtime → новый WSS →
  push-reconnect-confirmed` за `186 ms`; устойчивая identity не изменилась.
* Более сильный опыт с `0` окон Chrome дважды завершился delivery timeout,
  хотя browser process оставался жив. Он зафиксирован как граница локального
  background mode и не подменяет успешный критерий без Hamiltonian Page.

## Решения владельца

* Предметная сущность — зарегистрированный Service Worker Hamiltonian. Остановка
  и повторный запуск его внутреннего исполнения являются browser lifecycle, а
  не рождением нового Service Worker.
* Hamiltonian остаётся обычным Web Service Worker. Web Push разрешён как
  стандартный путь пробуждения без Page; Chrome extension и instrumentation не
  используются.
* Постоянная доступность означает, что при работающих Bun и Chrome Bun может
  пробудить тот же зарегистрированный Service Worker и причинно восстановить
  control WebSocket. Непрерывность одного socket и данных только в памяти не
  является требованием.
* Web Push используется для значимого пробуждения или восстановления, а не как
  частый скрытый heartbeat. Разрешение пользователя и политика
  `userVisibleOnly` являются частью обычного browser contract.
* Старый `sustechpoints` не является шаблоном реализации MF-428. Требуется
  корректный механизм для текущего Chrome, а не перенос прежнего кода.
* Канонический исходник Service Worker переписывается на TypeScript. Браузер
  получает собранный JavaScript через стабильный service-worker URL; отдельные
  вручную поддерживаемые `sw.js` и entry-прокладка не сохраняются.
* В договоре Hamiltonian существует сущность `Service Worker`.
  Понятие `ServiceWorkerGlobalScope` в целевую модель задачи не входит.
* Работа Service Worker и его нода не являются двумя результатами. Нода строится
  из фактических событий того же Service Worker и в каждый момент сообщает его
  реальное состояние.
* Сцена сохраняет одну ноду Service Worker. Потеря WebSocket переводит её в
  наблюдаемое состояние ожидания пробуждения или восстановления; успешный Push
  и reconnect обновляют ту же ноду. Реальный отказ Push или reconnect не
  скрывается.
* Review, тестирование, артефакты и закрытие являются стадиями одной задачи, а
  не её подзадачами.

## Текущая граница реализации

WebSocket, HTTPS, обычный `fetch` и Web Lock не удерживают исполнение обычного
Service Worker. MF-428 не обходит это ограничение. Bun сохраняет выданную
браузером PushSubscription, посылает стандартный Web Push при необходимости
пробуждения, а Service Worker восстанавливает причинно новое соединение как
продолжение той же зарегистрированной сущности.

## Принятые детали реализации

* Каждый явный Push показывает одно уведомление о результате восстановления;
  фонового частого Push и уведомлений-heartbeat нет.
* Логическая identity создаётся Page один раз для origin, а Service Worker
  хранит identity и control bootstrap в Cache Storage. Bun хранит VAPID identity
  и PushSubscription в локальном игнорируемом `.metafor` с правами `0600`.
* Регистрация PushSubscription проходит через идентифицированный control WSS.
  Web Push несёт одноразовое доказательство и свежую capability текущего Bun;
  успешное уведомление появляется только после server ACK.
* Одна нода показывает `Identity`, диагностическое `Исполнение`, `Push`,
  `Heartbeat`, состояние и двусторонний `WS/WSS`. Смена исполнения не создаёт
  вторую ноду.

## Границы

* Не добавлять вымышленный HTTP ping.
* Не включать `ServiceWorkerGlobalScope` в целевую модель, ноду, kind или
  подпись.
* Не объявлять WebSocket heartbeat гарантией доступности без Push.
* Не принимать DevTools, WebGPU Inspector или другой instrumentation за
  механизм удержания Worker живым.
* Не переходить к Chrome extension или instrumentation.
* Не использовать Web Push как частый скрытый heartbeat или обход политики
  уведомлений браузера.
* Не оставлять рядом TypeScript-исходник и вручную редактируемую JavaScript-копию
  Service Worker.
* Не менять generic Engine или Node System ради предметного смысла Hamiltonian;
  обнаруженный общий дефект регистрируется отдельно.
* Не переносить в задачу production-домены, несколько устройств или несколько
  Вселенных.

## Критерии готовности

* В `hamiltonian/README.md` закреплена identity зарегистрированного Service
  Worker, граница browser-managed исполнения, Web Push и смысл heartbeat.
* Обычный Chrome с закрытыми Page получает отправленный Bun Web Push, запускает
  тот же зарегистрированный Service Worker и восстанавливает control WebSocket
  без DevTools, extension и instrumentation.
* Чистый замер связывает одну устойчивую identity Service Worker с исходным и
  восстановленным WebSocket и доказывает причинную последовательность
  `push sent → push received → reconnect confirmed`.
* Та же одна нода `Service Worker` находится на живой сцене; она показывает
  готовность Push, ожидание/восстановление и фактический двусторонний WebSocket.
* Ошибка отправки Push, доставки или reconnect переводит ту же ноду в явное
  ошибочное состояние и не выдаётся за успешную доступность.
* В целевой модели и ноде отсутствует `ServiceWorkerGlobalScope`.
* Service Worker имеет один TypeScript-исходник, который проходит проверку и
  собирается Bun в исполняемый браузером JavaScript.
* Владелец принял работу Service Worker и состояние его ноды одним живым
  сценарием.

## Проверка результата

1. Запустить согласованный чистый Chrome-contour без DevTools и WebGPU Inspector
   instrumentation.
1. Зафиксировать identity Service Worker, PushSubscription и исходный control
   WebSocket.
1. Закрыть все Page и Window clients и дождаться штатного browser idle timeout.
1. Отправить Web Push из Bun и зафиксировать получение доверенного `push`.
1. Проверить, что тот же Service Worker восстановил новый WebSocket и Bun
   причинно связал его с отправленным Push.
1. Проверить TypeScript-исходник и реальный browser bundle Service Worker.
1. Искусственно нарушить отправку или reconnect и проверить, что фактический
   отказ становится состоянием той же ноды Service Worker.
1. Сохранить длительный замер и снимок принятого состояния в артефактах задачи.

## Результат проверки перед REVIEW

* Один canonical исходник Service Worker находится в
  `hamiltonian/browser/service-worker.ts`; Bun собирает и отдаёт его как
  `/sw-entry.js`, прежние ручные JavaScript-копии удалены.
* Strict TypeScript, реальная browser build и focused-набор Web Push, host и
  lifecycle-проекции прошли: `51 pass`, `0 fail`.
* Полный `bun run check` прошёл: `2456 pass`, `0 fail`; отдельный proof
  подтвердил все `42` ожидаемые типовые ошибки. После исправления live finding
  полный check повторён с тем же результатом.
* В обычном Chrome `151.0.7922.76` по доверенному HTTPS и без Hamiltonian Page
  причинно подтверждена цепочка `push-sent → новый WSS → worker identity →
  push-reconnect-confirmed` для одной стабильной Service Worker identity.
  Финальный `wakeId`, обе runtime/connection identity и граница строгого
  zero-window режима сохранены в
  [`web-push-wake-ordinary-chrome.md`](../artifacts/MF-428/web-push-wake-ordinary-chrome.md).
* Первое независимое ревью parent-fix нашло два P2: несогласованный owner в
  retirement прежнего Worker и право rejected/pre-arm socket публиковать
  `standby`. Оба пути исправлены и получили отдельные регрессии; повторное
  read-only ревью завершилось без findings. Новый WSS по-прежнему доказан
  монотонной connection generation, поэтому уже открытый до Push socket не
  может подтвердить пробуждение даже при совпавших миллисекундных timestamp.
* Живая сцена открыта владельцу для визуальной приёмки. Это closing gate:
  карточка и артефакты сохраняются в `REVIEW` до явного принятия состояния
  одной ноды `Service Worker`.
* После обнаруженного на живой сцене выпадения из Chrome задача была возвращена
  в `IN_PROGRESS`. Регрессионная проверка теперь проводит ноду через
  `active → standby → новое browser-managed исполнение` и на каждом состоянии
  требует неизменный parent Chrome; host-тест отдельно проверяет тот же owner
  в реальном событии регистрации Web Push.
* На финальном HTTPS-host Chrome трижды сменил внутреннее исполнение и WSS при
  неизменных Service Worker/device identity, включая наблюдаемый промежуток без
  socket. Подробности и граница отсутствующего автоматического screenshot
  сохранены в
  [`service-worker-parent-stability.md`](../artifacts/MF-428/service-worker-parent-stability.md).
