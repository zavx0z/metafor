# MF-428 — Различать несколько Chrome и их Service Worker

## Коротко

Если одновременно запущены несколько Chrome-профилей, Hamiltonian должен
показывать каждый наблюдённый Service Worker внутри того Chrome, которому он
принадлежит. Service Worker не должен становиться корневой нодой, сливаться с
Worker другого профиля или получать страницы чужого Chrome.

## Зачем

Один Chrome-профиль с несколькими вкладками уже использует один общий Service
Worker и один согласованный lifecycle. При одновременном запуске второго
профиля у того же origin появляется другой browser-local scope и другой Service
Worker. Без точной browser identity Hamiltonian показывает причинно неверную
топологию и не позволяет понять, какой Worker обслуживает какие страницы.

## Связь с дорожной картой

Задача относится к первому этапу Hamiltonian — управлению одной Вселенной на
одном устройстве в [`MF-425`](MF-425.md). Она обнаружена при визуальной работе,
но не является подзадачей `MF-424` и не относится к `@nodes/layout`: исправить
нужно Hamiltonian lifecycle projection и её browser ownership.

Постоянный владелец действующего закона —
[`hamiltonian/README.md`](../../hamiltonian/README.md), разделы о причинном
мониторе и странице оркестрации.

## Подтверждённые факты

* При одном Chrome-CDP с двумя вкладками обе page realm находятся внутри одного
  `Chrome` и используют общий Service Worker.
* При одновременной работе обычного Chrome и отдельного Chrome-CDP `@meta/chrome`
  подтвердил два разных browser process/profile.
* В этом двухпрофильном состоянии живая сцена показала наблюдённый `Service
  Worker` отдельной корневой нодой, хотя действующий Hamiltonian contract
  разрешает назначить browser parent после фактического `connect-window` с
  browser identity.
* Это входной lifecycle/ownership defect. Layout получает уже готовый
  `parentId` и не должен угадывать либо исправлять предметную принадлежность.
* Потеря принадлежности локализована в двух независимых местах: Service Worker
  не передавал host ownership-closed browser/profile snapshot, а page projection
  после authoritative replacement безусловно сохраняла отсутствующий remote
  `browser-runtime`. Оба дефекта относятся к Hamiltonian lifecycle/ownership,
  а не к layout.

## Решение владельца

* Вести это отдельной задачей Hamiltonian.
* Поддержать несколько одновременно наблюдаемых Service Worker и не смешивать
  исправление с текущей работой над раскладкой.
* В общей сцене каждый наблюдённый Chrome/profile является отдельной compound-
  нодой. Слева в её шапке остаётся имя runtime `Chrome`, справа показывается
  компактный идентификатор профиля, а полный идентификатор доступен в фактах.
* Наблюдённый Service Worker не показывается отдельно от своего Chrome после
  подтверждённого browser ownership: для второго Worker обязана существовать
  вторая Chrome-нода с его собственными страницами и transport.
* Действующая browser/profile identity — UUID Hamiltonian в origin-local
  storage Chrome-профиля (исторический key `hamiltonian-device`). Это не имя
  Google-профиля, PID, title, user agent или URL. UUID общий для вкладок одного
  storage profile, передаётся Service Worker и host, переживает quit/reopen
  вместе со storage; новый, очищенный либо incognito storage является новым
  owner.
* Логическая identity Service Worker, incarnation его текущего execution и
  версия исполняемого кода являются тремя разными величинами. Версия кода
  задаётся только валидным SemVer и видна в каждой ноде Service Worker.
* В ноде Service Worker компактная logical identity показывается справа в
  шапке, но не повторяется параметром. Описательный текст между шапкой и
  параметрами отсутствует.
* Hamiltonian server должен уметь потребовать установку exact SemVer кода
  Service Worker во всех известных browser/profile scope и отдельно показать
  подтверждённый результат либо препятствие каждого профиля.

## Подзадачи

### MF-428.1 — Показать каждый Chrome-профиль отдельной нодой

Статус: результат зафиксирован коммитом
`c490c3d652390954e234cbf8aeda2c666b27cab2`; оставшиеся restart/close критерии
позднее выполнены в `MF-428.2`. После этого родитель был передан в `REVIEW`, но
12 августа 2026 года вновь открыт из-за принятых `MF-428.3`–`MF-428.5`.

Материализовать все одновременно наблюдаемые browser/profile owner как
отдельные `Chrome` compound-ноды, вывести profile identifier в правой части
шапки и сохранить полный identifier в фактах. Страницы, Service Worker и их
transport должны находиться только внутри exact profile owner; отсутствие
owner-ноды после подтверждённого `connect-window` является ошибкой lifecycle-
проекции, а не основанием поднять Worker на корень.

Подзадача вводит общий декларативный закон, а не специальную обработку второго
Service Worker: каждый передаваемый между realm retained snapshot обязан быть
ownership-closed. Некорневая entity допустима только вместе с точной живой
owner-chain до объявленного root этого scope. Host агрегирует валидированные
profile-scoped snapshots целиком; presentation не синтезирует Chrome по факту
появления Worker и не исправляет отдельные виды нод вручную.

#### Результат

Потеря принадлежности локализована на границе Service Worker → host retained
aggregation. Worker сообщал свою identity, а host удерживал Service Worker с
`ownerId` браузера, но сам remote `browser-runtime` через эту границу не
передавался. Presentation закономерно не могла поставить `parentId` на
невидимого владельца и материализовала Worker как root.

Исправление передаёт и валидирует ownership-closed snapshot профиля целиком:
Chrome-root, Service Worker и все уже наблюдённые дочерние realm. Общий
валидатор проверяет owner-chain независимо от вида дочерней ноды; host отдельно
подтверждает только exact browser root и exact Service Worker текущего control
endpoint. Поэтому второй профиль не требует специальной ветки, а будущий новый
вид browser-owned realm проходит тот же закон.

Offline proof: `49` lifecycle/projection/browser-build тестов и все `33` host
теста прошли, `bun run typecheck` прошёл. Live proof на двух точно адресованных
browser-local scope одного Chrome-CDP process подтвердил две вкладки и один
Service Worker на профиль, две отдельные Chrome-ноды с разными profile ID и
отсутствие корневого Service Worker; reload exact target в каждом профиле
сохранил его profile и Worker identity. Обе проверенные консоли пусты.

`ServiceWorker.stopAllWorkers` через текущий одно-командный REST CDP surface не
доказал execution restart: `ServiceWorker.enable` не переживает открытие новой
CDP-сессии, поэтому Chrome вернул `ServiceWorker domain not enabled`. Этот
результат не был засчитан на этапе `MF-428.1`; restart execution и закрытие
профиля позднее доказаны в `MF-428.2`.

### MF-428.2 — Доказать restart execution и закрытие профиля

Статус: результат принят как baseline 12 августа 2026 года; новые обязательные
срезы `MF-428.3`–`MF-428.5` его не отменяют.

На двух точно адресованных browser-local scope доказать, что restart execution
одного Service Worker сохраняет его логическую identity и exact Chrome owner,
не создавая дубль либо root. Затем закрыть один scope целиком и доказать, что
его Chrome ownership-поддерево удалено, а второй profile, его страницы, Worker
и transport не изменились. Если live-сценарий обнаружит lifecycle defect,
исправить общий retained ownership/retirement contract без веток по номеру или
типу конкретной ноды.

#### Результат

Настоящий browser-managed restart выполнен через `Stop` exact регистрации на
`chrome://serviceworker-internals/` отдельно в normal и incognito scope.
Логические Worker identity `45d8fde1-…` и `5df2f151-…` не изменились, execution
incarnation сменились соответственно `ed0e4a42-… → 40b71c0f-…` и
`3a1ab9c8-… → 11e38947-…`. Оба Worker остались внутри прежних exact Chrome
owner, root и дубликат не появились.

Живое закрытие локализовало два общих defect. Во-первых, Chrome может закрыть
control socket раньше финального `tabs: []`, поэтому немедленное удаление по
состоянию topology недостаточно. Host теперь ждёт общую heartbeat/authority
grace; reconnect того же profile отменяет expiry, а при отсутствии control,
Web Push и pending wake атомарно забывает всё ownership-поддерево без terminal
fence стабильной identity. Явно полученный пустой window inventory позволяет
тот же переход без ожидания. Во-вторых, page projection сохраняла любую
`browser-runtime` ноду при авторитетной замене snapshot, из-за чего после уже
чистого host snapshot оставался пустой Chrome root. Теперь она сохраняет только
owner текущей page, а отсутствующий remote browser scope забывает целиком и
может позднее принять ту же стабильную identity снова.

Offline proof: `bun run typecheck`, все `35` host тестов, все `23` core
lifecycle теста и все `27` lifecycle projection тестов прошли. Отдельные тесты
доказывают немедленное закрытие по пустому inventory, abrupt close после grace,
отмену удаления при reconnect/rebirth, сохранение причинного closed WebSocket
до завершения endpoint и повторное появление забытой стабильной identity.

Финальный live-сценарий на host version `mf-428-projection-final` использовал
normal profile `b04b5959-…` и incognito profile `90a10c48-…`, по две exact
вкладки и разные Worker. После закрытия exact incognito window host записал
`browser-profile-unreachable`; retained snapshot revision `389` содержит только
normal Chrome, его один Worker, две page realm и два Service Worker API
transport. В готовой сцене пустого remote Chrome, root Worker и cross-profile
edges нет; CDP console normal target за `1500` мс вернула `0` записей.

### MF-428.3 — Ввести SemVer версии кода Service Worker

Статус: результат принят 12 августа 2026 года на checkpoint-коммитах
`002570bb010d3ad5fb777db8dd28fa8124e2d4a2` и
`79e64bd3f31187d780acc4d0fd6700b4520e52a0`; родительская MF-428 остаётся
`IN_PROGRESS`.

Подзадача с законом, расхождением, границами и критерием была зарегистрирована
до реализации project-коммитом
`48ec7327e45cca2ddfde13c41f52c25ceb4863aa`. Отдельный подготовительный коммит
перехода родителя `READY → IN_PROGRESS` перед кодом записан не был: требование
появилось в `9359da629ad4418f39da5762583a94f859c5a8c8` уже во время выполнения.
Поздний project-коммит `dd78a561d13278b1ece74c28c173d00728c21198` этого
ретроспективно не заменяет. Приёмочная проверка была отдельно подготовлена
коммитом `1e8e7b6e8f4b75f93caeed2b2e42ffb34b85beb9` до дополнительных probes.

Ожидаемый наблюдаемый результат: в каждой ноде Service Worker видна точная
версия загруженного кода в валидном SemVer с обязательными
`MAJOR.MINOR.PATCH`; prerelease/build metadata допустимы только по синтаксису
SemVer. Она не подменяется logical Worker identity, execution incarnation, Git
revision, версией host или произвольной строкой сборки.

Применимы уже принятые ownership/restart законы `MF-428.1` и `MF-428.2`:
несколько профилей имеют разные logical Worker identity, но могут исполнять
одну и ту же версию кода; restart одного execution без смены bundle сохраняет
эту версию. До checkpoint lifecycle и карточка показывали identity и
incarnation, но не имели отдельного доказанного источника версии кода; frozen
regression зафиксировал это исходное расхождение.

Границы: не выводить версию из cache busting URL, времени сборки, connection
order или host label; не менять logical identity при обновлении кода; не
расширять SemVer-контракт на остальные runtime без отдельного решения.

Критерий приёмки: contract отклоняет не-SemVer значение, обе ноды двух
профилей показывают exact code version, restart execution сохраняет её, а
переход на новый bundle меняет только code version и incarnation, сохраняя
logical identity и exact Chrome owner.

#### Результат

Действующий закон находится в разделе `Версия кода Service Worker`
[`hamiltonian/README.md`](../../hamiltonian/README.md). Product checkpoint
`002570bb0` связывает bundle-owned SemVer, внутренний Worker → host contract,
проекцию и live evidence. Приёмочный checkpoint `79e64bd3f` дополнительно
доказывает отклонение несовпадающих identity/snapshot version и смены version
без новой execution incarnation.

Прошли строгие host и WebWorker TypeScript checks, все реальные browser/Worker
builds, `bun run typecheck`, `git diff --check` и полный `bun test hamiltonian`
(`177/177`, `3751` assertions). Exact normal/incognito evidence, restart того же
bundle и контрольные суммы двух снимков сверены в
[`project/artifacts/MF-428`](../artifacts/MF-428/README.md). MF-428.4 и MF-428.5
в checkpoints этой подзадачи не входят.

### MF-428.4 — Принудительно обновлять Worker всех профилей с сервера

Статус: `READY`; по решению владельца выполняется после отдельной приёмки
MF-428.5.

Ожидаемый наблюдаемый результат: одна авторизованная серверная команда с exact
target SemVer адресует каждый известный browser/profile scope, доводит его
Service Worker до этой версии и показывает отдельный causal result профиля.
Успех всей операции допустим только после подтверждения target version каждым
достижимым профилем; недоступный, отклонивший или не завершивший активацию
профиль остаётся явным pending/failed result, а не скрытым успехом.

Текущий разрыв: host агрегирует lifecycle разных профилей, но доказанного
server-owned fleet update contract и команды обновления нет. До реализации
нужно frozen test определить browser update lifecycle — запрос проверки
регистрации, установка, активация, смена controller и восстановление control
connection — и доказать, на каком переходе сервер получает authoritative
подтверждение версии.

Границы: не смешивать профили через общий последний controller, не считать
отправку команды фактом установки, не уничтожать logical Worker identity, не
обходить browser Service Worker lifecycle и не расширять authority сервера за
пределы Hamiltonian Worker update.

Критерий приёмки: pure lifecycle test и live-сценарий с двумя точно
адресованными профилями запускают обновление с одной исходной SemVer на другую;
оба профиля независимо подтверждают target version, сохраняют свои Chrome
owner и logical Worker identity, получают новые execution incarnation и
восстанавливают transport без cross-profile edges. Отдельно доказаны
частичный отказ и последующее обновление временно недоступного профиля.

точное ownership-поддерево.

## Целевой закон

* Browser-local identity отличает одновременно работающие Chrome
  process/profile одного приложения и origin; одинаковые title, user agent и
  URL не являются достаточной identity.
* Каждая наблюдённая browser/profile identity материализует отдельную compound-
  ноду: runtime name показывается слева в шапке, компактная profile identity —
  справа, полный identifier — в фактах ноды.
* Retained lifecycle snapshot является ownership-closed: каждая некорневая
  entity содержит доступную в том же scope живую цепочку владельцев до exact
  browser/profile root. Snapshot с orphan child не принимается в aggregate.
* Каждый Service Worker после подтверждённого `connect-window` получает ровно
  один exact browser parent и остаётся внутри него во всех retained snapshots.
* Несколько вкладок одного Chrome/profile используют один логический Service
  Worker scope; несколько профилей не сливают свои Worker, page realm,
  transport или causal frontier.
* Перезапуск execution одного Service Worker обновляет его воплощение внутри
  того же browser scope и не создаёт корневую либо дублирующую ноду.
* Logical Worker identity, execution incarnation и SemVer исполняемого кода не
  взаимозаменяемы. Обновление кода сохраняет identity, но подтверждает новую
  версию и новое execution отдельно в каждом browser/profile scope.
* Авторизованное server-owned обновление задаёт exact target SemVer, сохраняет
  независимость профилей и не считается завершённым без per-profile result.
* В карточке Service Worker compact identity находится только справа в шапке;
  описательный блок и отдельный параметр `Identity` отсутствуют, code SemVer
  остаётся видимым параметром.
* Закрытие одного Chrome/profile удаляет только его ownership-поддерево и не
  изменяет страницы, Worker и transport другого профиля.
* Все страницы одного профиля сходятся к одному retained snapshot, а данные
  разных профилей объединяются в общей сцене только как явно разные browser
  ownership-поддеревья.

## Разрешённые вопросы identity

* Page владеет созданием origin-local UUID, Service Worker получает его только
  через точный `connect-window`/control bootstrap, host — через control
  endpoint. Chrome account name и глобальная user-data-dir не требуются.
* Полный quit/reopen не создаёт новый owner, пока сохранён browser storage.
  Очистка storage или новый off-the-record scope создаёт новое поддерево.

## Границы

* Не менять `@nodes/layout`, UI-геометрию, routing, clearance или renderer.
* Не скрывать корневой Service Worker и не назначать parent по названию
  приложения, URL, user agent, порядку подключения или последнему активному
  окну.
* Не сливать Service Worker разных browser profile только потому, что они
  зарегистрированы на одном origin.
* Не менять production-домены, authority или transport protocol Hamiltonian
  шире необходимого browser lifecycle identity/aggregation.

## Критерии готовности

* Pure lifecycle test с двумя разными browser identity, двумя Service Worker и
  несколькими вкладками доказывает точные parent/child и transport endpoints
  независимо от порядка событий.
* Contract test отклоняет profile snapshot без browser root, с чужим root либо
  с разорванной/cyclic owner-chain; host принимает и агрегирует целиком два
  валидных ownership-closed profile snapshot.
* Две вкладки одного профиля показываются внутри одного Chrome и используют
  один Service Worker; вкладки второго профиля находятся только в его отдельном
  Chrome и используют другой Service Worker.
* В общей сцене присутствуют обе Chrome-ноды; их правые заголовки и полные

* Ни один живой Service Worker после подтверждённого `connect-window` не

* Reload вкладки, restart Worker execution и закрытие одного профиля сохраняют

* Два профиля показывают SemVer фактически исполняемого Worker code; invalid

* В шапке каждой Service Worker ноды справа виден compact identifier; строки

* Одинаковые входные lifecycle observations и их стабильные перестановки дают

* Живой сценарий с двумя точно адресованными Chrome-профилями подтверждает
  результат в обеих вкладках каждого профиля; тест или screenshot одного

* Долговечный закон нескольких browser scopes актуализирован в

1. Сначала воспроизвести текущий defect на frozen lifecycle fixture без
   браузера и локализовать потерю exact browser identity.
1. Проверить один профиль с двумя вкладками как обязательный non-regression.

* Добавлен общий закон для любого browser-owned realm: snapshot пересекает

  имя Chrome, PID, title, user agent, URL или порядок подключения.

  безусловно сохранять любую ранее увиденную remote Chrome-ноду при
  authoritative snapshot replacement.
* Layout не определяет предметную принадлежность и не исправляет orphan-ноды;
  он получает уже проверенный `parentId` от Hamiltonian projection.

## Независимая closing review — FAIL

Дата review: 12 августа 2026 года. Проверены exact result commits
`c490c3d652390954e234cbf8aeda2c666b27cab2` и
`a223d02a6f251d57c346c5ae135ddb5a4535eec5`, closing handoff
`8417e20fb2ec541e8ccf84977cc4c2df77a577d8` и result HEAD. Verdict: **FAIL**;
карточку, артефакты и запись MF-428 в графе удалять нельзя до исправления и
повторной независимой review.

### Блокирующее несоответствие

Заявленная ownership closure проверяет только owner-chain entity, но не
принадлежность transport. `isHamiltonianLifecycleOwnershipClosed` в
`hamiltonian/core/lifecycle.js` собирает и обходит только entity; поля
`ownerId`, `sourceEntityId` и `targetEntityId` transport не проверяются.
`isBrowserProfileLifecycleSnapshot` в `hamiltonian/host.ts` подтверждает exact
browser и Worker entity, но также не проверяет transport endpoints. Поэтому
host принимает profile snapshot, transport которого пересекает границу другого
browser profile, а lifecycle projection материализует cross-profile edge.

Это нарушает owner document `hamiltonian/README.md`: page, Service Worker и их
transport не должны пересекать границу profile scope, а полученный snapshot
должен быть проверен до retained aggregation. Одновременно не выполнены
критерии карточки о точных transport endpoints и отсутствии cross-profile
edges.

### Независимые probes

* Pure validation probe создал формально корректные browser A, Worker A и page
  A, затем transport с owner Worker A и source page A, но target Worker B.
  Результат: базовый `isHamiltonianLifecycleSnapshot` вернул `true` и
  `isHamiltonianLifecycleOwnershipClosed(snapshot, [browserA])` также вернул
  `true`, хотя endpoint Worker B отсутствовал в scope A.
* End-to-end host probe подключил валидный profile B и описанный вредоносный
  profile A через настоящий `browser-lifecycle-snapshot`. Host принял snapshot,
  не закрыл WebSocket A (`readyState === 1`) и сохранил в retained aggregate
  оба browser root вместе с cross-profile transport A → B.
* Pure projection probe агрегировал эти два profile snapshot и получил прямую
  грань `service-worker-api:cross-profile` от page A к Worker B и обратную грань
  Worker B → page A. При этом parent page A и Worker A оставался browser A, а
  parent Worker B — browser B: нарушение не маскируется ошибкой parentId, это
  именно пропущенная проверка transport boundary.

### Public type

Новый public discriminated type в `hamiltonian/types.d.ts` сейчас не требуется:
пакет `hamiltonian` private, не имеет package exports, `types.d.ts` содержит
только ambient declaration для `multicast-dns`, а
`browser-lifecycle-snapshot` является внутренним control protocol между
собираемыми вместе Service Worker и host. Это не освобождает internal protocol
от полной runtime validation. Если host и Worker станут независимо
версионируемыми либо envelope будет экспортирован потребителям, discriminated
protocol type должен стать public contract.

### Исправленный contract

* `isHamiltonianLifecycleOwnershipClosed` теперь разрешает retained transport
  только если его `ownerId`, `sourceEntityId` и `targetEntityId` существуют как
  entity того же snapshot и owner-chain всех трёх заканчиваются в одном exact
  declared root. Transport между двумя roots отклоняется даже тогда, когда оба
  root перечислены как допустимые для общего snapshot.
* Host продолжает принимать browser/profile snapshot только через этот общий
  validator с единственным exact browser root. Поэтому entity другого profile,
  присутствующая в глобальном retained aggregate, не становится доступным
  endpoint локального profile snapshot.
* Lifecycle projection получила независимый защитный инвариант: transport,
  owner/source/target которого обнаруживают больше одного browser-runtime
  ancestor, не участвует в visibility traversal, не создаёт параметры, порты,
  прямую или обратную грань и не допускает message presentation. Обычный
  browser-owned → server transport остаётся допустимым, потому что server не
  является вторым browser root.
* Долговечный закон exact-scope transport closure добавлен в постоянный owner
  [`hamiltonian/README.md`](../../hamiltonian/README.md). Вывод независимой
  review о том, что отдельный public discriminated type сейчас не требуется,
  принят: `hamiltonian/types.d.ts` не изменялся.

* End-to-end host test сначала подключает и удерживает валидный profile B,
