# SYS-001 — Полный новый запуск после остановки

## Зачем

Повторный запуск должен создавать новый согласованный contour, а не частично
оживлять отдельный домен старого мира.

## Подтверждённые факты

* После остановки Лады Boundary сохраняет Chat в State `ожидание события` и
  pending Process execution.
* Живой WebSocket принадлежит Energy и после остановки отсутствует.
* Matrix восстанавливает известный State без повторного исполнения Process.
* Поэтому сохранённый pending execution может остаться без живого исполнителя.

## Решение владельца

Задача выполняется первой для восстановления рабочего контура Лады. Новый
запуск является холодным рождением всего причинно связанного contour; частичный
hot reload не вводится.

## Открытые вопросы

* Владелец внешнего управляющего контура.
* Предел попыток и задержка.
* Наблюдаемое состояние и сохранение первой причины отказа.
* Исход незавершённого Process при остановке.
* Отклонение позднего результата прежнего выполнения.

## Границы

Новый запуск создаёт все процессы заново и передаёт Matrix новый согласованный
срез Boundary. Частичное оживление запрещено.

## Критерии готовности

* Незавершённое execution прежнего contour получает однозначный наблюдаемый
  исход и не может позднее изменить новый мир.
* Process текущего process-bound State получает новую execution identity и
  новую живую Energy после полного рождения.
* Повторный полный запуск не создаёт два одновременных выполнения одного State.
* Обычный Process, завершённый до остановки, без причины повторно не запускается.
* Интеграционная проверка воспроизводит остановку на pending Process и успешное
  продолжение только новым execution.

## Проверка результата

* `bun run check`.
* `boundary/initial.spec.ts` подтверждает согласованную проекцию pending
  executions.
* `matrix/cold-restart.spec.ts` подтверждает новую identity, блокировку Atom и
  отклонение claim прежнего contour.
