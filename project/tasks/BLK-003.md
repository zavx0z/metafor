# BLK-003 — Проекция Atom и орбитальные обработчики внутри State

## Зачем

State должен показывать проекцию того же canonical Atom в выбранном состоянии.
Вокруг центрированной проекции Atom внутри пространства State располагаются
принадлежащие этому State Process. Это позволяет читать State как состояние
всего Atom и отделяет экземпляр состояния, экземпляр проекции Atom и
State-owned Process без копирования canonical данных.

## Подтверждённые факты

* Matrix связывает Process с exact State, а Transition выбирает по Conditions
  над Fields; Process сам не является переходом.
* Действующий production-закон Visual размещает Process внутри объёма трубки
  своего State. Точная новая композиция с центрированной проекцией Atom и
  внутренней Process-орбитой пока не переносится в production-контракт.
* В playground есть отдельный эксперимент `#/state-graph/process`: он берёт
  фактический Process 12 со всеми `action`, `success` и `error` Field-доступами,
  сохраняет владение State 19 и показывает Process на внутренней орбите State
  за центрированной проекцией Atom.

## Решения владельца

* Внутри State должна находиться проекция того же canonical Atom, а не новый
  дочерний Atom и не копия его данных.
* Центрированно вложенные State и Atom projection имеют не только один мировой
  центр, но и строго одинаковый внутренний диаметр Torus.
* Состав таких проекций одинаков; в разных ветвях State меняется выбранное или
  подсвеченное состояние.
* Ядро каждой проекции содержит все Fields canonical Atom, а не только Fields,
  используемые Conditions текущего State или его Process.
* Связи родительских Fields с Fields проекции показываются только там, где они
  нужны Conditions соответствующего Transition.
* Глубина модели концептуально может быть рекурсивной, но одновременно видимая
  глубина должна оставаться ограниченной. Дальние уровни допустимо показывать
  упрощённым изображением и уточнять при навигации внутрь.
* У Process нет общего Torus: его `action`, `success` и `error` показываются
  самостоятельными Tori на одной внутренней орбите State за центрированной
  проекцией Atom. Три Torus имеют общий радиус и разнесены на `120°`, поэтому
  равноудалены от центра и друг от друга. Ядро каждого содержит точные Field
  projections, используемые этим обработчиком.
* Каждый Field внутри Handler Torus соединяется только с соответствующим
  canonical Field в ядре Atom projection. `action.read` направлен от Atom к
  обработчику верхней Hermite-дугой; `success.write` и `error.write` направлены
  от обработчика к Atom нижними Hermite-дугами.
* Результат `action` передаёт Field projections в `success` или `error` по
  совпадающему canonical `Field.id`. Каждая Field-to-Field связь остаётся одной
  компактной endpoint/tangent-кривой с endpoint в точном центре каждой
  Field-сферы. Обе её endpoint-касательные направлены вниз, поэтому кривая
  выходит из action Field под общей плоскостью, один раз пересекает её и
  приходит к result Field сверху. Result batch хранит один радиус
  Handler-орбиты, один угол source Handler и по одному углу target Handler на
  кривую. Поэтому весь Field-пучок идёт по одному Handler route, а локальные
  смещения Fields не искажают орбиту. Связь между Tori и составная кривая не
  создаются.
* При прямой реконструкции renderer buffer долгота идёт по кратчайшей дуге
  Handler-орбиты, а синусная широта создаёт S-глубину непосредственно на сфере
  с радиусом этой орбиты. Локальные смещения Fields плавно затухают только у
  endpoints: точные центры Field-сфер сохраняются, а центральная половина
  отклоняется от сферы не больше чем на `0.05` layout units. Отдельной плоской
  кривой и следующей стадии деформации нет; sampled path не хранится.
* Сейчас направление фиксируется как отложенная задача; production layout,
  Bulk Store и renderer не меняются.

## Открытые вопросы

* Как строятся внутренние орбиты State и как на них размещаются несколько
  Process и их обработчики без пересечений.
* Какая минимальная проекция canonical Atom нужна внутри State и где проходит
  предел геометрии, текстуры или другого упрощённого представления.
* Какой точный runtime-бюджет ограничивает видимую глубину, количество
  экземпляров, GPU work и память.
* Как однозначно сопоставлять parent Field, projected Field и Condition, чтобы
  не показывать посторонние связи и не дублировать canonical relations.
* Где относительно Atom и State должны находиться Reaction, Mass и Energy.

## Границы

* Не материализовать бесконечное дерево сцены и не объявлять рекурсию бесплатной.
* Не копировать canonical Atom, его Fields или relations для каждого уровня.
* Не менять действующие layout-контракты до отдельного решения владельца.
* Не вводить GPU-, texture- или LOD-refactor до утверждения смысловой модели и
  измеримого бюджета.

## Критерии готовности

* Документ-владелец задаёт точный закон self-projection, внутренней орбиты
  Process и допустимых Field/Transition-связей.
* Public projection и Bulk Store сохраняют canonical identity без второго
  semantic Store и без копий одной сущности на каждый уровень.
* Один ограниченный алгоритм управляет видимой глубиной и имеет измеренный
  предел CPU, GPU и памяти.
* Playground доказывает несколько State одной композиции с разной активностью,
  орбитальный Process, несколько Process и точные `action/success/error` связи.
* Production-путь после отдельного решения владельца подтверждён тестами,
  визуальной проверкой и отсутствием полного rebuild сцены при навигации.
