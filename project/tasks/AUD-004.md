# AUD-004 — Сериализовать начальные чтения Boundary

## Зачем

Начальное состояние каждого домена должно представлять один согласованный
момент, иначе рождение Matrix или Bulk может смешать строки до и после записи.

## Подтверждённые факты

`materialize()` и `graphSnapshot()` используют общую очередь, а публичные
`initialState()`, `initialProjection()` и `replay()` обходят её.
`readBoundaryInitialState()` выполняет несколько последовательных запросов.

## Решение владельца

Полная сессия одного доверенного агента доказана и `MF-104` закрыта. Теперь все
четыре начальных чтения входят в ту же очередь, что `materialize()`, без новой
access policy или многопользовательского договора.

## Границы

* Сериализовать все четыре начальных чтения с записью.
* Не позволять чтению смешивать строки разных моментов.
* Сохранить один согласованный фундамент начального Bulk Store.

## Критерии готовности

Прямая проверка выполняет чтение одновременно с записью и доказывает один
согласованный срез.

## Результат

* `initialState`, `initialProjection`, `replay` и составной `graphSnapshot`
  используют одну последовательную границу вместе с `materialize`.
* Чтения, поставленные между двумя изменениями, целиком видят результат первого
  и ни одной части второго.
* Новая access policy, параллельный журнал и новая схема Boundary не добавлены.

## Проверка результата

* `bun test boundary/initial.spec.ts boundary/graph.spec.ts`
* `bun run typecheck`
* полный `bun run check` выполняется перед коммитом результата.
