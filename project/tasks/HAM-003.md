# HAM-003 — Разделить Hamiltonian по средам исполнения и механизмам

## Коротко

Сделать устройство Hamiltonian читаемым от штатной команды запуска до каждого
runtime-механизма. Сохранить одну тонкую точку входа, но разнести Bun host,
HTTP/REST, публикацию browser release, control transport, lifecycle, процессы,
peer, page, Service Worker и остальные Worker entrypoints по явным владельцам и
односторонним зависимостям.

## Зачем

Сейчас `bun run start` ведёт прямо в `hamiltonian/host.ts`, где в одном файле
собраны HTTP/TLS listener, static routes, browser build/watch, WebSocket
protocol, lifecycle aggregation, process и peer supervision, Web Push adapter и
laboratory REST API. Чтобы добавить новый REST endpoint, сначала приходится
разбираться во всём серверном runtime.

Та же проблема повторяется на browser-стороне: крупные `service-worker.ts`,
`public/app.js`, `core/lifecycle.js` и orchestration-модули одновременно несут
несколько обязанностей. Необъяснённая смесь JavaScript и TypeScript скрывает,
где находится настоящая platform boundary, а где сохранилась только
историческая форма файла.

Нужен не перенос по размерам и старым именам, а предметное понимание каждого
механизма, его runtime, состояния, внешнего договора, причинных входов и
потребителей. Только после этой карты код переносится небольшими эквивалентными
срезами с проверкой действующего пользовательского контура.

## Связь с дорожной картой

Задача относится к разделу
[`Hamiltonian и воплощения`](../ROADMAP.md#hamiltonian-и-воплощения). Она делает
физическую структуру доказанного standalone contour пригодной для дальнейших
placement, control и update-срезов, не принимая за них новых предметных решений.

## Связанные задачи и история

* `HAM-002` уже отделяет только Hamiltonian-specific visualization в
  `hamiltonian/visual`; lifecycle, control и bootstrap намеренно остаются за её
  границей. Текущая команда этой задачи помогает довести оставшиеся срезы
  `HAM-002`, но не прячет их visual-result внутри общего source refactor.
* Закрытая `UPD-001` сначала сняла import graph, затем по одному механизму
  собрала update-код под `hamiltonian/update/{shared,host,browser}` без изменения
  поведения. Это подтверждённый образец последовательности, а не готовая схема
  всех Hamiltonian-модулей.
* `UPD-002` меняет полный browser release contract. HAM-003 не перемещает
  одновременно затронутые host, Service Worker и page paths без точной
  координации с checkpoint текущего update-среза.
* Закрытая Web Push работа вынесла переиспользуемый runtime-separated механизм
  в `@metafor/web-push`, а Hamiltonian-specific identity, WSS wake и
  visualization сохранила в Hamiltonian adapter.
* `NODES-009.1`–`NODES-009.5` доказали односторонние границы `nodes`,
  `@nodes/layout`, `@nodes/ui`, `@nodes/hud` и вернули product palette в
  Hamiltonian. Общий пакет не должен знать Hamiltonian.
* Короткие `server.ts` в Boundary, Matrix, Energy и Bulk показывают полезную
  форму тонкого domain entrypoint. Dark остаётся историческим исключением, а не
  шаблоном для нового refactor.
* Историческая линия также содержит ранний удобный монолит Hamiltonian. Он был
  полезен как standalone proof, но его скорость изменения не является
  долгосрочной модульной границей.

## Подтверждённые факты

* `hamiltonian/package.json` определяет `start` как `bun run host.ts`.
* На baseline `main@0d6d4de2050c291f14bd319e186e365fa1caac34`
  `host.ts` содержит 2579 строк, `browser/service-worker.ts` — 1791,
  `core/lifecycle.js` — 1730,
  `browser/orchestration/lifecycle-projection.ts` — 1421,
  `public/app.js` — 1145, `browser/orchestration.ts` — 813.
* Размер является только сигналом смешанной ответственности. Граница
  определяется фактическим state ownership, side effects, runtime и import
  graph.
* В Hamiltonian уже существуют хорошие внутренние границы
  `hamiltonian/visual` и `hamiltonian/update`; переиспользуемые механизмы уже
  представлены отдельными `pkg/*` только там, где подтверждён самостоятельный
  договор и другие потребители.
* Текущие browser files исполняются разными способами: часть собирает host,
  часть публикуется напрямую, часть является отдельным Worker entrypoint.
  Поэтому вопрос `.js` или `.ts` нельзя решать одним массовым rename.

## Решения владельца

* Всё, что принадлежит только Hamiltonian, находится внутри Hamiltonian.
* Переиспользуемая часть получает отдельный пакет только после отделения
  Hamiltonian-specific identity, policy и composition.
* Сервер Hamiltonian является singleton: production process создаёт ровно один
  Bun server единственным прямым вызовом `Bun.serve` в штатной точке входа.
  Вторые server instances внутри того же процесса запрещены.
* Серверная декомпозиция выполняется чистыми именованными функциями. Функция
  получает все необходимые данные явными аргументами и возвращает результат;
  она не создаёт скрытый service instance и не владеет неявным mutable state.
  Единственный необходимый I/O остаётся у явных callbacks singleton-сервера и
  передаёт вычисления этим функциям.
* Прикладные `class`, `new`, constructor injection, composition container и
  `create*Server`/`start*Server` factories, создающие server, routes или
  Hamiltonian server mechanism owners, запрещены. Простая группировка функций
  по модулю не является основанием создавать объект с методами или жизненным
  циклом.
* Единственное состояние server runtime хранится как явные данные singleton-
  контура и передаётся функциям; его нельзя размножать по owner instances.
* Сервер должен иметь одну понятную точку запуска, но не один файл со всей
  реализацией: `server.ts` показывает singleton `Bun.serve`, а предметные
  вычисления импортирует как функции из понятных модулей.
* Модули распределяются по предметному смыслу и среде исполнения; исторические
  имена разрешено менять, если они искажают текущую ответственность.
* Рефакторинг должен помочь завершить уже начатую `HAM-002` и сохранить работу
  `UPD-002`, а не объявить их неудобными внешними помехами.
* Поведение, topology, lifecycle, update, transport и visual semantics не
  меняются скрыто вместе со структурным переносом.

## Целевая форма

```text
одна штатная команда запуска
└── server.ts
    ├── единственный прямой Bun.serve
    ├── plain routes object
    └── чистые функции предметных механизмов
```

## Обязательные требования к `server.ts`

1. `server.ts` является картой всей внешней границы Hamiltonian. По одному
   этому файлу разработчик должен понимать, какие запросы сервер принимает,
   какие условия проверяет и какой функции передаёт дальнейшую обработку.
1. В `server.ts` находится единственный прямой вызов `Bun.serve`. Созданный им
   Bun server является singleton production process; второй server instance и
   server factory запрещены.
1. Все HTTP/REST endpoints объявляются непосредственно в `routes` этого
   `Bun.serve`. Рядом с каждым endpoint видны path, допустимые HTTP methods,
   авторизация и остальные условия выбора обработчика.
1. Если один endpoint принимает несколько вариантов запроса, все варианты и
   условия выбора между ними находятся внутри самого handler этого endpoint в
   явном `switch/case` или `if/else`. Handler вызывает отдельную функцию для
   реализации выбранной ветки, но не передаёт ей скрытый выбор варианта.
   Скрытый универсальный HTTP dispatcher запрещён.
1. В `server.ts` видна полная WebSocket-граница: HTTP upgrade и callbacks
   `open`, `message`, `close`, `drain`.
1. В WebSocket `message` видны все поддерживаемые виды входящих сообщений и
   условие выбора каждого обработчика. Универсальная функция, внутри которой
   скрыты все message branches, запрещена.
1. `server.ts` не содержит предметную реализацию endpoint или WebSocket
   операции. Каждая видимая ветка только вызывает понятно названную функцию;
   её имя и явные аргументы показывают назначение обработки.
1. Серверная декомпозиция выполняется функциями, а не классами. Service,
   owner и composition instances, методы таких объектов, constructor injection
   и lifecycle containers запрещены.
1. Общий store или другое состояние нескольких функций объявляется простыми
   module-level данными в модуле-владельце. Ради хранения состояния нельзя
   создавать класс, service object или отдельный owner instance.
1. Структурный перенос не меняет URL, HTTP methods, авторизацию, ответы,
   WebSocket protocol, порядок effects или runtime behavior.

Точная директория каждого механизма определяется только после
`HAM-003.1`. Минимальные правила уже зафиксированы в
[`hamiltonian/README.md`](../../hamiltonian/README.md#закон-организации-исходников):

* executable entrypoint выбирает конфигурацию и собирает зависимости;
* HTTP/REST boundary Bun-воплощения видна отдельно от listener и composition;
* page, Service Worker, Dedicated Worker, layout Worker и peer process не
  смешивают runtime-specific side effects;
* shared contract не импортирует runtime implementation;
* composition зависит от механизмов, а механизмы не зависят от entrypoint;
* TypeScript является обычным source; каждый оставшийся JavaScript имеет
  доказанную причину прямого исполнения или публикации;
* новый общий пакет появляется только у фактически переиспользуемого договора,
  а не ради внешне чистого дерева директорий.

## Поведение процесса

Первый срез является только диагностическим: он фиксирует executable и served
entrypoints, runtime ownership, state/side-effect ownership, imports, bundles,
static routes, watchers, REST routes и причины JS/TS. Product source в нём не
перемещается.

После checkpoint руководитель регистрирует отдельные последовательные срезы по
одному причинному механизму. Обычная последовательность каждого move-среза:

1. frozen import/behavior witness и действующие focused tests;
1. move или rename без изменения public/runtime contract;
1. запрет обратного импорта и локальная typecheck/build/test защита;
1. проверка причинно связанного runtime, если механизм исполняется в нём;
1. checkpoint до следующего механизма.

Если перенос требует изменить поведение, public contract, другой owning domain
или среду приёмки, исполнитель останавливает расширение и регистрирует новый
срез. Файлы текущей подзадачи `UPD-002` или незавершённого среза `HAM-002` не
двигаются до checkpoint и согласованной границы, но их завершение остаётся
частью ответственности руководителя этой команды.

## Подзадачи

### HAM-003.1 — Зафиксировать точки входа и карту зависимостей Hamiltonian

Статус и исполнитель: `COMPLETE`, внутренний субагент текущей задачи Codex;
руководитель проверил карту по исходникам и tests.

Классификация: диагностический source-architecture срез; product files и
runtime behavior не изменяются.

Требование или диагностический результат: получить полную предметную карту от
каждого executable/served entrypoint до владеющих механизмов, exact HTTP/REST
boundary, runtime-specific side effects, shared contracts, bundle/static/watch
ownership и причин сохранения `.js` или перехода на `.ts`; на её основе задать
точную целевую структуру и атомарные следующие срезы.

Основание и связанная история: действующий закон организации исходников;
`HAM-002.1`, `UPD-001.1`, results `NODES-009.1`–`NODES-009.5`, Web Push package
boundary, карточки `HAM-002` и `UPD-002`, current package manifests, imports,
tests и Git-история крупных Hamiltonian файлов.

Наблюдаемое расхождение: штатный start и browser bootstrap входят в несколько
крупных mixed-responsibility файлов; место нового REST API и границы server,
page, Service Worker и shared lifecycle нельзя установить по дереву исходников.

Причина: подтверждена. Standalone proof рос добавлением runtime-поведения в
корневые host/page/core файлы. Позднейшие TypeScript bundles, visual/update
границы и reusable packages появились поверх прямой публикации прежних
JavaScript ESM, но общий execution/publication graph после этого не был
пересобран как единая архитектура.

Разрешённое изменение одного механизма: только карточка задачи с полным
inventory, подтверждёнными причинами, target dependency graph и порядком
move-only/rename-only подзадач; product source не изменяется.

Regression или опровергающее доказательство: все package scripts и executable
entrypoints, direct browser modules, Worker registrations, Bun.build entries,
static mappings, source watchers, HTTP/REST route registrations, public exports,
runtime imports и относящиеся к ним tests должны иметь ровно одного владельца в
inventory; пропущенный путь опровергает готовность среза.

Среда и критерий приёмки: canonical `main` из подготовительного commit этого
среза; карта позволяет от `bun run start` однозначно найти место нового REST
endpoint и проследить каждый browser/Worker bundle; для каждого крупного файла
отделены обязанности, state ownership и следующие независимые срезы; diff
содержит только project/domain documentation и проходит `git diff --check`.

Фактические действия: проверены canonical root, `main`, baseline, worktree и
чистое дерево; прочитаны постоянные законы, process, текущие `HAM-002` и
`UPD-002`, manifests, source и tests. Прослежены package scripts, `Bun.build`,
direct static map, source watchers, `Bun.serve.fetch`, WebSocket upgrade,
browser/Worker registrations, `Bun.spawn` entries и все импорты крупных mixed
files. Git-история показала исходный standalone monolith и последующие
послойные visual, update, Web Push и nodes extractions. Runtime не запускался,
product files не изменялись.

Результат и вывод: действующая структура содержит одну штатную команду, но не
тонкий entrypoint; семь основных execution-контуров и несколько способов
browser publication скрыты внутри нескольких общих файлов. REST adapter
отсутствует: API routes являются ветками общего `Bun.serve.fetch`. JavaScript
сохранился прежде всего у напрямую публикуемых browser ESM и общего
cross-runtime source; это объясняет форму, но не является постоянной
platform-необходимостью. Серверные entry/HTTP/control/lifecycle/process/peer
срезы независимы от browser release и могут начаться сразу. Visual moves
остаются у `HAM-002`; page, Service Worker, update и общий JS→TS переход ждут
точных checkpoints `HAM-002`/`UPD-002` и не дублируются здесь.

Действующий entrypoint, execution и publication inventory:

| Вход или runtime | Точка входа | Кто рождает или публикует | Фактическая ответственность |
| --- | --- | --- | --- |
| Bun server | `host.ts` | `bun run start` | CLI, composition, listener, HTTP, WSS, lifecycle, process, peer |
| Window | `public/window-entry.js` | `index.html` | ранний monitor, затем page и visual entry |
| Page runtime | `public/app.js` | Window entry, direct ESM | identity/lifecycle, WebRTC, SW API, Dedicated Worker, Web Push, update actions |
| Visual runtime | `browser/orchestration.ts` | host `Bun.build` | lifecycle subscriptions и пока ещё visual composition |
| Service Worker | `browser/service-worker.ts` | host `Bun.build`, page registration | control WSS, browser/profile journal, Window clients, push и update adapters |
| Dedicated Worker | `public/embodiment-worker-entry.js` | Page runtime, direct ESM | ранний monitor и worker embodiment runtime |
| Layout Worker | `visual/browser/layout-worker.ts` | visual runtime, host `Bun.build` | только layout adapter |
| Bun embodiment | `embodiment-process.ts` | `BunEmbodimentSupervisor` | отдельное process embodiment и IPC lifecycle |
| Peer process | `peer-process.ts` | `PeerProcessSupervisor` | Werift peer, signaling, RTC/DataChannel и IPC lifecycle |

Отдельные executable surfaces `create-tls.ts` и `soak/run.ts` не входят в
штатный start graph и сохраняют отдельные operational owners.

HTTP inventory внутри единственного `Bun.serve.fetch`:

* navigation: `GET /` и `GET /index.html`;
* browser publication: orchestration, layout Worker, Web Push client, Service
  Worker, static page/core/update assets;
* control transport: `/control` WebSocket upgrade;
* Web Push API: authenticated `GET /push/vapid-public-key` и
  `POST /lab/wake-service-worker`;
* update publication: authenticated `/manifest.json` и versioned module;
* laboratory observation: authenticated `/lab/status`.

У method semantics есть историческая асимметрия: navigation, VAPID и wake
проверяют method явно, а часть publication/status branches сейчас принимает
любой method. Structural extraction сначала сохраняет это наблюдаемое
поведение; его нормализация потребует отдельного requirement-среза.

Точная целевая зависимость:

```text
server.ts
-> server/composition
   -> server/listener
      -> server/http
         -> browser publication | update host | Web Push | lab status
      -> server/control-websocket
   -> server/lifecycle
   -> process supervision -> process entry
   -> peer supervision -> peer entry -> Werift adapter

browser/page entry -> page runtime + visual entry
browser/page runtime -> SW client | Dedicated Worker client | browser peer |
                        Web Push adapter | update contract
browser/service-worker entry -> SW mechanisms
browser/dedicated-worker entry -> worker runtime
visual entry -> visual package + layout Worker client
```

Entrypoints и composition зависят от механизмов; механизмы не импортируют
entrypoints. Shared contracts не импортируют runtime implementation.

Предметные target names после последовательных moves:

* корневой `host.ts` разделяется на тонкий `server.ts` и
  `server/composition.ts`;
* `public/app.js` становится `browser/page/runtime.ts`, а смешанный
  `core/orchestration.js` делится на shared browser/page identity и локальные
  page actions вместо сохранения общего имени `orchestration`;
* `embodiment-worker*` становится `browser/dedicated-worker/{entry,runtime}`;
* `embodiment-process.ts` становится `process/embodiment-entry.ts`;
* `peer-process.ts` становится `peer/process-entry.ts`;
* `core/lifecycle.js` отдельно делится на pure contract/validation,
  journal/registry и browser event adapter;
* `browser/orchestration.ts` после завершения `HAM-002` становится тонкой
  visual entry/composition, а не владельцем lifecycle механизма.

Следующие срезы выполняются без одного массового move:

1. сделать корневой server entrypoint явным и тонким;
1. отделить HTTP dispatch и route ownership от server composition, сохранив
   exact method/authorization/response behavior;
1. отделить browser publication/build/watch после checkpoint release contract;
1. отделить control WebSocket runtime;
1. отделить host lifecycle aggregation;
1. собрать существующие Bun process modules под process owner;
1. собрать peer supervision/entry/adapter под peer owner;
1. после `HAM-002` завершить visual entry boundary;
1. после checkpoints `UPD-002` разделить page и Service Worker mechanisms;
1. только затем переводить direct browser/core/update JavaScript в TypeScript
   по одному exact entry graph с сохранением URL и monitor-first ordering.

### HAM-003.2 — Сделать server entrypoint явным и тонким

Статус и исполнитель: `COMPLETE`, внутренний субагент текущей задачи Codex;
руководитель проверил diff и focused regressions.

Классификация: structural move-only срез operational entrypoint; host runtime
behavior и HTTP/control/lifecycle mechanisms не меняются.

Требование или диагностический результат: `bun run start` явно ведёт в
корневой `hamiltonian/server.ts`, который только создаёт Hamiltonian host,
публикует operational адреса и сообщает состояние запуска. Импортируемый
`host.ts` владеет factory/composition и больше не является executable CLI.

Основание и связанная история: закон организации исходников и checkpoint
`HAM-003.1`; короткие domain `server.ts` подтверждают понятную operational
форму, но конкретная реализация Hamiltonian сохраняет собственные multi-runtime
contracts.

Наблюдаемое расхождение: `hamiltonian/package.json` запускает `host.ts`, а в
конце того же 2579-строчного файла находятся `import.meta.main`, console output,
join URL projection и remote-HTTPS warning. По manifest нельзя отличить
operational entrypoint от всего host implementation.

Причина: первоначальный standalone proof объединил reusable host factory и CLI

Классификация: корректирующий source-architecture срез одного server

Требование или диагностический результат: `hamiltonian/server.ts`

Основание и связанная история: владелец отклонил результат `HAM-003.2-.7` после

process paths, но не отделили state/effect owners и не достигли исходной цели

visual layout, public paths, methods, payloads, timers, ordering, identity,
admission, lifecycle, Web Push, WebRTC или process behavior.

### HAM-003.9 — Объявить Bun routes непосредственно в `server.ts`

Статус и исполнитель: `IN_PROGRESS`, руководитель задачи Codex без субагентов.

Новое требование владельца: следовать документированному Fullstack Server API
Bun — объявить plain route object непосредственно в `Bun.serve({routes: {...}})`
файла `hamiltonian/server.ts`. `HamiltonianRoutes`, route factory и отдельный
`server/routes.ts` запрещены. HMR отключается явно, а `bun --hot` не
используется. Русский TSDoc каждого маршрута остаётся рядом с его фактической
регистрацией. Сервер является singleton: единственный production entrypoint
единственный раз вызывает `Bun.serve`. Декомпозиция серверной логики допускает
только чистые функции с явными входами и результатами; server classes,
mechanism instances, composition containers, constructors и server factories
запрещены. `server.ts` обязан показывать не только HTTP path registry, но и
полную входную WebSocket-поверхность: upgrade, `open`, `message`, `close`,
`drain`, все поддерживаемые `message.kind` и условия выбора между ними.

Расхождение и причина: checkpoint `151ab4cbb` удалил монолитный `host.ts`, но
ошибочно спрятал простую таблицу маршрутов в state-less class
`HamiltonianRoutes`. Класс не владеет состоянием или жизненным циклом и потому
является искусственной абстракцией поверх штатного Bun routes object.

Разрешённое изменение: перенести точные path/method bindings из
`server/routes.ts` в литерал `routes` непосредственного `Bun.serve`;
оставить внутри handler каждого endpoint явный `switch/case` или `if/else` со
всеми вариантами и условиями выбора, но передавать предметную реализацию
чистым именованным функциям. Аналогично WebSocket
callbacks и `message.kind` branches видны в `server.ts`, а каждая ветка только
вызывает свою функцию. Общие stores находятся как module-level данные в
предметном модуле. Удалить route/composition classes и любое factory-like
wiring. Integration-проверка запускает штатный singleton entrypoint в
изолированном процессе, а не создаёт второй listener через test factory.
Публичные URL, методы, ответы, авторизация, update/lifecycle и browser runtime
не меняются.

Критерий: source guard фиксирует ровно один прямой `Bun.serve`, literal routes
object и явный выключенный HMR в `server.ts`; отсутствие `server/routes.ts`,
server/route/composition classes, их instance construction, server factories и
второго listener. Route guard фиксирует все HTTP paths и methods, а также
проверяет, что варианты и conditions находятся в `switch/case` или `if/else`
самого endpoint handler, а не скрыты в вызываемой функции.
WebSocket guard фиксирует upgrade, `open/message/close/drain`, все текущие
client message kinds и вызов отдельной именованной функции в каждой ветке.
Предметная реализация этих операций отсутствует в `server.ts`, а вынесенная
логика проверяется как функции. Полный Hamiltonian suite, strict server
TypeScript, restart LaunchAgent и точный CDP target проходят.

## Критерии готовности

1. От `bun run start` видна одна тонкая server entrypoint и отдельные composition,
   HTTP/REST, publication/build, control, lifecycle, process, peer и Web Push
   границы.
1. Page, Service Worker, Dedicated Worker, layout Worker и peer имеют явные
   entrypoints, runtime adapters и односторонние contracts.
1. Каждый Hamiltonian-specific модуль находится внутри `hamiltonian`; каждый
   общий пакет имеет самостоятельный договор и фактическую переиспользуемость.
1. У каждого first-party `.js` есть доказанная platform-причина; остальной
   source переведён в TypeScript отдельными проверенными срезами.
1. Названия директорий и модулей описывают действующую ответственность, а не
   сохраняют историческое `orchestration`, `app` или `host` без уточнения.
1. REST endpoint добавляется внутри явного HTTP adapter без изменения server
   composition, bundle pipeline, lifecycle aggregation и peer supervision.
1. Import graph не содержит runtime cycles, reverse entrypoint imports или
   Hamiltonian imports из universal packages.
1. Все существующие unit, typecheck, browser build, Service Worker, host,
   release и live Hamiltonian scenarios остаются причинно эквивалентными
   baseline.
1. `HAM-002` доведена по своей visual-границе, а изменения `UPD-002` либо
   интегрированы после её checkpoint, либо не затронуты и явно защищены.
