# ENGINE-002 — Уменьшить передачу данных рендера без изменения картинки

## Коротко

Обычные прямоугольники, линии и текст не должны каждый кадр передавать на GPU
зарезервированные данные скелетной анимации. Объекты со скелетом продолжают
работать как прежде, а живая сцена Hamiltonian выглядит и ведёт себя так же.

## Зачем

Текущий Renderer хранит данные обычного объекта и матрицы `128` костей в одном
блоке. Поэтому каждый render item занимает `8448` байт даже тогда, когда у него
нет скелета.

Профилирование Hamiltonian на текущем срезе показало около `4,3` МБ записей
uniform-данных за один кадр при отсутствии skinned mesh. Разделение обычных
uniform-данных и матриц костей должно сократить этот объём примерно до `131` КБ,
но точный эффект требуется заново измерить после реализации.

## Связь с текущей работой

Это техническая подзадача текущего визуального среза
[`MF-424 — Визуально довести Hamiltonian вместе с владельцем`](MF-424.md) и
первого режима [`MF-425 — Управлять одной Вселенной на одном устройстве`](MF-425.md).
Она оптимизирует общий MetaFor Engine, а Hamiltonian служит первым живым
сценарием проверки.

Задача не блокирует дальнейшую визуальную доводку MF-424 и не заменяет
визуальную приёмку владельцем.

## Подтверждённые факты

* В `Renderer` один `PER_OBJECT_DATA_SIZE` сейчас складывает `256` байт обычных
  uniform-данных и `8192` байта матриц костей.
* Один общий буфер и один общий CPU-массив заполняются и записываются по полному
  размеру для каждого render item.
* В проверенном кадре Hamiltonian не было skinned mesh; capture содержал `511`
  draw-вызовов, два render-pass и не содержал WebGPU validation errors.
* GPU timestamp-query в этой проверке был недоступен. Точное GPU-время и
  фактический выигрыш пока не доказаны.
* Предупреждение Inspector о повторных `setBindGroup` не является основанием
  удалять их: вызовы используют разные dynamic offsets объектов.

## Решение владельца

* Оптимизацию вести отдельной задачей уровня Engine с префиксом `ENGINE`.
* Не менять ради неё наблюдаемое поведение и вид Hamiltonian.

## Границы

* Не добавлять специальную ветку Renderer только для Hamiltonian.
* Не уменьшать DPR, MSAA, частоту анимации, число нод, связей или сообщений.
* Не менять text stencil/cover, порядок прозрачного рендера и визуальные
  материалы.
* Не удалять обязательные dynamic offsets и bind group только по эвристике
  Inspector.
* Сохранить действующую поддержку skinned mesh и предел `128` костей.
* Не менять observer frame-readback и `copyTextureToTexture` в этой задаче.
* WebGPU Inspector остаётся внешним диагностическим инструментом и не входит в
  исходники или browser bundle MetaFor.

## Критерии готовности

* Обычные per-object uniform-данные и матрицы костей хранятся раздельно.
* Объект без скелета не очищает и не загружает собственный блок из `128` костей.
* Skinned mesh получает те же model, normal и bone matrices и сохраняет
  действующий результат обычных Engine-проверок.
* В живом Hamiltonian сохраняются ноды, связи, traffic particles, текст,
  выбор, pan/zoom и HUD без визуальной регрессии.
* Повторный GPU capture содержит render-pass и draw-вызовы без validation
  errors и показывает ожидаемое сокращение `writeBuffer` bytes.
* Clean frame-health и instrumented GPU capture измерены отдельно; отсутствие
  GPU timestamp-query явно отмечено, если оно повторится.

## Проверка результата

* Сфокусированные тесты Renderer и skinned mesh.
* `bun test pkg/engine hamiltonian/browser/orchestration`.
* `bun run typecheck`.
* Живая проверка Hamiltonian через `$metafor-visual-profiling`: clean frame
  stats, точная вкладка, camera-drag capture и проверка WebGPU validation
  errors.
* Сравнение количества и объёма `writeBuffer` до и после на сопоставимом кадре.

## Результат реализации

* `Renderer` хранит обычные per-object uniform-данные и матрицы костей в
  отдельных GPU/CPU-буферах. Обычный объект занимает `256` байт; блок
  `8192` байта записывается только для `skinned-mesh`.
* Для нескольких соседних skinned mesh записи bone-данных объединяются в один
  диапазон, а разреженные обычные объекты между ними не загружаются.
* Сфокусированный тест проверяет фактическую запись всех `128` матриц,
  обнуление незанятого хвоста и отсутствие записи `129`-й матрицы за границей
  блока.
* `bun test pkg/engine hamiltonian/browser/orchestration`: `83 pass`, `0 fail`.
* `bun run typecheck` и `git diff --check` завершились успешно.
* После полного перезапуска Hamiltonian отдельный трёхсекундный frame-health
  sample показал `120.5 fps`, `0` dropped frames, средний кадр `8.317 ms`,
  worst frame `18.6 ms`, CPU submit `0.2 ms`.
* Подтверждённый camera-drag capture `cap-7`: `516` draw-вызовов, `2`
  render-pass, `3` вызова `writeBuffer`, `132112` байт суммарно и `0` WebGPU
  validation errors. Из них per-object запись занимает `132096` байт — ровно
  `516 × 256`.
* При прежней раскладке тот же объектный набор потребовал бы `516 × 8448`, то
  есть передача per-object данных уменьшена ровно в `33` раза без уменьшения
  числа draw-вызовов.
* Визуальная проверка сохранила полную схему, связи, подписи и HUD. Эвристика
  Inspector про повторные bind group остаётся ложным срабатыванием: соседние
  вызовы используют offsets `[0, 0]`, `[256, 8192]`, `[512, 16384]`.
* GPU timestamp-query остался недоступен (`gpuTimeMs: null`), поэтому точное
  изменение GPU-времени не утверждается. Frame-health sample снят отдельно от
  capture, но текущая CDP-сессия уже была instrumented; он не считается новым
  clean cold-start измерением.
