# UI-008 — Загружать production UI модули без дублирования ядра

## Коротко

Продукт создаёт один WebGPU runtime и по необходимости динамически загружает
Button, Field, NodeEditor и другие UI-модули. Engine, Elements и общий код
Components присутствуют в итоговом module graph ровно один раз, а leaf-модуль
содержит только собственную реализацию.

## Зачем

Исходники уже разделены `Engine → Elements → Components → Node UI`, но public
exports оформлены неравномерно, а отдельная self-contained сборка каждого leaf
повторяет общий runtime и renderer. Для продуктовых проектов нужен единый ESM
contract: exact subpath import, динамический `import()`, общий split chunk и
одна runtime identity.

## Связь с дорожной картой

Задача продолжает универсальную WebGPU UI component library и создаёт её
production delivery boundary. Она не меняет Hamiltonian loader/release и не
владеет dev Workbench.

## Подтверждённые факты

* `UiRuntime` создаётся consumer bootstrap через `UiRuntime.create(canvas)`.
  `runtime.addSurface(surface, layout)` вызывает `surface.attachCanvas(runtime)`;
  обычные Element/Component functions получают `UiSurface`, а не создают свой
  runtime.
* Current exports: Engine только `.`, Elements `.` и `./flex`, Components только
  `.`, Node UI уже имеет три независимых subpath.
* `@nodes/ui` ошибочно держит dev-only `@ui/playground` в production
  dependencies.
* Bun `splitting` по умолчанию выключен. Отдельные browser builds на baseline:
  Button `480939`, Field `538575`, NodeEditor `485414` bytes — общий код
  повторяется.
* Те же три entrypoints в одной split build дают `494134`-byte shared core,
  `45082`-byte shared Components chunk, `37861`-byte NodeEditor и tiny
  Button/Field entrypoints; суммарно `577734` bytes. Текущие исходники уже
  структурно допускают дедупликацию, но manifest/delivery contract её не
  гарантирует.

## Решения владельца

1. Product bootstrap создаёт один `UiRuntime` на canvas/scene. Динамический
   leaf не создаёт второй runtime и не владеет его lifecycle.
2. Function-based Element/Component принимает существующую `UiSurface`.
   Surface-component создаётся leaf factory и подключается только через
   `runtime.addSurface()` владельца продукта.
3. Production modules публикуются как ESM subpath exports. Root barrels
   сохраняются для обычного статического consumer, но lazy consumer использует
   exact leaf import.
4. Exact Elements imports: `@ui/elements/runtime`, `surface`, `primitives`,
   `button`, `div`, `span`, `text`, `img`, `input`, `list`, `scrollbar`,
   `style`, `flex`, `flex-css`, `theme`, `icons`, `icon`, `polyline`,
   `virtual-input`, `targets`.
5. Exact Components imports: lowercase subpaths `button`, `field`, `pane`,
   `checkbox`, `badge`, `typography`, `text-field`, `switcher`,
   `progress-checkbox`, `slider-control`, `divider`, `list`, `table`.
6. Node UI сохраняет `node-editor`, `blender-node`, `link-curve`. Engine остаётся
   одной канонической root identity `@metafor/engine`; параллельные aliases
   одного Engine запрещены.
7. Product/release build получает весь набор entrypoints одним ESM graph и
   включает code splitting. Собирать каждый leaf отдельным self-contained
   bundle с собственной копией Engine/Elements запрещено.
8. Повторный dynamic import того же exact specifier использует browser module
   cache. Разные URL/revision одного core не считаются одной module identity.
9. UI-008 не публикует packages в npm, не меняет Hamiltonian release protocol и
   не добавляет production dependency на `@ui/playground`.

## Критерии готовности

1. Каждый заявленный subpath существует, компилируется и экспортирует только
   свой production contract.
2. Root imports остаются совместимыми; playground symbols не попадают в
   production exports.
3. Product fixture использует настоящий `import()` и один bootstrap-owned
   runtime host.
4. Split graph содержит leaf chunks и единственную реализацию Engine/UiRuntime;
   aggregate существенно меньше суммы independent self-contained builds.
5. UI-007 получает exact import checkpoint и не дублирует production contract.
6. Package/root typechecks, boundary tests и diff-check проходят.
