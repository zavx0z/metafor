# HAM-005 — Собрать стандартное окружение визуализации Window

## Коротко

Обновляемый `@import/main` создаёт стандартную Window-среду визуализации:
один canvas и один `UiRuntime` с принадлежащими ему `Space` и `HUD`. В первом
результате среда остаётся пустой от project-specific displays и surfaces:
встроенный surface-display отключён, graph и HUD-панели ещё не подключаются.

Статические HTML, style и font resources принадлежат существующему
`hamiltonian/web/static`. Executable initialization и lifetime `UiRuntime`
принадлежат `hamiltonian/web/import/main`.

## Зачем

Каждому последующему Window module нужен один общий visual host. Если первый
нодовый module сам создаст `Space`, `HUD` и renderer, эта инфраструктура станет
случайной собственностью одного module и следующие modules смогут создать
параллельные runtime. Стандартное пустое окружение должно появиться раньше
Hamiltonian graph, Inspector и другого предметного содержимого.

## Связь с дорожной картой

Задача продолжает clean-room направление
[`Загрузка Hamiltonian`](../ROADMAP.md#загрузка-hamiltonian) после уже
материализованного Window importer из [`LOAD-001`](LOAD-001.md). Она не
расширяет неизменяемый startup, не является update-механизмом `UPD-002` и не
продолжает structural refactor прототипа из [`HAM-002`](HAM-002.md).

## Связанные задачи и история

* `HAM-002.3`–`HAM-002.7` собрали и визуально проверили нодовый UI отдельно
  запускаемого прототипа. После owner-решения, зафиксированного в `e89c60e1e`,
  этот source остаётся behavior evidence и не переносится в clean-room loader.
* `LOAD-001.15` создала `@import/main`; correction `df3bcb663` вернула module
  composition из неизменяемого startup в обновляемый слой import. Действующий
  `@import/main` пока только подтверждает запуск сообщением в console.
* `HAM-004-R77`–`HAM-004-R84` закрепили слои `startup → import → modules`,
  function-owned modules и границу прототипа. Новый результат отличается от
  первого `internal`/`metafor` module: он создаёт общую Window-среду самого
  importer до предметного наполнения.
* Вынесенный в `/Users/zavx0z/repozitarium/interpreter` Interpreter служит
  действующим reference: его Window entrypoint создаёт один `UiRuntime` с
  `surfaceDisplay: false`, а затем добавляет явно именованные `UIDisplay`.
  Interpreter не является source dependency этой задачи.

## Подтверждённые факты

* `UiRuntime.create()` сам создаёт корни `Space` и `HUD`; отдельные
  `new Space()` и `new HUD()` не образуют полноценный visual runtime с
  renderer, ViewPoint, input и lifecycle.
* `surfaceDisplay: false` оставляет `runtime.display === null` и позволяет
  последующим владельцам создавать только явно именованные `UIDisplay` через
  `createDisplay()`.
* Текущий `hamiltonian/web/static/index.html` не содержит canvas, а
  `hamiltonian/web/import/main/main.ts` не создаёт visual runtime.
* `UiRuntime.create()` загружает font до завершения initialization. Постоянный
  font находится в `pkg/engine/static`, но новый clean-room server пока не
  публикует его через `hamiltonian/web/static`.
* `UiRuntime` сейчас использует `HTMLCanvasElement`, `window` и `document` и
  запускается в Window. Существующий layout Worker доказывает только отдельную
  worker-compatible вычислительную границу, не worker-rendering HUD/Space.

## Решения владельца

* Стандартное пустое visual-окружение создаётся отдельной задачей `HAM-005`, а
  не подзадачей `LOAD-001` и не продолжением `HAM-002`.
* Один общий `UiRuntime`, `Space` и `HUD` принадлежат `@import/main` как
  стандартной Window-среде для последующих modules.
* Первый результат не создаёт implicit или explicit project display, graph,
  Inspector, canvas controls либо другой HUD surface.
* Стандартные HTML, style и font resources обслуживает существующий
  `hamiltonian/web/static`; новый visual package или параллельный static owner
  не создаётся.
* Prototype `hamiltonian/visual` остаётся только reference поведения и не
  импортируется, не копируется и не переносится.

## Поведение процесса

Задача зарегистрирована отдельно от реализации. Перед первым product patch
руководитель создаёт последовательную подзадачу `HAM-005.1` с одним
наблюдаемым результатом, фиксирует её отдельным project-коммитом и только затем
изменяет code или static resources.

По прямому решению владельца задача выполняется только владельцем и текущим
Codex: субагенты не создаются и работа им не передаётся. Codex подготавливает
project/source changes и команды проверки, но не запускает и не перезапускает
Hamiltonian, browser contour, build или tests. Владелец сам выполняет запуск и
живую проверку, после чего сообщает наблюдаемый результат для фиксации в
карточке.

Пустой тёмный screenshot сам по себе не доказывает создание `Space` и `HUD`.
Первый срез обязан дать evidence фактического object tree и отсутствия

## Открытые вопросы

* Какой минимальный локальный ABI позже передаёт один созданный runtime
  загружаемым Window modules, не создавая глобальный mutable registry?
* Как последующий `internal/visual` создаёт первый явно именованный graph
  `UIDisplay`; это не входит в пустое стандартное окружение.
* Нужен ли отдельный worker entrypoint следующему visual module кроме уже
  существующего чистого layout protocol; worker-rendering не предполагается.

## Границы

Входит:

* стандартный canvas host, style и font resource через
  `hamiltonian/web/static`;
* создание и завершение одного `UiRuntime` в `@import/main`;
* `surfaceDisplay: false` и отсутствие project-specific surfaces;
* минимальная наблюдаемость действительного `Space`/`HUD` object tree;
* package/build/typecheck и browser regression этой Window-среды.

Не входит:

* импорт или перенос `hamiltonian/visual` и `browser/orchestration*`;
* `NodeSystemSurface`, graph projection, Inspector, canvas controls, palette,
  layout transition или lifecycle data;
* выбор первого `internal`/`metafor` module, его cache и Window module ABI;
* Dedicated Worker rendering, `OffscreenCanvas` или изменение Engine/UI для
  worker execution;
* изменение Service Worker importer, RPC, startup primitives, update release
  или Bun/server loading path;
* изменение Bulk, `pkg/visual` или универсальных `@nodes/*` законов.

## Критерии готовности

* После запуска `@import/main` страница содержит один полноразмерный canvas и
  один успешно созданный `UiRuntime`.
* Фактическое дерево содержит один `Space` и один `HUD`; `runtime.display`
  равен `null`, project-specific displays и surfaces отсутствуют.
* Font и остальные необходимые static resources обслуживаются через
  `hamiltonian/web/static` с корректным MIME и действующей cache-first policy.
* `@import/main` не импортирует prototype Hamiltonian, `internal`/`metafor`
  modules, Bulk или node-system presentation.
* Неизменяемые `@startup/main` и `@startup/service`, Service Worker RPC и
  существующие cache boundaries сохраняют поведение.

## Проверка результата

Следующие проверки подготавливает Codex, но запускает владелец:

* strict typecheck/build `@import/main` и нового clean-room Hamiltonian server;
* focused static route probe для HTML, style/font resource и MIME;
* browser regression первого install и повторной controlled navigation без
  дублирования canvas или `UiRuntime`;
* browser evidence фактических `Space`, `HUD`, `display === null` и отсутствия

`git diff --check`; результаты runtime, build или tests не утверждаются без
запуска владельцем.
