# HAM-005 — Собрать стандартное окружение визуализации Window

## Коротко

Обновляемый `@import/main` создаёт стандартную Window-среду визуализации:
один canvas и один `UiRuntime` с принадлежащими ему `Space` и `HUD`. В первом
результате среда остаётся пустой от project-specific displays и surfaces:
встроенный surface-display отключён, graph и HUD-панели ещё не подключаются.

Статические HTML, style и font resources принадлежат существующему
`hamiltonian/web/static`. Executable initialization и lifetime `UiRuntime`
принадлежат `hamiltonian/web/import/main`.

## Зачем

Каждому последующему Window module нужен один общий visual host. Если первый
нодовый module сам создаст `Space`, `HUD` и renderer, эта инфраструктура станет
случайной собственностью одного module и следующие modules смогут создать
параллельные runtime. Стандартное пустое окружение должно появиться раньше
Hamiltonian graph, Inspector и другого предметного содержимого.

## Связь с дорожной картой

Задача продолжает clean-room направление
[`Загрузка Hamiltonian`](../ROADMAP.md#загрузка-hamiltonian) после уже
материализованного Window importer из [`LOAD-001`](LOAD-001.md). Она не
расширяет неизменяемый startup, не является update-механизмом `UPD-002` и не
продолжает structural refactor прототипа из [`HAM-002`](HAM-002.md).

## Связанные задачи и история

* `HAM-002.3`–`HAM-002.7` собрали и визуально проверили нодовый UI отдельно
  запускаемого прототипа. После owner-решения, зафиксированного в `e89c60e1e`,
  этот source остаётся behavior evidence и не переносится в clean-room loader.
* `LOAD-001.15` создала `@import/main`; correction `df3bcb663` вернула module
  composition из неизменяемого startup в обновляемый слой import. Действующий
  `@import/main` пока только подтверждает запуск сообщением в console.
* `HAM-004-R77`–`HAM-004-R84` закрепили слои `startup → import → modules`,
  function-owned modules и границу прототипа. Новый результат отличается от
  первого `internal`/`metafor` module: он создаёт общую Window-среду самого
  importer до предметного наполнения.
* Вынесенный в `/Users/zavx0z/repozitarium/interpreter` Interpreter служит
  действующим reference: его Window entrypoint создаёт один `UiRuntime` с
  `surfaceDisplay: false`, а затем добавляет явно именованные `UIDisplay`.
  Interpreter не является source dependency этой задачи.

## Подтверждённые факты

* `UiRuntime.create()` сам создаёт корни `Space` и `HUD`; отдельные
  `new Space()` и `new HUD()` не образуют полноценный visual runtime с
  renderer, ViewPoint, input и lifecycle.
* `surfaceDisplay: false` оставляет `runtime.display === null` и позволяет
  последующим владельцам создавать только явно именованные `UIDisplay` через
  `createDisplay()`.
* Текущий `hamiltonian/web/static/index.html` не содержит canvas, а
  `hamiltonian/web/import/main/main.ts` не создаёт visual runtime.
* `UiRuntime.create()` загружает font до завершения initialization. Постоянный
  font находится в `pkg/engine/static`, но новый clean-room server пока не
  публикует его через `hamiltonian/web/static`.
* `UiRuntime` сейчас использует `HTMLCanvasElement`, `window` и `document` и
  запускается в Window. Существующий layout Worker доказывает только отдельную
  worker-compatible вычислительную границу, не worker-rendering HUD/Space.

## Решения владельца

* Стандартное пустое visual-окружение создаётся отдельной задачей `HAM-005`, а
  не подзадачей `LOAD-001` и не продолжением `HAM-002`.
* Один общий `UiRuntime`, `Space` и `HUD` принадлежат `@import/main` как
  стандартной Window-среде для последующих modules.
* Первый результат не создаёт implicit или explicit project display, graph,
  Inspector, canvas controls либо другой HUD surface.
* Стандартные HTML, style и font resources обслуживает существующий
  `hamiltonian/web/static`; новый visual package или параллельный static owner
  не создаётся.
* Prototype `hamiltonian/visual` остаётся только reference поведения и не
  импортируется, не копируется и не переносится.

## Поведение процесса

Задача зарегистрирована отдельно от реализации. Перед первым product patch
руководитель создаёт последовательную подзадачу `HAM-005.1` с одним
наблюдаемым результатом, фиксирует её отдельным project-коммитом и только затем
изменяет code или static resources.

По прямому решению владельца задача выполняется только владельцем и текущим
Codex: субагенты не создаются и работа им не передаётся. Codex подготавливает
project/source changes и самостоятельно выполняет package typecheck, но не
запускает и не перезапускает Hamiltonian, browser contour, build или tests.
Владелец сам выполняет остальные запуски и живую проверку, после чего сообщает
наблюдаемый результат для фиксации в карточке.

Пустой тёмный screenshot сам по себе не доказывает создание `Space` и `HUD`.
Первый срез обязан дать evidence фактического object tree и отсутствия
встроенного display, не добавляя WebGPU Inspector или другую диагностическую
обвязку в product source.

## Подзадачи

### HAM-005.1 — Создать пустую Window-среду Space и HUD

Статус и исполнитель: `IN_PROGRESS`, source checkpoint подготовлен; текущий
Codex совместно с владельцем, без субагентов. Codex подготавливает изменения и
выполняет package typecheck, владелец запускает build, tests и canonical browser
contour.

Классификация: первый причинный срез `HAM-005`; одно новое требование и один
изменяемый механизм — initialization стандартной Window visual-среды
обновляемым importer.

Требование или диагностический результат: после завершения `@import/main`
документ имеет ровно один полноразмерный canvas и один созданный через
`UiRuntime.create()` runtime. Он содержит принадлежащие ему `Space` и `HUD`,
работает в explicit-display mode без встроенного surface-display и пока не
содержит project-specific displays или surfaces.

Основание и связанная история: `LOAD-001.15` создала пустой `@import/main`, а
correction `df3bcb663` закрепила module composition в import layer. Interpreter
создаёт один `UiRuntime` с `virtualDisplay.surfaceDisplay: false`, после чего
отдельно добавляет именованные displays. Prototype checkpoints `HAM-002.3`–
`HAM-002.7` остаются только behavior evidence и не являются source base.

Наблюдаемое расхождение: `hamiltonian/web/static/index.html` не содержит
canvas, `@import/main` только пишет `main importer` в console, а clean-room
static routes не обслуживают font, обязательный для завершения
`UiRuntime.create()`.

Причина: clean-room loader доказал только запуск обновляемого Window importer;
его package ещё не зависит от общего UI runtime, а static owner не публикует
необходимые visual resources.

Разрешённое изменение одного механизма: добавить canvas и его inline layout к
существующему `hamiltonian/web/static`, обслужить существующий Engine font как
cache-first `/assets/*` endpoint, а в `@import/main` один раз создать и удержать
`UiRuntime` с отключёнными grid и surface-display. Разрешены только необходимые
package dependency, server route и focused regression этой границы.

Regression или опровергающее доказательство: focused static/package assertions
должны защищать один canvas, font route, `UiRuntime.create()`,
`surfaceDisplay: false`, отсутствие prototype imports и неизменность startup
module composition. Browser evidence владельца отдельно подтверждает actual
`Space`, `HUD`, `display === null`, отсутствие surfaces и повторного runtime.

Среда и критерий приёмки: canonical clean-room `hamiltonian/server.ts` и
существующий owner browser contour. Codex запускает package typecheck; владелец
запускает build, focused tests и первый/повторный browser path. Read-only diff
или package typecheck не выдаются за browser-приёмку.

Фактические действия: `hamiltonian/web/static/index.html` получил единственный
полноразмерный `visual-canvas` и inline layout без нового CSS endpoint.
`web/static/routes.ts` публикует существующий Engine font как
`/assets/fonts/JetBrainsMono-Bold.ttf`, поэтому действующая `/assets/*`
cache-first policy сохраняется без изменения startup service. `@import/main`
получил package dependency на `@ui/elements`, один module-local initialization
Promise, `UiRuntime.create()` с `grid: false` и `surfaceDisplay: false`, первый
resize, `ResizeObserver` и console object actual runtime. Prototype source,
startup и Service Worker importers не изменены. Добавлен focused boundary
regression `hamiltonian/tests/ham-005.boundary.spec.ts`.

Результат и вывод: source и regression подготовлены; `git diff --check` прошёл
до checkpoint. Первый owner-запуск typecheck выявил `TS2339` на
`import.meta.hot` в транзитивно подключённом Engine renderer: отдельный
`@import/main` tsconfig включал WebGPU и WGSL types, но не общую ambient
декларацию `types/hot.d.ts`. Correction добавила только эту декларацию в
TypeScript-программу Window package, не подключая Bun globals. После correction
Codex выполнил `bun run --cwd hamiltonian/web/import/main typecheck`: TypeScript
завершился с exit code `0`; предупреждение MacPorts locale `C.UTF-8` не влияло
на результат. Следующий owner-запуск выявил отдельное build-расхождение:
CLI-builder получил несколько WGSL file outputs и отказался возвращать их без
output directory. Этот новый механизм вынесен в `HAM-005.2`; tests и browser
path также ещё требуют owner evidence.

Подготовительный commit: `c7e3ca761`.

Result checkpoint: `143c2e86b`.

Correction checkpoint после owner typecheck: `d4ec844d4`.

В уже установленном canonical origin прежние HTML и importer закономерно

location.reload()

### HAM-005.2 — Собирать visual importer одним JavaScript artifact

Статус и исполнитель: `IN_PROGRESS`; текущий Codex совместно с владельцем, без
субагентов. Codex подготавливает build boundary и выполняет typecheck, владелец
запускает build, tests, server и canonical browser contour.

Классификация: новое подтверждённое расхождение того же родителя требует
изменения другого механизма — package-owned browser bundling, а не
initialization `UiRuntime` из `HAM-005.1`.

Требование или диагностический результат: `@import/main` со всеми Engine WGSL
dependencies собирается одним самодостаточным JavaScript artifact, который
действующий `/import/main` route может сохранить и вернуть без дополнительных
asset routes, cache entries или release manifest.

Основание и связанная история: общий `hamiltonian/macro.ts` уже находит
package-owner и выполняет его strict typecheck, но CLI build наследует
произвольный process cwd. Корневой `bunfig.toml` определяет `.wgsl` как text,
а prototype `server-runtime.ts` задаёт тот же loader явно; prototype остаётся
только evidence, его builder не переносится.

Наблюдаемое расхождение: после успешного `@import/main` typecheck owner-запуск
`hamiltonian` завершился ошибкой Bun 1.3.14 `cannot write multiple output files
without an output directory` внутри `macro.ts:build()`.

Причина: `UiRuntime` транзитивно подключает Engine renderer и его WGSL imports.
Macro запускает `bun build` не из найденного package-owner root, поэтому Bun не
видит package-owned loader configuration; для неизвестного `.wgsl` применяется
file loader и появляются дополнительные artifacts вместо встроенного текста.

Разрешённое изменение одного механизма: добавить `@import/main` собственный
`bunfig.toml` с `.wgsl = "text"` и запускать CLI build из `owner.root`, уже
найденного macro. Сохраняются действующие target, format, external, minify,
stdout artifact и package typecheck. `outdir`, новые HTTP routes, cache entries,
изменения Engine imports и общий multi-file release не добавляются.

Regression или опровергающее доказательство: focused test вызывает общий
`build("@import/main")` и требует непустой JavaScript result; прежняя
multi-output ошибка должна опровергнуть regression до correction. Static
assertions дополнительно закрепляют package loader и owner-root build cwd.

Среда и критерий приёмки: canonical checkout и Bun 1.3.14. Codex выполняет
typecheck; владелец запускает package build, focused test и `hamiltonian start`.
Успех build не заменяет последующую browser-приёмку `HAM-005.1`.

Фактические действия: в `@import/main` добавлен package-owned `bunfig.toml` с
text loader для `.wgsl`. Общий macro запускает CLI build с `cwd: owner.root`,
не меняя его output contract. Focused regression читает обе структурные
границы и вызывает `build("@import/main")`, требуя непустой JavaScript с
Window entrypoint. `outdir`, asset routes и изменения renderer не добавлены.

Результат и вывод: `bun run --cwd hamiltonian/web/import/main typecheck` прошёл
с exit code `0`; предупреждение MacPorts locale `C.UTF-8` не влияло на
результат. Общий `bun run typecheck` также подтвердил package typecheck, затем
завершился с exit code `2` на существующих ошибках
`hamiltonian/update/browser/**` и
`hamiltonian/update/shared/service-worker-release.js`, не относящихся к этому
срезу. Codex не запускал build, tests, server или browser; single-artifact
результат ожидает owner evidence.

Подготовительный commit: `9719edc4b`.

Result checkpoint: `6f725592c`.

Подготовленные команды владельца:

```bash

bun test hamiltonian/tests/ham-005.boundary.spec.ts
bun run --cwd hamiltonian start
```

## Открытые вопросы

* Какой минимальный локальный ABI позже передаёт один созданный runtime
  загружаемым Window modules, не создавая глобальный mutable registry?
* Как последующий `internal/visual` создаёт первый явно именованный graph
  `UIDisplay`; это не входит в пустое стандартное окружение.
* Нужен ли отдельный worker entrypoint следующему visual module кроме уже
  существующего чистого layout protocol; worker-rendering не предполагается.

## Границы

Входит:

* стандартный canvas host, style и font resource через
  `hamiltonian/web/static`;
* создание и завершение одного `UiRuntime` в `@import/main`;
* `surfaceDisplay: false` и отсутствие project-specific surfaces;
* минимальная наблюдаемость действительного `Space`/`HUD` object tree;
* package/build/typecheck и browser regression этой Window-среды.

Не входит:

* импорт или перенос `hamiltonian/visual` и `browser/orchestration*`;
* `NodeSystemSurface`, graph projection, Inspector, canvas controls, palette,
  layout transition или lifecycle data;
* выбор первого `internal`/`metafor` module, его cache и Window module ABI;
* Dedicated Worker rendering, `OffscreenCanvas` или изменение Engine/UI для
  worker execution;
* изменение Service Worker importer, RPC, startup primitives, update release
  или Bun/server loading path;
* изменение Bulk, `pkg/visual` или универсальных `@nodes/*` законов.

## Критерии готовности

* После запуска `@import/main` страница содержит один полноразмерный canvas и
  один успешно созданный `UiRuntime`.
* Фактическое дерево содержит один `Space` и один `HUD`; `runtime.display`
  равен `null`, project-specific displays и surfaces отсутствуют.
* Font и остальные необходимые static resources обслуживаются через
  `hamiltonian/web/static` с корректным MIME и действующей cache-first policy.
* `@import/main` не импортирует prototype Hamiltonian, `internal`/`metafor`
  modules, Bulk или node-system presentation.
* Неизменяемые `@startup/main` и `@startup/service`, Service Worker RPC и
  существующие cache boundaries сохраняют поведение.

## Проверка результата

Следующие проверки подготавливает Codex, но запускает владелец:

* strict typecheck/build `@import/main` и нового clean-room Hamiltonian server;

* browser regression первого install и повторной controlled navigation без

* browser evidence фактических `Space`, `HUD`, `display === null` и отсутствия
