# MF-412 — Испытательный Hamiltonian без переноса доменов

## Зачем

До перестройки production contour нужно на маленьком отдельном опыте проверить
саму управляющую схему: один fixed listener, общий Service Worker для вкладок,
выбор активного Window и доставка новой versioned сборки.

## Основание для старта

Владелец подтвердил, что найденный ранний опыт с WebSocket внутри Service
Worker доказал жизнеспособность самой идеи и поручил выполнить отдельный
полноценный эксперимент без подключения production-кода MetaFor. Минимального
направления `MF-411` для этого достаточно; дальнейшее уточнение его онтологии
может идти параллельно и не блокирует изолированный proof.

Ранний опыт остаётся входным evidence, но не заменяет проверку на текущих
браузерах и не становится скрытой зависимостью.

## Вопрос эксперимента

Может ли одно распределённое целое иметь Bun-, Service-Worker- и
Window-воплощения, переживать смену вкладки и версии и при этом не становиться
realtime-маршрутизатором доменов?

После первого Android proof владелец расширил опыт до полной standalone
инфраструктуры перед переносом MetaFor. Она должна одинаково работать в
browser- и server-only окружении, проверить peer-связь и singleton lifecycle,
но по-прежнему не переносить production-домены.

## Минимальный scope

* Один обычный Bun process держит один фиксированный HTTP/WebSocket listener.
* Listener отдаёт bootstrap, Service Worker и versioned испытательный module.
* Первая навигация явно проходит без существующего Service Worker: Window
  bootstrap регистрирует его и фиксирует, с какого момента page становится
  controlled.
* Service Worker видит несколько Window clients, поддерживает control/update
  channel с reconnect и сообщает о доступной версии.
* Ровно одно Window избирается для испытательного активного воплощения; после
  его закрытия другое Window может быть избрано.
* Один чистый versioned module имеет одинаковые bytes и SHA-256 во всех
  испытательных воплощениях.
* Window main получает versioned module через обычную загрузку, а Service
  Worker отдаёт уже подготовленную версию из Cache Storage. При смене version
  Window обязательно выполняет настоящий page reload: старый main realm
  уничтожается браузером, новый module и экземпляр рождаются в новой странице.
* Тот же module отдельно рождается в Dedicated Worker. При cold rebirth старый
  Worker завершается до создания нового, чтобы два активных воплощения не
  пересекались.
* На Bun-стороне тот же module рождается в отдельном OS process через
  `Bun.spawn` и IPC, не через Bun Worker. Этот процесс не открывает listener.
* Server-only вариант не требует открытого браузера: Bun host управляет теми же
  version, incarnation, singleton и rebirth законами для обычных OS processes.
* Общая объектная модель владеет version identity, lifecycle, lease/fencing,
  reconnect и логическими channel; browser и Bun содержат только platform
  adapters для MessagePort, IPC, WebSocket и peer carrier.
* Hamiltonian переносит только знакомство/signaling. После знакомства browser
  и Bun peer обмениваются испытательным realtime payload напрямую.
* Один peer carrier проверяет отдельные логические `oracle` и `force` channels;
  эти названия обозначают только форму теста и не утверждают production RPC или
  Force protocol MetaFor.
* Singleton main выбирается глобально среди нескольких вкладок, окон,
  browser families и устройств. Каждая новая authority получает возрастающий
  fencing token; per-window Dedicated Worker не объявляется singleton.
* Все действия наблюдаемы: identity версии, выбранный client, смена лидера,
  reconnect и причина нового воплощения.

## Что сознательно не доказывается

* Production Dark, Boundary, Matrix, Energy или Bulk не переносятся.
* Финальная схема WebRTC, STUN/TURN и Oracle/Force carrier не выбирается.
* Service Worker не считается бессмертным; опыт обязан допускать его остановку
  браузером и последующее восстановление.
* Получение bytes по WebSocket не объявляется cache update, пока опыт явно не
  создаст `Response`, не положит его в Cache Storage и не загрузит ожидаемую
  versioned запись.
* Не выполняется частичный hot reload причинно связанного contour. Это
  controlled rebirth испытательного воплощения.
* Частичная замена main-экземпляра внутри прежней страницы не считается
  обновлением Dark. Для main опыт использует полное уничтожение realm через
  reload.
* Не создаётся production API, shared package или новая междоменная dependency.
* Эксперимент не включается в root workspace и не импортирует пакеты MetaFor.
* Успешный WebRTC/DataChannel опыт не является принятием WebRTC как production
  carrier и не снимает будущие решения identity, authorization, gap и TURN.

## Варианты, которые можно сравнить внутри опыта

* Version manifest по WebSocket, code bytes обычным HTTP request через Service
  Worker.
* Version manifest и code bytes по WebSocket с явной записью ответа в Cache
  Storage.
* Window election только средствами Service Worker либо с дополнительным
  browser coordination primitive.
* Browser peer ↔ Bun peer через WebRTC DataChannel и детерминированный in-memory
  carrier в fixtures.
* Поведение control WebSocket при открытых Windows, закрытых Windows, background
  browser и полном завершении browser process. Отдельно различаются сохранение
  живого соединения и reconnect после нового запуска.

Выбор варианта в опыте не утверждает production protocol.

## Критерии готовности

* Две вкладки используют одну Service Worker registration и видят одну
  Hamiltonian identity.
* Первый install/activate/control path доказан отдельно от повторной загрузки
  уже установленного Service Worker.
* В каждый момент активен не более чем один выбранный Window; закрытие лидера
  приводит к наблюдаемому новому выбору.
* Bun host держит ровно один fixed listener, а испытательные части не открывают
  собственные servers.
* Новая versioned сборка действительно загружена, сохранена и выдана при
  повторном запросе; старая версия остаётся различимой.
* Одинаковые version и SHA-256 наблюдаются в Window main, Dedicated Worker и
  отдельном Bun OS process.
* Для Window main новое incarnation рождается после page reload, а Dedicated
  Worker завершается до отдельного нового рождения; Bun child завершается
  вместе с host и при новом рождении получает новое process/incarnation
  identity.
* Server-only host проходит version rebirth и singleton handoff без browser
  process и без дополнительных listeners.
* Несколько вкладок/окон/браузеров/устройств одновременно видят не более одного
  main singleton; смена владельца увеличивает fencing token и не переиспользует
  прежнюю lease.
* Peer proof открывает логические `oracle` и `force` channels, проверяет ordering,
  request/response, event stream, backpressure boundary, disconnect/reconnect и
  доказывает, что signaling WebSocket не переносит их realtime payload.
* Live-матрица охватывает доступные Chrome, Yandex и Safari на macOS и Chrome с
  Yandex на Android настолько, насколько это допускают установленные browser
  automation/debug interfaces. Непроверяемый шаг явно отмечается, а не
  заменяется предположением.
* Для Service Worker WebSocket экспериментально различены: открытая страница,
  отсутствие открытых страниц при живом browser process, background/lock и
  полностью завершённый browser process.
* Fixtures не требуют сети или browser и детерминированно проверяют lifecycle,
  election/fencing, multiplexing, reconnect/gap и ошибки обеих platform
  оболочек.
* Остановка/restart Service Worker или разрыв WebSocket приводит к reconnect,
  а не к предположению о бессмертном процессе.
* Hamiltonian не переносит испытательный realtime payload после знакомства
  частей.
* Результат оформлен как evidence: что доказано, что не доказано и какие задачи
  нужно изменить перед переносом production-кода.

## Промежуточная проверка 2026-08-08

Изолированный код находится в `hamiltonian` без подключения к root
workspace и без импортов MetaFor. Текущий stand держит один HTTP/WSS listener,
обычные Bun OS processes через IPC и direct WebRTC peer. Control WSS допускает
только identity, heartbeat, election, update и signaling; realtime frame на
нём закрывается policy violation. Один peer carrier создаёт два нативных
ordered/reliable DataChannel `oracle` и `force` с независимыми limits,
backpressure, sequence/gap и session-loss законами. Названия остаются
испытательными lane, а не production-протоколами MetaFor.

Versioned bytes фактически хешируются при записи и повторном чтении cache.
Window main рождается только у владельца host lease; новая version требует
page reload. Dedicated Worker остаётся per-Window. Серверная сторона использует
обычные `Bun.spawn` process для main-, worker-role- и peer-воплощений и не
открывает дополнительных fixed HTTP/WebSocket server. WebRTC peer использует
временные ICE/UDP endpoints. Concurrent process rebirth сериализован.

Автоматическая проверка: `61 pass, 0 fail, 227 assertions`. Она включает один
listener, auth/version/hash/cache, process birth/rebirth, election/lease/fence,
stale channel generation, reconnect, ordering/gap, RPC timeout/cancellation и
session loss, backpressure обеих lane, WSS authority resume, RTC repair,
stale-session rejection, browser/server placement, запрет realtime через WSS
и direct Bun↔Bun WebRTC.

Финальный двухминутный Chrome open-tab soak на v11 прошёл 9 проб и сохранил
все raw samples. Наблюдались две смены non-null Worker incarnation, пять
изменений физического WSS-состояния и три detached-состояния,
но browser-profile resume-capability сохранила прежние lease/fence и готовый
direct peer. Heartbeat вырос на 9, счётчики обеих realtime lane — на 12 каждый,
control relay остался нулевым. Это заменяет ошибочный критерий «один
Worker/socket обязан жить всё время» на проверяемый закон восстановления
logical authority.

Этот live-прогон предшествует переименованию испытательной RPC lane. Raw
evidence сохраняет прежние wire-name и доказывает сам двухканальный carrier,
reconnect и отсутствие realtime relay через control WSS, но не является
live-приёмкой нынешнего browser adapter с именем `oracle`. Текущий путь
проверен автоматическими fixtures, browser build, direct Bun↔Bun WebRTC и
свежим Chrome v12 evidence: host channels `oracle`/`force`, оба счётчика больше
нуля, realtime relay через control WSS равен нулю, DOM и screenshot показывают
успешные Oracle response и Force echo.

Server-only и browser-hosted main теперь явно взаимоисключены. В browser-mode
Bun процессы являются lifecycle probes без authority; в server-mode authority
имеет только Bun main, Window leader не выдаётся, а cold rebirth повышает fence.
Динамический Bun↔Window handoff намеренно не изобретён до owner-gate `MF-414`.

Живая матрица проверила:

* macOS Chrome: прямой peer, две вкладки на одном Service Worker WSS, ровно один
  main, handoff лидера с новым lease/fence без смены WSS;
* macOS Yandex: direct peer, полный process quit удаляет соединение, reopen
  сохраняет `deviceId`, но создаёт новые connection/SW/session incarnation;
* macOS Safari: независимый profile подключился, стал лидером и выполнил
  прямой двухканальный proof прежнего RPC wire-name; DOM не прочитан, потому
  что Allow Remote Automation отключён; после закрытия Safari Yandex получил
  новый fence и direct peer;
* Android Chrome: trusted TLS/LAN, direct peer, zero-window и force-stop удаляют
  физическое соединение, reopen восстанавливает логическое peer-состояние новым
  connection epoch;
* Android Yandex: direct peer и force-stop/reopen; спустя 30 секунд screen-off
  WSS исчез. Последующее wake не удалось стабильно автоматизировать из-за
  оставшегося lock/sleep состояния телефона.

Закрытие всех Window не имеет единого browser contract: Chrome Android закрыл
WSS почти сразу; Chrome macOS сохранял его на пятой секунде; Safari закрыл
позднее. Полный browser quit нигде не может сохранить тот же physical socket.
Поэтому опыт опирается на durable identity, новый connection/session epoch и
recovery, а не на бессмертный Service Worker.

Это ещё не основание переносить MetaFor. До решения владельца остаются remote
ICE/STUN/TURN, production trust/auth, mapping действующих Oracle/Force contracts,
causal frontier при reconnect и выбор Bun WebRTC adapter. Safari DOM acceptance
и стабильный Android wake также остаются неполными наблюдениями. Подробное
evidence находится в
[`artifacts/MF-412/README.md`](../artifacts/MF-412/README.md).

## Stop condition

Если минимальный опыт требует изменения действующих доменов, listener Dark или
Force history, scope слишком велик. Он останавливается и упрощается до
изолированного control-plane proof.
