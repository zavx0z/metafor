# UPD-001 — Собрать механизм обновлений Hamiltonian в одной директории

## Коротко

Весь уже работающий механизм обновлений Hamiltonian будет находиться под одной
понятной границей `hamiltonian/update`. Серверная и браузерная части останутся
раздельными по среде исполнения, но больше не будут спрятаны внутри больших
файлов host, Service Worker и страницы.

## Зачем

Локальное обновление браузерного кода уже доказано, но его решения распределены
между сборкой host, Service Worker, страницей, manifest и lifecycle-допуском.
Перед добавлением других устройств и серверных процессов нужно сначала сделать
этот механизм видимым как одно целое, не меняя его действующий закон.

## Связь с дорожной картой

Это первая задача отдельной линии `UPD` в разделе
[`Обновления Hamiltonian`](../ROADMAP.md#обновления-hamiltonian). Она развивает
управление одной Вселенной на одном устройстве из
[`MF-425 — Управлять одной Вселенной на одном устройстве`](MF-425.md), но не
расширяет среду обновления за пределы уже доказанного локального браузерного
контура.

## Связанные задачи и история

* Закрытая `MF-428` доказала локальное обновление Service Worker во всех сейчас
  запущенных Chrome-профилях одного Mac, отдельные logical identity и новые
  execution incarnation после смены версии.
* [`MF-411 — Определить, что делает Hamiltonian и где он работает`](MF-411.md)
  относит выдачу versioned code и новое воплощение частей к Hamiltonian, не
  передавая ему обязанности Dark или Boundary.
* [`HAM-002 — Собрать визуальный слой Hamiltonian в одном контуре`](HAM-002.md)
  собирает только visual-код под `hamiltonian/visual`; lifecycle, control,
  bootstrap и обновления в эту границу не входят.

## Подтверждённые факты

* `Bun.build` создаёт точный Service Worker bundle, а `/manifest.json` отдаёт
  отдельные `version` и `sha256` этого выпуска.
* Host сравнивает заявленную версию каждого подключённого Service Worker с
  текущим выпуском и не допускает устаревшее исполнение к прикладной работе.
* Устаревший Service Worker получает требование обновления и вызывает штатный
  browser-managed `registration.update()`.
* Успех подтверждается только новым исполнением того же логического Service
  Worker с целевой версией и восстановленной связью.
* Web Push может разбудить Service Worker для проверки, но не переносит код.
* Изменение browser source reload-ит main realm, а холодный restart host с теми
  же browser artifacts сам по себе reload не вызывает.

## Решения владельца

* Все задачи направления обновлений получают префикс `UPD`.
* Первая задача собирает весь действующий механизм обновлений в одной
  директории внутри Hamiltonian.
* Целевая верхняя граница первой задачи — `hamiltonian/update`.

## Поведение процесса

Перед первым переносом нужно зафиксировать полный import graph и разделить код
по фактической среде исполнения: host, browser и общие чистые договоры. Затем
каждый перенос выполняется отдельным последовательным срезом с неизменным
наблюдаемым поведением и существующими frozen regressions. Новый механизм,
новая среда обновления или новый способ приёмки получает отдельную следующую
задачу линии `UPD`.

## Границы

* Не менять SemVer, manifest, SHA-256, logical identity, execution incarnation,
  lifecycle-допуск и критерий успешного обновления.
* Не добавлять доставку кода между устройствами, обновление выключенных
  устройств или серверных процессов.
* Не вводить подпись выпусков, trust root, anti-rollback, fleet registry,
  частичный rollout или общий rollback.
* Не передавать код через Web Push и не считать Web Push частью доставки
  выпуска.
* Не переносить visual projection и отображение версии из
  `hamiltonian/visual` или lifecycle presentation в update-механизм.
* Не менять обязанности Dark, Boundary, Matrix, Energy, Bulk или Force.
* Не создавать новый публичный пакет: первая граница остаётся внутренней частью
  Hamiltonian.

## Подзадачи

### UPD-001.1 — Зафиксировать import graph механизма обновлений

Статус и исполнитель: `COMPLETE`, внутренний субагент текущей задачи Codex.

Классификация: диагностический срез перед первым structural move; product
source не изменяется.

Требование или диагностический результат: зафиксировать полный действующий
import/ownership graph локального browser-update, разделить host-, browser- и
действительно общие чистые части, определить точную внутреннюю структуру
`hamiltonian/update` и последовательность move-only срезов.

Основание и связанная история: закрытые `MF-428.3`–`MF-428.8`, product commits
`002570bb0`, `8a9805d49`, `260aa786a`, `bf10ae45c`, `84a1c99af` и
`72561b4e2`, финальная двухпрофильная приёмка `1579d11cd`, closing commit
`63be214c6`, закон `Версия кода Service Worker` в
[`hamiltonian/README.md`](../../hamiltonian/README.md) и browser source reload
law того же владельца.

Наблюдаемое расхождение: единый действующий update-механизм распределён между
host build/manifest, Service Worker, page source reconciliation,
lifecycle/admission и их integration tests; точная dependency boundary ещё не
зафиксирована.

Причина: механизм возник последовательными поведенческими срезами MF-428 и
browser lifecycle до отдельного owner-решения собрать его в одном внутреннем
контуре.

Разрешённое изменение одного механизма: только карточка, полный import и
ownership inventory, целевая структура и атомарная последовательность
последующих переносов; product source, runtime и действующее поведение не
изменяются.

Regression или опровергающее доказательство: source imports и exports,
`Bun.build` entrypoints, manifest/static routes, host/Service Worker/page
protocol consumers, package boundaries, frozen update/reload tests и
существенная Git-история MF-428.

Среда и критерий приёмки: canonical `main` из подготовительного commit этого
среза; inventory покрывает все source/test consumers, явно удерживает Bun-only
код вне browser bundle, отделяет generic build primitives и visual projection
и задаёт по одному наблюдаемому structural результату для каждого следующего
среза.

Фактические действия:

* На canonical `main@fb1e2b4deaec8827cec9be95a4bcbede999b9528`
  проверены root, branch, чистое рабочее дерево и единственный worktree;
  runtime не запускался и product source не изменялся.
* Полностью прочитаны `AGENTS.md`, карта владельцев `docs/README.md`,
  `project/README.md`, `ROADMAP.md`, `BACKLOG.md`, `TODO.md`, эта карточка,
  применимые законы и проверки в `hamiltonian/README.md`, а также активная
  граница `HAM-002`.
* Через Git восстановлена закрытая линия `MF-428.3`–`MF-428.8`: введение
  Worker SemVer (`002570bb0`), local release/admission (`8a9805d49`), защита
  Worker-authored incarnation/version (`260aa786a`), pre-identity bootstrap
  (`bf10ae45c`), browser-safe rejection (`84a1c99af`), синхронизация fixtures
  (`72561b4e2`), двухпрофильная live-приёмка (`1579d11cd`) и closing cleanup
  (`63be214c6`). Удалённая карточка `MF-428` прочитана из parent closing
  commit, а не восстановлена в рабочее дерево.
* Проверены фактические imports/exports, `Bun.build` entrypoints, HTTP/static
  routes, source watchers, Worker/page control messages, package manifests и
  все прямые source/test consumers. Репозиторный поиск по `registration.update`,
  `service-worker-update/current`, Worker version, manifest и source revision
  не обнаружил второго local browser-update вне `hamiltonian`.
* Руководитель отдельно выполнил frozen baseline до structural moves:
  `bun test hamiltonian/core/service-worker-code-version.spec.ts
  hamiltonian/core/cache.spec.ts hamiltonian/core/runtime.spec.ts
  hamiltonian/browser-build.spec.ts hamiltonian/host.spec.ts` — `82 pass`,
  `0 fail`, `2332` assertions; реальный orchestration/layout Worker bundle
  собран тестом.

Результат и вывод:

Действующий механизм состоит из двух согласованных browser-переходов. Первый
заменяет executable Service Worker через exact `{version, sha256}`, stale
admission и browser-managed `registration.update()`. Второй обновляет весь
фактически отданный browser artifact set: host вычисляет source fingerprint,
page выполняет один reload при его изменении, а versioned module после
SHA-256-проверки воплощает Window main и Dedicated Worker. Это одна граница
UPD-001, но не один runtime-модуль: Bun-only вычисления, Service Worker и page
обязаны остаться физически разделены.

#### Действующий import и ownership graph

* Host entry `hamiltonian/host.ts` сейчас одновременно владеет generic
  `Bun.build`/static/listener wiring и update-решениями. Он:
  * задаёт entrypoints `browser/service-worker.ts`,
    `browser/orchestration.ts`, `visual/browser/layout-worker.ts` и Web Push
    client, собирает четыре bundles и читает напрямую served HTML/JS/CSS/core;
  * строит versioned module source и его top-level manifest release, извлекает
    из точного Worker bundle SemVer, считает отдельный Worker SHA-256 и отдаёт
    оба договора через `/manifest.json`; `/sw-entry.js` и versioned module
    остаются HTTP wiring того же host;
  * вычисляет `hamiltonianBrowserSourceRevision` по четырём bundles и всем
    напрямую served text artifacts, встраивает baseline в navigation HTML,
    наблюдает `browser/public/core`, `visual`, `pkg/nodes`, `pkg/ui` и
    `pkg/web-push`, а после успешной общей пересборки отправляет `source-update`;
  * держит per-profile update state (`workerCodeVersion`,
    `workerUpdateRequired`, embodiments и pending targets), до update отзывает
    application topology/peer, сравнивает identity snapshot с manifest
    release, отправляет `service-worker-update` либо `service-worker-current`
    и считает успехом только target version в новой execution incarnation;
  * выдаёт новой execution pre-identity server declaration без прежней browser
    boundary, после browser declaration восстанавливает полную exact boundary.
* Service Worker entry `hamiltonian/browser/service-worker.ts` импортирует
  `browser/service-worker-code-version.ts`, pure SemVer guard из
  `core/service-worker-code-version.js`, browser cache helpers из
  `core/cache.js`, generic lifecycle/control runtime и browser-safe socket
  rejection. Внутри entry сейчас смешаны:
  * Worker-owned code version и identity/lifecycle facts;
  * guards дублированных inline shapes `ServiceWorkerRelease` и
    `VersionManifest`;
  * запрет application path до `service-worker-current`, обработка
    `service-worker-update`, вызов `registration.update()` и восстановление
    application после current admission;
  * получение top-level manifest module, SHA-256/cache retention и публикация
    `version-ready` всем Window;
  * relay `source-update` от control socket к Window.
* Page implementation `hamiltonian/public/app.js` получает bootstrap через
  `core/monitor.js`, сохраняет `hamiltonian-source-revision` до открытия
  control path, принимает `source-update` и reload-ит realm ровно один раз.
  Здесь же находятся `activateVersion`, динамический import versioned module,
  fingerprint `version:sha256`, рождение Dedicated Worker и решение reload
  активного main. Чистые `mainRealmRequiresReload` и
  `sourceRevisionRequiresReload` исторически спрятаны среди несвязанных
  control helpers в `core/browser-control.js`; их tests ошибочно находятся в
  общем `core/runtime.spec.ts`.
* Единственная действительно общая чистая часть сейчас — SemVer contract
  `core/service-worker-code-version.js`: его импортируют Bun host и browser
  Worker/version constant. Exact `{version, sha256}` contract при этом
  продублирован локальными host/Worker interfaces и validators и должен стать
  вторым shared contract. Bun CryptoHasher и browser Web Crypto/Cache API не
  являются shared implementation и не могут находиться в одном runtime-файле.
* `core/cache.js` и `core/cache.spec.ts` несмотря на исторический путь являются
  browser-only release cache: их единственный product consumer — Service
  Worker. `browser/service-worker-code-version.ts` также move-only leaf.
* Generic lifecycle/declaration ownership остаётся в `core/lifecycle.js`,
  browser identity — в `core/orchestration.js`, control reconnect — в
  `core/runtime.js`, browser-safe close helper — в
  `browser/control-socket-rejection.ts`, а page lifecycle authorship — в
  `browser/page-lifecycle-declaration.ts`. Update вызывает эти владельцы, но не
  забирает их договоры.
* `browser/orchestration/lifecycle-projection.ts` только отображает уже
  наблюдённый `codeVersion`; его tests про card header, ownership и atomic
  facts replacement являются integration consumers. Они остаются у
  `hamiltonian/visual`/lifecycle и не переносятся в update.
* Web Push остаётся внешним wake/reconnect consumer без code payload.
  `embodiment-process.ts` проверяет SHA-256 Bun embodiment source, но это
  generic/server execution path, а не второй browser-update и не входит в
  UPD-001.

Прямые frozen owners/consumers: `host.spec.ts` содержит release/source,
current/stale admission, multi-profile revoke, new-incarnation и bootstrap
integration; `core/service-worker-code-version.spec.ts` — SemVer;
`core/cache.spec.ts` — browser hash/cache retention; `core/runtime.spec.ts` —
два page reload predicates; `browser-build.spec.ts` — реальные Worker/page
entry builds и наличие update gate в bundle; `core/lifecycle.spec.ts`,
`browser/orchestration/lifecycle-projection.spec.ts` и `soak/observer.spec.ts`
защищают смежные identity/incarnation/visual/live outcomes. Изолированного unit
test самого Worker handler `service-worker-update/current` сейчас нет:
`registration.update()` и `applicationReady` защищены только bundle-source
assertions плюс host/live evidence. Отдельного regression на failed source
build также нет, хотя host записывает `source-update-failed` и не рассылает
revision. Оба доказательства уже требуются критериями UPD-001 и должны
появиться в соответствующих extraction-срезах без изменения поведения.

#### Точная целевая внутренняя структура

```text
hamiltonian/update/
├── shared/
│   ├── service-worker-release.js
│   └── service-worker-release.spec.ts
├── host/
│   ├── browser-release.ts
│   ├── browser-release.spec.ts
│   ├── service-worker-admission.ts
│   └── service-worker-admission.spec.ts
└── browser/
    ├── service-worker-code-version.ts
    ├── release-cache.js
    ├── release-cache.spec.ts
    ├── service-worker-update.ts
    ├── service-worker-update.spec.ts
    ├── page-update.js
    └── page-update.spec.ts
```

`shared/service-worker-release.js` владеет pure SemVer и exact release shape,
используемыми host и browser. `host/browser-release.ts` владеет Worker release
из exact bundle, browser artifact fingerprint и manifest projection, получая
готовые bundle/static bytes от host adapters; generic `Bun.build`, listener,
static response, filesystem watch и versioned embodiment source остаются вне
него. `host/service-worker-admission.ts` владеет current/stale/pending/new-
incarnation решением, но topology teardown, lifecycle declaration registry и
socket send/close остаются callback wiring host.

`browser/service-worker-update.ts` владеет update/current protocol decision,
application gate и browser-managed update, но не общим control socket или
lifecycle journal. `browser/release-cache.js` владеет browser Web Crypto,
Cache Storage и top-level versioned module preparation.
`browser/page-update.js` владеет navigation source baseline, одноразовым
source reload, `version:sha256` activation и main-realm reload decision; page
entry передаёт ему storage/import/reload/birth callbacks. Между runtime-
директориями действует только направление `host|browser -> shared`;
`shared` не импортирует Bun, DOM, ServiceWorker, Cache Storage, lifecycle или
visual, а `browser` никогда не импортирует `host`.

Public package и root export не создаются. `host.ts`, Service Worker и page
сохраняют только adapter wiring. Существующие URL можно удержать прежними
static mappings, но физические owners и source watcher должны указывать на
`update`; это не разрешает менять manifest/protocol shape.

#### Последовательность следующих атомарных срезов

1. Move-only перенести SemVer contract/spec и executable Worker version в
   `update/shared` и `update/browser`; заменить imports без изменения contract
   или version. Exact bundle SHA может измениться из-за physical source path в
   inline sourcemap и должен считаться новым точным release artifact, а не
   ложной byte-for-byte эквивалентностью.
2. Move-only перенести browser hash/cache leaf со spec в
   `update/browser/release-cache`; Service Worker остаётся единственным product
   consumer.
3. Извлечь два page reload predicates и их exact tests из mixed
   `core/browser-control.js`/`core/runtime.spec.ts` в `page-update`, не меняя
   `public/app.js` wiring.
4. После координации общего `host.ts` извлечь pure Worker release, artifact
   fingerprint и manifest projection в `host/browser-release`; generic builds,
   routes и watchers только подают bytes/requests. Здесь же закрепить failed
   build no-publication regression.
5. Извлечь current/stale/pending-incarnation state machine в
   `host/service-worker-admission`; сохранить host integration для двух
   профилей, synchronous topology revoke и pre-identity bootstrap.
6. Извлечь `service-worker-update/current`, `applicationReady` и
   `registration.update()` в browser update controller с отдельным frozen
   handler test; entry сохраняет control/lifecycle callbacks.
7. Перенести top-level manifest fetch, SHA-256/cache retention и
   `version-ready` preparation из Service Worker в `release-cache` controller.
8. Извлечь source baseline/reload и version activation из `public/app.js` в
   `page-update`; page остаётся владельцем фактических realm callbacks, но не
   решений о fingerprint/reload.
9. Финальный integration slice добавляет `update` в physical source watch,
   удаляет старые update decisions/imports из `host.ts`, Service Worker и page,
   повторяет полный import audit, strict host/WebWorker checks, реальные
   bundles, `bun test hamiltonian` и только затем двухпрофильный live-сценарий.

Активный `HAM-002` уже изменил `host.ts` для `visualRoot`, stylesheet и layout
Worker bundle, а его следующие projection/browser срезы могут менять
`host.spec.ts` и `browser/orchestration.ts`. UPD не переносит эти owners:
первые три leaf-среза независимы, а любой host/page integration slice должен
начинаться только после повторной проверки HEAD и координации точных файлов с
текущим HAM-002. В частности, нельзя потерять `visualRoot` watcher или включить
visual projection в update только потому, что его bytes входят в browser
source fingerprint.

### UPD-001.2 — Собрать договор версии Service Worker под update

Статус и исполнитель: `COMPLETE`, внутренний субагент текущей задачи Codex.

Классификация: move-only structural slice одного shared release contract;
поведение, SemVer и update protocol не меняются.

Требование или диагностический результат: перенести pure SemVer/release
contract и executable Service Worker version из исторических `core`/`browser`
путей в `hamiltonian/update/shared` и `hamiltonian/update/browser`, затем
перевести все host, Worker и test consumers на новую физическую границу.

Основание и связанная история: UPD-001.1 checkpoint `f8f18e75f` подтвердил,
что SemVer validator — единственная текущая shared update-часть, а executable
version — browser-only leaf; MF-428.3 закрепила их действующий закон.

Наблюдаемое расхождение: release identity уже является update contract, но
validator физически лежит среди общего lifecycle/control `core`, а version
constant — рядом с полным Service Worker entrypoint.

Причина: version contract появился до owner-решения `hamiltonian/update`.
Первый move перевёл imports, но не расширил вручную перечисленные host
`sourceWatchers`: прежний test строил physical entry, но не доказывал, что новая
owner-директория входит в production source watch.

Разрешённое изменение одного механизма: move-only
`core/service-worker-code-version.js` со spec в `update/shared`, move-only
`browser/service-worker-code-version.ts` в `update/browser`, механические
замены imports и точных test paths. Значение версии `1.1.3`, validator,
protocol, manifest, cache, admission и lifecycle не изменяются.

Regression или опровергающее доказательство: перенесённый SemVer spec, строгие
host/WebWorker TypeScript checks, `browser-build.spec.ts`, focused host version
tests и production Worker build. Проверка должна подтвердить отсутствие старых
physical owners и всех старых imports. Exact bundle SHA не обязан совпадать:
новые source paths входят в inline sourcemap и образуют новый точный artifact.
После повторной проверки `browser-build.spec.ts` также обязан прочитать
physical `host.ts` и доказать exact `hamiltonian/update` root внутри массива,
который host передаёт recursive `watch`.

Среда и критерий приёмки: canonical `main` из подготовительного commit этого
