# MF-104 — Доказать полную рабочую сессию одного агента

## Зачем

Нужно доказать не отдельные методы, а что один доверенный агент может через
готовую RPC-поверхность выполнить всю согласованную рабочую задачу.

## Связь с дорожной картой

Задача следует за инвентаризацией и реализацией всех необходимых RPC. Только
после неё возвращаются работы по конкурентности, правам доступа и ветвлению.

## Границы

* Начальный запрос содержит rules, действующие capabilities, revision и scoped
  RPC snapshot без разработки новых прав или scope.
* Агент читает history и Mass, применяет структурное изменение и наблюдает
  фактический результат через RPC.
* Агент изменяет runtime Field через предметный RPC, после чего наблюдает
  вычисленный State и исход Process; прямой `state.set` или `process.run` не
  используется.
* Следующий запрос получает только изменение с причинной границей.
* Ответ проверяется по первичным источникам.
* Скрытый контекст прошлой сессии не используется как истина.
* Access policy, scope и конкурентные writes не разрабатываются в этой задаче.

## Критерии готовности

Один воспроизводимый сценарий доказывает чтение, изменение, source projection,
Boundary, Bulk, history, Mass и проверку ответа одним агентом.

## Результат

* Один `agent/local` входит в настоящий in-memory Monad RPC-контур, соединённый
  с реальными Matrix, Energy, Boundary, Dark и Bulk. Все действия агента
  проходят через публичные методы, а внутренние Boundary identities остаются
  только у providers.
* Начальный envelope содержит digest трёх действующих документов-правил,
  фактический Git HEAD, source revision, действующие capabilities, полный Graph
  текущего root, exact Force frontier и task goal/scope.
* `meta.declaration.apply` добавляет optional Field одним structural patch,
  публикует изменённый `meta.ts`, материализует Boundary и обновляет Bulk Store.
* `meta.field.value.apply` запускает обычную причинную цепочку
  `Gluon → Photon → Z → W+`. Агент не вызывает `state.set` или `process.run` и
  наблюдает `ready`, committed output и acceptance/settlement через Graph и
  `meta.process.execution.read`.
* Тот же Process изменяет существующий Mass key; bounded
  `energy.mass.result.read` возвращает результат и ту же exact frontier.
* `bulk.observer.captureViewport` возвращает валидный PNG receipt и Store proof,
  в котором присутствует добавленный Field.
* Обнаруженный сценарием `Photon test` разрыв Bulk исправлен: Process-bound
  State становится текущим в Store без отдельного `Photon replace`.
* Второй history request начинается с `throughSequence + 1` предыдущей
  frontier, возвращает только Particle delta и не повторяет Graph snapshot.
* Новые права, частичная Graph projection, конкурентные writes, второй журнал,
  отдельный bootstrap endpoint и скрытый agent context не добавлены.
