# HAM-001 — Удерживать одну декларацию нодовой системы каждого контура

## Коротко

Hamiltonian должен показывать одну согласованную текущую нодовую систему,
собранную из точных деклараций действующих контуров. Перезапуск воплощения не
должен оставлять старое поддерево, смешивать две эпохи либо превращать дочернюю
ноду в корневую из-за потерянного владельца.

## Зачем

Ошибка нескольких Chrome-профилей и обнаруженный после перезапуска Hamiltonian
дубль серверного `RTCPeerConnection` имеют одну структурную причину: отдельные
lifecycle-наблюдения содержат identity и owner, но система не везде удерживает
одну полную текущую декларацию контура и не заменяет её целиком при новой
incarnation. Исправлять каждый следующий тип ноды отдельной веткой нельзя —
следующий пропущенный owner снова даст orphan, stale subtree или cross-contour
edge.

## Связь с дорожной картой

Задача относится к первому этапу Hamiltonian — управлению одной Вселенной на
одном устройстве в [`MF-425`](MF-425.md) — и к причинному монитору страницы
оркестрации. Постоянный владелец закона — раздел
`Декларация нодовой системы каждого контура` в
[`hamiltonian/README.md`](../../hamiltonian/README.md).

Универсальная форма `NodeSystemDocument`, UI и layout принадлежат пакетам
`nodes`, `@nodes/ui` и `@nodes/layout`, но они не определяют Hamiltonian-
ownership. Hamiltonian обязан передать им уже согласованные `parentId`, roots и
transport endpoints.

## Связанные задачи и история

* `MF-428.1` ввела ownership-closed browser/profile snapshot после того, как
  Service Worker второго профиля оказался корневой нодой без видимого Chrome.
  Это первый частный контур, уже приблизившийся к общему закону HAM-001.
* `MF-428.2` доказала replacement и retirement browser/profile scope, но не
  определяла смену server host epoch.
* `MF-428.5` меняет только presentation-поля карточки Service Worker и не может
  влиять на lifecycle ownership или `parentId`. Её checkpoint —
  `70fe491c1453afe4b5bd1e0f850f28f70deef6d9`.
* `NODES-008` меняет только геометрию `@nodes/layout`; ошибочная topology уже
  присутствует до передачи layout и не является его ответственностью.

## Подтверждённые факты

* Страница на owner screenshot была загружена от старого host
  `server:9f42bb94-98fc-4184-b0b2-234b40b86967`, version
  `mf-428-3-live`, и удерживала его server scope revision `6007`.
* В старом scope находились `peer-process:7c27e95a-…`, PID `70519`, и
  `rtc-peer:79b84615-…:server` в состоянии `connected`, вложенный в этот
  process.
* После полного restart появился host
  `server:dc8b3fca-a5be-4d3d-9302-b736d6e8eb28`, version
  `mf-428-5-live`, со своим `peer-process:1efb4bf5-…`, PID `84670`, и
  `rtc-peer:ad91be8e-…:server` в состоянии `new`.
* Page projection фиксирует server identity из navigation bootstrap. Registry
  удерживает snapshots разных `scopeId` параллельно, поэтому новый server scope
  не заменил старый. Новый RTC стал видимым через DataChannel к browser side,
  но его новый peer-process owner не был видимым; `visualParentId` вернул
  `null`, и RTC временно стал отдельной корневой нодой.
* Frozen read-only probe воспроизвёл результат без browser и layout:
  `server:old → server-contour`, `peer-process:old → server-contour`,
  `rtc:old → peer-process:old`, `rtc:new → null`.
* Существующие projection tests проверяют завершение process внутри одной
  server epoch, а host tests — peer repair/rebirth внутри одного host. Полного
  перехода `host A → host B` с двумя последовательными server scopes нет.

## Решения владельца

* Использовать короткий пакетный префикс `HAM`; родительская задача имеет номер
  `HAM-001`.
* Ввести общий declarative lifecycle law для всех Hamiltonian-контуров, а не
  индивидуальную обработку видов нод.
* Новая incarnation того же logical contour атомарно заменяет прежнюю без
  обязательной перезагрузки страницы. Декларации действительно разных
  контуров могут сосуществовать.
* Дефект server restart является первой отдельно принимаемой подзадачей
  `HAM-001.1`.
* Карточка подготовлена для ручного запуска владельцем. Координатор не запускает
  отдельную задачу Codex автоматически.

## Целевой закон

* Каждый independently authoritative Hamiltonian contour публикует одну текущую
  декларацию: stable logical contour identity, incarnation, exact root,
  monotonic revision/frontier, owned entity и transport.
* Каждая некорневая entity имеет полную доступную owner-chain. Каждый transport
  имеет проверенного owner и endpoints; межконтурное соединение появляется в
  общей сцене только через явно проверенную boundary identity.
* Registry различает разные logical contours, но для одного contour принимает
  только одну текущую incarnation. Replacement применяется атомарно: старая
  declaration, её subtree, transport и frontier удаляются до публикации нового
  node-system document.
* Snapshot/live events одной declaration сходятся к одинаковому результату
  независимо от стабильной перестановки. Stale incarnation и non-monotonic
  revision не могут вернуть удалённое поддерево.
* Presentation материализует только принятую декларацию. Она не угадывает owner
  по виду ноды, URL, title, PID, порядку подключения или последнему активному
  scope и не поднимает orphan на корень.

Точная wire-форма декларации, logical contour key и допустимые boundary
references должны быть выражены одним внутренним runtime-validated contract.
Пока пакет private и producer/consumer собираются вместе, отдельный public
export в `types.d.ts` не обязателен; при независимом версионировании этот вывод
пересматривается.

## Подзадачи

### HAM-001.1 — Заменять серверное поддерево при новой incarnation Hamiltonian

Статус: подзадача принята и завершена руководителем 12 августа 2026 года;
исполнитель — субагент
`HAM-001.1 — Заменять серверное поддерево при новой incarnation Hamiltonian`;
руководитель — текущая задача Codex. Исходный project-checkpoint запуска —
`921f1bf99`; первоначальный checkpoint результата — `086d1f663`, checkpoint
boundary reconciliation — `3d3e9439b`, follow-up checkpoint declaration-
authoritative projection и causal reconnect proof — `b8beed697`, no-reload
source checkpoint — `293d3259e`, stale browser peer checkpoint — `c2878cd03`.

Ожидаемый наблюдаемый результат: страница, загруженная при host A, после
полного запуска host B без reload сходится к одной server-декларации B. Старый
server A, его Bun/peer process, RTC и transport отсутствуют; все runtime B
вложены в exact server B, и ни в одном опубликованном node-system document RTC
B не становится корневой нодой.

Причина уже установлена: projection якорит видимость к server ID navigation
bootstrap; snapshot registry индексирует A и B разными `scopeId`; replacement
работает только внутри прежнего одноимённого scope; host snapshot не даёт page
полной replacement-декларации новой server incarnation. Transport traversal
может сделать дочерний RTC видимым раньше отсутствующего owner.

Первый regression до product fix подаёт frozen server A declaration, затем
server B declaration и доказывает исходный stale/orphan результат. Acceptance
test обязан проверить обе стабильные перестановки snapshot/live events и
каждый промежуточный опубликованный document, а не только финальный кадр.

Границы: не перезагружать page как способ очистки; не скрывать orphan RTC; не
назначать parent по `kind`; не сливать две host epoch; не менять layout,
renderer, browser profile identity, Service Worker presentation или transport
protocol шире необходимого declaration/replacement contract.

Критерий приёмки: frozen projection и host/page integration tests доказывают
атомарный `A → B`, один exact server root, полное удаление subtree A,
ownership-closed subtree B и отсутствие stale resurrection. Live restart
точно адресованного Hamiltonian contour сохраняет browser profiles, заменяет
только server declaration и не создаёт root/duplicate RTC.

Control WebSocket входит в тот же критерий:

* после `host A → host B` каждый подключённый browser/profile показывает свой
  фактически active WSS к exact server B;
* endpoint видимой WSS-грани и host-side connection/heartbeat относятся к одной
  server incarnation B и одной exact Service Worker identity;
* закрытый WSS к server A удалён вместе с declaration A и не остаётся ни
  гранью, ни retained transport;
* физически active и identity-confirmed WSS не может отсутствовать в
  node-system document после принятия declaration B;
* ни одна стабильная перестановка snapshot/live events и ни один опубликованный
  промежуточный document не смешивают heartbeat B с гранью A, не теряют active
  WSS и не создают WSS с отсутствующим endpoint.

Следующие отдельно наблюдаемые нарушения других контуров регистрируются новыми
подзадачами HAM-001 только после приёмки текущего среза. Их нельзя молча
захватывать в patch HAM-001.1.

Фактический результат: runtime-validated declaration registry использует
configured Hamiltonian identity как stable server key, заменяет server subtree
по incarnation целиком и сохраняет другую configured identity. Ownership-closed
server и browser/profile snapshots остаются раздельными; exact control WS/WSS
передаётся минимальной boundary reference между уже принятыми declarations.
Host публикует новую server declaration через Service Worker в page, а
projection заменяет A на B до следующего опубликованного document.

Offline evidence: core validator/registry regression проверяет stale
incarnation, non-monotonic revision/frontier, чужой boundary и независимую
identity; frozen projection проверяет обе перестановки stale-live/successor
snapshot и каждый промежуточный document; host integration сохраняет тот же
browser/profile без reload, заменяет A/WSS A на B/WSS B и связывает heartbeat с
exact Service Worker и server B. Повторно прошли применимые MF-428 проверки
profile ownership, ownership closure, unreachable close, WSS retirement,
reconnect и RTC/process recovery. В первоначальном checkpoint live runtime не
запускался: до отдельного exact-target proof существующий процесс не трогали.

Blocking review первоначального checkpoint выявил, что replacement endpoint
contour обязан в той же registry operation удалить boundary-запись другой
current declaration, если она ссылается на прежнюю incarnation. Follow-up
contract и projection regression проверяют этот invariant без зависимости от
порядка следующего wire update: ни одна retained declaration и ни один
промежуточный document не сохраняют stale boundary edge.

Менеджерский full host gate затем выявил недетерминированность прежнего
reconnect regression: фиксированная пауза после client close не доказывала, что
host уже записал terminal WebSocket observation до snapshot нового соединения.
В этом reconnect regression product defect не воспроизвёлся отдельно и в
повторном full suite; proof теперь ждёт фактический close handshake и bounded
causal wait точного
`connection-close` того же connection до открытия reconnect epoch.

Менеджерский exact-target live proof на clean checkpoint `058623b87` подтвердил
replacement A → B, отсутствие references A и orphan RTC, сохранение прежнего
browser/profile и active identity-confirmed WSS B с heartbeat challenge/ack.
При этом page получила две внутренне валидные current declarations: browser
declaration содержала exact Service Worker endpoint, server declaration — exact
WSS boundary к этому endpoint и server B. Несмотря на это, materialized document
потерял Service Worker и WSS. Следовательно, host declaration и wire path были
валидны, а defect находился после aggregation: raw snapshot либо terminal live
event мог структурно удалить subject, который всё ещё удерживала current
declaration.

Follow-up projection law удерживает entity и transport current declaration до
следующей принятой декларации соответствующего logical contour. Regression
после принятия browser endpoint и WSS B подаёт более новый raw snapshot с тем
же source frontier, но без endpoint, затем отдельное terminal live-наблюдение:
ни один промежуточный document не теряет Service Worker или WSS. Следующая
accepted browser declaration, действительно исключившая endpoint, атомарно
удаляет его и reconciled server boundary. Post-fix live restart ещё не повторён;
предыдущий version-changing прогон также вызвал page reload и поэтому не
доказывает no-reload acceptance.

Менеджерский post-fix live proof на isolated origin подтвердил topology и WSS
часть A → B: остался один server B без references A и orphan RTC, прежние
browser/profile и Service Worker сохранились, exact WSS B имел те же endpoints
и heartbeat 4/4. Но даже при одинаковом `HAMILTONIAN_VERSION` page получила
новые navigation/time origin: source revision включала новый host epoch и тем
самым детерминированно вызывала reload при каждом cold host restart. Это тот же
непринятый no-reload результат HAM-001.1, а не отдельная подзадача.

Follow-up source-revision contract использует fingerprint полного фактически
served browser code и не включает host incarnation либо build generation.
Navigation HTML сохраняет revision A как baseline до control connection, а host
B сообщает revision своего current served code. Frozen regression и host
integration доказывают, что bootstrap и control используют один fingerprint:
одинаковый полный набор browser artifacts при A и B не требует reload;
изменение любого из четырёх bundles либо directly served text создаёт другую
revision и сохраняет однократный reload настоящего source update. Post-fix
no-reload live proof после этой коррекции ещё не выполнен.
Result checkpoint `293d3259efc1e921014abe4eb72745f6ef39baca` продолжает
projection checkpoint `b8beed697` и исправляет выявленный на его live-проверке
host-incarnation reload, не объявляя всю родительскую HAM-001 завершённой.

Финальный manager live на clean `a73e83e6` доказал no-reload часть: A и B
сохранили exact time origin, navigation ID и source revision; host B, heartbeat,
registry server declaration и exact WSS B были current. Но materialized document
остался на A и layout отклонил duplicate identity: current browser declaration
ещё удерживала disconnected browser RTC с session A, когда server declaration и
live page-source уже перешли к session B. Это продолжение того же A → B
acceptance HAM-001.1, а не новый отдельно принимаемый результат.

Причина находится в declaration path, а не в layout: Service Worker принимал
каждое `page-lifecycle` в browser journal и передавал live envelope, но не
публиковал вслед за ним новую browser declaration. Projection одновременно
правильно не удаляла объявленный RTC A по terminal live и неправильно
материализовала ещё не объявленный RTC B того же declaration-owned source.
Следующий разрешённый шаг — frozen declaration regression всех промежуточных
documents, затем синхронное продвижение browser declaration и общий запрет
undeclared structural membership внутри уже объявленного contour до следующей
принятой declaration. Kind-specific скрытие и изменение layout запрещены.

Follow-up implementation проводит structural `page-lifecycle` через
browser/profile declaration в том же Service Worker event-turn. Entity и
transport events создают строго возрастающие declarations; message observation
продвигает causal journal, но не меняет structural declaration. До принятия
этой declaration projection не материализует новый structural subject от уже
объявленного source или под уже объявленной owner-chain. Frozen regression
проверяет обе перестановки server B относительно browser live events и каждый
промежуточный document: RTC A остаётся единственным до declaration B, затем
атомарно уступает RTC B; duplicate layout identity, orphan и возврат server A
не возникают. Layout IDs, renderer и geometry не менялись.

Повторный manager exact-target live proof на clean checkpoint `48ab9d01d`
завершил приёмку. На изолированном origin host A был полностью остановлен и
host B запущен с теми же identity, version и browser source fingerprint.
Страница сохранила exact `timeOrigin`, navigation ID, browser/profile и Service
Worker identity без reload. В итоговом document остался один server B и одна
согласованная RTC session B; references A, orphan RTC и duplicate layout
identity отсутствовали. Exact WSS B соединял тот же Service Worker с server B,
а host-side challenge/ack достиг `5/5`. Scene осталась в live state; layout и
renderer не изменялись. Созданные руководителем host и CDP target после
проверки остановлены и закрыты.

Result checkpoint `c2878cd03b1395b68d884757596dbc1992b2242d` продолжает
no-reload checkpoint `293d3259e` и закрывает обнаруженный его финальным live
acceptance stale browser peer gap. Offline manager recheck на metadata
checkpoint `48ab9d01d71299e84e6521c647ad74415ef5ea5f` подтвердил три focused
regression (128 assertions), clean diff и exact восьмифайловый scope. Родитель
HAM-001 по решению владельца остаётся `IN_PROGRESS`; эта приёмка не является
его переводом в `REVIEW` или closing review.

### HAM-001.2 — Показывать действующее WebRTC-соединение между браузером и сервером

Статус и исполнитель: выполняется; субагент
`HAM-001.2 — Показывать действующее WebRTC-соединение между браузером и
сервером`; руководитель — текущая задача Codex.

Классификация: новый отдельно наблюдаемый результат того же родителя,
Hamiltonian owner и node-system declaration contract. Это не продолжение
принятой `HAM-001.1`: замена server A на B уже доказана отдельно.

Требование: когда current peer session действительно `connected` и её каналы
Oracle и Force открыты, живая сцена показывает ровно две соответствующие линии
между exact browser и server `RTCPeerConnection`. После закрытия или замены
этой session её линии отсутствуют.

Основание и связанная история: `HAM-001.1` ввела ownership-closed declarations
контуров и minimal cross-contour boundary для WSS. Общий закон declaration и
boundary принадлежит [`hamiltonian/README.md`](../../hamiltonian/README.md).

Наблюдаемое расхождение: на пользовательском live-контуре `ham-001-live` host
status сообщает `connected` и каналы `oracle`, `force`; current browser и
server declarations содержат matching RTC endpoints одной session, но ни одна
current declaration не содержит transport `data-channel`. Поэтому сцена
показывает RTC-ноды без обеих линий.

Причина: подтверждена до реализации. Ownership-closed browser и server
snapshots правильно исключают cross-contour DataChannel, а единственный
boundary producer server declaration выбирает только control WebSocket и не
переносит уже наблюдённые Oracle/Force DataChannel.

Разрешённое изменение одного механизма: обобщить существующий runtime-
validated declaration boundary producer так, чтобы он проецировал фактически
наблюдённый cross-contour transport к exact current declarations и endpoints.
Никакой второй механизм, включая ownership snapshot, projection materializer,
layout, renderer, RTC signaling и Oracle/Force protocol, в срез не входит.

Regression или опровергающее доказательство: frozen declarations с matching
RTC endpoints и двумя открытыми DataChannel сначала воспроизводят отсутствие
линий, затем проверяют оба порядка принятия declarations и каждый
промежуточный document. Host integration обязан получить transport из
фактического peer lifecycle, а не вывести его из peer status, session ID или
вида ноды. Close/replacement удаляет обе старые линии.

Среда и критерий приёмки: offline validator/registry, frozen projection и
host/page integration показывают ровно две exact boundary-линии, исключают
stale/orphan edge и повторяют применимые `HAM-001.1`, WSS, RTC recovery и
ownership regressions. Затем тот же пользовательский контур
`http://127.0.0.1:4400` остаётся работающим и без reload как способа исправления
визуально показывает владельцу Oracle и Force; isolated origin этого не
заменяет.

Фактические действия: единственный declaration boundary producer обобщён на
фактически наблюдённые cross-contour WebSocket и DataChannel. Он сверяет
owner/source/target с exact current declarations и принимает Oracle/Force
только для retained physical `opened/open` observation между каноническими
server/browser RTC endpoints одной current session. Прежняя WSS-семантика
сохранена: owner=source — exact Service Worker, target — exact self-owned server
root. Ownership snapshot, projection materializer, layout, renderer, signaling и
Oracle/Force protocol не менялись.

Результат и вывод: frozen regression проверяет оба порядка declarations и
каждый промежуточный document: до physical boundary линий нет, после неё есть
exact Oracle и Force без orphan RTC. Validator/registry negative matrix
отклоняет wrong direction/owner, lane/ID/session/state, stale declaration и
ambiguous duplicate entity. Host integration получает обе грани из реального
Werift peer lifecycle и удаляет их при replacement. Полный offline gate: `102
pass`, `0 fail`; root typecheck и diff check проходят.

Live-приёмка пользовательского результата не пройдена. После полного restart
точного contour на result checkpoint page сохранила прежние `timeOrigin`,
navigation ID и source revision; host стабильно удерживал одну connected peer
session. Десять последовательных samples за пять секунд показывали два exact
RTC endpoints и две `opened/open` Oracle/Force boundary, lifecycle pending `0`

### HAM-001.3 — Установить, почему действующие WebRTC-линии не попадают в кадр

Статус и исполнитель: диагностическая подзадача принята и завершена
руководителем 13 августа 2026 года; исполнитель — субагент
`HAM-001.3 — Установить, почему действующие WebRTC-линии не попадают в кадр`;
руководитель — текущая задача Codex.

Классификация: новый диагностический результат того же родителя и Hamiltonian
presentation path. Он следует после отдельного HAM-001.2 checkpoint, потому что
пользовательский live-контур выявил новое нарушение, неизвестную downstream-
причину и потенциально другой изменяемый механизм.

Требование или диагностический результат: установить первую точную границу,
на которой две current Oracle/Force boundary и оба RTC endpoints перестают
соответствовать пикселям WebGPU canvas. Подзадача завершается подтверждённой
причиной и воспроизводящим regression, а не product fix.

Основание и связанная история: result checkpoint HAM-001.2
`2e8a9949849d580b439ab06bec0dd51eb7e7450d` и owner law
[`hamiltonian/README.md`](../../hamiltonian/README.md) подтверждают exact
declaration boundary. Исходный live canvas сохранён в
[`project/artifacts/HAM-001`](../artifacts/HAM-001/README.md).

Наблюдаемое расхождение: current declarations и document status устойчиво
показывают два RTC endpoints, две open DataChannel и `19/14`, но canvas-пиксели
не содержат browser RTC и обе линии. Host session при этом `connected`, каналы
Oracle/Force действуют, generation не меняется и repair не происходил.

Причина: подтверждена в долгоживущей lifecycle projection до scheduling и
layout. При смене incarnation browser declaration projection помечает
superseded все source из frontier прежней декларации. Page source законно
продолжается через смену Service Worker и присутствует в successor declaration,
но общий superseded-фильтр удаляет его envelopes из новой декларации. Поэтому
browser RTC остаётся в current declaration registry, однако не попадает во
внутреннюю entity map; две boundary DataChannel теряют видимый target ещё до
`NodeSystemDocument` и не доходят до layout.

Разрешённое изменение одного механизма: только диагностическое наблюдение и
воспроизводящий regression на первой найденной расходящейся границе. Product
behavior, declaration producer HAM-001.2, projection, layout, renderer,
signaling и Oracle/Force protocol в этом срезе не изменяются.

Regression или опровергающее доказательство: один и тот же exact input
последовательно сравнивается на границах retained declarations → projection
document → scheduled/applied positioned layout → surface layout → canvas.
Проверка обязана отличить stale pixel от stale model и не делать вывод по
status text, screenshot timing либо виду ноды.

Среда и критерий приёмки: read-only наблюдение оставленного пользовательского
contour `http://127.0.0.1:4400` и минимальный offline regression подтверждают
одну точную причину. Сервер, profile, вкладка и canvas не перезапускаются и не
очищаются как способ диагностики. После causal handoff исправление получает
следующий номер; HAM-001 остаётся `IN_PROGRESS`.

Фактические действия: на неизменённом пользовательском contour exact-target
read-only probe подтвердил host PID `57075`, epoch `0517dda7-…`, peer session
`c45768a2-…`, состояние `connected`, каналы Oracle/Force и `peerRepairs=0`.
Applied `PositionedNodeSystem` содержал `19` нод и `14` рёбер, только server
RTC и ни одного DataChannel route. Fresh `HamiltonianLifecycleProjection` в
той же page realm и с теми же тремя current declarations приняла весь input и
дала `20` нод, `16` рёбер, оба RTC и exact Oracle/Force edges. Сервер, вкладка,
profile, navigation, canvas и product runtime не перезапускались и не
изменялись.

Результат и вывод: минимальный regression воспроизводит первую расходящуюся
границу без renderer и layout: declaration `worker A` содержит продолжающийся
page source, successor `worker B` содержит тот же page source и новый browser
RTC. Fresh projection одного successor показывает RTC, а долгоживущая
projection после `A → B` его теряет. Проверка проходит `1 pass`, `6 expect()`;
весь файл projection — `33 pass`, `0 fail`, `345 expect()`. Product behavior не
менялся. Следующий отдельный срез должен исправлять только retirement
superseded source при replacement declaration incarnation: source, который
точно продолжается в successor declaration, нельзя подавлять вместе с
действительно завершёнными source прежней incarnation.

Подготовительный commit: `2d99865f4`.

Result checkpoint: `69eb8d8c7934f8d4f117e21211324124591e42b6`.

### HAM-001.4 — Сохранять ноды, которые продолжаются в новой декларации

Статус и исполнитель: выполняется; субагент
`HAM-001.4 — Сохранять ноды, которые продолжаются в новой декларации`;
руководитель — текущая задача Codex.

Классификация: отдельный behavior patch того же родителя после принятой
диагностики HAM-001.3. Он не расширяет HAM-001.2 и не возвращает HAM-001.1 в
работу.

Требование: при замене incarnation одной declaration ноды и transports,
чьи exact source keys прямо присутствуют в successor declaration, остаются в live-
проекции. Только source, которые successor больше не объявляет, могут быть retired
как superseded.

Основание: diagnostic result HAM-001.3
`69eb8d8c7934f8d4f117e21211324124591e42b6` доказал, что current registry и fresh projection
корректны, а долгоживущая projection подавляет continuing page source при replacement browser
declaration. Действующий declaration law принадлежит [`hamiltonian/README.md`](../../hamiltonian/README.md).

Разрешённое изменение одного механизма: только retirement superseded source в lifecycle
projection. Exact source key, который присутствует в successor declaration frontier, не подавляется;
отсутствующие source по-прежнему удаляются. Declaration producer, registry, Service Worker journal,
scheduling, layout, renderer, RTC signaling, Oracle/Force protocol и source identity в этот срез не входят.

Regression: diagnostic regression HAM-001.3 становится acceptance regression и обязан
показать одинаковый document для fresh successor и stateful `A → B`. Negative cases удерживают
retirement source, которого в successor нет, и не дают stale live envelopes воскресить прежнюю
incarnation. Полный projection suite и применимые HAM-001.1/2 regressions остаются зелёными.

Среда и критерий приёмки: после offline regression тот же уже поднятый
пользовательский contour `http://127.0.0.1:4400` переводится на result checkpoint полным
restart причинно связанного Hamiltonian contour. Страница не перезагружается как способ
очистки. Current document и applied layout дают два RTC endpoints и exact Oracle/Force lines; stale source
прежней incarnation не воскресает. Сервер остаётся работать для визуальной приёмки
владельцем. Новое нарушение после этого граничного результата получает следующую
подзадачу.

Подготовительный commit: `74189a548`.

## Решения HAM-001.1

Stable server key выводится из configured Hamiltonian identity; profile key —
из уже принятого profile UUID. Общая runtime-validated declaration-форма
достаточна для server и browser/profile adapters. Boundary transport хранит
только exact references на current declarations и endpoints, не копируя чужое
ownership-поддерево; будущие device contours этим срезом не определяются.

## Границы

* Не превращать `NodeSystemDocument` в канонический runtime Store или историю.
  Декларация является retained current lifecycle projection.
* Не переносить предметное ownership-решение в `nodes`, `@nodes/ui`,
  `@nodes/layout`, renderer или geometry.
* Не добавлять branches по конкретным видам нод и не скрывать invalid topology
  presentation-фильтрами.
* Не менять production Dark, Boundary, Matrix, Energy, Bulk, authority либо
  Force/Oracle protocols без отдельной задачи.
* Не считать screenshot, финальный документ или зелёный layout доказательством
  атомарности replacement: проверяются также входной contract и промежуточные
  документы.

## Критерии готовности

* Постоянный Hamiltonian owner document определяет declaration, logical contour,
  incarnation, root, revision/frontier, ownership closure и replacement.
* Runtime validator отклоняет декларацию без exact root/owner-chain, со stale
  incarnation, non-monotonic revision/frontier либо недопустимым
  cross-contour endpoint до retained aggregation.
* Retained registry атомарно заменяет declaration одного logical contour и не
  изменяет declarations других контуров.
* Pure permutations и integration tests проверяют server, browser/profile,
  page/Worker и peer/process paths без специальных веток по kind.
* Любая материализованная некорневая нода имеет exact видимого parent; stale
  subtree, root orphan, duplicate incarnation и cross-contour edge отсутствуют
  во всех опубликованных документах.
* Live restart host и уже принятые browser/profile restart/close scenarios
  подтверждают один и тот же общий закон.
* Независимая closing review сверяет owner document, internal/public contracts,
  code, tests, artifacts и live evidence до закрытия задачи.
