# MF-411 — Определить, что делает Hamiltonian и где он работает

## Коротко

Нужно простыми законами отделить Hamiltonian от самой Вселенной и определить,
какие его части работают в серверной программе и какие — в браузере.

## Зачем

Отделить причинную жизнь Вселенной от уровня, который рождает, размещает,
знакомит, обновляет и заново воплощает её части. Без этого один физический
listener снова случайно становится владельцем Dark, Bulk или другого домена.

## Связь с дорожной картой

Это родитель ближайшей линии и текущая архитектурная задача. Сначала
фиксируется закон и карта воплощений, затем выполняется ограниченный
эксперимент. Его уже доказанные границы закреплены в
[`hamiltonian/README.md`](../../hamiltonian/README.md). Раскладывать production-код по новым
местам до завершения этого закона запрещено.

## Подтверждённая текущая основа

* Закрытая `MF-409` оставила один физический listener Dark на одну текущую
  Вселенную.
* Boundary, Matrix, Energy и Bulk живут отдельными Bun-процессами и открывают к
  Dark исходящие Oracle и Force WebSocket.
* `../../quantum/dark/server.ts` одновременно владеет Dark runtime, внутренними domain
  sockets и browser wiring Bulk, поэтому один порт сейчас достигнут ценой
  прямых импортов Bulk в Dark.
* Boundary владеет каноническими фактами. Dark координирует Oracle и Force.
  Bulk владеет производной проекцией наблюдателя и не участвует в автономной
  причинной жизни Вселенной.
* Текущий one-Dark-listener является рабочим baseline. Новое направление не
  объявляет историческую `MF-409` ошибкой и не меняет runtime само по себе.

## Принятое направление

Hamiltonian — целое над отдельными runtime-процессами и browser contexts. Его
воплощения могут находиться:

* в Bun host process;
* в Service Worker;
* в Window startup;
* позднее — на другом устройстве или host.

Hamiltonian:

* отдаёт неизменяемый startup, запускает обновляемые importers и через них
  загружает точные `internal`/`metafor` modules;
* знакомит воплощения и переносит signaling;
* выбирает или подтверждает место запуска;
* запускает, останавливает и заново воплощает части;
* не принимает Particle вместо Dark;
* не фиксирует факт вместо Boundary;
* не остаётся прокси в обычном Oracle или Force realtime.

## Решение владельца о серверной среде

Browser и server используют один смысловой путь загрузки:

```text
тонкая точка входа → startup → release → internal / metafor
```

`server.ts` является только минимальной точкой входа серверного процесса. Он
не содержит рабочую логику приложения, доменов, выпуска или обновления. Его
задача — запустить устойчивый server startup и передать ему управление.

Server startup получает, проверяет и запускает текущий server release. Release
определяет согласованный состав сменяемых `internal`/`metafor` частей, а вся
среда после startup может быть целиком обновлена и заново запущена. Browser и
server различаются только платформенными способами загрузки, хранения и
перезапуска; буквальный Service Worker API на сервер не переносится.

Это целевой закон, а не описание текущей реализации. Сейчас
`@hamiltonian/startup` не имеет env `server`, а корневой `server.ts` напрямую
импортирует `@hamiltonian/release` и содержит HTTP/WSS surface. Расхождение
нужно устранить отдельными срезами только после принятия общего закона
Hamiltonian; runtime в `MF-411` не меняется.

## Решение владельца о документации

Корневой `hamiltonian/README.md` является короткой картой документации и
содержит только назначение Hamiltonian, общий проверяемый закон, границы
ответственности и ссылки на документы владельцев. Подробности packages,
прототипа, визуальной раскладки, запуска и проверок принадлежат их точным
документам-владельцам.

Каждый package Hamiltonian имеет собственный `README.md`, который описывает
его предметную ответственность, поддерживаемые среды, жизненный цикл, public
границы и связи с соседними packages. Технические детали остаются у типов,
кода и руководства разработки; один закон не копируется между документами.

Namespace с собственной директорией хранит общий закон в её корневом
`README.md`; поэтому владельцем `@internal/*` является
`hamiltonian/internal/README.md`, а вложенные директории принадлежат конкретным
packages. Общая граница `@metafor/*` описывается одной строкой в корневом
`hamiltonian/README.md`: отдельный `METAFOR.md` оркестратору не нужен.
Evidence рабочего прототипа принадлежит задаче его приёмки и очистки packages,
а после её закрытия постоянные выводы остаются только у настоящих package и
domain owners.

Документация определяет устройство прямыми положительными законами. Каждый
абзац сначала называет сущность, её ответственность, владельца решения и
наблюдаемый результат. Граница между доменами задаётся распределением
ответственности: «Hamiltonian владеет доставкой; загруженный domain owner —
предметной работой», а не перечнем того, чем Hamiltonian не является.
Отрицание допустимо только внутри точно названного условия ошибки или
ограничения принятого перехода.

Hamiltonian-документация описывает управление воплощениями и интерфейс с
загружаемыми функциями MetaFor. Онтология, внутренний lifecycle и связи
предметных доменов принадлежат их документам-владельцам из
[`docs/README.md`](../../docs/README.md). На границе Hamiltonian использует
общее понятие domain owner/domain transport и ссылку на карту MetaFor;
перечисление Particle, State, Transition, Process, канонических фактов и
visual-проекций в контракт оркестратора не переносится.

Общая карта ответственности `startup → release → internal / metafor`
принадлежит только корневому `hamiltonian/README.md`. Package и namespace
README описывают свой собственный закон и ссылаются на root; общая таблица
Startup/Release/Internal/MetaFor в них не повторяется. Таблица нескольких
владельцев допустима только для специфической внутренней композиции package,
которой root не владеет.

Корневой `hamiltonian/README.md` является единственным владельцем общего
терминологического словаря. Русское название используется в обычной прозе, а
английское написание фиксируется рядом как точный идентификатор или канонический
термин: `identity`, `incarnation`, `env`, `artifact`, `release`, `placement`,
`listener`, `signaling`, `control`, `transport`, `contract`, `current`,
`candidate`, `handover`, `contour`, `declaration`, `revision`, `frontier`.
Package README ссылаются на словарь и объясняют отдельно только собственные
public types и имена среды.

Корневой README владеет только законом оркестрации. Законы визуальной среды,
деклараций нодовой системы и причинного монитора принадлежат
`@internal/visual`: `hamiltonian/internal/README.md` кратко называет эту
функцию, а `hamiltonian/internal/visual/README.md` содержит полный закон и
отдельно различает принятое целевое устройство от реализованного состояния.
`@hamiltonian/visual` остаётся временным prototype package до `HAM-006` и не
является владельцем долговечного закона.

закон, clean-room packages, рабочий прототип, node-system presentation, Web
Push, команды запуска и удалённые task artifacts. Первый результат исправил
эту смесь, но пропустил общего владельца `internal`, поместил непакетный

Второй результат исправил иерархию владельцев, но корневой и package-level

опровержение прежних моделей, а положительное распределение управления

Третий результат исправил форму законов, но таблицы границ скопировали в

Тем самым документ оркестратора стал вторым сокращённым владельцем онтологии

Четвёртый owner review уточнил владельцев файлов: отдельный `METAFOR.md`
дублирует достаточную общую границу корневого README, а `PROTOTYPE.md` хранит

Пятый owner review обнаружил дублирование общей таблицы ответственности в
startup, release и internal README. Эти copies создают несколько владельцев
одного закона и расходятся при следующем изменении root.
Шестой owner review обнаружил, что обычная проза смешивает русские понятия с
английскими словами без зафиксированного смысла. Общего словаря нет, поэтому
читатель не может отличить точное имя кода от случайного англицизма.
Седьмой owner review установил, что корневой README всё ещё хранит
prototype-derived закон деклараций нодовой системы, а подробный договор
остаётся у временного `@hamiltonian/visual` вместо `@internal/visual`.

Причина: первый owner-map учитывал только существующие packages и не разделил
package, namespace и непакетную предметную документацию. Исторически
`internal` является общим пространством сменяемой функциональности
Hamiltonian, а имя package задаёт функцию, не execution context.

Разрешённое изменение одного механизма: изменить только Markdown-документацию
Hamiltonian и входную карту `docs/README.md`; хранить namespace law в
`hamiltonian/internal/README.md`; удалить дублирующий `METAFOR.md`; перенести
prototype evidence в задачу, выбранную владельцем для приёмки и очистки;
исправить package README и ссылки. Не менять TypeScript/JavaScript, manifests,
scripts, public types, runtime, routes, tests или project graph.

Текущая коррекция сохраняет принятую иерархию и смысловые границы, но

### MF-411.2 — Объяснить конечный Hamiltonian простыми пользовательскими историями

Статус и исполнитель: `REVIEW`, текущий Codex; сохранение скачивания после
исчезновения исходного PWA-адреса зафиксировано и ожидает owner review.

Коррекция сохраняет тот же механизм и границу документации. В первом примере
три устройства распределяли только Boundary, Matrix и Energy, поэтому их сумма
не образовывала полный контур Вселенной. Пример должен показать полный состав

## Онтологическая граница имени

В классической механике Hamiltonian задаёт динамику системы, а не означает
«сервер обновлений». Поэтому имя допустимо только для целого закона рождения и
изменения воплощений; Bun server, Service Worker и Window являются его
частичными воплощениями, но не каждым отдельным Hamiltonian.

Если после точного описания останутся только cache, signaling и process
supervision, классическое имя не подходит. Тогда задача обязана оставить
нейтральное рабочее название, а не растягивать термин молча.

## Уже принятые ограничения

* Browser loading contract определён в [`LOAD-001`](https://github.com/zavx0z/metafor/blob/e1e83ce5221c96b4decb5ce80f69a473cd13cb9c/project/tasks/LOAD-001.md): неизменяемый
  `startup` запускает обновляемый `import`, служебные modules Hamiltonian живут
  в `internal`, а functionality MetaFor — в отдельном `metafor`.
* Полный многосоставный update после startup принадлежит
  [`UPD-002`](https://github.com/zavx0z/metafor/blob/c6e2692b2b164240ca84e6dc98b4bfc4fa370ac1/project/tasks/UPD-002.md); он не должен возвращать WSS code delivery или
  включать prototype source в новую реализацию.
* Universe, Dark и Boundary имеют identity, не равную PID, вкладке, Worker или
  сетевому адресу.
* В одной Вселенной логически один Dark и один Boundary.
* Bulk не является общим обязательным gateway: он проявляет Вселенную для
  конкретного наблюдателя.
* Energy может иметь несколько воплощений и находиться на разных устройствах.
* Cardinality Matrix ещё не утверждена: возможны общая и
  observer-specific Matrix.
* В целевом устройстве между доменами нет production-импортов
  implementation-кода. Связь проходит через утверждённые contracts и
  transport; текущее нарушение Dark → Bulk остаётся migration debt.
* Один фиксированный внешний port не означает отсутствие исходящих sockets,
  ICE, STUN или TURN.
* Частичный hot reload причинного contour не вводится. Первая версия обновления
  рассматривает versioned code и полное новое воплощение выбранной части.
