# MF-415 — Интерактивная сцена оркестрации Hamiltonian

## Зачем

Текстовая Mermaid-схема испытательного Hamiltonian не позволяет владельцу
поэтапно разбирать живую топологию и управлять уже существующими lifecycle
действиями. Нужна самостоятельная интерактивная страница, которая показывает
фактически наблюдаемую инфраструктуру и может расширяться вместе с принятыми
решениями.

## Связь с дорожной картой

Задача развивает доказанный результат `MF-412`, но не переписывает его
исторические evidence. Hamiltonian перестаёт быть скрытым экспериментом и
становится верхнеуровневым техническим contour. Production-домены MetaFor в
этом срезе не переносятся.

## Решения владельца

* Hamiltonian переносится из `experiments/hamiltonian` в `/hamiltonian`.
* Оркестрация показывается живой WebGPU-сценой через MetaFor Engine, HUD и UI.
* Новый пакет `pkg/ui/node` владеет универсальными нодовыми системами и может
  расширять существующие UI elements, components и panels.
* Визуальная грамматика нод берётся из уже разработанной владельцем
  Blender-derived Penpot-системы и `zavx0z/node`; Hamiltonian не создаёт рядом
  собственный язык «инфраструктурных карточек».
* ELK вычисляет первоначальную двумерную расстановку нод по их точным
  renderer-метрикам.
* При добавлении и удалении нод позиции неизменившихся нод сохраняются, а
  серверный Libavoid пересчитывает только маршруты рёбер вокруг фиксированных
  препятствий. Он работает через уже существующий listener Hamiltonian и не
  открывает второй port или server.
* Ноды можно перетаскивать. Пользовательские coordinates сохраняются в
  origin-scoped browser storage, переживают topology updates и page reload и
  остаются presentation state, а не фактом Hamiltonian или мира.
* Рамка на пустом месте выделяет несколько нод; drag любой выбранной ноды
  перемещает всю группу атомарно. Shift добавляет ноды к текущему selection.
* Ширина ноды изменяется drag левой или правой границы с удержанием
  противоположного края. Width сохраняется вместе с coordinates и также
  остаётся presentation state.
* Body и header карточек полупрозрачны, чтобы пересекающие их edges и
  перекрытые ноды оставались видимы. Text, sockets и borders сохраняют полную
  непрозрачность и читаемость.
* Pan/zoom viewport сохраняется как observer-local state конкретной Window в
  `sessionStorage`, переживает reload и не синхронизирует камеры разных вкладок.
* Libavoid route является безопасным obstacle-avoiding guide. WebGPU renderer
  скругляет его повороты сегментами кубической кривой Безье, не заменяя маршрут
  одной прямой кривой, которая могла бы пересечь ноду.
* Постоянные подписи на edges скрыты; semantic label показывается tooltip
  рядом с cursor только при наведении на узкий hover-corridor самой линии;
  hovered edge сохраняет собственный tone-цвет и становится толще. Tooltip
  предпочитает top и у границ surface/browser выбирает right, bottom или left.
* Realtime-проекция страницы передаётся через `BroadcastChannel`, чтобы UI
  оркестрации не становился Oracle- или Force-клиентом.
* Страница дополняется поэтапно вместе с владельцем; новые управляющие действия
  не считаются разрешёнными автоматически.

## Действующий закон среза

`@ui/node` является transport- и domain-neutral presentation package. Он
владеет generic node/port/edge model, проверкой, ELK layout, viewport,
selection и HUD rendering, но не импортирует Hamiltonian, Bulk, Dark, Oracle
или Force.

Внутренняя геометрия ноды строится content-first: точные метрики реально
загруженного TrueType-шрифта → Flex plan → размер и ports для ELK → rendering
того же plan. Нода, текст и sockets масштабируются одним transform. Ручные
screen-minimum для текста и скрытый DOM measurement запрещены; фиксированные
метрики допустимы только как детерминированный fallback без renderer.

ELK и Libavoid имеют разные обязанности. ELK предлагает первоначальные
координаты нод. После появления живой схемы неизменившиеся ноды становятся
якорями: структурное обновление не вправе произвольно перестраивать их
положение. Libavoid получает уже измеренные фиксированные rectangles и ports и
строит orthogonal edge routes, но сам ноды не перемещает. Новый node получает
предложенную ELK позицию с детерминированным устранением пересечения с
сохранёнными нодами. HTTP-запрос раскладки является локальной presentation
инфраструктурой Hamiltonian, а не Oracle RPC, Force stream или новым realtime
transport.

Drag ноды изменяет только presentation geometry. Во время движения card и все
её ports следуют за pointer в graph coordinates; после отпускания новый anchor
сохраняется и тот же server-side Libavoid пересчитывает edge routes. Это не
lifecycle action, не authority-команда и не сообщение BroadcastChannel.
Сохранённая позиция применяется только к известному node id; исчезнувшая нода
не удерживается в topology, но при повторном появлении может вернуться к своему
последнему пользовательскому anchor.

Рамочное выделение и resize принадлежат той же presentation geometry. Group
drag сохраняет один набор positions и только после release делает общий
Libavoid reroute. Resize допускается с обеих сторон, не сжимает card меньше её
точного intrinsic Flex-размера и перемещает sockets и connected endpoints до
серверного reroute. Эти действия не становятся topology facts.

Hamiltonian владеет преобразованием своих реальных host, Service Worker,
Window, Bun process и peer snapshots в UI document. `BroadcastChannel`
переносит только sanitised browser-local orchestration projection. Он не
заменяет control WSS, per-Window MessagePort, Bun IPC, WebRTC signaling или
прямые `oracle`/`force` DataChannel и не является источником authority.

Новая Window сначала получает полный snapshot через существующий attach path,
а затем может принимать coalesced live-проекцию. Сообщения UI не содержат
token, resume capability, SDP/ICE или Oracle/Force payload.

## Первый срез

* безопасный перенос существующего Hamiltonian на верхний уровень;
* подключение Hamiltonian и `@ui/node` к root workspace;
* полноэкранный canvas, созданный `UiRuntime` и добавленный в настоящий HUD;
* ELK-граф из фактической topology: host/listener, Service Worker, browser
  connections, Windows, выбранный leader, Dedicated Workers, Bun embodiments
  и direct peer;
* Oracle и Force видны только как две логические линии direct carrier;
* pan, zoom, fit, selection и инспектор выбранного узла;
* live-обновление topology через versioned `BroadcastChannel`;
* только уже существующие lifecycle-действия Hamiltonian, доставляемые по
  прежнему направленному control path, а не как доверенные BC-команды.

## Границы

* Не подключать production Dark, Boundary, Matrix, Energy или Bulk.
* Не использовать `pkg/visual` как владельца инфраструктурной раскладки мира.
* Не переносить управление, signaling или secrets в `BroadcastChannel`.
* Не считать BroadcastChannel межустройственным или межпрофильным transport.
* Не менять Oracle/Force protocol и не использовать их для состояния сцены.
* Не изобретать placement/restart actions сверх уже реализованных Hamiltonian
  операций без отдельного обсуждения с владельцем.
* Не переписывать raw evidence `MF-412` после перемещения исходников.

## Критерии готовности первого среза

* `/hamiltonian` запускает и проверяет прежний standalone contour после move.
* `@ui/node` имеет public contracts, проверку ссылок и детерминированный ELK
  layout без предметных imports.
* Hamiltonian browser bundle использует `UiRuntime.addHudSurface()` и рисует
  фактическую topology, а не synthetic fixture.
* Structural change сохраняет координаты прежних нод, размещает только новые и
  запускает серверный Libavoid routing; telemetry-only update сохраняет всю
  геометрию.
* Добавление и удаление нод автоматически доказывает отсутствие overlap и
  неизменность coordinates surviving nodes.
* Libavoid обслуживается тем же Hamiltonian listener; второго port/server нет.
* Поздно открытая Window получает initial snapshot до live updates.
* Stale epoch/revision не откатывает сцену.
* Pan, zoom, fit, selection и inspector проверены автоматически и визуально.
* Drag ноды перемещает card и ports в graph coordinates, сохраняет anchor и
  после reload восстанавливает его до Libavoid routing.
* Рамка выделяет несколько нод, group drag сохраняет positions всей группы, а
  обе вертикальные границы изменяют и восстанавливают ширину карточки.
* Renderer строит rounded cubic Bézier corners по Libavoid waypoints и не
  теряет исходные endpoints или obstacle-safe corridor.
* BroadcastChannel envelope не содержит secrets, SDP/ICE и Oracle/Force data.
* Существующие lifecycle, singleton, reconnect и RTC tests остаются зелёными.
* Root typecheck и минимальные релевантные tests проходят.
* Живой Chrome-сценарий доказывает WebGPU render и обновление двух вкладок.

## Проверка текущего первого среза

На 2026-08-08 в текущем рабочем дереве выполнен живой Chrome-сценарий на
обычной странице Hamiltonian:

* MetaFor Engine создал полноэкранный WebGPU HUD, а ELK разложил фактические
  host, listener, Bun process, Service Worker, browser profile, Window и peer;
* две Window одного browser profile имели разные `tabId`, общий `deviceId` и
  показали одинаковую BroadcastChannel revision и одинаковые node/link counts;
* host status одновременно видел обе Window внутри одного connection;
* WebGPU Inspector захватил один настоящий кадр: два render pass, 303 draw call
  и ноль validation errors;
* GPU timestamp-query на этом adapter не дал измеряемое pass timing; это не
  выдаётся за доказательство GPU performance.

После owner-review исходной геометрии выполнен второй, актуальный прогон `v14`:

* все node/header/body/fact/port и inspector slots построены существующими
  `flexRow`/`flexColumn`, а MetaFor Engine измеряет строки через
  `UiSurface.measureText`;
* две вкладки получили одну revision и одинаковый graph; выбор `This Window`
  заполнил inspector и показал существующие lifecycle actions;
* полный Hamiltonian + `@ui/node` suite: 79 tests, 0 failures, 380 assertions;
* свежий WebGPU capture: два render pass, 512 draw call, ноль validation errors;

После решения владельца о Libavoid выполнен третий прогон `v15`:

  listener; новый server или port не создаётся;
* package и полный Hamiltonian suite: 83 tests, 0 failures, 406 assertions;
  root typecheck и browser bundle прошли;
* live Chrome initial показал 7 нод / 9 связей; открытие второй Window дало

* source screenshots, ожидания и checksums находятся в

После решения владельца о ручном placement выполнен прогон `v16`:

* весь edge теперь один connected polyline mesh: прямые части не дробятся,

После решений владельца о hover, viewport, resize и group placement выполнен

единственном listener `4400`.

Первый видимый срез остаётся `IN_PROGRESS`: владелец должен по живой сцене
определить следующий уровень раскрытия и первое действительно разрешённое
управляющее действие. Это намеренно не заменяется заранее придуманным UI.

## Следующие вопросы владельцу

После первого видимого среза по одному уточняются:

* какие уровни topology скрывать или раскрывать;
* какие метрики должны быть постоянно видимы;
* какие lifecycle-действия разрешить из inspector;
* как показывать перенос embodiment между устройствами;
* какие действия требуют подтверждения, lease/fence или отдельного owner gate.
