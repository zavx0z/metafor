# MF-419 — Причинно точный монитор Hamiltonian

## Зачем

Текущая сцена смешивает периодические topology snapshots, локальные состояния
и короткоживущую traffic presentation. Из-за этого нода может появиться позже
собственного рождения, edge — позже первого сообщения, а UI способен показать
`live` для уже закрытого transport. Это не точный монитор жизненного цикла.

## Решение владельца

Построить причинно точный живой монитор. Каждая нода, связь, смена состояния и
движущийся сигнал происходит только из фактически наблюдённого lifecycle-event
настоящего runtime-владельца. Структура сцены уточняется маленькими срезами
вместе с владельцем на одном уже работающем contour.

## Реестр требований владельца

* Назначение интерфейса — точный мониторинг настоящего жизненного цикла, а не
  приблизительная картинка topology. Нельзя заранее рисовать ещё не возникшую
  ноду, держать уже умершую ноду `active`, придумывать ownership/transport edge
  или выдавать исторический snapshot за происходящее сейчас событие.
* Страница всегда открывается по единственному адресу
  `http://127.0.0.1:4400/`. Служебные `?boot=...`, `?token=...` и другие URL для
  отдельных проверочных сценариев не являются пользовательским runtime.
* Самый ранний достоверный кадр текущей navigation содержит server, который
  отдал документ, и новую page realm. Все последующие ноды и edges появляются
  строго в фактическом порядке их рождения, подключения, обмена и завершения.
* Service Worker не изображается активным заранее. Его регистрация,
  активация/controller, MessagePort и WebSocket наблюдаются раздельно у
  настоящих владельцев. Локальное существование page подтверждает Service
  Worker; host/server принимает глобальную регистрацию и управляет connection,
  lease/election, но не подменяет локальное наблюдение Worker.
* Lifecycle BroadcastChannel создаётся и подписывается в самом раннем browser
  entrypoint до загрузки прикладных импортов. Ранние события можно удержать
  только до появления первого subscriber; канал не должен становиться скрытой
  историей и позднее выбрасывать сообщения пачкой.
* Сигнал на edge рисуется максимально близко к реальному send/receive после
  загрузки. Несколько секунд тишины с последующим одновременным появлением
  накопленной партии недопустимы. Причину любой задержки нужно устанавливать
  полным timeline/CPU/GPU/network/lifecycle-профилированием, а не предполагать,
  что виноваты вычисления или раскладка.
* Heartbeat и иные сообщения движутся по фактически существующему transport;
  они не создают фиктивный отдельный `REST heartbeat edge`. На локальном
  contour WebSocket называется `ws`/`websocket`, а не `wss`.
* Наблюдённый transport не исчезает только потому, что перестал работать.
  Пока существуют оба его runtime-endpoint, terminal lifecycle-event переводит
  тот же edge в точное состояние `inactive/closed`; новая transport incarnation
  заменяет этот слот. Полное удаление допустимо только при завершении owner или
  endpoint, когда саму связь больше не к чему привязать.
* В сцене нет выдуманного агрегата «Профиль браузера». Вместо него page
  собственным lifecycle-событием наблюдает реальный текущий user-agent runtime
  (`Chrome` в поднятом контуре). Он становится общей parent-нодой для
  `Эта страница` и фактически присоединившегося `Service Worker`.
  Внутри page остаются `main → RTCPeerConnection страницы` и параллельный
  `Dedicated Worker`; server RTCPeerConnection находится внутри `Peer process`.
  Service Worker получает Chrome parent только после направленного
  `connect-window` с browser identity, а не заранее.
* Dedicated Worker показывается подключённым или завершённым только по
  наблюдённым событиям его реального Worker handle/realm. Исчезновение его
  transport, перерождение incarnation и аварийное завершение не должны
  оставлять ghost-ноду или ложное состояние «отключился».
* Раскладка и transform холста не восстанавливаются из предыдущей загрузки. Новая page
  incarnation начинает с чистой геометрии; добавление или удаление нод заново
  рассчитывает всю актуальную раскладку, а сохранившиеся ноды плавно переходят
  в новые положения.
* Локальный host автоматически наблюдает browser/public/core и `pkg/ui` source.
  После bounded debounce он сначала успешно пересобирает orchestration bundle,
  затем передаёт новую source revision по существующему control path. Каждая
  controlled page принимает одну revision ровно один раз и перезагружается без
  reload-loop; build failure страницу не перезагружает. Первичное получение
  Service Worker controller остаётся отдельным bootstrap reload, если браузер
  явно сообщает `reload required`.
* У layout есть ровно две responsive-ориентации по фактическому размеру окна
  браузера: landscape (`width >= height`) использует горизонтальный flow
  `RIGHT`, portrait (`height > width`) — вертикальный `DOWN`. Выбранная
  ориентация применяется на каждом уровне compound hierarchy, а не только к
  root/bootstrap. Переход окна через portrait/landscape границу запускает один
  полный пересчёт актуальной структуры и плавное перемещение нод; telemetry
  update без смены структуры или ориентации layout не трогает.
* Единственный владелец раскладки — собственный pure TypeScript engine. Его
  serializable fixed-point input содержит measured intrinsic cards, exact
  parameter ports, полный containment tree, semantic edges и viewport. Одно
  синхронное ядро вычисляет все node/compound/gateway/edge coordinates;
  renderer только отображает и анимирует результат. Web Worker допустим позже
  только как adapter вокруг неизменного ядра. ELK, Libavoid, WebGPU layout,
  manual placement, supplied gateways/bends/anchors и product post-routing в
  новом engine отсутствуют.
* Каждый semantic edge остаётся одним domain edge между точными видимыми
  parameter sockets: source всегда `out/EAST`, target всегда `in/WEST`, в том
  числе в `DOWN`. Любая промежуточная compound boundary пересекается только
  `WEST/EAST`; edge не проходит через unrelated child, ancestor или запрещённый
  source/target hierarchy transition. Маршрут orthogonal, сохраняет clearance,
  containment и spacing, упрощается только удалением duplicate/collinear points.
* Bottom-up placement резервирует собственную intrinsic content-band каждого
  compound до его children и routing padding сверх obstacle clearance. Large
  compound empty area является acceptance defect. Для выбранной владельцем
  portrait `compact` policy empty ratio проверяется до soft turn/length objective;
  для landscape сохраняется socket-aligned policy. После hard validity цели
  лексикографичны: total/max turns, total/max Manhattan и detour, bounds/fit,
  compound empty ratio, clearance variance и crossings.
* Результат детерминирован по semantic ID: повторы и stable permutations дают
  битово одинаковую fixed-point geometry. Frozen proof обязан проходить в
  `RIGHT` и `DOWN`; если placement не оставляет legal corridor, router не двигает
  rectangles молча, а возвращает machine-readable `NO_LEGAL_ROUTE` witness.
* Внутреннее содержимое ноды следует Blender/Penpot-грамматике владельца:
  параметры представлены полями и controls только из `@ui/components`, а не
  самодельными прямоугольниками или строками renderer. Строка может иметь
  фактические sockets слева и справа. Общий Flex card-plan измеряет label,
  control и обе socket-позиции; эти intrinsic размеры и port centers передаются
  TypeScript engine, который единолично располагает ноды и маршрутизирует edges.
  Параметр, который данный монитор не имеет права изменять, остаётся тем же
  штатным UI-control, но передаётся ему в `disabled`-состоянии; read-only
  значение нельзя подменять отдельной текстовой имитацией поля.
  * Визуальный stroke обязан физически доходить до центра нарисованного socket.
    Section уже содержит exact endpoint; renderer не добавляет connection stub,
    anchor, gateway, bend или иной post-route.
  * Ни один edge не может визуально подключаться к произвольной границе карточки
    без показанного socket. Для port-bearing связи source/target обязаны сохранять
    фактический `portId`; отсутствие или потеря порта является ошибкой topology
    projection и не маскируется node-boundary fallback в layout или renderer.
  * Socket существует только у конкретного параметра ноды. Поэтому каждый
    source/target любого edge обязан ссылаться на параметр через `portId`, а сам
    socket рисуется в строке этого параметра слева или справа. Node-level endpoint
    в центре или на произвольной границе карточки запрещён типом, validation и
    layout adapter.
  * Сторона socket определяется только направлением параметра: каждый `in`
    расположен на `WEST`/левой стороне, каждый `out` — на `EAST`/правой.
    Исключения по виду transport, endpoint или роли ноды запрещены.
  * TypeScript engine обязан давать плотную органичную раскладку и выбирать
    кратчайшие доступные orthogonal routes с минимальным числом преломлений.
    Пересечение нескольких уровней compound hierarchy само по себе не является
    основанием для лестницы: если при фиксированных фактических портах доступен
    общий прямой коридор через границы owners, route должен использовать его.
    Приёмка сравнивает точное число bends и Manhattan length ответа engine;
    renderer не имеет права улучшать или маскировать неудачный route вручную.
* Во время стартового роста графа авто-вписывание меняет offset/scale
  бесконечного холста так, чтобы все ноды оставались видимыми в `UIDisplay`.
  Первое ручное pan/zoom передаёт transform холста пользователю и прекращает
  дальнейшее автоматическое вписывание до явного повторного включения.
* Отдельный HUD-стик открывает окно управления видом всего графа. В окне есть
  переключатель авто-вписывания и независимая команда «Показать весь граф»;
  разовая команда не обязана возвращать постоянный авто-режим.
* Граф живёт на бесконечном 2D-холсте внутри `UIDisplay` в engine `Space`.
  Пространственный `ViewPoint` управляет положением дисплея в `Space`, а
  `offsetX/offsetY/scale` управляют только холстом внутри дисплея. Инспектор и
  окно управления холстом живут в camera/head-locked `HUD`, появляются поверх
  нод и не влияют ни на layout geometry, ни на canvas transform, ни на
  `ViewPoint`.
* Edge между потомками одного containment owner целиком маршрутизируется внутри
  ближайшего общего owner. Boundary proxy используется только при реальном
  пересечении границы контейнера; internal edge нельзя превращать в self-loop
  внешнего owner и выводить наружу.
* У каждого материализованного transport edge постоянно виден полный базовый
  stroke между его фактическими портами. Движущиеся частицы рисуются поверх
  этой линии и не могут быть её единственным визуальным доказательством.
  Вырожденная либо почти дублирующая точка route должна быть безопасно удалена
  до построения stroke geometry; ошибка одного join не должна молча скрывать
  весь edge.
* Layout каждого parent/compound node резервирует отдельный внутренний routing
  padding для edges сверх obstacle buffer дочерних карточек. Internal route не
  прижимается к border родителя: его точки сохраняют настроенный clearance и от
  child obstacles, и от внутренней границы общего owner.
* Заголовок инспектора — имя выбранной ноды, подзаголовок — предметный тип
  выбранной ноды. Постоянного заголовка «Инспектор Гамильтониана» нет.
* Нажатие на ноду только меняет selection и обновляет содержимое инспектора.
  Закрытый инспектор не открывается автоматически; его открывает только
  отдельный HUD-стик.
* Шапка инспектора использует стандартную высоту общего `HudWindow`: наличие
  подзаголовка не создаёт увеличенный нижний отступ перед divider.
* Один routing spacing выводится из фактического расстояния между центрами
  соседних портов. Этот же размер обязателен между параллельными edges и между
  edge и ближайшей нодой либо compound border на верхнем и вложенном уровнях.
  В текущей parameter-row геометрии это `24 px` высоты поля + `4 px` gap =
  `NODE_SYSTEM_PORT_PITCH=28 px`; это актуальное значение заменяет исторический
  `24 px` срез старых отдельных port rows/Libavoid.
  Его нельзя повторно складывать с самим собой как общий пустой отступ:
  parent body → первый child использует один pitch, а corridor с одним edge
  между двумя children — два pitch, по одному с каждой стороны edge.
* Все структурные и визуальные изменения проверяются в одном корневом live
  contour и показываются владельцу для совместной графической настройки. До
  визуального решения владельца задача и соответствующий срез не закрываются.
* Число materialized nodes/edges не является доказательством видимости. При
  любом auto-fit каждая нода обязана иметь различимую экранную рамку, каждый
  socket — различимый marker, а каждый edge — постоянный контрастный base
  stroke. Текст, поля и их внутренние отступы масштабируются вместе строго
  пропорционально: минимальный экранный font size без полного reflow карточки
  запрещён, потому что ломает поля и обрезает содержимое. Renderer-only minima
  остаются только у topology strokes: node border `1.25 px`, socket `5.5 px` и
  edge `1.8 px`. Они не передаются обратно в ELK, layout bounds или canvas
  transform.

## Утверждённый закон

* При начале page-кода гарантированно существуют две ноды: server, отдавший
  документ, и текущая page realm с новой `pageIncarnation`.
* Следующее page-owned observation рождает parent текущего user-agent runtime:
  в локальном контуре это `Chrome`. Page входит в него сразу после observation,
  а Service Worker — только после фактической browser identity в
  `connect-window`. Это runtime owner, а не восстановленный «профиль».
* Service Worker, WebSocket, MessagePort, Dedicated Worker, Bun process,
  RTCPeerConnection и DataChannel появляются только после наблюдения их
  собственного lifecycle.
* Service Worker владеет локальной регистрацией Window. Host принимает её в
  общую topology и владеет connection, election, lease и fencing, но не
  подтверждает существование локальной page.
* Edge соответствует реальному transport и имеет собственную incarnation.
  Heartbeat является сообщением по WebSocket или MessagePort, а не отдельным
  edge. На локальном HTTP contour это `ws:`, а `wss:` появляется только при TLS.
  Наблюдённое закрытие сохраняется как состояние transport edge, а не стирается
  из текущего monitor view, пока его endpoints продолжают существовать.
* Одно сообщение имеет одну identity. Наблюдения send и receive связываются с
  ней и не создают два независимых presentation-события.
* Gap sequence показывается явно. Snapshot используется только на causal
  frontier для bootstrap или восстановления, но не изображает lifecycle.
* В каждом browser realm BroadcastChannel создаётся и подписывается первым
  dependency до прикладных модулей.

## Утверждённый визуально-пространственный контракт

* Граф нод является содержимым `UIDisplay` в engine `Space`, как штатный
  display-space интерфейс MetaFor. Внутри дисплея находится бесконечный
  2D-холст графа; он не является отдельной камерой или HUD.
* Engine `ViewPoint` управляет наблюдением самого `UIDisplay` в `Space`.
  Pan/zoom графа меняет только `canvasTransform = {x, y, scale}` внутри
  дисплея и не меняет pose пространственного `ViewPoint`.
* Инспектор выбранной ноды и управление видом принадлежат отдельному
  camera/head-locked `HUD`, рисуются поверх display и нод и не участвуют ни в
  ELK/layout, ни в `canvasTransform`, ни в pose `ViewPoint`.
* Открытие, закрытие, перемещение и resize любого HUD-окна не сдвигают ноды и
  не меняют холст или пространственный ViewPoint. Это проверяется сравнением
  полного `canvasTransform` и ViewPoint pose до и после операций с окнами.
* Наблюдённый user-agent runtime отображается parent-контейнером `Chrome` в
  текущем контуре. В нём соседствуют owner-контейнер «Эта страница» и реальная
  нода `Service Worker` со своим `ServiceWorkerGlobalScope`. В page находится
  `main` текущего Window realm; browser `RTCPeerConnection` вложен в `main`, а
  созданный этой page `Dedicated Worker` вложен непосредственно в «Эта
  страница». Server RTC остаётся внутри `Peer process`.
* Такая вложенность выражает фактическое runtime ownership и не создаёт
  фиктивные transport edges. Реальный `Worker messaging` соединяет `main` и
  `Dedicated Worker`; Oracle/Force RTCDataChannel соединяют две реальные RTC
  ноды.
* Edge между нодами внутри одного containment owner остаётся внутри ближайшего
  общего owner. Только edge, реально пересекающий границу owner, получает
  boundary proxy и выходит наружу.
* Порядок отрисовки учитывает containment и фактическое положение endpoints:
  фон каждого owner рисуется раньше участков edge, проходящих внутри него, а
  дочерние карточки — поверх этих участков. Родительская карточка не должна
  скрывать `Worker messaging` или внутренний путь RTCDataChannel от socket
  дочернего RTC к границе owner.
* Parent layout задаёт явный внутренний routing padding. Геометрия контейнера
  обязана оставить ELK corridor между child obstacle и border owner;
  нахождение edge формально внутри parent при расстоянии в несколько пикселей
  от рамки не считается правильной раскладкой.
* При неизменных topology и размерах display раскладка и `canvasTransform` не
  меняются сами по себе. Периодический сдвиг графа с возвратом считается
  дефектом: нужно отличить повторный ELK/layout transition от лишнего auto-fit
  и устранить источник, а не маскировать движение задержкой или анимацией.
* Реальная замена incarnation в том же визуальном runtime-слоте не скрывается:
  новые identity ноды и transport отображаются сразу. Но если новый ELK/result
  сохранил те же frames и bounds, такая замена не запускает layout transition и
  auto-fit. В частности, штатное завершение Chrome `ServiceWorkerGlobalScope`
  и пробуждение нового воплощения не должны каждые ~30 секунд сдвигать весь
  граф с возвратом.
* Landscape UIDisplay строит всю compound hierarchy слева направо (`RIGHT`),
  portrait — сверху вниз (`DOWN`). `Chrome`, page, `main`, server и `Peer
  process` получают один и тот же выбранный flow для расположения своих
  непосредственных children; причинное containment при этом не меняется.
  Resize, меняющий только размер внутри той же ориентации, сохраняет layout и
  пользовательский transform. Resize через границу ориентации пересчитывает
  layout и анимирует переход, а auto-fit применяется только по действующей
  политике владельца холста.
* На каждой новой загрузке авто-вписывание холста показывает растущий стартовый
  граф, пока пользователь не начал pan/zoom холста. Первое ручное движение
  немедленно выключает дальнейшее авто-вписывание для этой page incarnation.
  После этого resize `UIDisplay` также сохраняет полный пользовательский
  `canvasTransform`; повторный fit при resize разрешён только пока явно включён
  авто-режим.
* Отдельный HUD-стик открывает окно «Вид холста». В нём есть явный
  переключатель авто-вписывания и отдельное разовое действие «Показать весь
  граф». Разовый fit не обязан включать авто-режим; явное включение
  авто-вписывания снова разрешает fit при последующих структурных изменениях.
* Заголовок инспектора не содержит постоянную надпись «Инспектор
  Гамильтониана»: он показывает `title` выбранной ноды, а подзаголовок — её
  предметный `kind`. При отсутствии выбора используется нейтральное состояние.
* Selection ноды не меняет open-state инспектора. Стандартный title bar не
  увеличивается из-за subtitle, а divider следует общему вертикальному ритму
  HUD-окон.
* Фактический port pitch является единственной единицей routing geometry:
  edge↔edge и edge↔node/compound-border используют одинаковое расстояние на
  root и contained routes.
* Compound layout не резервирует невидимые lanes без причины. Один pitch
  отделяет body parent от первого child; если между соседними children проходит
  один edge, их frames разделены двумя pitch, а не тремя.

## Подтверждённая исходная точка

* Hamiltonian работает на одном listener `127.0.0.1:4400`.
* Live-профиль показал несовместимые состояния: page отображала connected/live,
  когда host journal уже содержал закрытие соответствующего WebSocket и другой набор
  фактически открытых connections.
* Нода Service Worker сейчас идентифицирована через `connectionId`, локальная
  page — через сохраняющийся `tabId`, а MessagePort, IPC и DataChannel edges не
  различают собственные поколения.
* Traffic cursor принимает скачок sequence, bounded backlog молча удаляет
  старые observations, а большая часть точек фиксирует send без связанного
  receive.
* Коммит `378624c` удерживает presentation до появления route, но не исправляет
  потерю причинного порядка topology.

## Порядок совместной работы

Следующий layout-срез начинается в новой короткой сессии и не меняет продукт
до offline proof. Точный live ELK graph замораживается как fixture; реальный
pipeline Layered, scopes и dependencies восстанавливаются из metadata
установленного `elkjs` и официальной документации. Затем отдельный минимальный
Node/Bun harness выполняет dependency-aware многопараметрический поиск и строит
Pareto-набор по attachment, containment, overlaps, spacing, visible turns,
Manhattan length, detour, bounds и fit scale. Поиск не запускает Hamiltonian,
WebGPU, browser, Service Worker или WebRTC; полный runtime и CDP используются
только для 3–5 финалистов. Отсутствие отдельного option не считается
доказательством невозможности совместной конфигурации фаз.

Бюджет: одна гипотеза — 20 минут, 10 внешних tool calls и два patches; одна
сессия — 90 минут или три итерации. Две неудачные гипотезы, смена hard law либо
одновременная необходимость менять UI geometry, ELK и renderer требуют STOP и
нового handoff. Configuration search ограничен 10 000 внутренних layouts или
восемью минутами CPU в одном процессе; первый живой CDP-кадр должен появиться
не позже восьмой минуты live-фазы.

1. Материализовать только гарантированные server и текущую page из navigation
   bootstrap; открыть monitor BC первым dependency всех browser realm.
1. Перевести Service Worker, controller bootstrap, MessagePort и WebSocket на
   lifecycle events их владельцев.
1. Добавить incarnation-aware OS process, Dedicated Worker, peer и DataChannel.
1. Связать send/receive общей message identity, gap detection и bounded
   retained snapshot от causal frontier без replay исторических сообщений.
1. Каждый срез сразу показать владельцу в том же browser contour и только
   после визуального решения переносить общее правило в `@ui/node`.

## Границы

* Не выводить runtime lifecycle из текущего внешнего вида или следующего
  snapshot.
* Не выдумывать не наблюдённые сущности, состояния, edges и сообщения.
* Не смешивать пересборку нод с `MF-411`, production placement и переносом
  доменов MetaFor.
* Сохранять один существующий Hamiltonian runtime и точное browser targeting.
* Не добавлять WebGPU Inspector в исходники или browser bundle.
* Frustum-aware деактивация monitor display, остановка BC и освобождение GPU
  buffers после готовой пространственной модели принадлежат отдельной
  зависимой задаче [`MF-421`](MF-421.md), а не текущему структурному срезу.
* Сохранять routing, selection и render-on-demand. Ручной canvas transform и
  geometry живут только в текущей page incarnation. Новый load начинает с чистого ELK;
  добавление или удаление ноды полностью пересчитывает раскладку, surviving
  nodes плавно переходят к новым позициям. Пока авто-вписывание включено,
  canvas transform показывает весь переход; после первого ручного pan/zoom
  topology продолжает двигать только ноды, но не холст. Telemetry-only update
  geometry, canvas transform и ViewPoint не меняет.

## Критерии готовности

* Холодная и тёплая загрузка начинают сцену с точных server и текущей page.
* Каждая runtime-сущность и transport появляются, меняются и завершаются только
  после owner lifecycle-event с точной incarnation.
* WebSocket reconnect, page reload, Worker/process rebirth и peer reconnect не
  смешивают прежнее и новое воплощение.
* Одно сообщение показывается один раз; send/receive связаны; gap не скрывается;
  стартовые сообщения не выходят запоздалой пачкой.
* Общая и предметная части структуры разделены между `@ui/node` и Hamiltonian,
  а каждый визуальный срез утверждён владельцем.
* Live object tree подтверждает `Space → UIDisplay → graph` и отдельный
  `HUD → inspector/canvas controls`; HUD-операции сохраняют canvas transform и
  pose ViewPoint, а ручной pan/zoom холста выключает auto-fit до явного
  включения.
* Итоговый кадр показывает `Эта страница → main → browser RTC` и параллельный
  `Эта страница → Dedicated Worker`, с реальными internal transport edges и
  без ложного ownership edge; `Worker messaging` не покидает общий page owner.
* Релевантные тесты, typecheck, browser build и живая визуальная проверка
  проходят на итоговом срезе.
* В landscape live-кадре граф использует ширину UIDisplay и базовый stroke
  MessagePort между page и Service Worker виден целиком без необходимости
  ждать движущуюся частицу; portrait live-кадр подтверждает вертикальный
  вариант того же причинного графа.

## Completion-аудит актуального среза

* **Подтверждено — первый причинный кадр.**
  `lifecycle-projection.spec.ts` начинает только с server и текущей page,
  `bootstrap-layout.spec.ts` проверяет `2/0`, а внешний clean-load timeline
  фактически наблюдал этот кадр на `353,3` мс до полного `10/9`.
* **Подтверждено — только owner lifecycle.**
  Проекция материализует Service Worker и точную WebSocket incarnation только
  из owner events; terminal transport остаётся inactive до end endpoint или
  замены incarnation. Host integration отдельно проверяет, что `closed WS`
  удаляется лишь после page-observation завершения старого Worker и отклоняет
  поддельный successor.
* **Подтверждено — incarnation, sequence и causal frontier.**
  `core/lifecycle.spec.ts` проверяет привязку event к owner incarnation,
  монотонный sequence, gap, retained structural frontier и продолжение live
  потока строго после него. Reconnect/rebirth integration tests покрывают
  новую физическую incarnation без смешения с прежней authority/session.
* **Подтверждено — одно сообщение и отсутствие поздней партии.**
  Send/receive одного message identity дают одну presentation; late subscriber
  не получает уже доставленную traffic history. В актуальном clean-load первое
  observation было на `331,5` мс, route на `620,0` мс, presentation на
  `620,1` мс; route→signal занял `0,1` мс, а не несколько секунд.
* **Подтверждено — пространственная и предметная структура.**
  Live evidence сообщает `Space>UIDisplay>graph;HUD>inspector,canvas-controls`;
  workspace/spatial tests проверяют независимость HUD. Точный canvas
  `2026-08-09-chrome-parent-v22-routed-canvas.png` показывает общий
  `Chrome → {Эта страница, Service Worker}`, внутри page — `main → browser
  RTC` и параллельный Dedicated Worker, а реальные internal/external edges
  выходят из фактических портов без ownership edge.
* **Подтверждено — техническая целостность.**
  Актуальный объединённый срез прошёл `188` tests и `3769` проверок без
  падений; root и strict core typecheck, обе browser build и
  `git diff --check` проходят. Чистая вкладка на `/` имеет `11/9`, нулевые
  очереди, no gap, complete layout, verified spatial runtime и пустую console.
* **Ожидает решения владельца — финальное визуальное принятие.**
  Последний canvas v22 снят и показан после добавления реального Chrome parent
  и исправления compound routing, но владелец ещё не подтвердил именно этот
  итоговый срез. До такого подтверждения MF-419 остаётся `IN_PROGRESS`, commit
  и закрывающая процедура не выполняются.

## Подтверждённый промежуточный срез

* Navigation bootstrap сразу создаёт только server и текущую page realm.
* Service Worker, controller, MessagePort, WebSocket и Dedicated Worker
  материализуются из lifecycle-журнала своих browser realm.
* Два дочерних Bun process сами сообщают через IPC о рождении, активном
  состоянии, сообщениях и штатном завершении; host проверяет, удерживает и
  передаёт исходные envelopes без смены event identity. При аварийной смерти
  child уже ничего сообщить не может: host как владелец OS process handle
  наблюдает exit, закрывает точную IPC incarnation, завершает process entity и
  запускает новое воплощение.
* Новый server epoch немедленно сбрасывает прежний reconnect backoff. События
  процессов прошлого host не создают ноды, edges или отложенные частицы.
* Тёплая загрузка в живом Chrome построила `6 нод · 6 связей` за 1,06 секунды
  от navigation: два IPC, WebSocket, controller, MessagePort и Worker
  messaging; `pending=0`, sequence gap отсутствует. Следующая 1,2-секундная
  проба приняла шесть новых сообщений без отложенной партии.
* После добавления отдельного WebRTC peer process тёплая загрузка построила
  `7 нод · 7 связей` за 1,01 секунды с `pending=0` и без gap. Автоматическая
  и живая проверки подтвердили cold rebirth peer process после `SIGKILL`:
  прежний PID исчезает, новая incarnation появляется без ghost-ноды.
* Browser и server RTCPeerConnection, два RTCDataChannel и их сообщения
  материализуются из событий настоящих владельцев. Oracle/Force send и receive
  несут одну message identity и дают одну движущуюся частицу.
* Полное профилирование нашло прежнюю пятисекундную паузу не в ELK или WebGPU:
  Werift после уже успешной локальной ICE-пары ждал таймаут своего неявного
  Google STUN. Loopback server переведён в ICE-lite; прямой adapter test теперь
  соединяет обе стороны и обменивается Oracle/Force за 0,29 секунды вместо
  примерно 5,3 секунды.
* После исправления чистая живая загрузка показала navigation bootstrap
  `2 ноды · 0 связей` за 0,49 секунды. Сообщения начали рисоваться на первом
  кадре routed layout за 0,92 секунды, а плавный переход всей схемы
  `9 нод · 9 связей` завершился за 1,18 секунды; `pending=0`, gap отсутствует.
  CPU-профиль не обнаружил вычислительной паузы: renderer и WebGPU выполняют
  короткие работы, а остальное время main thread свободен.
* Фальшивая агрегирующая нода «Профиль браузера» удалена: у неё не было
  собственного runtime owner или lifecycle. Задача остаётся `IN_PROGRESS` до
  совместного утверждения предметной структуры сцены владельцем.
* Control WebSocket и все три IPC-границы теперь фиксируют обе стороны одного
  сообщения с общей identity и точной transport incarnation. Старый отдельный
  traffic-сигнал удалён: одно физическое сообщение больше не порождает вторую
  безымянную частицу. Локальный transport и его сообщения называются
  `websocket`, а не `wss`. Завершающий аудит удалил также оставшийся
  `edge-traffic` parser/relay, browser endpoint и отдельный ранний BC: сигнал
  теперь не может попасть в сцену иначе, чем через lifecycle `message`.
* Перед первым live hello host передаёт retained snapshot только активных
  entity/transport и causal frontier всех owner-source. Service Worker делает
  такой же snapshot своей realm. Исторические сообщения до frontier не
  replay-ятся. Чистая проверка больше не получает sequence 8 раньше 1–7, а
  тёплая загрузка продолжила Service Worker с sequence 289, server с 72 и peer
  с 53 без ложного gap. После
  окончательной раскладки очередь удаляет сообщения закрытых incarnation,
  поэтому она не может позже выйти ложной пачкой; на живой загрузке
  `trafficPending=0` уже через 2,4 секунды и остаётся нулём.
* Retained snapshot теперь является авторитетным текущим состоянием на своём
  frontier: более новый snapshot удаляет пропущенные при разрыве закрытые
  entity/transport, но старый retained envelope не откатывает уже принятое
  live-состояние. Частично достигнутый frontier оставляет непокрытую часть gap,
  а превышение capacity завершается явной ошибкой вместо скрытого обрезания.
* Loopback navigation больше не проходит через временный `/?token=...`:
  первый запрос `http://127.0.0.1:4400/` сразу получает HTML с локальной join
  capability. Чистый live-профиль показал `2 ноды · 0 связей` за 0,56 секунды,
  первые routed edges и сигналы за 0,77 секунды, полные
  `9 нод · 9 связей` за 1,04 секунды; URL всё время оставался корневым,
  `gap=0`, `trafficPending=0`.
* Стартовые traffic observations больше не получают общее позднее время при
  materialization edge. Каждый сигнал сохраняет исходный `at`, сразу появляется
  в соответствующей времени точке маршрута, а уже истёкший сигнал не запускается
  повторно. Повторная тёплая загрузка на высоком sequence закончилась с
  `9/9`, нулевыми очередями и без browser console/runtime diagnostics.
* Автоматическое завершение браузером Service Worker проверено на живом
  contour. Старая нода, MessagePort и WebSocket завершаются, новая incarnation
  открывает собственные transport; граф возвращается к `9 нод · 9 связей`,
  `gap=0`, `pending=0`. Два heartbeat, отправленные непосредственно перед
  смертью старого Worker, остались `sent` без выдуманного `received`, то есть
  реальная потеря не скрыта.
* Ручной rebirth Dedicated Worker проверен по полному журналу: `stop`,
  `stopped`, `birth` и `ready` имеют по одной паре `sent/received` с общей
  identity. Completion-проверка выявила, что немедленный `terminate()` иногда
  обрывал финальный BroadcastChannel старой realm: сцена оставалась `10/10` с
  gap `1–1`. Теперь Worker сначала передаёт направленный retained snapshot с
  frontier, а page как владелец Worker handle после `terminate()` сама фиксирует
  `worker-message closed → entity ended`. Три последовательных live rebirth
  сменили incarnation при постоянных `9/9`, `gap=0` и обеих очередях `0`.
  Полный Hamiltonian прогон итогового среза: 111 тестов, 3300 проверок, без падений; root typecheck и
  `git diff --check` проходят. На этом промежуточном срезе визуальная структура
  ещё ожидала совместного решения владельца.
* Аварийный `SIGKILL` готового Bun `main-probe` проверен и автоматическим тестом,
  и на живой странице. Host наблюдает exit `137`, фиксирует `IPC closed`, затем
  причинно связанный `entity ended`; новое incarnation рождается через 70 мс и
  становится active через 82 мс. Старые entity/transport отсутствуют в retained
  snapshot, server placement обновляет fencing token. Живая сцена не мигнула:
  замена пришла до следующего структурного commit, поэтому состав оставался
  `9/9`, переход завершился примерно через 550 мс, `gap=0`, обе очереди вернулись
  к нулю, browser console осталась пустой.
* Финальный single-channel аудит проверен на полностью перезапущенном contour:
  активный Service Worker исполняет `sw.js?mf419-v16`; page, Service Worker и
  Dedicated Worker держат ровно по одному BroadcastChannel с именем
  `metafor.hamiltonian.lifecycle.v1`. Удалённый `/core/traffic.js` отвечает 404,
  старый `edge-traffic` frame закрывается policy error, а lifecycle-проекция не
  рисует message без активного transport с точно совпадающими концами. Живая
  root-страница построила сначала `2/0`, затем `9/9`; обе очереди нулевые,
  layout transition завершён, console пуста.
* Completion-аудит обнаружил, что ранний BC и typed lifecycle layer продолжали
  хранить уже доставленные сообщения (`512` в живой page), поэтому гипотетический
  поздний subscriber получил бы старую traffic-пачку. Оба буфера переведены в
  одноразовую startup-очередь: она существует только без subscriber, очищается
  при первой подписке и не становится историей. На живом `v15` оба backlog
  оставались `0` весь 47-секундный профиль, включая реальное завершение и новую
  incarnation Service Worker; граф сохранил `9/9`, `gap=0`, обе presentation-
  очереди `0`, transition `complete`. Recent identity dedup ограничен `1024`.
* Следующий completion-аудит обнаружил ещё одну историческую память: page
  сохраняла retained snapshot каждой уже завершённой Service Worker incarnation.
  Теперь событие `entity ended` сразу удаляет snapshot этого owner. В 80-секундном
  живом профиле `v16` последовательно наблюдались четыре incarnation Service
  Worker, но в page всё время оставались ровно два snapshot: server и один
  текущий Worker. После каждой замены граф сохранял `9/9`, `gap=0`, оба backlog
  и обе presentation-очереди `0`, transition `complete`; console осталась пустой.
* Live traffic-аудит при выведенном вперёд Chrome принял 41 сообщение за
  6 секунд без pending-очереди. При этом обнаружено, что lifecycle-проекция
  навсегда сохраняла identity каждого уже показанного сообщения. Теперь это
  только bounded recent dedup на 4096 identity: он связывает ближайшие
  `sent/received`, но не превращается в traffic history. После полного
  перезапуска contour root-страница снова построила `2/0 → 9/9` примерно за
  секунду; в первом интервале live-пробы счётчик сразу вырос `213 → 229`,
  `trafficPending=0`.
* Completion-аудит cursor выявил, что после визуального удаления старой
  incarnation её sequence frontier, terminal identity и structural event всё
  ещё могли храниться до конца жизни page. Теперь завершённый source удаляется
  из active frontier, его structural records удаляются, а защита от позднего
  события остаётся только в bounded recent tombstone (`512` source, по `2048`
  entity и transport). В шести последовательных live rebirth активных source
  оставалось ровно `6`, structural records — `15`; recent retired вырос
  `1 → 6`, terminal identity `2 → 12`, как ограниченная защита. Во всех шести
  срезах graph был `9/9`, `gap=0`, обе очереди `0`.

## Deferred joint ELK routing capability boundary 2026-08-09

* `CompoundGraphPostprocessor` не рассматривается как место исправления: он
  остаётся штатным переводом local sections в reference coordinate space и их

  после этой границы запрещены owner law.
* Exact installed elkjs 0.11.1 schedule даёт допустимое окно по времени, но не
  готовый router input: synchronized hierarchical phases завершают P5, затем

  после всего recursive layout вызывается compound restore. Следовательно
  original cross-hierarchy route мог бы быть рассчитан один раз после resize и
