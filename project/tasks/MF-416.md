# MF-416 — Живые сообщения на рёбрах Hamiltonian

## Зачем

Статическая topology показывает наличие каналов, но не показывает их живую
работу. Владелец требует видеть каждое фактически прошедшее сообщение прямо на
его edge: одно сообщение — одна движущаяся частица с градиентным хвостом.

## Связь с дорожной картой

Задача продолжает принятую интерактивную страницу оркестрации Hamiltonian и не
меняет transport, authority или причинные протоколы MetaFor.

## Решения владельца

* Событие должно возникать максимально рано, а не выводиться из следующего
  topology snapshot или изменения счётчика.
* В browser realm отдельный BroadcastChannel инициализируется раньше
  прикладного тела каждого Window, Service Worker и Dedicated Worker.
* Одно сообщение отображается одной частицей с градиентным хвостом на edge.

## Действующий закон среза

Browser boundary публикует минимальный versioned traffic envelope сразу после
успешного send либо при начале обработки принятого сообщения. Bun IPC не имеет
доступа к browser-origin BroadcastChannel: host передаёт его observation через
существующий control path, а Service Worker немедленно публикует его в browser
channel. Observation-envelope не трассирует сам себя.

Traffic envelope содержит только event identity, producer identity, sequence,
edge ID, направление, время и безопасный message class. Содержимое сообщения,
секреты, signaling, RPC params/result и Particle payload запрещены.

## Границы

* Не изменять wire payload Oracle/Force и не вводить новый causal transport.
* Не реконструировать сообщения из агрегированных counters.
* Не анимировать ownership-рёбра, по которым сообщения не проходят.
* Не запускать постоянный render loop в пустой сцене.
* Не проектировать историю, replay или долговременное хранение traffic events.

## Критерии готовности

* Все показанные message channels имеют устойчивый edge ID и точку раннего
  наблюдения: control WSS, MessagePort, UI BroadcastChannel, Bun IPC, peer
  supervision и прямые Oracle/Force lanes.
* Дубликат либо невалидный traffic envelope не создаёт вторую частицу.
* Одно принятое событие создаёт ровно одну частицу; направление соответствует
  send/receive, а градиентный хвост следует фактическому Bézier route.
* Несколько одновременных сообщений остаются отдельными частицами.
* Render-on-demand останавливается после исчезновения последней частицы.
* Unit/integration tests, typecheck и browser bundle проходят.
* В точной пользовательской CDP-вкладке живые WSS, MessagePort,
  BroadcastChannel и Oracle/Force сообщения визуально проходят по своим edges.
