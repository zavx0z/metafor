# Редактирование правил

Правила редактирования и обновления правил проекта после обнаружения ошибок.

---

## ⚠️ Важно: Когда обновлять правило

**Обновляй правило если:**

* ✅ Пользователь указал на ошибку после применения правила
* ✅ Нашли частую ошибку (добавить в антипаттерны)
* ✅ Изменился процесс/инструмент
* ✅ Добавилась новая best practice

**Не обновляй если:**

* ❌ Единичный случай (не общая проблема)
* ❌ Личное предпочтение (не best practice)
* ❌ Не проверил с пользователем

---

## 📝 Процесс обновления

### Шаг 0. Анализ причины ошибки

**Перед исправлением — задай вопрос:**

> «Почему я не применил правило? Что в правиле не так, что это повторилось?»

**Типы ошибок:**

| Тип                             | Вопрос                                | Решение                             |
| ------------------------------- | ------------------------------------- | ----------------------------------- |
| Механическое действие в правиле | «Это описывает "как" вместо "что"?»   | Перенести механику в инструмент     |
| Нет процесса применения         | «Как понять когда применять правило?» | Добавить чек-лист триггеров         |
| Противоречие между правилами    | «Какое правило конфликтует?»          | Устранить противоречие              |
| Слишком абстрактно              | «Что конкретно делать?»               | Добавить пример без привязки к коду |

**Пример анализа:**

``` text
Ситуация: Правило описывает механическое действие вместо принципа.

Анализ:
1. Тип ошибки: Механическое действие в правиле
2. Вопрос: «Это описывает "как" вместо "что"?»
3. Причина:
   • Правило описывает процесс вместо принципа
   • Нет разделения между «что делать» и «как делать»
   • Механика должна быть в инструменте, не в правиле
4. Решение:
   • Переформулировать правило как принцип
   • Механику перенести в инструмент автоматизации
   • Добавить чек-лист «что не включать в правило»

Результат: правило переформулировано как универсальный принцип.
```

### Шаг 1. Исправь ошибку в коде

Сначала реши задачу пользователя, исправь ошибку в коде/файле.

``` text
Пользователь: правило module.md не описывает как создавать store.ts

AI: Исправил код, добавил store.ts по аналогии с другими модулями.
```

### Шаг 2. Предложи кратко обновить правило

**Формат краткого предложения:**

```markdown
📝 Предлагаю обновить правило <file.md>:

Кратко:
• <что добавить/изменить #1>
• <что добавить/изменить #2>

Согласны? Покажу подробно что изменю.
```

**Пример:**

```markdown
📝 Предлагаю обновить правило module.md:

Кратко:
• Добавить раздел "3.1. Store-файлы" с описанием структуры store.t.ts + store.ts
• Добавить примеры импорта типов из store.t.ts

Согласны? Покажу подробно что добавлю.
```

### Шаг 3. Покажи подробно (после согласия)

**Формат подробного описания:**

```markdown
Подробно что добавлю в <file.md>:

## <номер>. <название раздела>

<содержимое раздела>

---

Внеси изменения?
```

**Пример:**

```markdown
Подробно что добавлю в module.md:

## 3.1. Store-файлы

Для store создавай пару файлов:

```text
{name}.t.ts  ← интерфейс {Name}Store
{name}.ts    ← инстанс store: {Name}Store
```

**Пример:**

```typescript
// store.t.ts
export interface ModuleStore {
  data: Uint32Array
  offset: number
}

// store.ts
import type { ModuleStore } from './store.t.ts'

export const store: ModuleStore = {
  data: null as unknown as Uint32Array,
  offset: 0,
}
```

---

Внеси изменения?

``` text
AI: Обновил module.md, добавил раздел 3.1 "Store-файлы".
```

### Шаг 4. Обнови правило (после подтверждения)

После подтверждения пользователя обнови правило:

``` text
AI: Обновил module.md, добавил раздел 3.1 "Store-файлы".
```

## 📋 Правила обновления

| Правило            | Описание                                        |
| ------------------ | ----------------------------------------------- |
| **Сначала кратко** | 1-3 пункта по сути изменений                    |
| **Потом подробно** | Только после согласия пользователя              |
| **Конкретика**     | Указывай номер раздела и название               |
| **Минимум текста** | Без воды, только содержимое                     |
| **Точность**       | Проверяй что раздел не дублирует существующий   |
| **Ссылки**         | Добавляй ссылки на связанные правила если нужно |

## 🔁 Триггеры для перечитывания правил

**Перед действием — перечитай правило если:**

| Триггер                                                    | Правило для перечитывания                            |
| ---------------------------------------------------------- | ---------------------------------------------------- |
| Редактируешь Markdown-файл                                 | `.qwen/rules/markdown.md`                            |
| Создаёшь новый модуль                                      | `.qwen/rules/module.md`                              |
| Работаешь с пакетами `@boundary/*`, `@metafor/*`           | `.qwen/rules/packages.md`                            |
| Документируешь код (TSDoc)                                 | `.qwen/rules/tsdoc.md`                               |
| Пишешь чистые функции                                      | `.qwen/rules/fp.md`                                  |
| Работаешь с графами                                        | `.qwen/rules/graph.md`                               |
| Создаёшь новый skill                                       | `.qwen/rules/skills.md`                              |
| Создаёшь новое правило                                     | `.qwen/rules/rules.md`                               |
| **Пользователь указал на ошибку после применения правила** | **Перечитай правило заново, найди упущенную деталь** |

**Пример:**

``` text
Ситуация: Добавил язык в блок кода, но без пробела (```text вместо ``` text)

Действие:

1. Пользователь указал на ошибку
2. Перечитал markdown.md раздел 5.1
3. Нашёл требование: «Между ``` и языком должен быть пробел»
4. Исправил формат: \`\`\` text
```
