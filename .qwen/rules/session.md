# Работа с историей сессии

Правила поиска, анализа и использования сообщений из истории чата.

---

## ⚠️ Важно: Когда обращаться к истории

**Обращайся к истории если:**

* ✅ Пользователь просит вспомнить что-то из сессии ("вспомни о...", "мы обсуждали...")
* ✅ Нужно восстановить контекст после долгого перерыва
* ✅ Пользователь ссылается на предыдущее сообщение ("как я сказал выше...")
* ✅ Нужно подвести итоги по теме

**Не обращайся если:**

* ❌ Задача самодостаточна (не требует контекста)
* ❌ Пользователь начал новую тему явно
* ❌ История слишком большая (риск переполнения контекста)

---

## 🔍 Поиск по истории

### Формат запросов от пользователя

| Фраза                      | Что искать                            |
| -------------------------- | ------------------------------------- |
| **"вспомни о ..."**        | Все сообщения по теме/ключевым словам |
| **"мы обсуждали ..."**     | Диалог по конкретной теме             |
| **"как я сказал выше"**    | Предыдущие сообщения пользователя     |
| **"что мы решили по ..."** | Итоги обсуждения, решения             |
| **"покажи историю ..."**   | Хронологию сообщений по теме          |

### Процесс поиска

```text
1. Определи ключевые слова из запроса
2. Просканируй историю сессии
3. Найди все релевантные сообщения
4. Определи хронологию обсуждения
5. Выяви ключевые решения/изменения
6. Подготовь структурированную сводку
```

## 📝 Формат ответа на "вспомни о ..."

### Структура сводки

```markdown
## Тема: <название темы>

### 📋 Оригинальное предложение

<цитата или пересказ первого сообщения по теме>

### 🔍 Анализ (на момент обсуждения)

<контекст, проблема, архитектура на тот момент>

### 🏗️ Изменения после обсуждения

<что было изменено, создано, обновлено>

### ✅ Текущее состояние

<как выглядит сейчас, итоговое решение>

### 📊 Итог

<таблица или список ключевых решений>

### 🎯 Вывод

<краткий вывод по теме>
```

### Пример сводки

```markdown
## Тема: Создание `unlock` метода в @{domain}

### 📋 Оригинальное предложение

Вы обнаружили в `@{semantics}/{module}.ts` код для снятия блокировки с бран:

```typescript
const state = storeGet()
const blockPtr = state.braneBlockPtrs[index]!
return { offset: blockPtr + 2, value1: 0 }
```

**Ваше предложение:**
> Создать метод `unlock` в `@{domain}/index.ts` и удалить импорт из `@{semantics}/`

### 🔍 Анализ архитектуры (на тот момент)

**Проблема:**

| Данные             | Где хранились               | Кто использовал                                     |
| ------------------ | --------------------------- | --------------------------------------------------- |
| `braneBlockPtrs`   | `@{domain}/{package}/store` | @{domain}/{package}, @{semantics}                   |
| `heap`             | `@{domain}/{package}/store` | @{domain}/{package}, @{domain}/fields, @{semantics} |

**Вывод:** @{semantics} вынужден импортировать из @{domain}/{package} напрямую.

### 🏗️ Изменения после обсуждения

#### 1. Создано `@{domain}/store` (общее хранилище)

```typescript
export const store = {
  heap: Uint32Array,          // ← общее
  braneBlockPtrs: number[],   // ← общее
}
```

#### 2. Обновлён `@{semantics}/{module}.ts`

**Было:**

```typescript
import { storeGet } from "@{domain}/{package}"
```

**Стало:**

```typescript
import { storeGet } from "@{domain}/store"
```

### ✅ Текущее состояние

**Импорты в @{semantics}/{module}.ts:**

```typescript
import { storeGet } from "@{domain}/store"
import { heapUpdate } from "@{domain}/{package}"
```

### 📊 Итог

| Вопрос                       | Решение                                         |
| ---------------------------- | ----------------------------------------------- |
| Создавать ли `unlock` метод? | ❌ Не создан — логика осталась в @{semantics}    |
| Удалить ли прямые импорты?   | ✅ Частично — `storeGet` из `@{domain}/store`    |

### 🎯 Вывод

Ваше предложение было **архитектурно верным** — мы вынесли общие данные в `@{domain}/store`.

`unlock` метод не был создан потому что:

* Логика простая (4 строки)
* `heapUpdate` — прямой API для GPU
* Дополнительная абстракция не добавляет ценности

## 📋 Правила работы с историей

| Правило               | Описание                                 |
| --------------------- | ---------------------------------------- |
| **Цитируй точно**     | Используй кавычки для цит сообщений      |
| **Указывай контекст** | Что было до/после обсуждения             |
| **Выделяй решения**   | Что было решено, что изменено            |
| **Показывай код**     | Было → Стало (если применимо)            |
| **Краткий итог**      | Таблица или список ключевых пунктов      |
| **Без воды**          | Только факты из сессии                   |

## 💬 Уровень детализации ответов

### По умолчанию: **только Итог**

**Всегда давай краткий ответ сразу**, без развёрнутого обоснования и примеров.

**Формат:**
```text
[Краткий ответ — суть]

## Итог

[Таблица/список — ключевые факты]
```

**Пример:**
```text
Пользователь: как в Rust передают мутируемый объект?

AI: В Rust — по мутабельной ссылке с контролем на уровне системы типов.

## Итог

| Язык       | Как передаётся               | Кто контролирует   |
| ---------- | ---------------------------- | ------------------ |
| Языки с GC | Копирование ссылки (неявно)  | Разработчик        |
| Rust       | `&mut T` или владение (явно) | Компилятор         |
```

### По явному запросу: **Обоснование + Примеры + Итог**

Развёрнутый ответ — только если пользователь попросил:
- «объясни», «почему», «подробнее»
- «сравни», «покажи пример»
- «как это работает»

---

### 📋 Обоснование

| Проблема                                                    | Решение                                                          |
| ----------------------------------------------------------- | ---------------------------------------------------------------- |
| Много текста в ответе → пользователь тратит время на чтение | Краткий ответ → экономия времени                                 |
| Всё в одном сообщении → нельзя быстро ухватить суть         | Итог сразу → направление мысли видно за 5 секунд                 |
| Нет выбора что читать дальше                                | Пользователь решает: углубиться или перейти к следующему вопросу |

**Принцип:**

```text
AI думает развёрнуто → отвечает кратко
Пользователь видит суть → решает что дальше
Время сэкономлено → качество не пострадало
```

**Выгода:**
- ⚡ Быстрое получение направления мысли
- 📚 Узнаешь новое без перегрузки
- 🎯 Сам решаешь когда углубиться

---

### Триггеры для развёрнутого ответа

| Триггер                                       | Уровень   |

| «почему», «объясни», «подробнее»              | Полный    |
| «сравни», «покажи пример», «как это работает» | Полный    |
| Любой другой вопрос без уточнений             | Итог      |
