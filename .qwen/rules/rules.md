# Создание правил

Этот документ описывает процесс создания новых правил в директории `.qwen/rules/`.

---

## 0. Принципы создания правил

**Универсальные правила для создания правил:**

| Принцип                       | Описание                                            | Пример из правил проекта                                                                                                |
| ----------------------------- | --------------------------------------------------- | ----------------------------------------------------------------------------------------------------------------------- |
| **Универсальность**           | Правило применяется к любому коду, не к конкретному | ✅ «Данные хранятся там, где их используют» (packages.md)<br>❌ «Данные в `@{domain}/store.ts`»                           |
| **Без ссылок на код**         | Не упоминай конкретные пакеты, пути, переменные     | ✅ «Создавай пару файлов: `.t.ts` для типов, `.ts` для реализации» (module.md)<br>❌ «Создавай `store.t.ts` и `store.ts`» |
| **Принципы, не детали**       | Описывай «зачем» и «что», не «как»                  | ✅ «TSDoc объясняет неявные связи и ограничения» (tsdoc.md)<br>❌ «TSDoc для поля `data: Uint32Array`»                    |
| **Контекст через инструмент** | Механику выноси в инструменты, не в правила         | ✅ «Форматируй таблицы через skill» (skills.md)<br>❌ «Выравнивай колонки по 10 пробелов»                                 |

---

## 1. Когда создавать новое правило

**Создавай новое правило, если:**

* ✅ Тема не покрывается существующими правилами
* ✅ Правило будет использоваться в 3+ задачах
* ✅ Есть чёткая ответственность (не пересекается с другими)
* ✅ Можно дать конкретное название (не "разное")

**Не создавай, если:**

* ❌ Можно добавить раздел в существующее правило
* ❌ Тема слишком узкая (1-2 задачи)
* ❌ Ответственность пересекается с другим правилом

### Примеры решений

| Ситуация                                   | Решение                                   |
| ------------------------------------------ | ----------------------------------------- |
| Нужно описать формат TSDoc для нового типа | Добавить в `tsdoc.md`, не создавать новое |
| Новый домен (например, "тестирование")     | Создать `testing.md`                      |
| Правила для нового языка (Python)          | Создать `python.md`                       |
| Частный случай существующего правила       | Добавить раздел, не создавать новое       |

## 2. Структура файла правила

### 2.1. Имя файла

**Формат:**

```text
<domain>.md
```

**Требования:**

| Требование               | Пример                                 |
| ------------------------ | -------------------------------------- |
| lowercase                | `testing.md` ✅                         |
| без пробелов             | `testing.md` ✅                         |
| без дефисов (если можно) | `testing.md` ✅ лучше `unit-testing.md` |
| .md расширение           | `testing.md` ✅                         |

**Примеры:**

```text
✅ testing.md
✅ python.md
✅ database.md
✅ security.md

❌ Testing.md      # не lowercase
❌ unit testing.md # пробел
❌ rules.md        # слишком общее
```

### 2.2. Заголовок

**Формат:**

```markdown
# <Название правила>

Краткое описание (1-2 предложения).
```

**Пример:**

```markdown
# Тестирование

Правила написания unit-тестов и интеграционных тестов для проекта.
```

### 2.3. Обязательные разделы

| Раздел          | Описание                | Пример                    |
| --------------- | ----------------------- | ------------------------- |
| **Назначение**  | Что покрывает правило   | "Правила для unit-тестов" |
| **Структура**   | Как организованы тесты  | `*.spec.ts`, `tests/`     |
| **Примеры**     | Код с комментариями     | ✅/❌ примеры               |
| **Чек-лист**    | Проверка перед коммитом | 5-10 пунктов              |

### 2.4. Рекомендуемые разделы

| Раздел             | Когда добавлять                    |
| ------------------ | ---------------------------------- |
| **Best Practices** | Есть устоявшиеся паттерны          |
| **Антипаттерны**   | Частые ошибки команды              |
| **Инструменты**    | Специфичные утилиты (jest, pytest) |
| **Ссылки**         | Связи с другими правилами          |

## 3. Формат Markdown

### 3.1. Заголовки

**Иерархия:**

```markdown
# Название правила       ← H1 (только один)
## Раздел               ← H2 (уникальный заголовок)
### Подраздел          ← H3 (уникальный заголовок)
#### Детали            ← H4 (если нужно)
```

**Правила:**

* Заголовки должны быть уникальными (проверяет markdownlint)
* Без пропусков уровней (не переходить с H2 на H4)
* Нумерация не требуется — markdownlint гарантирует уникальность

### 3.2. Таблицы

**Формат:**

```markdown
| Колонка 1 | Колонка 2 | Колонка 3 |
| --------- | --------- | --------- |
| Значение  | Значение  | Значение  |
```

**Требования:**

* Пробелы вокруг `|`
* Выровненные колонки (по самому длинному значению)
* Выровненные pipe-символы по вертикали

**Пример:**

```markdown
| Тип       | Где                  | Для чего                 |
| --------- | -------------------- | ------------------------ |
| Локальное | `@{pkg}/store.ts`    | Данные для одного пакета |
| Общее     | `@{domain}/store.ts` | Данные для нескольких    |
```

### 3.3. Блоки кода

**Всегда указывай язык:**

````markdown
✅ Правильно:
```typescript
const x: number = 42;
```

```text
Простой текст
```

❌ Неправильно:
```
const x: number = 42;
```
````

**Пустые строки между блоками:**

````markdown
✅ Правильно:
```typescript
const x = 1;
```

```typescript
const y = 2;
```

❌ Неправильно:
```typescript
const x = 1;
```
```typescript
const y = 2;
```
````

### 3.4. Списки

**Маркированные:**

```markdown
* Пункт 1
* Пункт 2
* Пункт 3
```

**Нумерованные:**

```markdown
1. Первый пункт
1. Второй пункт
1. Третий пункт
```

**Вложенные (4 пробела):**

```markdown
1. Родительский
    1. Дочерний
    1. Ещё один
```

### 3.5. Выделение

| Тип         | Формат        | Пример          |
| ----------- | ------------- | --------------- |
| **Жирный**  | `**текст**`   | **важно**       |
| *Курсив*    | `*текст*`     | *примечание*    |
| `Код`       | `` `текст` `` | `function()`    |
| ❌ Запрет    | `**⛔**`       | **⛔ Запрещено** |
| ✅ Разрешено | `**✅**`       | **✅ Требуется** |

## 4. Перекрёстные ссылки

### 4.1. Управление контекстом

**⚠️ Важно:** Не открывай связанные правила заранее!

**Правильный подход:**

1. **Примени текущее правило** — реши задачу по этому правилу
2. **Проверь ссылки** — только если задача требует углубления
3. **Открой связанное правило** — только конкретный раздел по ссылке

**Пример:**

``` text
Задача: "создай store для модуля"
→ Прочитай .qwen/rules/module.md (раздел Store-файлы)
→ Видишь ссылку .qwen/rules/packages.md#2-Хранилища-store
→ Если нужно понять архитектуру → открой .qwen/rules/packages.md раздел 2
→ Если нет → не читай .qwen/rules/packages.md
```

### 4.2. Формат wiki-ссылок

**Формат:**

``` markdown
`.qwen/rules/<файл>.md#<раздел>` — описание
```

**Примеры:**

```markdown
✅ Правильно:
* `.qwen/rules/tsdoc.md#2-Store-TSDoc` — формат документации store
* `.qwen/rules/module.md#3-Store-файлы` — структура файлов store
* `.qwen/rules/packages.md` — архитектура пакетов (на весь файл)

❌ Неправильно:
* `.qwen/rules/tsdoc.md#Store-TSDoc` — без номера раздела
* [tsdoc](tsdoc.md) — не использовать markdown-ссылки
```

### 4.3. Раздел ссылок

**Добавь в конец правила:**

```markdown
## N. Ссылки

* `.qwen/rules/<файл>.md#<раздел>` — описание связи
* `.qwen/rules/<файл>.md#<раздел>` — описание связи
```

**Пример:**

```markdown
## 9. Ссылки

* `.qwen/rules/tsdoc.md#2-Store-TSDoc` — документация store
* `.qwen/rules/module.md#3-Store-файлы` — структура store-файлов
* `.qwen/rules/fp.md#1-Чистые-функции` — принципы чистых функций
```

## 5. Процесс создания

### 5.1. Шаг 1: Проверка существующих

```bash
# Посмотреть существующие правила
ls .qwen/rules/

# Найти упоминания темы в правилах
grep -r "тестирование" .qwen/rules/
```

### 5.2. Шаг 2: Создать файл

```bash
# Создать файл правила
touch .qwen/rules/testing.md

# Открыть в редакторе
code .qwen/rules/testing.md
```

### 5.3. Шаг 3: Заполнить структуру

```markdown
# Тестирование

Краткое описание.

---

## 1. Назначение

Что покрывает правило.

## 2. Структура

Как организовано.

## 3. Примеры

Примеры кода.

## 4. Чек-лист

- [ ] Пункт 1
- [ ] Пункт 2

## 5. Ссылки

* `.qwen/rules/<файл>.md` — описание
```

### 5.4. Шаг 4: Добавить ссылки в QWEN.md

**Отредактировать `/QWEN.md`:**

```markdown
* **Тестируешь код?** — см. `.qwen/rules/testing.md`
```

### 5.5. Шаг 5: Проверка

```bash
# Проверить markdownlint
# (если установлен)
markdownlint .qwen/rules/testing.md

# Проверить ссылки
grep "\[\[" .qwen/rules/testing.md

# Убедиться что файл в списке
ls .qwen/rules/
```

## 6. Чек-лист перед сохранением

- [ ] Имя файла lowercase, без пробелов
- [ ] Заголовок H1 только один
- [ ] Разделы H2 нумерованы (1., 2., 3.)
- [ ] Подразделы H3 с номером родителя (1.1., 1.2.)
- [ ] Таблицы выровнены (колонки и pipe)
- [ ] Блоки кода с указанием языка
- [ ] Между блоками кода пустая строка
- [ ] Списки используют `*` (маркированные) или `1.` (нумерованные)
- [ ] Ссылки в формате `.qwen/rules/<файл>.md#<раздел>`
- [ ] Раздел "Ссылки" в конце (если есть связи)
- [ ] Ссылка добавлена в `/QWEN.md`
- [ ] Файл заканчивается пустой строкой

## 7. Примеры правил

### 7.1. Простое правило (testing.md)

```markdown
# Тестирование

Правила написания unit-тестов и интеграционных тестов.

---

## 1. Назначение

Правило покрывает:
* Unit-тесты для функций
* Интеграционные тесты для API
* E2E тесты для UI

## 2. Структура

Тесты располагаются рядом с тестируемым кодом:

```text
src/
  module.ts
  module.spec.ts  ← тесты
```

## 3. Примеры

✅ Правильно:

```typescript
test("возвращает true для валидных данных", () => {
  expect(validate({ name: "test" })).toBe(true)
})
```

❌ Неправильно:

```typescript
test("тест 1", () => {
  // без описания что тестируется
})
```

## 4. Чек-лист

- [ ] Имя теста описывает ожидаемое поведение
- [ ] Тест изолирован (нет зависимостей между тестами)
- [ ] Используется arrange-act-assert паттерн

### 5. Ссылки

* `.qwen/rules/fp.md#1-Чистые-функции` — тестируемые функции

### 7.2. Сложное правило (database.md)

``` markdown
# База данных

Правила работы с базой данных, миграциями и ORM.

---

## 1. Назначение

Правило покрывает:

* Миграции схемы
* Репозитории для доступа к данным
* Транзакции и блокировки

## 2. Структура

``` text
db/
  migrations/      ← миграции
  schema/          ← схема БД
src/
  repositories/    ← доступ к данным
```

## 3. Миграции

### 3.1. Именование

Формат: `YYYYMMDD_HHMMSS_description.sql`

Пример: `20250106_120000_add_users_table.sql`

### 3.2. Требования

* Каждая миграция атомарна
* Откат миграции обязателен (DOWN)
* Тестирование на staging перед production

## 4. Репозитории

...

### 5. Ссылки на правила

* `.qwen/rules/testing.md` — тестирование репозиториев

## 8. Поддержание актуальности

### 8.1. Когда обновлять

Обновляй правило если:

* ✅ Изменился процесс/инструмент
* ✅ Добавилась новая best practice
* ✅ Нашли частую ошибку (добавить в антипаттерны)
* ✅ Появилась связь с новым правилом

### 8.2. Версионирование

Не использовать версионирование в файлах правил.

**Вместо:**

```text
testing-v2.md  ❌
testing.md     ✅ (просто обновить)
```

**Принцип:**

* Последняя версия всегда в файле
* История в git
* Нет обратной совместимости

### 8.3. Устаревшие разделы

Если раздел устарел:

```markdown
> **⛔ Устарело:** Этот раздел устарел с версии 2025.01.
> Используйте новый подход: `.qwen/rules/new-rule.md#section`.
```

### 8.4. Исправление ошибок после применения правила

**Сценарий:** Пользователь указал на ошибку после применения правила.

**Процесс:**

```text
1. Пользователь применяет правило → находит ошибку
2. Пользователь сообщает об ошибке
3. AI исправляет ошибку в коде/файле
4. AI предлагает кратко обновить правило (по сути)
5. Если пользователь согласен → AI показывает подробно что изменит
6. После подтверждения → AI обновляет правило
```

**Пример диалога:**

``` text
Пользователь: правило module.md не описывает как создавать store.ts

AI: Исправил код, добавил store.ts.

📝 Предлагаю обновить правило module.md:

Кратко:
• Добавить раздел "3.1. Store-файлы" с описанием структуры store.t.ts + store.ts

Согласны? Покажу подробно что добавлю.

---

Пользователь: да

AI: Подробно что добавлю в module.md:

## 3.1. Store-файлы

Для store создавай пару файлов:
- {name}.t.ts ← интерфейс {Name}Store
- {name}.ts ← инстанс store: {Name}Store

...

Внеси изменения?

---

Пользователь: вноси

AI: Обновил module.md, добавил раздел 3.1
```

**Формат краткого предложения:**

```markdown
📝 Предлагаю обновить правило <file.md>:

Кратко:
• <что добавить/изменить #1>
• <что добавить/изменить #2>

Согласны? Покажу подробно что изменю.
```

**Формат подробного описания:**

```markdown
Подробно что добавлю в <file.md>:

## <номер>. <название раздела>

<содержимое раздела>

---

Внеси изменения?
```

**Правила:**

| Правило            | Описание                           |
| ------------------ | ---------------------------------- |
| **Сначала кратко** | 1-3 пункта по сути изменений       |
| **Потом подробно** | Только после согласия пользователя |
| **Конкретика**     | Указывай номер раздела и название  |
| **Минимум текста** | Без воды, только содержимое        |
