# Правила построения графа зависимостей

## Назначение

Документ описывает правила визуализации типов и связей между модулями с помощью Draw.io.

---

## Структура таблицы типов

### Формат таблицы

Каждый тип представляется в виде таблицы с заголовком:

``` text
{Type} @{package}/{module}
```

**Пример:**

``` text
{Type} @{package}/{module}
```

### Колонки таблицы

| Колонка  | Ширина | Описание                 |
| -------- | ------ | ------------------------ |
| property | ~110px | Имя поля типа            |
| type     | ~155px | Тип поля (с дженериками) |
| label    | ~245px | Описание поля на русском |

### Стиль элементов

| Элемент           | Стиль                                           |
| ----------------- | ----------------------------------------------- |
| Заголовок таблицы | `shape=table;startSize=30;fontSize=16`          |
| Строка таблицы    | `shape=tableRow;horizontal=0`                   |
| Ячейка property   | `shape=partialRectangle;align=left;fontSize=16` |
| Ячейка type       | `shape=partialRectangle;fontSize=12`            |
| Ячейка label      | `shape=partialRectangle;align=left;fontSize=12` |

## Правила именования

### Заголовок таблицы

**Формат:**

``` text
{Type} @{package}/{module}
```

**Примеры:**

- ✅ `{Type} @{package}/{module}`
- ❌ `{Type}` (без указания модуля)
- ❌ `@{package}/{module} {Type}` (неверный порядок)

### Типы в колонке type

**Правила:**

1. **Примитивы:** `string`, `number`, `boolean`, `any`
2. **Опциональные:** `string?`, `ProcessesSchema?`
3. **Дженерики:** `Superposition<𝛴, ɸ>`, `ParseNode[]`
4. **Массивы:** `ParseNode[]`, `string[]`

**Примеры:**

``` text
string
string?
Superposition<𝛴, ɸ>
ProcessesSchema?
ParseNode[]
m?
``` text

## Связи между таблицами

### Типы связей

| Тип               | Описание                     | Пример                            |
| ----------------- | ---------------------------- | --------------------------------- |
| **Ссылка на тип** | Поле ссылается на другой тип | `mass` → `Mass`                   |
| **Вложенность**   | Тип содержит другой тип      | `Meta` содержит `ProcessesSchema` |

### Визуализация связи

**Стиль ребра:**

``` xml
style="edgeStyle=none;html=1;exitX=1;exitY=0.5;exitDx=0;exitDy=0;"
``` text

**Направление:**

- От строки с полем → к таблице типа
- Выход из правой границы строки (`exitX=1`)
- Вход в левую границу таблицы (по умолчанию)

**Пример:**

``` xml
<mxCell id="96" style="edgeStyle=none;html=1;exitX=1;exitY=0.5;" edge="1" source="87" target="91"/>
```

Где:

- `source="87"` — строка `{field}` в таблице `{Type}`
- `target="91"` — таблица `{Class} @{package}/{module}`

## Расположение на холсте

### Координаты

**Правила:**

1. Таблицы не должны перекрываться
2. Связанные таблицы располагаются рядом
3. Источник связи → слева, целевая таблица → справа

**Пример:**

``` text
Type @{package}/{module}          Class @{package}/{module}
x: 250, y: -900         x: 790, y: -580
```

### Размеры

**Таблица Meta:**

- Ширина: 510px
- Высота: 300px (9 строк × 30px + заголовок 30px)

**Таблица Mass:**

- Ширина: 240px
- Высота: 60px (1 строка × 30px + заголовок 30px)

## Чек-лист перед сохранением

- [ ] Заголовок таблицы в формате `{Type} @{package}/{module}`
- [ ] Три колонки: property, type, label
- [ ] Шрифт описания (label) = 12px
- [ ] Шрифт типа (type) = 12px для сложных типов
- [ ] Связи идут от строки поля к таблице типа
- [ ] Таблицы не перекрываются
- [ ] Все поля типа описаны в таблице

## Экспорт в Draw.io

**Порядок действий:**

1. Создать таблицу через меню **Insert → Advanced → Table**
2. Задать стиль заголовка: `shape=table;startSize=30`
3. Заполнить строки данными
4. Создать связь через **Insert → Link → Arrow**
5. Задать стиль связи: `edgeStyle=none;exitX=1;exitY=0.5`
6. Сохранить файл `.drawio`

**Проверка:**

- Открыть файл в Draw.io
- Убедиться, что все связи корректны
- Проверить читаемость текста

## Data Flow диаграммы

### О диаграммах

Data Flow диаграммы показывают **поток данных** от входных типов к конечной структуре данных. В отличие от графа зависимостей, акцент делается на **выходных данных**, которые получаются после применения API.

### Структура Data Flow

**Уровни диаграммы:**

``` text
┌─────────────┐     ┌─────────────┐     ┌─────────────────┐
│ Входные     │     │ Промежуточ- │     │ Выходные        │
│ типы        │ ──→ │ ные типы    │ ──→ │ данные          │
│ (Types)     │     │ (FieldType) │     │ (SchemaType)    │
└─────────────┘     └─────────────┘     └─────────────────┘
``` text

**Пример для `{Type} @{package}/{module}`:**

``` text
{Type} @{package}/{module}    {FieldType} (выход)    {SchemaType}
┌──────────────┐         ┌──────────────┐     ┌─────────────┐
│ string       │───────→ │ string       │ ──→ │ {SchemaType}  │
│ number       │───────→ │ number       │ ──→ │ {SchemaType}  │
│ boolean      │───────→ │ boolean      │ ──→ │ {SchemaType}  │
│ enum         │───────→ │ enum         │ ──→ │ {SchemaType}  │
│ array        │───────→ │ array        │ ──→ │ {SchemaType}  │
└──────────────┘         └──────────────┘     └─────────────┘
```

### Таблицы выходных данных

#### Формат заголовка

Заголовок таблицы указывает **тип данных** без суффиксов `.required()` / `.optional()`:

**Примеры:**

- ✅ `string`
- ✅ `number`
- ✅ `boolean`
- ✅ `enum`
- ✅ `array`
- ❌ `string.required()` (избыточно)
- ❌ `{FieldType}<{Type}>` (избыточно)

#### Структура таблицы

Каждая таблица выходных данных имеет **три колонки**:

| Колонка  | Ширина | Описание            |
| -------- | ------ | ------------------- |
| property | ~100px | Имя поля структуры  |
| type     | ~100px | Тип поля            |
| label    | ~150px | Описание на русском |

**Пример для `string`:**

``` text
┌────────────────────────────────────────────┐
│ string                                     │
├───────────┬─────────────┬──────────────────┤
│ property  │ type        │ label            │
├───────────┼─────────────┼──────────────────┤
│ type      │ "string"    │ Тип поля         │
│ required  │ boolean     │ Обязательность   │
│ default   │ string?     │ Значение по ум.  │
└───────────┴─────────────┴──────────────────┘
``` text

#### Типы полей

**Правила для колонки `type`:**

1. **Строковые литералы:** `"string"`, `"number"`, `"boolean"`, `"enum"`, `"array"`
2. **Булевы типы:** `boolean` (для поля `required`)
3. **Опциональные типы:** `string?`, `number?`, `boolean?`, `T?`, `T[]?`
4. **Дженерики:** `T`, `T[]`

**Примеры для всех типов:**

``` typescript
// string
{ type: "string", required: boolean, default: string? }

// number
{ type: "number", required: boolean, default: number? }

// boolean
{ type: "boolean", required: boolean, default: boolean? }

// enum
{ type: "enum", values: T[], default: T? }

// array
{ type: "array", required: boolean, default: T[]? }
``` text

### Стили для Data Flow

#### Таблицы

| Элемент         | Стиль                                           |
| --------------- | ----------------------------------------------- |
| Заголовок       | `shape=table;startSize=30;fontSize=16`          |
| Строка          | `shape=tableRow;horizontal=0`                   |
| Ячейка property | `shape=partialRectangle;align=left;fontSize=14` |
| Ячейка type     | `shape=partialRectangle;fontSize=12`            |
| Ячейка label    | `shape=partialRectangle;align=left;fontSize=12` |

#### Связи

**Стиль ребра:**

``` xml
style="edgeStyle=none;html=1;exitX=1;exitY=0.5;exitDx=0;exitDy=0;"
``` text

**Направление:**

- От типа в таблице `Types` → к таблице выходных данных
- Выход из правой границы строки типа
- Вход в левую границу таблицы выходных данных

### Расположение на холсте

**Правила:**

1. **Таблица Types** — слева (источник)
2. **Таблицы выходных данных** — справа (цель)
3. **Расстояние между таблицами** — ~100-200px
4. **Таблицы выходных данных** — группируются по 2 в ряд

**Пример компоновки:**

``` text
{Type} @{package}/{module}
┌─────────────────┐
│ string ─────────┼──→ string       ┌──→ number
│ number ─────────┼──→ number       │
│ boolean ────────┼──→ boolean      │
│ enum ───────────┼──→ enum         └──→ array
│ array ──────────┘──→ array
```

**Координаты (пример):**

``` text
{Type}:          x: 820,  y: -795,  w: 310px, h: 180px
string:          x: 1170, y: -480,  w: 350px, h: 120px
number:          x: 1550, y: -480,  w: 350px, h: 120px
boolean:         x: 1170, y: -330,  w: 350px, h: 120px
enum:            x: 1550, y: -330,  w: 350px, h: 120px
array:           x: 1170, y: -180,  w: 350px, h: 120px
```

### Процесс создания Data Flow

**Пошаговая инструкция:**

1. **Определить входные типы**
   - Какие типы импортируются (например, из `@{package}/{module}`)
   - Создать таблицу `{Type} @{package}/{module}`

2. **Определить выходные структуры**
   - Какие данные получаются после применения API
   - Для каждого типа — отдельная таблица

3. **Создать таблицы выходных данных**
   - Заголовок: только название типа (`string`, `number`, ...)
   - Колонки: `property`, `type`, `label`
   - Заполнить поля структуры

4. **Создать связи**
   - От каждого типа в `Types` → к соответствующей таблице
   - Стиль: `edgeStyle=none;exitX=1;exitY=0.5`

5. **Расположить на холсте**
   - `Types` — слева
   - Выходные таблицы — справа, сгруппированы
   - Избегать перекрытий

6. **Проверить**
   - Все ли типы охвачены
   - Корректны ли типы полей
   - Читаемость текста

### Чек-лист для Data Flow

- [ ] Заголовки таблиц без суффиксов `.required()` / `.optional()`
- [ ] Три колонки: property, type, label
- [ ] Строковые литералы в кавычках: `"string"`, `"number"`
- [ ] Опциональные типы: `string?`, `T?`, `T[]?`
- [ ] Связи от типов → к выходным таблицам
- [ ] Таблицы не перекрываются
- [ ] Шрифт описания (label) = 12px
- [ ] Шрифт типа (type) = 12px

## Правила совместной работы с draw.io файлами

### Механика workflow

``` text
┌─────────────────────────────────────────────────────────┐
│ 1. AI сделал изменения → git add                        │
│ 2. Пользователь сделал изменения                        │
│ 3. AI: git diff (сравнивает staged vs working)          │
│ 4. AI: точечно редактирует только то, что не тронул     │
│ 5. AI: git add (сохраняет новую версию)                 │
└─────────────────────────────────────────────────────────┘
``` text

**Команды для проверки:**

``` bash
# После своих изменений
git add tasks/file.drawio

# Перед новыми правками — увидеть изменения пользователя
git diff HEAD tasks/file.drawio

# Или сравнить staged vs working copy
git diff --cached tasks/file.drawio    # что в staging
git diff tasks/file.drawio             # что изменено после staging
``` text

### Поиск конкретных ячеек для редактирования

**Вместо перечитывания всего файла — используем grep:**

``` bash
# Найти ячейку по ID
grep -n 'id="240"' tasks/file.drawio

# Найти ячейку по значению
grep -n 'FlatStructure' tasks/file.drawio

# Найти все ячейки в контейнере
grep -n 'parent="iB3CXa2FmsO-2bHBSgqK-700"' tasks/file.drawio

# Посмотреть контекст (строки до и после)
grep -n -A5 -B5 'FlatStructure' tasks/file.drawio
``` text

**Пример workflow:**

``` bash
# 1. Смотрим что изменил пользователь
git diff HEAD tasks/entangled-dataflow.drawio | grep -A3 "FlatStructure"

# 2. Находим строки в текущем файле
grep -n "FlatStructure" tasks/entangled-dataflow.drawio
# Вывод: 184: <mxCell id="240" value="FlatStructure (Map)" ...

# 3. Читаем только нужный фрагмент
read_file(..., offset=183, limit=25)

# 4. Точечно редактируем
edit(file, old_string, new_string)

# 5. Сохраняем
git add tasks/entangled-dataflow.drawio
```

### Что делать

✅ **Обязательно:**

1. **После каждого своего редактирования:**

   ``` bash
   git add tasks/filename.drawio
   ```

2. **Перед новым редактированием:**

   ``` bash
   git diff HEAD tasks/filename.drawio
   ```

   — чтобы увидеть, что изменил пользователь

3. **Использовать grep для поиска:**
   - Найти ID ячейки или контейнер
   - Найти строки для редактирования
   - Прочитать только нужный фрагмент

4. **Редактировать точечно:**
   - Если пользователь добавил контейнер → добавлять таблицы внутрь него
   - Если пользователь изменил связи → не трогать их
   - Если пользователь изменил координаты → не перезаписывать

### Что нельзя делать

❌ **Запрещено:**

- Делать `git checkout` без явной команды пользователя
- Перезаписывать весь файл целиком
- Менять ID ячеек, которые создал пользователь
- Изменять связи, которые уже настроены
- Редактировать без проверки `git diff`
- Перечитывать весь файл вместо использования grep

### Пример правильного workflow

**Сценарий:** Пользователь добавил контейнер

**AI делает:**

``` bash
# 1. Проверяет изменения
git diff HEAD tasks/file.drawio

# Видит: пользователь добавил контейнер

# 2. Находит контейнер в файле
grep -n 'parent="..." tasks/file.drawio

# 3. Добавляет таблицы ВНУТРЬ контейнера (не перезаписывая)
<mxCell id="new-table" value="New Store" parent="...">

# 4. Сохраняет
git add tasks/file.drawio
```

- [ ] Проверил `git diff HEAD` перед новыми правками
- [ ] Использовал `grep` для поиска ячеек (не перечитывал весь файл)
- [ ] Не перезаписал изменения пользователя
- [ ] Не изменил существующие связи (если не требовалось)
- [ ] Закоммитил с понятным сообщением
